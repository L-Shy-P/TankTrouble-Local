任务原文写「**`GameController` 的 `playerIdOtherWeaponIds` / `playerIdDefaultWeaponId`**」——
**这两个字段不在 `GameController` 里**。实测：

- `grep` 全 `game_core/js/`，`playerIdOtherWeaponIds` 只出现在 `46989e393ad0e356ac8a0c6c53b362f9.js`（RoundModel，10 处）+ `training_mode.js`（2 处，训练框架清坦克用）。
- `GameController` 只有三个**纯转发**方法：
**`ce217c9b090cc73ce0e1faa13d20ca15.js:L1@18004..L1@18359`**（逐字原文）：

## 二、完整实现（逐项 + 原文）

### 2.1 道具拾取

#### 2.1.1 拾取事件是怎么产生的（先有碰撞，才有 Pickup）

道具箱的 body/fixture 是 `createCrateBody` 造的（`categoryBits=COLLECTIBLE`、`maskBits=TANK`），
坦克的 base/turret fixture 的 `maskBits` 里都含 `COLLECTIBLE`。
两者碰上时，`RoundModel.PreSolve` 走 `COLLECTIBLE|TANK` 分支：
**禁用物理接触（所以箱子不会被坦克推走）**，同时把 `TANK_COLLECTIBLE_COLLISION` 事件塞进队列：
**`46989e393ad0e356ac8a0c6c53b362f9.js:L1@5295..L1@5516`**（逐字原文）：

```javascript
case Constants.COLLISION_CATEGORIES.COLLECTIBLE|Constants.COLLISION_CATEGORIES.TANK:{collisionEvent.collisionType=RoundModel._EVENTS.TANK_COLLECTIBLE_COLLISION;collisionEvent.data=data;b2dcontact.SetEnabled(false);break;}
```

【解释】上面这段的 `SetEnabled(false)` 是**在 `PreSolve` 里、每个接触帧都调**的，
所以箱子实际上**不会被坦克撞飞**（唯一能推动它的只有别的箱子？——箱子 `maskBits` 只有 `TANK`，所以也不会互撞）。
【解释，未验证】对沙箱的含义：**道具箱的位置可以当成静止的**（`linearDamping=4.0` 也让它很快就停）。

配套的 `getActiveWeapon`（2.3 有完整原文）：
`otherWeaponIds` 为空 → 返回**默认武器**；否则返回 `otherWeaponIds[length-1]`（**数组末位**）。
而新枪是 `unshift` 到**数组头部**的。于是：

- **手上只有默认武器时**捡第一把 → `unshift` 后数组长度 1 → `getActiveWeapon` 返回**这把新枪** →
  `updateTankBodyTurret(..., 新枪)` → **形状真的变了**。
- **手上已经有枪时**再捡 → `unshift` 把新枪放到**头部**，`getActiveWeapon` 还是取**末位**（= 最早捡的那把，没变）→
  `updateTankBodyTurret` **仍被调用**，但传的是**同一把枪** → 先把旧炮管 fixture 全删掉、再**按同样的几何重建一遍**
  （【解释】净效果 = 形状不变，但该帧 fixture 指针被换了一茬）。

> **所以任务描述里「只有捡第一个才改形状，之后进队列」是准确的**，
> 精确说法是：**「只有当这把枪成为 `getActiveWeapon` 时才改形状」**；
> 成为活性武器的时机有两个：① 手上没有非默认武器时捡到它；② 前面的武器 `done()` 被销毁后轮到它。

**完整的时间线**（沙箱要按帧复刻）：

```
第 N 帧 model.update():
  _removeDestroyed()
  b2dworld.Step()
  _filterAndDispatchCollisionEvents()   ← COLLECTIBLE|TANK 事件在这里派发
      → RoundController.TANK_COLLECTIBLE_COLLISION
          → pickUpCrate → setWeaponState → unshift + updateTankBodyTurret（炮管夹具当场换掉）
          → destroyCollectible → destroyedCollectibleIds 入队
  _removeDestroyed()                    ← 箱子 body 在同一帧被销毁
  ...tank/projectile/trap/collectible/weapon/upgrade/counter/zone update
```
【解释】拾取发生在**物理步进之后、这一帧结束之前**；炮管 fixture 是**当帧**就换掉的。

## 四、【解释】（我的解读，可能错；推断已标注）

### 4.1 一句话串起来（全部有原文支撑，纯属把上面的事实排成时间线）

1. 坦克出生：`BulletWeapon`（默认枪，`isDefault()===true`）→ 进 `playerIdDefaultWeaponId`；
   `createTankBody` 造 **base 60×80 方块 + bullet 炮管**。
2. 路上撞到武器箱：`PreSolve` 发 `TANK_COLLECTIBLE_COLLISION` →
   - 若 `getQueuedWeapons().length >= 3` → **什么都不发生**（箱子还在地上，下次接触再试）。
   - 否则 `pickUpCrate`：造 WeaponState → `setWeaponState` → `unshift` 进数组 → 若这是第一把 → **立刻换炮管形状**。
3. 开火：`pullTrigger` → `weapon.fire()` → 有弹药就出弹；各种枪自己的 `_triggerPulled`/`_reloadTime`/`_weaponCharge` 限制节奏。
4. 用尽：`weapon.done()` 变 true（**判据每把枪不同：松扳机 / 装填完 / 放气完 / 0.8s / 2.0s**）→
   `RoundController.update` 扫描 → `destroyWeapon` → 从数组里 `splice` → `getActiveWeapon` 取下一位（**就是排队最久的那把**）
   → `updateTankBodyTurret` **当帧换形状**。
5. 捡到护盾：`setUpgradeState` → `addTankBodyUpgrade(tankBody, upgrade)` → 坦克身上多一个 **4.3m 半径的圆 fixture**，
   `restitution=1.0` → 子弹/别的坦克撞上来被弹开；`_lifetime<=0` 时 `destroyUpgrade` 摘掉。

### 4.2 "后摇"到底是什么（重要）

**【解释】** 原版**没有一个叫"后摇"的全局量**。玩家感受到的"打完这把枪要等一下才换下一把"，
是每把枪自己的 `done()` 门槛造成的：

| 玩家感受到的 | 代码里的真身 |
|---|---|
| 双管/地雷：弹打光了还换来换去？不，**你得松手** | `done()` 里的 `!this._triggerPulled`；`_triggerPulled` 由 `release()` 清，而 `release()` 由 `RoundController._updateWeaponLockingAndFiring` 在**松火键**时调 |
| 霰弹：打完 3 发要等 1 秒 | `_reloadTime=SHOTGUN_RELOAD_TIME(1.0)`，`done()` 要 `_reloadTime<=0` |
| 加特林：打光 20 发要等它"放气" | `_weaponCharge` 只在松手时以 `dt/1.5` 下降，`done()` 要 `_weaponCharge==0` |
| 激光：就一发，等 0.8 秒才换枪 | `done()` 要 `_timeSinceFire > LASER_MAX_LIFETIME(0.8)` |
| 追踪弹：发射后 2 秒才换枪 | `done()` 要 `_activationTime<=0`（发射时置 2.0） |

### 4.3 护盾（【解释】）

- 护盾 = **挂在坦克 b2body 上的圆形 fixture**（不是独立 body、不是子弹型的"场"）。
  所以它**跟着坦克移动/旋转**，并且**参与所有已配置的碰撞**（TANK / PROJECTILE / SHIELD / ZONE）。
- 弹开子弹是**两层**：Box2D 的 `restitution=1.0` 负责"真的弹走"；
  `PreSolve` 的 `PROJECTILE_SHIELD_COLLISION` 负责"这一下算命中" → `hitShield()` 记一次 bounce。
  **两层都要复刻**：只做物理弹开（不记 bounce）→ 子弹会比原版多活；只记 bounce（不弹）→ 弹道全错。
- **自己的子弹在"还没对主致命"时穿过自己的盾**（`SetEnabled(false)`）。`deadlyToOwner` 在撞过一次墙后变 true
  ⟹ 【解释】开盾玩家打出、先在墙上弹了一下的子弹，会**回头被自己的盾弹开**。
- **破片（地雷）撞盾是"被吸收"**：`hitShield` 把速度乘 0 → 下一帧 `done()` ⟹ 当帧消失。
- **霰弹撞盾 = 剩余寿命被压到 ≤0.7s**（`timeAlive` 顶到 ≥1.3s）。
- `_weakened` **不动物理**；它只影响"内置 AI 认为你还有没有保护"（`AIUtils.checkProtected`）+ UI 闪烁。

### 4.4 护盾的质量副作用【解释，box2d 行为已验证】

`shieldFixtureDef.density=10.0`，而 `b2Body.CreateFixture` 里写着 `this.m_density>0&&this.ResetMassData()`
（见 §2.2.3 引用）。参考 `TANK.WIDTH×HEIGHT = 3m×4m`、base `density=1.0`：
- 【解释，数值未逐位验证】base 质量 ≈ 12（Box2D 单位），护盾圆面积 ≈ π×4.3²≈58 → 护盾质量 ≈ 580。
- **⟹ 开盾的坦克质量会暴涨（数十倍量级）**。它会明显更难被推动 / 更容易把别人顶开。
- 【解释，未验证】这也意味着"护盾到期/被风暴销毁"的瞬间质量会掉回去，可能出现一次推力突变。

### 4.5 队列方向（【解释】）

`unshift` + `getActiveWeapon` 取末位 ⟹ **数组头是"最新捡的"，数组尾是"正在用的（最早捡的）"** ⟹
**用枪顺序 = 捡枪顺序（FIFO）**。`getQueuedWeapons()` 返回的数组是**倒序**的（最新→次早），
它只用于"还有几把在排队"和 UI 图标，**不能拿它当"下一把"**；下一把永远是`getActiveWeapon`。

### 4.6 形状改变对物理的影响（【解释】）

炮管是**实心 fixture**（会撞墙、会撞别的坦克、会碰到道具箱、会挡子弹），而且比坦克本体更长：
bullet 炮管从 y=-26px 伸到 y=-54px，而本体前边缘在 y=-40px ⟹ **炮管探出本体 14px（0.7m）**。
不同枪的炮管尺寸/形状差别很大（地雷=没有、导弹发射后=没有、激光=两个 fixture）。
⟹ **"换成地雷"或"发射导弹"会立刻改变坦克的碰撞轮廓**，这既是确定性物理，也是原版真实行为。

### 6.2 确定 vs 不确定（决定"什么能进树"）

**确定（可以逐帧复刻）**：
- 炮管形状切换（三种触发都是确定事件）；护盾夹具的挂/摘；拾取判定（箱子静止）；
- 弹道反弹、护盾弹开、bounce 计数上限 5；
- 每把枪的 `done()` 时刻（给定输入）。

**不确定（不能假装能算）**：
- **霰弹每一发的散布**：`ShotgunWeapon.getProjectileStates` 每颗弹丸取 2 次 `Math.random()`
  （`randomSeed=Math.random()-0.5` 决定角度扰动与横向间距；速度也是 `MIN+Math.random()*(MAX-MIN)`），20 颗 = 40 次随机；
**`7b2ed8ad3598d7321f8f3d2b04b1eac8.js:L12@18219..L12@18941`**（逐字原文）：

```javascript
getProjectileStates:function(tank){var result=[];for(var i=0;i<Constants.SHOTGUN_NUM_BUCKSHOT;++i){var randomSeed=Math.random()-0.5;var rot=tank.getRotation()+randomSeed*Constants.SHOTGUN_BUCKSHOT_SPREAD;var spread=randomSeed*Constants.SHOTGUN.SPACE.m;var sinRot=Math.sin(rot);var cosRot=Math.cos(rot);var speed=Constants.SHOTGUN.MIN_SPEED.m+Math.random()*(Constants.SHOTGUN.MAX_SPEED.m-Constants.SHOTGUN.MIN_SPEED.m);var projectileState=ProjectileState.withState(IdGenerator.instance.gen('sg'),tank.getPlayerId(),Constants.WEAPON_TYPES.SHOTGUN,tank.getX()+sinRot*Constants.SHOTGUN.OFFSET.m+cosRot*spread,tank.getY()-cosRot*Constants.SHOTGUN.OFFSET.m+sinRot*spread,sinRot*speed,-cosRot*speed);result.push(projectileState);
```

- **加特林每一发**也各取 2 次 `Math.random()`：
**`7b2ed8ad3598d7321f8f3d2b04b1eac8.js:L17@23425..L17@23797`**（逐字原文）：

```javascript
getProjectileStates:function(tank){var randomSeed=Math.random()-0.5;var rot=tank.getRotation()+randomSeed*Constants.GATLING_GUN_BULLET_SPREAD;var spread=randomSeed*Constants.GATLING_GUN.SPACE.m;var sinRot=Math.sin(rot);var cosRot=Math.cos(rot);var speed=Constants.GATLING_GUN.MIN_SPEED.m+Math.random()*(Constants.GATLING_GUN.MAX_SPEED.m-Constants.GATLING_GUN.MIN_SPEED.m);
```

【解释】⟹ **沙箱无法预测"我方下一发霰弹/加特林会打出什么弹道"**。
但这不阻塞，因为主人已定案：**射击计划不进树，子弹出膛后走正常刷新**——
沙箱只需要把**已经在场的真实弹丸**克隆进去（现在的 `acquireFusedBullet` 正是这么做的）。

**时间源风险**：`Projectile.update` / `hitShield` 用 `new Date().getTime()`（真实墙钟）做反弹窗口与时间戳
（`PR:L4@76364`、`PR:L4@76390`）。【解释，未验证】沙箱若接虚拟时钟，这 35ms 窗口的行为会与真实时间不一致；
反过来说，**同一帧多次命中是否被去重，取决于真实世界过了多少毫秒**——这是个非确定性来源，**施工前要先定"沙箱里要不要复刻它"**。

### 6.3 与权威版 §10「刷新条件③ = 坦克形状改变」的对齐（★ 施工建议）

- 权威版写：**「③ 坦克形状改变（⚠️ 不是"捡到道具"：只有捡第一个才改形状，之后进队列，用完一个自动装下一个时才改）」**
  —— **代码完全支持这个口径**：`updateTankBodyTurret` 全文件只有 3 个调用点
  （`setWeaponState` / `destroyWeapon` / `updateWeapon`）。
- 【解释】**一个坑**：`setWeaponState` 在"非第一把"时**也会**调用 `updateTankBodyTurret`（删掉再按同样几何重建）。
  如果沙箱把"函数被调用"当成"形状变了 → 刷新"，**每次捡枪都会多刷新一次**（性能白花，语义没变）。
  **建议：按"活性武器的 type 变了 / 炮管 fixture 集合变了"来判断刷新，而不是按调用点判断。**
- 另外，**导弹发射**（`updateWeapon`）也会改形状——这是权威版 §10 刷新条件③里"形状改变"的**第三种触发**，
  文档里没单列，**建议补进清单**。

### 6.4 一句话总结

> 原版的这一摊**全部是可复刻的确定逻辑 + 3 个随机点（霰弹/加特林散布、迷宫取点、`Math.random` 刷箱）**。
> 沙箱要做的是：**把"拾取判定 → 队列 → done() → 换枪 → 换炮管 fixture → 护盾 fixture → 弹开/吸收"这条链
> 按帧序 1:1 复刻**；弹药计数**直接读真实武器的 field**（主人原话：计数器直接读玩家的数据就行）；
> 不在树里预测"我方未来的霰弹/加特林弹道"。
