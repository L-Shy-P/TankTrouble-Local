## 一、职责（一句话）

**给定当前坦克位姿 + 一段固定操作，预测未来第 0..durationFrames 帧的坦克位姿（以及由位姿推出的死亡帧）；它是上层“树”的物理预演机。**

【代码原文】当前代码里实际存在**三条**不同的坦克运动预测实现，不能当成一条：

| # | 入口 | 实际驱动方式 | 谁在用 |
|---|---|---|---|
| A | `ai_tactics.simulateTankInputs` | 自研纯运动学积分 + 中心线 raycast 撞墙即停 | 规则版 AI 的躲弹候选评估（`ai_tactics` 自己） |
| B | `adapter.simulateTank` → `simulateTankClone` | 私有克隆 Box2D 世界 + 调用真实 `Tank._computeSpeed/_computeRotationSpeed` | 测试、`VantageScoring.scorePath` 单路回退、旧 `simulateNode` |
| C | `adapter.simulateTankBatch` / `simulateTankBatchScored` | 单世界 9 候选：优先 Rust `vt_rollout_batch` / `vt_score_paths`；失败回退 JS `simulateFusedBatch` | **主树**（`VantageTree.rolloutNine` 等） |

> 【代码原文】主树 `rolloutNine` 的顺序见 `game_core/js/vantage_tree.js:3961-4012`：先 `simulateTankBatchScored`（Rust），失败才 `VantageScoring.scorePaths` → `adapter.simulateTankBatch`。
> 【解释，未验证】因此“沙箱预测坦克”的默认权威不是 `simulateTankInputs`，也不是 `simulateTankClone`，而是 C 里的 Rust/融合批量；A/B 是遗留/回退路径。

### 2.1 `ai_tactics.simulateTankInputs`（纯运动学，规则 AI 路径）

**完整原文（40 行）**：

> 原文：`game_core/js/ai_tactics.js:2798-2837`

```js
    function simulateTankInputs(tank, inputs, duration, world) {
        var rot = tank.getRotation();
        var x = tank.getX();
        var y = tank.getY();
        var dt = 0.02;
        var t = 0;
        var fwd = Constants.TANK.FORWARD_SPEED.m;
        var back = Constants.TANK.BACK_SPEED.m;
        var rotSpd = Constants.TANK.ROTATION_SPEED;
        var hitWall = false;
        var samples = [];

        while (t <= duration + 0.0001) {
            samples.push({ t: t, x: x, y: y, rot: rot });
            if (t >= duration) break;

            var rs = 0;
            if (inputs.left && !inputs.right) rs = -rotSpd;
            else if (inputs.right && !inputs.left) rs = rotSpd;

            var sp = 0;
            if (inputs.forward) sp += fwd;
            if (inputs.back) sp -= back;

            var step = Math.min(dt, duration - t);
            rot += rs * step;
            var nx = x + Math.sin(rot) * sp * step;
            var ny = y - Math.cos(rot) * sp * step;

            if (world && typeof B2DUtils !== 'undefined' &&
                B2DUtils.checkLineForMazeCollision(world, { x: x, y: y }, { x: nx, y: ny })) {
                hitWall = true;
                break;
            }
            x = nx;
            y = ny;
            t += step;
        }
        return { samples: samples, hitWall: hitWall };
    }
```

**逐条事实（都能从上面的原文直接读到）：**

1. **没有 `Step`、没有 Box2D 积分**。位置由 `x += sin(rot)*sp*step`、`y -= cos(rot)*sp*step` 直接累加；`step = Math.min(0.02, duration - t)`。
2. **dt 写死 `0.02`**（L2802），与页面其它地方的 `_frameDtSec`/校准无关。`duration` 单位是**秒**（调用者传 `maxSim`，例如 `1.6`，见 `ai_tactics.js:3127-3132`）。
3. **速度常量取游戏原值**：`fwd = Constants.TANK.FORWARD_SPEED.m`（15.95）、`back = Constants.TANK.BACK_SPEED.m`（12.8）、`rotSpd = Constants.TANK.ROTATION_SPEED`（5.0），**没有乘 SPEED modifier**。
4. **完全没有读 `locked`**（函数体内没有出现 `locked`）。
5. 左右同时按：`rs = 0`（L2815-2816）；前后同时按：`sp = fwd - back`（L2818-2820），按源码字面是**净向前 3.15 m/s**。
6. **先转后走**：`rot += rs*step`（L2823）之后才用**新角度**算 `nx/ny`（L2824-2825）。这与 Box2D 在同一 Step 内“先按旧角速度设速度、再积分”的次序不同。
7. **撞墙检测**：`B2DUtils.checkLineForMazeCollision(world, {旧中心}, {新中心})`（L2827-2828）；命中则 `hitWall = true` 并 `break`（L2829-2830）——**整个循环停掉**，不滑动、不沿墙爬、不推开、也不返回撞墙点的位置（只返回撞墙前已 push 的样本）。
8. 该检测只看**坦克中心到下一个中心的线段**，不包含车体宽高、炮塔形状、其它坦克、子弹、陷阱、道具、护盾。
9. `world` 为 falsy 时（L2827 的 `world &&`）**完全跳过撞墙检测**——`ai_tactics.js:5695` 就传了 `null`。
10. 返回值只有 `{samples, hitWall}`；没有 `dead/deathFrame`（死亡是调用方用别的函数评估的）。

> 【代码原文】L2810 的循环上界是 `t <= duration + 0.0001`，因此当 `duration` 是 0.02 的整数倍时会多推一个末端样本：`samples.length = duration/0.02 + 1`。
> 【解释，未验证】这条 0.0001 容差是为了在浮点 `t` 累加后仍然收下终点帧；对非整除的 `duration`，最后一步是 `step = duration - t` 的残步。

**事实：**

- `FRAME_DT: 0.02` 是**硬编码字面量**（L108），**不是**从 `Constants` 读的，也**不会**被 `setFrameDtSec()` 更新；真正给物理 `Step` 用的是文件级 `_frameDtSec`（见 §2.5）。

### 2.3 `vantage_sandbox.getCloneWorld`（私有克隆世界，B 路径的底座）

**完整原文（L168-193）**：

> 原文：`game_core/js/vantage_sandbox.js:168-193`

```js
    function getCloneWorld(gameController) {
        var maze = gameController.getMaze();
        if (!maze) return null;
        if (_cloneCache && _cloneCache.mazeRef === maze) return _cloneCache;

        var world = new Box2D.Dynamics.b2World(
            Box2D.Common.Math.b2Vec2.Make(0, 0), true);
        B2DUtils.createMaze(world, maze);   // 原版：克隆全部墙

        var tankBodies = {};
        var tanks = gameController.getTanks();
        for (var pid in tanks) {
            if (!tanks.hasOwnProperty(pid)) continue;
            var tk = tanks[pid];
            if (!tk || !tk.getB2DBody || !tk.getB2DBody()) continue;
            tankBodies[pid] = B2DUtils.createTankBody(world, tk);   // 原版建体
        }

        _cloneCache = {
            mazeRef: maze,
            world: world,
            tankBodies: tankBodies,
            bulletBodies: []
        };
        return _cloneCache;
    }
```

**事实：**

- 缓存是**按迷宫对象引用**的单个全局 `_cloneCache`（L166, L171），不是按 aiId；换图才重建；`clearCaches()`（L633-636）可以主动清。
- 世界用零重力 + `doSleep=true` 构造（L173-174），与游戏真实世界构造同参（见 §2.12）。
- 墙：`B2DUtils.createMaze(world, maze)`（L175），是原版建墙函数。
- 坦克：遍历 `gameController.getTanks()`，对每个有真实 body 的坦克调用 **原版** `B2DUtils.createTankBody(world, tk)`（L177-184）。这会给坦克车体+炮塔夹具，filter 与游戏完全一致（见 §2.12），因此**坦克-坦克、坦克-墙、坦克-子弹的物理碰撞在原版 mask 下是打开的**。
- 子弹池 `bulletBodies: []` 初始为空，随后由 `acquireBulletBody` 按需创建（L186-191, L198-219）。
- **没有**克隆 SHIELD、TRAP、COLLECTIBLE、ZONE；文件头 L164 自己写明“未克隆项：护盾 SHIELD 夹具…、陷阱”。
- 【事实】缓存建立后若又出现新坦克（例如 DeathMatch 复活/中途加入），`getCloneWorld` **不会**再遍历一次把新坦克补进去；只有 `simulateTankClone` 对**本 AI 自己**做了一次懒补建（L465-468），对手不会补。
- 缓存建立后若某坦克被销毁，`simulateTankClone` 会在重摆阶段把对应克隆体 `SetActive(false)`（L485-487）。

**配套的子弹池原文（L195-228）**：
> 原文：`game_core/js/vantage_sandbox.js:195-228`

```js
    /** 子弹克隆体池：按需补建；每轮模拟前全停，acquire 时按轮次号复用 */
    var _cloneRound = 0;

    function acquireBulletBody(cw, projectile) {
        var i, slot = null;
        for (i = 0; i < cw.bulletBodies.length; i++) {
            if (cw.bulletBodies[i].lastRound !== _cloneRound) { slot = cw.bulletBodies[i]; break; }
        }
        if (!slot) {
            var rb = projectile.getB2DBody();
            var radius = 0.25;
            try {
                radius = rb.GetFixtureList().GetShape().m_radius;
            } catch (eR) {}
            slot = {
                body: null,
                lastRound: -1
            };
            slot.body = B2DUtils.createProjectileBody(cw.world, projectile, radius);
            cw.bulletBodies.push(slot);
        }
        slot.lastRound = _cloneRound;
        slot.body.SetActive(true);
        return slot.body;
    }

    /** 本轮未被 acquire 的池槽全部停用（每轮模拟结束时调用） */
    function parkUnusedBullets(cw) {
        for (var i = 0; i < cw.bulletBodies.length; i++) {
            if (cw.bulletBodies[i].lastRound !== _cloneRound) {
                cw.bulletBodies[i].body.SetActive(false);
            }
        }
    }
```

### 2.5 `vantage_sandbox.simulateTankClone`（B 路径的驱动核心；也是 `adapter.simulateTank` 的实现）

**完整原文（L454-578，125 行）**：

> 原文：`game_core/js/vantage_sandbox.js:454-578`

```js
    function simulateTankClone(gameController, aiId, inputs, durationFrames, opt) {
        var cw = getCloneWorld(gameController);
        var FRAME = _frameDtSec;
        var i;
        opt = opt || {};

        var me = gameController.getTank(aiId);
        var meBody = cw ? cw.tankBodies[aiId] : null;
        var samples = [];

        // 克隆世界建后才出现的坦克：动态补建克隆体（原版建体函数）
        if (cw && me && me.getB2DBody && me.getB2DBody() && !meBody) {
            meBody = B2DUtils.createTankBody(cw.world, me);
            cw.tankBodies[aiId] = meBody;
        }

        // 克隆世界不可用（无迷宫等极端态）：退化为静止采样（保接口不炸）
        if (!cw || !meBody || !me || !me.getB2DBody()) {
            for (i = 0; i <= durationFrames; i++) {
                samples.push({ t: i * FRAME, x: me ? me.getX() : 0, y: me ? me.getY() : 0, rot: me ? me.getRotation() : 0 });
            }
            return { samples: samples, hitWall: false, dead: false, deathFrame: -1 };
        }

        // ① 重摆：全部坦克克隆体 → 各自真实位姿/速度（对手快照驱动）
        // ⚠ 本 Box2D 版本 SetTransform(t) 只收单个 b2Transform；两参摆位
        //   必须用 SetPositionAndAngle(pos, angle)（2026-08-15 离线实锤：
        //   传错参数 → t.GetAngle is not a function → v6 运行态全灭的真凶）
        var pid, tb, rpos, rvel, rbody;
        for (pid in cw.tankBodies) {
            if (!cw.tankBodies.hasOwnProperty(pid)) continue;
            var rt = gameController.getTank(pid);
            rbody = rt && rt.getB2DBody ? rt.getB2DBody() : null;
            if (!rbody) { cw.tankBodies[pid].SetActive(false); continue; }
            cw.tankBodies[pid].SetActive(true);
            rpos = rbody.GetPosition(); rvel = rbody.GetLinearVelocity();
            cw.tankBodies[pid].SetPositionAndAngle(
                Box2D.Common.Math.b2Vec2.Make(rpos.x, rpos.y), rbody.GetAngle());

**逐步事实：**

1. **取 clone 世界与 `FRAME`**：`cw = getCloneWorld(gameController)`；`FRAME = _frameDtSec`（L455-456）。`_frameDtSec` 定义在 L1035，默认 0.02，可由 `setFrameDtSec` 改成 `[0.005, 0.2]`（L1036-1039）。
2. **克隆世界不可用时的退化**（L470-476）：直接按固定位姿采样 `durationFrames+1` 帧，返回 `{samples, hitWall:false, dead:false, deathFrame:-1}`，不模拟。
3. **重摆全部克隆坦克**（L478-495）：对 `cw.tankBodies` 里每个坦克读真实 body 的位姿/线速度/角速度，写入克隆体；真实坦克已不存在的置 `SetActive(false)`。**没有任何“对手输入模型”**——对手克隆体此后只保留这份快照速度，只有 Box2D 碰撞能再改它，不会有人调用 `Tank.update` 把它的速度重设回它的按键。
   - 【代码原文】L479-481 注释特别说明：本 Box2D 版本的 `SetTransform(t)` 只收单参数，摆位必须用 `SetPositionAndAngle(pos, angle)`。
4. **我方摆到 `opt.startPose`，速度/角速度清零**（L497-501）：`meBody.SetLinearVelocity((0,0)); SetAngularVelocity(0)`。**注意这里与融合路径 v127 不同**（融合路径 L1343-1367 继承真实线/角速度）；与 Rust 路径的清零一致（§2.13）。
5. **子弹克隆**（L503-535）：遍历 `gameController.getProjectiles()` 的**所有真实子弹**（不只威胁表），逐颗 `acquireBulletBody`；
   - 若给了 `opt.threats` 且 `opt.tGlobal > 0`：在 threats 中按 id 找同一条，用 `TankTroubleAITactics.positionOnProjectilePath(path, speed, tGlobal)` 求“节点起点时刻”的位置（L514-525）；
   - 否则用真实 body 当前位置（L527-531）；
   - 线速度**始终**写真实 body 的当前速度（L532-533），即使位置是用未来折线求的。
   - `parkUnusedBullets` 停用本轮没 acquire 的槽（L535）。
6. **借用真实 Tank 的原版速度函数**（L537-541）：先快照 `me.forward/back/left/right/speed/rotationSpeed`，再 `locked = !!me.locked`。
7. **逐帧循环**（L544-570），`k = 0..durationFrames`：
   - 先把**当前**克隆体位姿 push 进 `samples`（L545-549），所以 `samples[k]` 是“走了 k 步之后”的位姿；当 `durationFrames=0` 时只有 1 个起始样本。
   - `locked`：每帧把克隆体线速度/角速度清 0（L553-555），与游戏 `Tank.update` 的 locked 分支同语义。
   - 非 locked：把 `me.forward/back/left/right` 设成本帧 inputs（`!!` 归一），调用**真实** `me._computeSpeed()`、`me._computeRotationSpeed()`（L557-562），再用**克隆体当前角度** `a = meBody.GetAngle()` 写速度：`(sin(a)*me.speed, -cos(a)*me.speed)`、角速度 `me.rotationSpeed`（L563-566）。
   - `cw.world.Step(FRAME, 10, 10)`（L569）——dt 是 `_frameDtSec`，速度迭代 10、位置迭代 10。游戏原版是 `b2dworld.Step(deltaTime, 10, 10)`，迭代数相同、dt 不一定相同（§2.12）。
8. **恢复真实 Tank 实例字段**（L572-575）：恢复 `forward/back/left/right/speed/rotationSpeed`；**没有改过** `me.x/y/rotation/locked`，所以不恢复它们。恢复不是 `try/finally`（若中途异常会留下脏字段）。
9. **返回值**（L577）：`{samples, hitWall, dead:false, deathFrame:-1}`。
   - 【代码原文事实】`hitWall` 在 L543 声明为 `false`，**函数体内再无任何赋值**，所以 B 路径的 `hitWall` 永远是 `false`。
   - 【代码原文事实】`dead`/`deathFrame` 是写死的 `false/-1`；死亡在 B 路径里由调用方另做（`simulateNode` 用 `checkDeath`，`VantageScoring.scorePath` 用 `scoreFrame` 的 `fr.dead`）。
10. **碰撞行为直接由这个克隆世界的 Box2D 决定**：
    - 墙是静态体（density 0、friction 0.05、restitution 0），坦克是动态体（车体 density 1、friction 0.25、restitution 0；炮塔 density 0）；因此**贴墙滑动是 Box2D 求解器的真实接触响应**。
    - 坦克夹具 mask 含 `TANK`（见 §2.12），克隆世界里所有坦克互撞；**坦克互推在该路径真实存在**——但对手没有驱动，只是以 L492-494 写入的快照速度惯性漂移。
    - 子弹夹具 mask 含 `TANK`，所以子弹-坦克在该路径是**物理碰撞**（克隆世界没有“命中即死/子弹销毁”的结算），子弹会一直存在并可能给坦克一个很小但非零的冲量。【解释，未验证】冲量量级未测；坦克 mass 远大于子弹（坦克 density 1、约 3x4 m 车体，子弹 density 0.01、半径约 0.25 m）。

    function createFusedCandidateBody(world, tank, opIndex) {
        var body = B2DUtils.createTankBody(world, tank);
        var MAZE = Constants.COLLISION_CATEGORIES.MAZE;
        var PROJ = Constants.COLLISION_CATEGORIES.PROJECTILE;
        var TANK = Constants.COLLISION_CATEGORIES.TANK;

        // 正常夹具：候选坦克只和墙碰撞（候选之间、候选与子弹都不碰撞）
        var shapes = [];
        var fixture = body.GetFixtureList();
        while (fixture) {
            var fd = fixture.GetFilterData();
            fd.maskBits = MAZE;
            fixture.SetFilterData(fd);
            shapes.push(fixture.GetShape());
            fixture = fixture.GetNext();
        }

        // 传感器夹具：与子弹产生 isSensor 接触，不反弹不阻挡
        for (var si = 0; si < shapes.length; si++) {
            var sensorShape = cloneFusedShape(shapes[si]);
            if (!sensorShape) continue;
            var sfd = new Box2D.Dynamics.b2FixtureDef();
            sfd.shape = sensorShape;
            sfd.density = 0.0;
            sfd.friction = 0.0;
            sfd.restitution = 0.0;
            sfd.isSensor = true;
            sfd.userData = { type: 'fusedSensor', opIndex: opIndex };
            sfd.filter = new Box2D.Dynamics.b2FilterData();
            sfd.filter.categoryBits = TANK;
            sfd.filter.maskBits = PROJ;
            body.CreateFixture(sfd);
        }
        return body;
    }
```

**事实（这是“撞墙/互推怎么处理”的关键）：**

- 先用**原版** `B2DUtils.createTankBody(world, tank)` 建候选体（L902），即初生时拥有与游戏相同的车体+炮塔夹具和完整 mask。
- 随后对**每个普通夹具**改写 `fd.maskBits = MAZE`（L907-916）。于是 9 个候选坦克的**实体夹具只和墙碰撞**：
  - 候选 ↔ 候选：被 filter 掉（`maskBits` 里没有 `TANK`）；
  - 候选 ↔ 子弹：被 filter 掉（`maskBits` 里没有 `PROJECTILE`）。
- 再为每个原夹具复制一个**同形状 sensor**夹具（L918-933）：`isSensor=true`、`density=0`、`friction=0`、`restitution=0`，`categoryBits=TANK`、`maskBits=PROJECTILE`，`userData={type:'fusedSensor', opIndex}`。它**不产生碰撞响应**，只用于之后的接触检测判死。
- 【事实】融合世界里**完全没有对手坦克体**：`getFusedWorld` 只创建本 AI 的 9 个候选（L985-988），不会 `createTankBody` 对手。
- 【结论，直接由源码推出】C 路径（Rust/JS 融合）的**坦克互推不存在**；贴墙滑动仍是 Box2D 真接触响应（候选实体夹具 ↔ 墙）。文件头 L160-161 那句“贴墙滑动 / 坦克互推全是真 Box2D 碰撞响应”描述的是**拷贝区5 = `getCloneWorld`+`simulateTankClone`（B 路径）**，不是后来加的融合世界候选体。

- `_updateModifiers`：先把所有 modifier 初始化为默认 1.0，再遍历该玩家的 upgrade 列表；遇到 `UPGRADE_TYPES.SPEED_BOOST` 时 `newModifiers[SPEED] += upgrade.getField('speedBoost')`。也就是**多个加速升级会相加**。
- `SpeedBoostUpgrade.createInitialUpgradeState` 把传入的 `speedBoost` 存进 `_speedBoost`；`Upgrade.getField('speedBoost')` 返回 `this._speedBoost`（基类 `getField` 会加下划线找字段）。
- 生成点：`CRATE_SPEED_BOOST` 箱子被拾取时调用 `createInitialUpgradeState(..., Constants.SPEED_BOOST_LIFETIME, Constants.SPEED_BOOST_EFFECT)`，即 **+0.3、持续 10 秒**。因此拾取后 modifier = 1.0 + 0.3 = **1.3**，前进/后退/转速全部 ×1.3。
- 【解释，未验证】`_updateModifiers` 的调用点（`46989e39...js:1` 字节 12492/15079/25618）分别是“坦克创建 / 升级创建 / 升级销毁”；它**不是每帧**调用，但 `_computeSpeed` 每次都实时读取 `getModifier`，所以拾取/到期后的下一帧就会反映新倍率。
- 【解释，未验证】`AGENTS.md` 里主人说“加速箱不在真实游戏中”，而代码里存在完整 `CRATE_SPEED_BOOST → SPEED_BOOST` 创建路径与 0.3/10s 常量。本文只陈述代码事实：**只要真实对局里 modifier 不是 1.0，B/C 路径会自动带上这个倍率；A 路径不会**。

### 2.14 与真实游戏 `Tank.update` 的逐字节一致性裁决

**结论：不是逐字节一致。** 一致的只到“速度/角速度的计算与赋值公式”；步长、世界内容、初速度、对手、子弹、时段内状态变化都不一致。

**(a) 一致的部分（B/C 路径）：**

1. `_computeSpeed` / `_computeRotationSpeed` 是**直接调用真实 Tank 实例上的同名方法**（`vantage_sandbox.js:561-562`、`1701-1702`、`1214-1223`），不是复写。这两个函数本身执行一致。
2. 赋值公式一致：`SetLinearVelocity(sin(a)*speed, -cos(a)*speed)` + `SetAngularVelocity(rotationSpeed)`；预测用 `meBody.GetAngle()`，而游戏 `Tank.update` 用的 `this.rotation` 是它第一行刚从 `b2dbody.GetAngle()` 同步来的，同一时刻同值。
3. `locked` 分支一致：都是速度/角速度清零且不调用 `_compute*`（游戏 `update`；`vantage_sandbox.js:553-567`、`1697-1711`）。
4. 对 `forward/back/left/right` 的读取一致：`_computeSpeed` 读原始字段；预测在调用前把原始字段设为本帧 inputs（`!!` 归一）。

**(b) 不一致的部分（B/C 路径与游戏本体）：**

| 维度 | 游戏本体 | B 克隆路径 | C 融合/Rust 路径 |
|---|---|---|---|
| 每帧 dt | `deltaTime = min((now-last)/1000, 0.1)` 可变 | `_frameDtSec`（默认 0.02，可校准） | JS 融合 `_frameDtSec`；Rust `frame_dt()`（ABI 同步，默认 0.02） |
| Step 迭代 | `Step(dt,10,10)` | 同 | 同 |
| 世界内容 | 墙/所有坦克/子弹/陷阱/道具/护盾/毒雾/出生区…… | 墙+所有克隆坦克+所有子弹；无陷阱/道具/护盾/区域 | 墙+本 AI 的 9 个候选+子弹；无对手、无陷阱/道具/护盾/区域 |
| 初始线/角速度 | 保持上一帧 `Tank.update` 设置的速度 | **清零**（L497-501） | JS 融合：继承真实值（L1343-1367）；Rust：清零（`rollout.rs:709-717`） |
| 对手 | 每个坦克每帧都被自己的 `Tank.update` 驱动 | 只在开场写一次真实位姿/速度，之后无人驱动（惯性+碰撞） | 完全没有对手体 |

### 2.15 对四个具体问题的直接回答

**Q1：预测时坦克怎么被驱动？用了哪些常量（速度、转速、加速度、摩擦…）？**

- A 路径：纯运动学。每帧先 `rot += rs*step`，再用**已更新的** rot 算 `x += sin(rot)*sp*step`、`y -= cos(rot)*sp*step`，其中 `step = min(0.02, duration-t)`；`sp` 由 `FORWARD_SPEED.m=15.95`、`BACK_SPEED.m=12.8` 组合；`rs` 取 `ROTATION_SPEED=5.0`（左负右正）。**没有加速度、摩擦、质量**。
- B/C 路径：每帧调用真实 `Tank._computeSpeed/_computeRotationSpeed`（含 SPEED modifier），把 `(sin(bodyAngle)*speed, -cos(bodyAngle)*speed)` 和 `rotationSpeed` 写到 Box2D body，然后 `Step`。**没有加速度/摩擦常量**；摩擦/惯性由 Box2D 夹具参数决定（车体 density 1、friction 0.25、restitution 0；墙 density 0、friction 0.05、restitution 0；body linearDamping 0）。
- 速度常量：15.95 / 12.8 / 5.0 / 尺寸 3×4 m / 炮塔 0.7×1.4 @ y=-2.0 m / 20 px每米。详见 §三。

**Q2：撞墙/贴墙滑动/坦克互推是怎么处理的？Box2D 还是自研？**

- A 路径：**自研**。用 `B2DUtils.checkLineForMazeCollision` 对“中心→下一中心”做**一次 maze-only raycast**；命中即 `break`，不滑动、不推、不看车体/炮塔形状。`world=null` 时连这个都不做（`ai_tactics.js:5695`）。
- B 路径：**真 Box2D**。私有克隆世界，墙+所有坦克+所有子弹用原版建体函数和原版 mask；贴墙滑动、坦克互推、子弹-坦克接触全部由 Box2D 求解。对手没有输入驱动，只是快照速度惯性漂移。
- C 路径：**真 Box2D（JS）或 Rust Box2D 移植**；候选实体夹具 mask 改成只撞 MAZE，**候选之间不碰、没有对手体**，所以**没有坦克互推**；墙碰撞和贴墙滑动仍由 Box2D 求解。子弹与候选是 sensor，不推坦克。
- 【解释，未验证】这正是 `vantage_sandbox.js:160-161` 文件头“贴墙滑动 / 坦克互推全是真 Box2D 碰撞响应”容易误读的地方：那句话描述的是**克隆路径（拷贝区5）**，不是融合候选路径。

**Q3：locked / SPEED modifier / 弹簧绳之类的特殊状态怎么处理？**

- `locked`：B/C 读取真实 `me.locked`，整个 rollout 每帧把速度/角速度清 0，不调用 `_compute*`；A 完全不处理。游戏本体 `update` 也是清零，语义一致。**locked 在窗口内解除不会反映**。
- SPEED modifier：B/C 直接调用真实 `_computeSpeed/_computeRotationSpeed`，所以自动带 `getModifier(SPEED)`（默认 1.0；SPEED_BOOST 每次 +0.3、持续 10 s，多升级相加）；A 用裸常量、**不带 modifier**。**窗口内拾取/到期不会推进**。
- 弹簧绳：**完全不进坦克运动**。`springRopeLength/springRopeFrameScore` 只在 `vantage_scoring.js` 里作为帧分扣分项；开启时会让若干 Rust 评分/重评分快路返回 null，但不改任何 body/速度。默认关（`SCORING_DEFAULTS.springRopeEnabled=false`）。游戏原版 JS 里搜不到 `SPRING` 逻辑。
- 其他特殊状态：SHIELD/TRAP/COLLECTIBLE/ZONE 在 B/C 里**都没有克隆**（文件头自述；`COLLECTIBLE` 在 `vantage_sandbox.js` 全文未出现）。`opt.speedCap`（贴墙爬行校准）只在 JS 融合路径生效，且只钳**正**速度；B 与 Rust 都不生效。

**Q4：每帧 `Step(dt, velIter, posIter)` 的参数是什么？**

- 游戏：`b2dworld.Step(deltaTime, 10, 10)`，`deltaTime=(now-lastUpdate)/1000` 且 `min(..., 0.1)`（`46989e39...js:1` 字节 26455；`ce217...js:1` 字节 2024-2166）。
- B 克隆：`cw.world.Step(_frameDtSec, 10, 10)`（`vantage_sandbox.js:569`）。
- C JS 融合：`fc.world.Step(_frameDtSec, 10, 10)`（`vantage_sandbox.js:1725`）。
- Rust：`fc.world.step(frame_dt(), 10, 10)`（`rollout.rs:819`）。
- 子弹-only 轨迹：`cw.world.Step(_frameDtSec, 10, 10)`（`vantage_sandbox.js:423`）。
- 死亡判定迷你世界：`_deathWorld.Step(0.001, 1, 1)`（`vantage_sandbox.js:1983`）。
- `_frameDtSec` 默认 0.02、可校准 0.005~0.2；`buildConstants().FRAME_DT` 恒 0.02（两套口径，见 §5.1#3）。

## 四、【解释】我推断的语义（每条都标“未验证”）

> 以下是从代码事实出发的归纳，不是源码直接写明的设计意图。凡涉及“为什么/应该”的，全部标【解释，未验证】。

1. **【解释，未验证】坦克运动模型是“速度伺服”，不是“加速度模型”。** 游戏和预测都在每帧直接把速度设成目标值（`SetLinearVelocity`/`SetAngularVelocity`），没有加速度、摩擦、质量项进入速度计算；所谓“惯性”只存在于 Box2D 两个 Step 之间被求解器改掉的速度分量。常识校验：前进 15.95 m/s、后退 12.8 m/s、转速 5 rad/s（约 286°/s、一圈约 1.26 s），与 TankTrouble 这种快节奏小地图坦克一致。
2. **【解释，未验证】B/C 路径之所以逐帧调用真实 `_computeSpeed`，是为了不重写公式、自动带上 SPEED modifier 和任何未来新增的 modifier。** 事实依据是 `simulateTankClone`/`simulateFusedBatch` 都只在算速度前后改 `me.forward/back/left/right/speed/rotationSpeed` 六个字段（§2.5/§2.9），其余不动。
3. **【解释，未验证】A 路径（`simulateTankInputs`）是规则版 AI 的“低成本前向模型”，不是树的物理权威。** 事实依据：它没有 Box2D、没有 locked、没有 modifier、只做中心线 raycast；调用点全在 `ai_tactics` 内部的躲弹候选评估。
4. **【解释，未验证】“撞墙”在 A 路径的语义是“本步直接取消并终止整段”，副作用是 AI 会把“顶墙”当成不可行，而不是像 Box2D 那样沿墙滑。** 这会系统性低估“贴墙绕行”的可行路线；但 A 路径不服务树，影响面需要单独评估。
5. **【解释，未验证】B 路径的克隆世界用真实对手位姿+速度快照，严格说是“对手以当前速度惯性漂移”的一阶近似。** 事实依据：L482-495 只写一次速度，循环里只驱动 `meBody`；对手在真实游戏里本应被它自己的 `Tank.update` 持续改写速度。
6. **【解释，未验证】C 路径不做对手、不做坦克互推，是“单坦克+共享子弹+墙”的模型。** 事实依据：`getFusedWorld` 只建 9 个 `me` 候选；候选实体 mask 只有 MAZE；sensor 只对子弹。若对手贴脸推 AI，C 路径捕不到这个力。
7. **【解释，未验证】B 路径里子弹与坦克的物理碰撞可能是“非意图副作用”。** 事实依据：克隆世界用原版 `createProjectileBody`（mask 含 TANK）+ 原版 `createTankBody`（mask 含 PROJECTILE），而 B 路径没有“子弹命中即销毁/判死”的结算；因此子弹会持续存在并与坦克发生接触。量级未测。
8. **【解释，未验证】`speedCap` 是为“贴墙爬行时实际速度远低于名义速度”打的补丁。** 事实依据：v128 注释明说“树发现真实车在贴墙附近爬行（实际速度<<名义速度）时传入 opt.speedCap，rollout 前进速度一律钳到实测值”。它只在 JS 融合路径生效，且只钳正值；这是否有意（倒车是否也需要）未在代码里写明。
9. **【解释，未验证】`consts.FRAME_DT=0.02` 与可校准的 `_frameDtSec` 是两套时间口径。** 物理 Step 用 `_frameDtSec`；而 `buildConstants` 暴露的 `FRAME_DT` 永久是 0.02；`vantage_scoring` 在缺少 `trackFrameDt` 时会退回 `adapter.constants.FRAME_DT`。若校准真的把 dt 改成 0.015~0.035，这些退回点会产生时间基准错位。影响范围未验证。
10. **【解释，未验证】SPEED modifier 在整段 75 帧里被当作常量。** 事实依据：B/C 每帧只是重新调用 `_computeSpeed`，读的是**模拟发起时**真实 roundModel 的当前 modifier；rollout 内不会推进加速箱的 10 秒寿命，也不会模拟“中途拾取/到期”。如果剩余寿命小于预测窗（树上限 10 秒，升级寿命 10 秒；75 帧通常 1.5 秒），一般无事；边缘情况未验证。
11. **【解释，未验证】Rust 与 JS 融合的“候选初速度”不一致会改变“带着动量入场”的轨迹。** 事实依据：JS 融合 L1343-1367 继承真实线/角速度；Rust `rollout.rs:709-717` 清零；B 路径 L497-501 也清零。哪一个是权威（或两者是否可接受）代码里没有写；影响帧数/幅度未验证。
12. **【解释，未验证】方向约定三条路径一致。** 事实依据：`Tank.update` 与 B/C 都用 `speedX=sin(angle)*speed`、`speedY=-cos(angle)*speed`；A 用 `nx=x+sin(rot)*sp*step`、`ny=y-cos(rot)*sp*step`，符号完全相同；左转/右转三条路径也都是左减右加（`-ROTATION_SPEED`/`+ROTATION_SPEED` 与 A 的 `rs=-rotSpd`/`+rotSpd`）。常识校验：θ=0 时前进方向是 (0,-1)，右转时 θ 增大→前进方向转向 +x，与屏幕坐标下“右转”一致。

### 6.3 动手前建议按顺序裁决的 5 件事（不替主人做决定）

1. **权威路径**：树到底以哪条为准？Rust 优先 + JS 融合确认，还是只认 JS 融合？三套路径必须先收敛。
2. **帧长权威**：以游戏实测 dt 为准，并同步给 JS `_frameDtSec`、JS `consts.FRAME_DT`、Rust `vt_set_frame_dt`、评分 `trackFrameDt`；否则 6.1#5 必炸。
3. **初始动量**：预测起始帧要不要继承真实 body 的线/角速度？要就三条路径一起改（至少 JS 融合与 Rust 对齐），不要就在文档里明确写“起步归零”并承担原地旋转/蹭墙局面的误差。
4. **对手契约**：平时不模拟对手时，是“完全无对手体”还是“保留快照惯性漂移的对手体”？“贴脸被推”由谁负责？当前代码是前者的 C 路径 + 后者的 B 路径，不能同时默认。
5. **speedCap**：贴墙爬行校准是否进权威路径？若进，必须同时进 Rust（传 speed_cap 或在 JS 预算速度里钳），并把“只钳正值”的行为改成明确规则（是否也钳倒车/转速）。
