### 1.2 死亡判定有几条路径？

按"**这个 `dead/deathFrame` 是谁算出来的**"分，当前代码里共有 **4 条活的路径 + 1 条已退役的导出路径**：

| # | 路径 | 触发条件 | 谁算死亡 | `deathAuthority` | 是否会被下游再确认 |
|---|---|---|---|---|---|
| **A** | **融合世界（JS Box2D）** | `adapter.simulateTankBatch` 在 Rust 关/失败时；`adapter.simulateTankBatchJsFused`（扫描/确认）；`simulateTankBatchScored` 只借它摆弹（0 帧） | `simulateFusedBatch`：sensor 接触扫描 + **JS 独有**的几何回溯补判 | `'fused'` | 不需要（它就是权威） |
| **B** | **Rust 候选** | `RUST_PHYSICS_ENABLED=true` 且桥就绪且帧步长兼容：`rolloutBatch`（`simulateRustBatch`）、`scorePaths`（`simulateTankBatchScored`）、`rescoreNodes`（`rescoreTankSamples`） | Rust 的 Box2D 子集（`rollout.rs`/`rescore.rs`） | `'rust-candidate'` | **会**：最终执行路线上的节点由 `confirmNodeDeathWithJsFused` 走 JS 融合重算 |
| **C** | **静态重叠 `checkDeath`** | 批量路径整个不可用时的单路回退 `scorePath`；`simulateNode` 导出（**树已不调用**） | 死亡世界"摆位 → `Step(0.001,1,1)` → 查 IsTouching" | `'check'` | 会被当作 stale 再刷新（`nodeIsStale`：无 `scoreCache` 且 authority 不是 fused/rust-candidate → stale） |
| **D** | **融合世界的几何回溯补判** | 与 A 同一个函数内：contact 路径整段没抓到、但 `polyGap<0` | `fusedCircleSensorPolyGap` 逐帧扫描 | 仍标 `'fused'`（结果对象没有独立字段） | 不单独区分 |
| **E** | **旧 `VantageSandbox.simulateNode`** | 导出给 `game_core/test_vantage_sandbox.html` 用；`grep` 全仓，运行期树**零调用** | 递归调 `adapter.checkDeath` | 无（返回对象只有 `dead/deathFrame`） | —— |

> 路径 A/D 在同一个 `simulateFusedBatch` 里，但算法完全不同（见 §二.2.1.6）；
> 因为结果对象的字段一样，下游无法区分"这条 deathFrame 是接触抓到的还是几何补判的"。
> 【我的解释】这是文档里最值得单列的一条：**补判只会更敏感（少漏），但它的漏判面（仍是逐帧采样）与接触路径相同。**

### 1.3 `deathAuthority` 的 4 个取值分别代表什么

`deathAuthority` 字段起源于 `vantage_tree.js:1390`：

【代码原文】`vantage_tree.js:1390`：

|---|---|---|

### 1.4 谁是权威？

**结论（分两层，必须分开说）：**

1. **代码注释/设计口径**：JS 融合世界是死亡权威，Rust 是候选，`checkDeath` 是最后的保命回退。
   【代码原文】`vantage_scoring.js:2484`：

   ```js
                // v24：融合世界的传感器接触就是死亡判定权威，批量结果里已带
   ```

   【代码原文】`vantage_tree.js:596`：

   ```js
    *      只把静态路径留作 fused 不可用时的保命回退。
   ```

   【代码原文】`vantage_tree.js:3049-3051`（`confirmExecutionNodeDeath` 的注释）：

   ```js
     * v77：把 JS 融合世界确认结果写回节点。只有 deathAuthority 为
     * 'rust-candidate' 的节点才需要确认；确认后改标 'fused'（或回退
     * 'check'），并同步分数/死亡帧/回传父链。
   ```

2. **代码实际执行的粒度**：
   - 一次九操作 rollout 若走 Rust（`simulateTankBatchScored`，`vantage_tree.js:3966-4001`），**9 条候选的死亡帧全部是 Rust 值**；
   - 只有**最终被选为执行路线**的那个节点会被 `confirmExecutionNodeDeath` 用 JS 融合重算（`commit` 的两处：`vantage_tree.js:6482`、`6624`；新弹路径：`vantage_tree.js:7406-7407`）；
   - 未选中的 8 条候选、以及更深层的节点，可以继续携带 Rust/`check` 的死亡帧参与比较与生长。
   【我的解释】所以"融合世界是权威"这句话，在当前代码里应读作：
   **"执行路线节点的死亡结论，最终必须由融合世界确认"**，而不是"树上所有节点的 deathFrame 都来自融合世界"。
   这个区别对"绿死"排查很重要：**选路阶段用的是候选值，不是权威值。**

#### 2.1.13 `fusedSensor × PROJECTILE` 完整链路（从建体到判死）

把上面散点按**时序**串起来（每条都带行号）：

1. **建 maze 墙**：`getFusedWorld` → `B2DUtils.createMaze(world, maze)`（`vantage_sandbox.js:958`）。墙 fixture `categoryBits=MAZE`、`maskBits=TANK|PROJECTILE|TRAP`（b714 第 5 行）。
2. **建候选体**：`createFusedCandidateBody`（`901-935`）→ `B2DUtils.createTankBody(world, me)`（`902`）。原版建体给车体 `categoryBits=TANK`、`maskBits=...|PROJECTILE|...`（b714 第 5 行）。
3. **改实体夹具 mask**：`903-913` 把候选体**每个** fixture 的 `maskBits` 改成 `MAZE`。⟹ 候选×候选、候选×子弹的**实体**碰撞全部被过滤掉。
4. **建 sensor 夹具**：对每个原夹具复制同形状（`cloneFusedShape`，`654-684`），设 `isSensor=true`、density/friction/restitution=0、`userData={type:'fusedSensor', opIndex:opIndex}`、`filter.categoryBits=TANK`、`filter.maskBits=PROJECTILE`（`918-934`）。
5. **过滤配对成立条件**（Box2D）：`(catA & maskB) && (catB & maskA)` = `(TANK & PROJECTILE) && (PROJECTILE & TANK)` = **true**。
6. **建子弹体**：`acquireFusedBullet` → `B2DUtils.createProjectileBody(fc.world, projectile, radius)`（`1157`）：`categoryBits=PROJECTILE`、`maskBits=TANK|MAZE|SHIELD|ZONE`、`bullet=true`、`restitution=1.0`（b714 第 5 行）。半径取真实 fixture（`1135-1139`），退化时回退档案值并 `fusedDropLog`（`1141-1150`）。
7. **摆位**：`simulateFusedBatch` 对每个活弹 `SetPositionAndAngle + SetLinearVelocity`（`1416-1585`），来源 real / track / path / approx 四选一（见 §2.1.6(2)）。
8. **推进**：每帧对 9 个候选设速度，然后 `fc.world.Step(FRAME,10,10)`（`1725`）。
9. **窄相置位**：`b2Contact::Update` 对 sensor 走 `isSensorFlag` 分支：`if(f){ s = TestOverlap(shapeA,xfA,shapeB,xfB) }`（f1a5ef 单行，逐字）。即 **sensor 的 IsTouching 只由"两 shape 当前是否重叠"决定**（AABB 先过门）。

## 四、【解释】（所有推断均未定为结论）

### 4.1 权威模型的准确读法

代码给的下游规则是：

- `nodeIsStale`（`vantage_tree.js:4228-4244`）：**没有 `scoreCache` 时**，只有
  `deathAuthority ∈ {fused, rust-candidate} 且 freshSig 与当前签名一致` 才算 fresh；
  否则 stale。⟹ `'check'` 和无 authority 的节点**天然会被下一次层刷新重算**。
- `confirmExecutionNodeDeath`（`vantage_tree.js:3059`）：**只对 `'rust-candidate'` 生效**。
- `tick` 新弹分支（`vantage_tree.js:7406`）：也只对 `'rust-candidate'` 的 commitNode 调确认。

【我的解释】因此可以把权威模型读成三层：
1. **执行层权威** = JS 融合（被选中的执行节点最终要变成 `'fused'`）；
2. **选路层证据** = Rust 候选 + 未确认的 fused 批量（`'fused'` 也可能只是 `scorePaths` 给批量打的标签）；
3. **保命回退** = 静态 `checkDeath`（`'check'`）。
"绿死"要分清楚是**哪一层**出错：
- 选路层用了 Rust 的乐观值，执行层没抓住 → 执行层确认失败/被跳过；
- 执行层自己的 sensor 漏 → 几何补判也没扫到（两者都是逐帧）；
- 威胁表/摆弹漏 → 弹根本不在世界里（v38/v119/v134/v137 系列都在打这一类）。

### 4.2 静态重叠检测 vs 真实物理步进：本质差异

【我的解释】本质差异不是"一个准一个不准"，而是：
- `checkDeath` 是**两个离散轨迹之间的独立点集求交**——它假设"提供轨迹的人已经把物理算对了"；
- 融合世界是**一个共享物理系统**——它把"轨迹怎么来"和"有没有撞"放在同一个引擎里算，代价是 9 个候选共享同一个子弹体，
  且必须处理"候选停不停车"与"接触扫描在 Step 前还是后"的时序问题。

`checkDeath` 漏判面：
1. **帧间穿越**：弹位只在采样帧给（通常 0.36 m 间隔，普通弹；激光 3.6 m），两点都不重叠时检测不到。**但这不是"必然"**，见 §4.3。

3. **弹种语义**：非匀速直线弹（激光扫掠、导弹制导、破片撞墙即停）在折线里是近似；见 `vantage_sandbox.js:1108-1128` 的弹种档案与 TODO。
4. **上限截断**：`min(bulletPositions.length, 64)`（`vantage_sandbox.js:1966`）。
5. **只有点集没有时间**：它不检查"第 i 帧到第 i+1 帧之间"的先后关系；坦克的预测轨迹本身可以是"被子弹推着走"的（旧克隆世界里弹会实体碰撞，见 §4.7）。

   `auditContactList` 注释列了三种根因假设，**未定案**（§五.4）。
2. **sensor 无 CCD**（§4.4 实证）：帧间穿越仍可能漏。
3. **摆弹不完整/近似**：`approx` 分支前推、威胁表缺失、`lifeLeft<=0` 曾被关弹的历史修复（v136/v137）。
4. **对手/护盾/陷阱/道具/风暴没进世界**：见 §4.6。
5. **时序性停用**：寿命/破片在接触扫描前 `SetActive(false)` → contact 被销毁（§4.5）。

### 4.3 逐帧采样会不会"必然穿透"？——用数字验一遍

先把数算出来（来源 §3.3）：

- 普通弹每帧位移 = 18 m/s × 0.02 s = **0.36 m**（校准到 0.03 s 时 0.54 m）。
- 车体 = 3.0 m × 4.0 m；弹半径 0.25 m ⟹ 圆相对车体的有效宽度 ≥ 3.5 m。
- 炮塔 = 0.7 m × 1.4 m；圆相对炮塔短边的有效宽度 ≥ 1.2 m。
- 激光每帧位移 = 180 × 0.02 = **3.6 m**；融合世界给它的人造半径 = **0.05 m** ⟹ 有效宽度约 0.8 m。
- 破片/霰弹/加特林 0.5~0.7 m/帧。

**方向性结论（对"逐帧采样必然穿透"的验算）**：

1. **普通弹打车体**：采样间隔 0.36 m 远小于有效宽度 3.5 m。
   若弹道穿过车体内部，**必有至少一个采样点落在体内**（一维投影上也成立：宽度/步长 ≈ 9.7）。
   ⟹ "逐帧采样必然穿透普通弹" **不成立**。这是 **过度推广**，不能作为绿死解释。
2. **普通弹擦角**：如果弹道只切到一个角，弦长可以任意小；两个相邻采样点都可能落在体外。
   ⟹ **可能**漏，而且这正是需要"扫掠判定"而不是"点判定"的地方。**但它是小概率几何事件，不是主因。**
3. **激光**：真实半径 0（点圆/射线扫掠），180 m/s，3.6 m/帧；融合世界强行给它 0.05 m 圆，
   有效宽度 0.8 m < 3.6 m。⟹ **垂直穿越也会漏**。这是**确定的**漏判面，
   `vantage_sandbox.js:1118-1128` 的 TODO 自己也承认。
4. **破片**：0.1 m 半径、30 m/s 上下，0.6 m/帧，对 1.2 m 有效炮塔宽度仍有覆盖，对车体更没问题；
   但破片走"撞墙即停"语义，**它的漏判主要来自"该停没停/该消失没消失"的语义**（v162 已修），不是采样。
5. **斜穿**：真正的漏判条件是"弦长 < 采样步长"，即 `v_target × dt > chord`。
   对普通弹要 `chord < 0.36 m`（角点擦过）；对激光几乎总是成立。

【我的解释】所以正确的表述是：**"逐帧采样对最薄形状 + 最快弹（激光）会确定性漏；对普通弹只在掠角弦长 < 步长时漏，不是必然。"**

### 4.7 JS 与 Rust 的差异（会让"两边答案不同"）

| 差异 | JS | Rust | 后果 |
|---|---|---|---|
| 几何回溯补判 | `simulateFusedBatch` 有 `geoHit` 扫描（`1653-1688`、`1852-1861`） | `rollout.rs` 只有 sensor 接触扫描（`894-924`），全文无 polyGap 扫描 | v151 那种"几何重叠但 touching=false"的情形，**JS 会判死、Rust 判活**；这正是"Rust 候选说安全、JS 融合说死"的一类 |
| 帧步长 | `_frameDtSec` 校准；树把值推给沙箱 | `frame_dt()`，由 `vt_set_frame_dt` 推入；旧 wasm 无此导出时 JS 强制停 Rust | 不兼容时 Rust 快路自动关闭（`vantage_sandbox.js:1053-1078`） |
| 弹种语义 | v162/v164 在 JS 融合世界复刻破片撞墙即停/不归一化 | rollout.rs 有同样的 shrapnel 分支（`840-890`） | 已对齐 |

| 世界内容 | 墙 + 9 候选 + 弹 | 同构（`rollout.rs` 自述 line 1-3） | —— |

【我的解释】最重要的结论是：**"Rust 候选"不是 JS 融合的加速等价物**，
两边的判死能力有**结构性差别**（几何补判只在 JS），所以 `deathAuthority` 的区分不是形式主义，而是真实分歧。

### 4.8 `deathFrame` 的语义与 fd=0 的口径冲突（逐条对账）

目前代码里同时存在两套约定：

| 位置 | 写法 | 对 fd=0 的处理 |
|---|---|---|
| `safeFramesForDeath`（`vantage_tree.js:4099-4102`） | `if (!(fd >= 0)) return planned; ... if (fd <= 1) return 1;` | **承认 fd=0**，按"一选就是死、执行 1 帧" |
| `simulateTankBatchScored`（`vantage_sandbox.js:2349`） | `dead: r.deathFrame > 0` | **fd=0 → dead=false** |
| `rescoreTankSamples`（`vantage_sandbox.js:2501`） | `dead: rn.deathFrame > 0` | **fd=0 → dead=false** |
| `score_paths.rs`（`165-166`） | `if death_frame > 0` | **fd=0 → 按活满处理** |
| `scorePaths`（`vantage_scoring.js:2470`） | `for (i = 1; i <= frames; i++)` | 循环从 1 开始，`deathFrame===0` **不可能命中** |
| `scanNodeDeath` JS 融合分支（`vantage_tree.js:2038-2043`） | `if (j0 && j0.dead && j0.deathFrame != null)` + `safeFramesForDeath(0,...)` | **能识别 fd=0**（因为 raw fused 的 `dead` 是 true） |
| `rolloutNine` 的 Rust scored 分支（`vantage_tree.js:3997`） | 只打 `deathAuthority`，不改 `dead` | 沿用 Rust 映射后的 `dead=false` |

【我的解释，方向已验算】
- 若 `fd=0` 表示"起手位姿就已经和弹重叠"，那么"该节点是死"在几何上是确定的；
  但四条上游映射把 `dead` 置 false，节点会被当成"活满 75 帧"。
- 下游 `buildCandidate` 只在 `r.dead` 为真时调 `safeFramesForDeath`，所以 `fd=0 → alive`。
- 这是一个**口径矛盾**，不是"某个函数写错了名字"：`safeFramesForDeath` 的注释与上游映射对 fd=0 的语义相反。
- **能不能说"fd=0 就是绿死"？不能。** 需要先确认"fd=0 在实战里到底出现多频繁"（§五.2：
  我没有实测数据）。但它是**明确可压的隐患**：修口径的成本极低，收益是消掉一个"确定会漏"的分支。

    `n = Math.min(bulletPositions.length, _deathBulletBodies.length)`（`vantage_sandbox.js:1966`）；
    注释说 v21 "全部入检不再按下标截断"，但池上限仍是 64。树侧 `MAX_EVAL_BULLETS=64` 与之对齐，
    所以主链路不会超；但任何直接调 `adapter.checkDeath` 传 >64 颗的调用方（含测试）会静默丢弹。
    **未解决**：是否要把"截断"也做成响度失败（像 `fusedDropLog`）。判别：`grep checkDeath` 调用方。

14. **`safeFramesForDeath(fd<=1)=1` 会执行 1 帧（§2.2.3、§2.2.7）。**
    注释原文："fd=0=起手就撞上、fd=1=走 1 步就死，两者都是'一选就是死'，都只执行 1 帧"。
    在 `fd=1` 的样本定义下，"走 1 步"就是走到死帧。**未解决**：这是"反正下一帧就重新决策/换路"的有意设计，
    还是"最小段长不得为 0"的实现妥协？它对"绿死"的贡献需要实测（尤其 fd=1 的节点是否经常被选中执行）。
    判别：统计 `jsConfirmCount`/`jsConfirmEarlier` 与执行节点 `segmentFrames` 分布。

15. **对手模型：当前融合世界完全不模拟对手，但 `AGENTS.md` 的定案是"护盾/近距离时模拟对手，总深度 ≤1 秒"。**
    `getFusedWorld` 只建 `me` 的 9 个候选（`vantage_sandbox.js:986-989`）。
    【解释，未验证】这可能就是"对手贴身推挤"类偏差的来源；但文档与代码的落差是"未实现"，不是"实现错"。
    **未解决**：智能体版是否要求现在就把"护盾/近距离对手"补进融合世界。
    判别：以权威版 §10.4 为准，先确认当前是否在施工范围内。

16. **`b2BodyDef.allowSleep` 差异（候选/子弹/死亡世界）与"睡眠后不产生接触"的风险。**
    融合候选子弹由 `createTankBody/createProjectileBody` 建体：坦克 `allowSleep=false`（b714:5），
    子弹 `bullet=true` 但**没有设 `allowSleep`**（b714:5 的 `createProjectileBody` 没有 `allowSleep=false`）。
    融合批次每轮 `SetAwake(true)` 并设速度；`SetActive(true)` 后也有 `SetAwake(true)`（`1174-1177` 附近由调用方做，`1420`/`1585`）。
    **未解决**：在长 batch（75 帧）里，速度被墙反射后短时变慢，子弹是否会 `Sleep` 而停止碰撞？
    Box2D 的睡眠需要 `m_sleepTime >= b2_timeToSleep`（默认 0.5s）且速度低于阈值；
    `b2_velocityThreshold=0.0` 被游戏显式设为 0（b714:5），**可能**让速度很小的时刻也满足睡眠条件。
    我没有在融合世界里看到"每帧强制 SetAwake"的处理（只有设置速度时 `SetAwake(true)`，`1420`/`1585`），
    列此条要求复核。判别：在 bullet-only 世界跑 75 帧，打印 `IsAwake()`/接触数。

> 📌 这一节不是"bug 清单"，而是"**在往下写代码前必须先裁定或先实测**"的清单。

## 六、对"一次性写对"的影响

> 这一节把 §二~§五 收敛成"**重做 / 接智能体版时，哪些决定必须一次做对**"。
> 每条都注明依据；不引入文档之外的新设计。

### 6.1 先定"一个 fd 语义、一个权威枚举"

- **必须一次做对**：`deathFrame` 的定义（fd 是"能走几步"还是"第几帧死"）、`fd=0/1/-1` 的语义、
  `deathAuthority` 的取值集合与写入者。当前代码在这一点上是**多口径并存**（§4.8、§五.1、§五.2）。
- 依据：`safeFramesForDeath` 与四处 `>0` 映射相反；`'computed'` 无生产者。
- 建议做法（**解释，未验证**）：让**只有一个函数**负责把"物理结果"翻译成
  `{dead, deathFrame, deathAuthority}`，其余消费方只读；新增任何 authority 取值时，
  必须同时给出"谁写、谁确认、谁消费"三件事，否则禁止写入。

### 6.2 选路层 ≠ 执行层：确认必须覆盖"全部非 fused 来源"

- 现状：只有 `deathAuthority === 'rust-candidate'` 的**执行节点**会被 JS 融合确认（`vantage_tree.js:3059`、`7406`）；
  未选中的候选、以及 `'check'`/空 authority 的节点可能带着非权威死亡帧继续参与比较。
- **必须一次做对**：明确"哪些节点允许携带非权威值参与*比较*、哪些节点进入*执行*前必须被确认"。
  否则会出现"比较时用乐观值选了路，执行前才发现是死的"——`confirmExecutionRoutePick` 已经为此写了
  "确认后恰好 1 帧真死才改选"的补救（`vantage_tree.js:3092-3104`），但补救只覆盖 fd=1。
- 依据：§1.4、§2.2.7。

### 6.3 判死要"扫掠"还是"点采样"：按弹种分档，别一刀切

- **必须一次做对**：给每一类弹定义"判死用点采样还是扫掠"。
  数字结论（§4.3）：普通弹 0.36 m/帧 vs 车体有效 3.5 m → 点采样足够；
  激光 3.6 m/帧、真实半径 0 → **必须扫掠**；角点掠过的弦长 < 步长的情形需要扫掠才严谨。
- 依据：`vantage_sandbox.js:1118-1128` TODO（激光）、`vantage_sandbox.js:1653-1688`（几何补判仍是点）。
- **不要**把"逐帧采样必然穿透"写成全局结论（主人此前已纠正过一次）；范围要按弹种/几何算，见 §4.3。

### 6.4 sensor 接触漏判的根因要么修、要么明确"几何补判是正式机制"

- 现状：JS 有 `geoHit` 补判（`1653-1688`、`1852-1861`），Rust **没有**（`rollout.rs` 只有 contact 扫描）。
- **必须一次做对**：如果接受"几何补判"作为正式判死机制，就必须**两份实现都有**，
  并在 authority/诊断里能区分"contact 判死"与"geometry 判死"（现在都标 `'fused'`，且返回值无字段）。
- 依据：§4.7、§五.4。

### 6.5 世界内容清单：判死世界里"没有的东西"要先裁

- 现状缺失（§4.6）：对手坦克、护盾夹具、陷阱、道具、风暴区、武器炮塔形状、激光扫掠、导弹制导。
- **必须一次做对**：按 `AGENTS.md` 的树职责边界（确定的/很少改变的/简洁）逐项裁定"进/不进"，
  并把裁定写进接口（例如：护盾必须进，因为玩家也会用；风暴如果是另一条致死源，要不要进树）。
- 依据：`vantage_sandbox.js:164`；`AGENTS.md`「树的职责边界」一节。
- 特别注意：**"没模拟"不等于"不会死"**。如果风暴/陷阱/对手撞击能致死，而树只报"绿"，
  那和"子弹漏判"是同一种事故。

### 6.6 时间基准纪律：所有按帧换秒的地方必须走同一条函数

- 现状隐藏点：`sample.t` 恒等于 `frame*0.02`（Rust 映射）、`threatBulletPos` 用 `trackFrameDt`、
  融合摆弹用 `trackFrameDt`、`nodeWindowSig` 用 `trackDtOf`、`simState.tGlobal` 用树 `FRAME_DT`。
  v124/v129/v137 的注释记录过多起"同一条轨迹被两个帧长读成两条弹道"的事故。
- **必须一次做对**：定死"一条轨迹自带帧长"这个真源；任何"帧下标 ↔ 秒"的换算只允许调它。
- 依据：`vantage_sandbox.js:1030-1078`、`vantage_tree.js:1895-1901`（`trackDtOf`）、`vantage_scoring.js:1768-1778`。

### 6.7 摆弹完整性：不静默丢弹，但兜底策略要先确认

- 现状：v38 已经有"近似摆放 + 计数 + 每秒一条 warning"（`vantage_sandbox.js:1005-1029`、`1526-1566`）；
  但"威胁表没有这颗弹"时是靠 `getProjectiles()` 全量遍历补的，**近似用的还是真实位姿+真实速度直线前推**。
- **必须一次做对**：裁定"摆不进去时"的兜底语义：
  - 保守（当它可能命中）还是近似（按当前速度推）？
  - 世界条数上限（`MAX_EVAL_BULLETS=64`）与 Rust caps（256）不一致时怎么办？
- 依据：§五.7；主人已明确否定过"保守包络"这类自创设计，所以**先问，不要自己加**。

### 6.8 顺序纪律：停用 / 生命周期 / 接触扫描

- 现状：融合世界"Step → 弹寿命/破片 → SetActive(false) → 扫 contact"（§4.5）；
  真实游戏"Step → 派发碰撞事件 → 对象 update"。
- **必须一次做对**：明确"一帧内的因果顺序"，并在两侧对齐；特别是
  "本帧命中"与"本帧到期/撞墙消失"同时发生时谁赢。
- 依据：`vantage_sandbox.js:1727-1815`；`46989...js:1` 的 `RoundModel.update`。

### 6.9 判死实现里禁止"从函数名反推语义"

- 本文中已经出现的两个反面教材：
  - `safeFramesForDeath` 名字像"安全帧数"，但它对 fd<=1 返回 **1**（会执行 1 帧）；
  - `ensureDeathWorld` 名字像"建死亡世界"，但它的子弹没有速度、没有 `bullet=true`，`Step(0.001)` 只是触发 overlap。
- **必须一次做对**：所有"安全/危险/死亡"的函数，注释里直接写清**输入输出的单位和边界**（fd 的定义域、采样时刻、谁在 Step 前/后）。
- 依据：§2.1.9、§2.1.10、§2.2.3。

### 6.10 验证工具是现成的：先用审计，再改代码

- 现成只读钩子：
  - `adapter.getFusedDropStats()`（`vantage_sandbox.js:2201-2208`）→ 摆弹完整性；
  - `adapter.getLastFusedBatchSummary()` / `getFusedBatchAuditHistory()`（`2210-2211`）→ 最后 40 批的
    `placements/contacts/overlapNoContact/deathFrames/dead`；
  - `auditFusedGeometry` / `auditContactList` / `auditContactTruth`（`796-899`）→ 逐帧几何/接触真值；
  - `noteFusedDrops`（`vantage_tree.js:2247-2265`）→ 树侧累计计数。
- **建议的"一次性写对"前置动作**（**解释，未验证**）：
  1. 拿一段"绿死"录像，取 `getLastFusedBatchSummary()` 与 `getFusedBatchAuditHistory()`，
     确认死亡节点对应的那次 rollout 是 `contacts` 为空还是 `overlapNoContact` 非空；
  2. 若 `overlapNoContact` 非空 → sensor 根因（§五.4）；
  3. 若 `geometry.proximity` 最小 polyGap > 0 → 采样/摆位问题（§4.3/§6.7）；
  4. 若该弹根本不在 `placements` 里 → 威胁表/截断问题（§五.7）。
- 依据：这些字段就是 v144~v153 为定位绿死专门加的；不用再发明新的调试通道。

### 6.11 一句话总结

> **融合世界 = 9 候选共享一个 Box2D 世界、用 sensor 报接触、每帧 Step(FRAME,10,10)；
> 它没有 sensor 级 CCD，也没有帧间扫掠；JS 版本额外用"逐帧精确多边形重叠"补接触漏判，Rust 版本没有这个补判。
> `checkDeath` = 把弹摆到离散采样点上、Step(0.001) 生成接触的静态 overlap，同样没有扫掠。
> 权威模型是"Rust/静态产候选，JS 融合确认执行节点"，但当前 fd=0 口径、authority 标签、
> 世界内容清单三处存在"同一事实两种写法"；重做时先把这三处裁定成一个真源，再谈绿死归因。**
