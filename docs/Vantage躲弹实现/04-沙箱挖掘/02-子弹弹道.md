## 一、职责

**一句话**：物理沙箱要给上层（树 / 规则版 Vantage）提供一套“**给定当前局面 + 一组操作，预测未来若干帧**”的弹道预测；子弹预测在这条链路上有**三套并行的表示**，它们不是一件事：

| 表示 | 生成函数 | 数据形态 | 谁在用 | 是否含寿命截断 |
|---|---|---|---|---|
| **A. raycast 折线 `path`** | `getProjectilePaths` → `B2DUtils.calculateProjectilePath` → `calculatePath` | 起点 + 每个反弹点/终点，直线段折线；**段内无采样点** | 威胁表初版、渲染、无 track 时的评分/摆弹回退；`bulletPath`（当前无调用方） | ❌ 不按 lifetime 截断；只有 `maxLen`（默认 300m）和反弹预算 |
| **B. bullet-only Box2D 逐帧轨迹 `track`** | `simulateBulletTracks` | `[{t,x,y,alive:true}...]`，**每帧一个点**；帧长 `frameDt` 随轨迹一起返回 | commit 后挂到 `threat.track`；JS 评分 `threatBulletPos`、融合世界摆弹、树内 `trackPosAt`；也打包给 Rust `scorePaths/rescoreNodes` | ✅ 每颗弹按 `lifetime - getTimeAlive()` 在自己寿命处断供 |
| **C. 融合世界里的真实 Box2D 圆弹** | JS `simulateFusedBatch`；Rust `rolloutBatch` / `scorePaths` / `rescoreNodes` | `{x,y,vx,vy,radius,lifeLeft,active,isShrapnel}` 圆体，逐帧 `Step`/`step` | 死亡权威：JS 融合 = 权威，Rust = 候选（最终执行路线仍回 JS 确认） | ✅ 逐帧 `lifeLeft -= FRAME`；另有破片特殊规则 |

**链路（按调用顺序）**：

```text
real game projectiles (RoundModel.getProjectiles / getB2DBody)
   │
   ├─(1) getProjectilePaths(bounces=cfg.pathBounces=5, maxLen=pathMaxLenTiles*MAZE_TILE_SIZE=300m)
   │       └─ 弹种档案决定 LASER/MINE 用 0 次反弹，其余用 5
   │       └─ B2DUtils.calculateProjectilePath(realWorld, p, effBounces, maxLen, collideWithTanks=false)
   │
   ├─(2) tree commit → ensureThreatTracks / attachNewThreats
   │       └─ simulateBulletTracks(needFrames≈480, onlyIds?)
   │            └─ 白名单：BULLET/DOUBLE_BARREL/SHOTGUN/GATLING_GUN；LASER/HOMING/MINE 不做 track
   │            └─ 私有 bullet-only Box2D 世界，只放墙，按 FRAME(默认0.02s) 步进录点
   │
   ├─(3) 评分/摆弹：有 track 用 track（Math.round(q/dt) 查帧，不插值）；
   │      无 track 用 bulletPosAt(path, speed, q)（按弧长/速度精确插值，末端 null）
   │
   └─(4) 死亡判定：JS simulateFusedBatch（权威） / Rust rolloutBatch（候选）
           └─ Rust scorePaths / rescoreNodes 用 bullets + threats(track/path) 重评分 + 验证
```

**关键事实（先摆出来，后面逐条给出原文）**：

1. 折线**不是等距采样**：只在 `calculatePath` 的 RayCast 命中点/末端 push 顶点；
   “1m 采样”发生在评分模块 `computeThreats` 的遍历里（`step = MAZE_TILE_SIZE * PATH_STEP_SIZE = 10 * 0.1`）。
2. 默认折线反弹预算 `pathBounces=5`，但 `calculatePath` 的循环是 `while (remainingLength>0 && bounces<=maxBounces)`，
   每轮 `++bounces` ⇒ 默认最多 **6 次 RayCast / 6 个命中点**（历史注释称“6 次全图射线”）。
   `LASER`/`MINE` 档案给 `bounces:0` ⇒ 只 1 次 RayCast。
3. 折线**不看 lifetime**，`maxLen=300m`；而普通弹 18m/s × 10s = 180m，霰弹/加特林 2s 更短。
4. `track` 不设反弹次数上限，靠 Box2D `restitution=1.0` 自己弹，靠 `lifeLeft` 截断。
5. `path[0]` 活引用（`calculatePath` 里 `path.push(position)`，position 是 `b2body.GetPosition()` 的活引用）
   在沙箱的两个 adapter 出口已被 v17 深拷贝切断；但**根函数本身没改**，其它直调者仍会拿到活引用。

   307	        return (lt > 0) ? lt : NO_LIFETIME_SEC;

   322	            var lifeLeftFrames = Math.ceil(lifeLeftSec / FRAME);

> - 它**只统计 `isBallisticProjectile` 白名单**；LASER/HOMING/MINE 不参与这个建议帧数。

## 四、【解释】

> 本节以下所有“⇒”都是我的算术/推断，标【解释，未验证】；出现方向性结论时都附一遍常识验算。

### 4.1 折线是怎么生成的？采样密度、最大反弹数、寿命截断分别是多少？

#### 4.1.1 生成链

【解释，未验证】

1. `computeThreats`（评分）或外部调用方先要折线：
   `adapter.getProjectilePaths(cfg.pathBounces, maxLen)`（`vantage_sandbox.js:2088`）。
2. 对每颗未 `done()`、body 存在且 active 的弹：
   - `speed = body.GetLinearVelocity().Length()`（真实当前速度）；
   - `effBounces` = 档案 `bounces`（`LASER/MINE` 为 0，其它保留调用方的 5）；
   - `B2DUtils.calculateProjectilePath(realWorld, p, effBounces, maxLen, false)`
     （`vantage_sandbox.js:2114`）。
3. `calculateProjectilePath` 直接取 `b2body.GetPosition()` / `GetLinearVelocity()` 转调
   `calculatePath(b2dworld, position, direction, maxBounces, maxLength, collideWithTanks)`
   （`b714588...js:5`）。
4. `calculatePath` 的循环：
   - `path.push(position)`（**活引用**；见 §4.2）；
   - `currentDirection = direction.Copy(); currentDirection.Normalize();`
   - `remainingLength = maxLength; bounces = 0;`
   - `while (remainingLength>0 && bounces<=maxBounces)`：
     - 从 `currentPosition` 到 `nextPosition = currentPosition + currentDirection*remainingLength` 做一次 `RayCast`；
     - **忽略** `PROJECTILE`、`COLLECTIBLE`；`collideWithTanks=false` 时也忽略 `TANK`；
     - 命中 `MAZE/SHIELD`：`path.push(closestPoint.Copy())`，把入射方向按法线反射，
       `remainingLength -= max(0.01, fraction*remainingLength)`，从命中点继续；
     - 命中其它（且允许撞坦克时）：记 `hit`，`path.push(closestPoint.Copy())`，结束；
     - 什么都没命中：`path.push(nextPosition)`，结束；
     - `++bounces`。
5. 沙箱在返回前把 `rawPath` 的**每个点**深拷贝成 `{x,y}`（`vantage_sandbox.js:2120-2123`），
   再做“首段方向与真实速度点积 > 0.1”的健康校验（`2128-2134`）。

⇒ **折线只在“RayCast 命中点/末端”放顶点，段内完全没有采样点**。折线“采样密度”这个词容易混：
- 折线本身：顶点 = 碰撞点，密度由几何决定；
- 评分消费 `computeThreats`：每段按 `n = max(1, ceil(segLen/1m))` 补采样点，**1m 一个**，且 `t>1.5s` 停、首次出 10m 圈锁窗；
- 逐帧消费 `bulletPosAt`：按 `弧长/速度` 精确插值（不是先采样再查表）。

#### 4.1.2 采样密度：三个不同的“密度”

| 消费者 | 采样/查询 | 步长 | 截断 |
|---|---|---|---|
| 折线 `path` | 只在命中点/末端有顶点 | 几何决定 | `maxLen`（默认 300m）+ 反弹预算 |
| `computeThreats` | 沿段线性补点 | `MAZE_TILE_SIZE * PATH_STEP_SIZE = 10m × 0.1 = 1m` | `t > baseTimeMax=1.5s`；首次出 `hitRadius=10m` 圈 |
| `track` | 每帧一个点 | `frameDt = _frameDtSec`（默认 0.02s，可校准 0.005~0.2） | 每颗弹 `lifeLeft`；树传给 simulate 的 `durationFrames` |
| 评分取 track 帧 | `Math.round(q/dt)` 取最近帧，不插值 | 同上 | 越界/null；`alive===false`/无点 |
| 评分取折线 | `positionOnProjectilePath` 精确插值 | 连续 | `t > 总长/speed + 0.05` 返回 null |

【解释，未验证】方向性/量级验算：
- 普通弹 18 m/s，一帧 0.02s 走 0.36m；1m 采样 ⇒ 约每 2.8 帧一个采样点。
- 激光 180 m/s，一帧 0.02s 走 3.6m；若真用 1m 采样，约每 5.6ms 一个点——但激光不在 track 白名单、也不参与寿命/轨迹截断，
  实际是折线单段 + 融合世界圆体（见 §4.4）。
- 坦克最大前进 15.95 m/s < 子弹 18 m/s，所以“子弹在固定半径圈外的时段坦克追不上”这条评分前提在数量级上成立。

#### 4.1.3 最大反弹数

【解释，未验证】

- **折线**：`getProjectilePaths` 的 `effBounces`：
  - `LASER` / `MINE`（档案 `bounces:0`）⇒ 0；
  - `BULLET / DOUBLE_BARREL / SHOTGUN / GATLING_GUN / HOMING_MISSILE`（档案为 `null`）⇒ 调用方的 `cfg.pathBounces`，默认 **5**。
- `calculatePath` 的循环条件 `bounces <= maxBounces` 且每轮 `++bounces`：
  `maxBounces=5` ⇒ 最多 **6 轮 RayCast / 6 个命中点**（起点 + 6 个 hit point；若最后一轮没命中则更少）。
  这正是源码注释里“全局 pathBounces=5 → 6 次全图射线”（`vantage_sandbox.js:2692`）的由来。
- **track**：无反弹次数计数；Box2D `restitution=1.0` 自由反弹，只受寿命/duration 限制。
- **融合世界**：同样无反弹次数计数；JS `simulateFusedBatch` / Rust rollout 逐帧只做寿命和速度判据。
- **原版游戏**：`done()` 里有 `bounces.length >= timeoutBounceCount(5)`，但 `bounces` 会被 `update()` 用
  **墙钟时间窗口 35** 清理（见 §4.3.3），所以它**不是**一个“整条寿命最多 5 次”的累计上限（按代码字面）。

⇒ 【解释，未验证】AI 折线的“5 次反弹”与游戏 `done()` 里的“5”**不是同一条规则**：
- 游戏 `done()` 的 5 是“窗口内保留 5 个时间戳”（窗口单位见 §五争议 2）；
- 折线的 5 是“AI 的 RayCast 预算”。
两者只在“如果窗口真表示 5 次累计”时才可能巧合一致。

#### 4.1.4 寿命截断

【解释，未验证，附算术】

- **折线没有寿命截断**。`getProjectilePaths` / `calculatePath` 完全不读 `lifetime` / `timeAlive` / `done()` 以外的寿命。
  上限只有 `maxLen=30格×10m=300m` 和反弹预算。
  - 普通弹 18m/s×10s = **180m** < 300m ⇒ 在开阔图上折线可能比真实弹多飞 120m；
  - 霰弹/加特林 2s、速度 25~35m/s ⇒ 50~70m，远小于 300m；折线/融合世界若给满 2s 会**高估射程**；
  - 激光 180m/s×0.8s = **144m**（单段折线通常到第一堵墙就停）。
- **track**：`slot.lifeLeft = max(0, lifetimeSecOf(pr) - getTimeAlive())`（`vantage_sandbox.js:388-391`），
  逐帧 `slot.lifeLeft -= FRAME`，`<=0` 停用。每颗弹的最多采样点 =
  `min(durationFrames+1, ceil(剩余寿命 / FRAME))`。
  - 例：剩余 10s、FRAME=0.02、durationFrames=480 ⇒ 481 点（t=0..9.6s）；
  - 剩余 6s ⇒ `ceil(6/0.02)=300` 点（t=0..5.98s）；
  - 剩余 2s ⇒ 100 点（t=0..1.98s）；
  - 剩余 ≤0 ⇒ 摆位时 `slot.active=false`，**不产出 track**，调用方回退折线。
- **融合世界**：`lifeLeft = max(0, lifetimeSecOf(pr) - getTimeAlive() - qAge)`（`1529-1532`/`1573-1576`），
  逐帧 `bs.lifeLeft -= FRAME`（`1730`）。`qAge` 是“从现在到本节点起点”的前推秒数，v165 才修。
- **原版**：基类 `timeAlive += deltaTime`，`done()` 判 `timeAlive>=lifetime`；
  `Shrapnel` 覆写 `done()`（速度²≤0.01）且 `update` 不调 `_super()`，所以寿命对它不生效；
  `Shotgun` 撞墙/盾把 `timeAlive` 抬到 ≥1.3s（剩余 ≤0.7s）。

**各弹种“寿命 / 反弹 / 窗口”对照**：

| 弹种 | 原版 lifetime | 原版 done 附加条件 | 撞墙行为 | 沙箱 track | 沙箱融合世界 |
|---|---|---|---|---|---|
| BULLET(-1) | 10.0s | `stopped` 或 `bounces.length>=5`（窗口） | 基类：记录时间戳，Box2D restitution=1 反弹 | ✅ 白名单；`lifetimeSecOf=10` | ✅ 普通圆弹 + 寿命 |

| DOUBLE_BARREL(1) | 6.0s | 同基类 | 基类反弹 | ✅ | ✅ |
| SHOTGUN(2) | 2.0s | 同基类 | `_super()` + `timeAlive=max(timeAlive,1.3)` | ✅ 但**没有实现 1.3/0.7 钳制** | ✅ 但**没有实现 1.3/0.7 钳制** |

### 4.3 每颗弹的寿命、反弹次数上限、反弹时间窗怎么算？不同弹种有什么差异？

#### 4.3.1 原版基类（三条独立机制）

【代码原文】已在 §2.3 引用：
- 构造函数 `Projectile.constructor(projectileState,lifetime,timeoutWindow,timeoutBounceCount,...)`；
  各弹种由 `RoundModel.setProjectileState` 传入 `PROJECTILE_BOUNCE_TIMEOUT_WINDOW=35`、
  `PROJECTILE_BOUNCE_TIMEOUT_COUNT=5`。
- `update(deltaTime)`：
  `timeAlive += deltaTime;`
  `currentTimeout = new Date().getTime() - this.timeoutWindow;`
  从 `bounces[0]` 起找第一个 `>= currentTimeout` 的元素，`bounces.splice(0,i)`；找不到就不 splice；
  然后按 `|len²-initialSpeed²|>0.01` 归一化速度（`len===0` 置 `stopped=true`）；
  最后同步 x/y/speed。
- `hitMaze()` / `hitShield()`：只 `bounces.push(new Date().getTime())`。
- `done()`：`timeAlive>=lifetime || stopped || bounces.length>=timeoutBounceCount`。

⇒ **“反弹次数上限”按代码字面不是累计 5 次，而是“`bounces` 里保留的时间戳 ≥5 个”**。
【解释，未验证】由于清理窗口只有 35（与 ms 时间戳同单位 ⇒ 约 35ms），
要让 `bounces.length` 达到 5，必须在 **~35ms 内发生 5 次撞墙/撞盾事件**——
正常 0.02s/帧的对局里，一帧最多派发有限次碰撞，这几乎要求一帧内 5 次；这更像是**角落抖动保护**，
不是“子弹一辈子只能弹 5 次”。这一点与项目文档里“寿命 10s / 反弹 5 次”的表述不一致（见 §五争议 2）。

【解释，未验证】清理循环还有个边界：**当数组里所有时间戳都已经过期时，循环找不到
`>= currentTimeout` 的元素，不会 splice，旧时间戳会留着**；一旦下一个新时间戳进来，
下一次 update 才会一次性清掉旧的。这个边界让“窗口”不是严格的“只留 35ms 内”，
但不足以把 35ms 变成 35s。

#### 4.3.2 弹种差异（实现层）

| 弹种 | 寿命（原版） | 基类 bounce 机制 | 覆写点 | 沙箱是否复刻 |
|---|---|---|---|---|
| BULLET | 10s | 有 | 无 | track ✅；融合 ✅；折线 ❌ 不看寿命 |
| LASER | 0.8s | 有 | 无独立类 | track ❌（排除）；融合 ⚠️ 0.05 圆 + 寿命；折线 ❌ 单段、不看寿命 |
| SHOTGUN | 2s | 有 | `hitMaze/hitShield` 把 `timeAlive` 抬到 ≥1.3 | track/fused **没有实现**撞墙减命（见 §五争议 4） |
| HOMING_MISSILE | 10s | 有 | `update` 完全覆写：>2s 制导、激活时 `makeDeadlyToOwner`；其余同基类节奏 | track ❌（排除）；fused ⚠️ 直线+反弹近似（§4.5） |
| MINE 破片 | 0（=不靠寿命） | `update` 不调 `_super()` ⇒ **不用**基类 bounce 机制 | `hitMaze/hitShield` 速度清零；`done` 速度²≤0.01 | track ❌（排除）；fused ✅ 方向变化启发式；折线 `bounces=0` 单段 |
| GATLING_GUN | 2s | 有 | 无 | track ✅；融合 ✅ |

#### 4.3.3 沙箱侧的实际算法（与“窗口”无关）

- **track**：每颗弹只做 `lifeLeft -= FRAME`，没有 `bounces` 数组、没有窗口、没有次数。
- **融合世界**：同样只做 `lifeLeft -= FRAME`；破片额外做方向变化/速度²判据。
- **折线**：只做 `effBounces` 次数和 `maxLen`；没有时间窗、没有寿命。

⇒ 【解释，未验证】所以“反弹时间窗 35”这条机制**完全没有进入沙箱预测**。
如果 35 的真实语义确实是“5 次累计”的窗口（例如单位应为秒），
那么 track/fused/折线都会**高估**反弹寿命；反之如果它只是 35ms 抖动保护，则影响很小。
在单位没定案前，不能拍方向。见 §五争议 2。

### 4.4 激光（半径 0）现在怎么处理的？`needsSweep` 有没有真的实现？

### 4.5 追踪导弹现在的“弹道”是怎么近似的？

【解释，未验证，带原文】

原版 `HomingMissile.update`（`418...js:10`）：
1. `timeAlive += deltaTime`，清理 `bounces`（墙钟窗口）；
2. `if (timeAlive > HOMING_MISSILE_ACTIVATION_TIME(=2.0))`：
   - `makeDeadlyToOwner()`；
   - 起点格 → `maze.getDistancesFromPosition`；对所有坦克（**包括发射者**）按迷宫距离选**最近**；
     距离相等时优先非发射者；
   - 迷宫距离 ≤1 格：瞄准坦克真实坐标；否则瞄准最短路径的下一格中心；
   - 把目标转到导弹 body 本地坐标，按 `relativeToMissile.x/y` 的正负，
     `newSpeedX ±= ACCELERATION(40)*deltaTime`、`newSpeedY ±= ACCELERATION(40)*deltaTime`；
   - `if (len² - initialSpeed² > 0.01)` 把速度乘回初速（注意这里没有 `abs`）；
   - 同步 x/y/speed。
3. 未激活前：继承基类的反弹/速度语义，没有制导加速度。

沙箱现状：
- `isBallisticProjectile` 排除 HOMING_MISSILE ⇒ **没有 track**。
- `_projProfile[HOMING_MISSILE]` 只有 `{radiusFallback:0.25, bounces:null, wall:'bounce', steers:true}`；
  `steers` **没有任何读取点**。
- `getProjectilePaths` 对它走全局 `cfg.pathBounces=5` 的 raycast：**直线 + 最多 6 个墙面反射点**，
  速度=当前真实 body 速度向量；不考虑 2s 激活、不考虑最近坦克、不做加速度转向。
- 融合世界摆弹：无 track ⇒ 用 `th.path`；若 `q` 仍在折线总长内，
  位置取折线上的点，速度方向取“下一帧位置 - 当前位置”；
  若超出折线，则落到 `approx` 分支：用**当前真实 body 位姿/速度**按
  `advFrames=(tGlobal-nowTGlobal)/FRAME` 直线前推。⇒ 每个 rollout 内部是“折线+直线外推”的拼接，
  跨 tick 才通过刷新拿到真实速度（因此能粗略跟随，但不是制导）。
- Rust `rolloutBatch`/`scorePaths` 收到的是融合世界摆好的圆体，**Rust 侧没有制导代码**；
  它只会做普通圆弹的固定速度/寿命/反弹。
⇒ 一句话：**追踪导弹现在的“弹道”= 直线 + 墙面反弹的普通弹近似；`steers` 是标记，不是实现。**

【解释，未验证】方向性验算：
- 原版制导每帧加速度 40 m/s² × 0.02s = 0.8 m/s 分量；速度约 18 m/s，一帧转约
  `atan(0.8/18)≈2.5°`（然后归一化回初速）。沙箱的折线近似在两次刷新之间完全不会转；
  所以“近距/长视界”下，制导导弹的预测位置误差可能远大于普通弹（这正是 §五未解决项之一）。
- 同理，原版 2s 激活对“谁被打死”影响重大：激活前 `makeDeadlyToOwner` 未调用（但撞墙会调，见 §五争议 1），
  激活后才追最近坦克；沙箱的直线近似既不会换目标、也不会在 2s 前后表现出差异。

【解释，未验证】

- **死亡权威**：JS `simulateFusedBatch` 是权威；Rust `rolloutBatch/scorePaths` 的 `dead/deathFrame`

### 争议 1（最高优先）：自己的弹到底从什么时候开始能打死发射者？

**代码原文**（`46989e393ad0e356ac8a0c6c53b362f9.js:1`，去转义后）：

```javascript
case Constants.COLLISION_CATEGORIES.TANK|Constants.COLLISION_CATEGORIES.PROJECTILE:{
  if(data.projectile.isDeadlyToOwner()||data.tankA.getPlayerId()!=data.projectile.getPlayerId()){
    collisionEvent.collisionType=RoundModel._EVENTS.TANK_DEADLY_COLLISION;
    collisionEvent.data=data;
  }
  b2dcontact.SetEnabled(false);
  break;
}
```

配套事实：
- 基类构造 `this.deadlyToOwner=false;`（`418...js:4`）；
- `makeDeadlyToOwner()` 只把标志置 true（`418...js:4`）；
- `MAZE|PROJECTILE` 碰撞时无条件 `if(!isDeadlyToOwner()) makeDeadlyToOwner()`（`46989...js:1`）；
- `SHIELD|PROJECTILE` 对“非本方的盾”也会 `makeDeadlyToOwner()`（`46989...js:1`）；
- `Shrapnel.update` 第一次 update 就 `makeDeadlyToOwner()`（`418...js:6`）；
- `HomingMissile.update` 在 `timeAlive>2` 时才 `makeDeadlyToOwner()`（`418...js:10`）。

**按代码字面**：同一玩家的弹在 `deadlyToOwner===false` 时撞到发射者，**不会生成 `TANK_DEADLY_COLLISION`**
（`tankA.playerId == projectile.playerId`），因此不会 `killTank`；接触还会 `SetEnabled(false)`。
而碰过迷宫/非本方盾/破片首帧/导弹 2s 之后，`deadlyToOwner=true`，就能打死发射者。

**与项目口径冲突**：`AGENTS.md` 与权威版 §14.1 都记着主人原话
「**激活前也能打死**……**所有武器不分敌我**」，并且明确写过“导弹从发射起就能打死发射者 / 不要从
`makeDeadlyToOwner` 函数名反推”。**本次审计没有找到另一条能绕开上面 `if` 的击杀路径**
（`TANK_DEADLY_COLLISION` 是 `82e43...js:1` 里 `killTank` 的唯一弹丸入口）。

⇒ **未解决。** 需要一次实机/无头对照：让 AI 发射后立刻倒车撞自己的弹（不碰墙），
看是否 `killTank`；再让同一颗弹先碰墙一次，重做对照。**在那之前：
- 不许在沙箱里加“这是自己的弹所以不判”的逻辑（AGENTS 明禁）；
- 也不许据此断言“激活前不致命”。**

### 争议 2：`PROJECTILE_BOUNCE_TIMEOUT_WINDOW = 35` 的单位与语义

**代码事实**：
- 常量值 35，构造时原样传给 `Projectile.create(...)`（`46989...js:1`；`b714588...js:1`）；
- `update` 用 `new Date().getTime() - this.timeoutWindow` 清理 `bounces`（`418...js:4`）；
  `new Date().getTime()` 是毫秒 ⇒ **按字面就是 35ms**；
- `done()` 用 `bounces.length >= 5`（`418...js:4`）。

**两种读法**：
- 字面读法：**5 次撞墙/撞盾事件必须在 ~35ms 内发生**，否则时间戳会被清理；
  这更像“角落抖动保护”，不是“整条寿命只能弹 5 次”。
- 设计意图读法：35 若本意是“35 秒”，则 5 次是 35s 窗口内的累计上限；
  但代码里**没有任何 ×1000 的换算**。

⇒ **未解决**。两种读法对折线的 `pathBounces=5` 给出相反结论：
- 字面读法下，折线的 6 次命中是**额外加的 AI 预算**，真实弹在长走廊里可能反弹远多于 6 次；
- 意图读法下，折线的 6 次命中比真实的“5 次”还多 1 次。
> 需要主人裁示或实机对拍：在长走廊贴墙打一发，数真实反弹次数。

附带坑：`update` 的清理循环在“所有时间戳都已过期”时不会 `splice`（`418...js:4`），
所以窗口不是严格的 35ms 上限；这一段容易被误读成“旧时间戳一定被删光”。

### 争议 7：折线不看 lifetime / 反弹预算与游戏 `done()` 不是同一规则

- 折线：`maxLen=30格=300m` + `bounces=5 → 最多 6 次命中`，不读 `lifetime/timeAlive`；

- 例：普通弹 180m 最大射程 < 300m 折线；霰弹/加特林 2s 的 50~70m 也远小于 300m；
  但折线会沿墙反弹到第 6 个命中点，融合世界则按真实寿命关弹。
- ⇒ **无 track 时的评分/摆弹会看到“寿命外”的折线子弹**；`computeThreats` 的 1.5s 视界能挡住一部分，
  但树/`bulletPosAt` 在更长视界（如 8s）下仍可能查询到它。
- **未解决/需裁示**：折线是否也要按 `lifetime - timeAlive` 截断？若截，截在“弧长/速度”的哪一段？
  注意主人已说“树只管固定的子弹”，这里属于“固定弹道”的准确性问题，不是可选项。

| 弹位来源 | Rust 自己 step | Rust 自己 step + threats 评分 | `threat_bullet_pos`（track/path 查位） |

⇒ **未解决**：
- LASER 在同一棵树的“Rust 候选 vs Rust 重评分”两条路上半径不同（0.05 vs 0.0）；
- rescore 没有破片标记，只能靠 JS 给的 `path` 截断（MINE 档案 `bounces:0`）大致等价，
  但这不是 ABI 显式语义，不能保证“撞盾/撞墙当帧消失”在 rescore 路径与融合世界逐字一致；
- rescore 的寿命没扣 `qAge`（代码 TODO 自己承认），可能让远节点上的弹**多活** `tGlobal-nowTGlobal` 秒。
- 需要一次三路对拍（同一颗激光、同一颗破片、同一颗快到期普通弹），并回归。

### 争议 9：`sweepDangerFrames` / `steers` / `wall` / `needsSweep` 都是未使用字段/接口

- `sweepDangerFrames`（`vantage_rust_bridge.js:1542`）全仓无调用方；
  它是“坦克扫过区域 × 子弹轨迹”的粗筛，**不是激光扫掠**；
- 档案 `wall` / `steers` / `needsSweep` 都没有读取点（见 §2.1.5）。
- ⇒ **未解决**：要么实现，要么删除/改名，不要让后来者按名字猜语义（AGENTS 第一条教训）。

### 争议 10：`bounces` 用墙钟时间，沙箱/无头环境的 `Date` 接管情况未在本审计中验证

- 原版 `new Date().getTime()`（`418...js:4`）是墙钟；沙箱所有“是否已 `done()`”的过滤都调
  `pr.done()`（`projectileDoneOrInactive` `vantage_sandbox.js:275-276`；`getProjectiles` `2058`）。
- AGENTS 记过“无头里 GameController.update() 用 `new Date()`，虚拟时钟必须同时接管
  `performance.now/Date.now/Date 构造函数`”，但**本次只读审计没有找到无头环境的接管代码位置**，
  也**没有跑数据**。
- ⇒ **未解决**：若接管不完整，真实弹的 `done()`（尤其 `bounces.length>=5` 分支）会随真实墙钟漂移，
  树的预测再准也会被输入状态带偏。需要查无头接管点 + 一次长对局对拍 `timeAlive` 与墙钟。

### 争议 11：校准帧长与树帧长不是同一个数

- 树用 `FRAME_DT=0.02` 算 `trackFramesForTree`、`EVAL_FRAMES`、节点时间（`vantage_tree.js:790/793/1801`）；
- 沙箱 `simulateBulletTracks` 用 `_frameDtSec`（可校准 0.005~0.2）步进；
- 轨迹自带 `frameDt` 解决“查询侧”的换算，但**需求侧**（需要预测多少秒）仍按 0.02 折算：
  - 若实际 `_frameDtSec>0.02`，480 帧覆盖的秒数变多（可能白算）；
  - 若实际 `<0.02`，480 帧覆盖的秒数变少（可能不够树视界）。
- ⇒ **未解决/需裁示**：是让树用沙箱实际 dt 反算帧数，还是统一强制 `_frameDtSec=0.02`？
  主人已定“时间这个应该是代码问题，不是架构问题”（AGENTS），所以这是代码层要修的。

### 争议 12：破片“方向变化 >2.5° = 撞墙”是启发式，不是事件

- `vantage_sandbox.js:1749-1756`；Rust `rollout.rs:852-863`；两处注释都承认是 v162 启发式。
- 问题：擦角碰撞可能只改变 <2.5° 而没被识别；一帧多次碰撞/接触法线变化也可能误判。
- ⇒ **未解决**：需要与真实 `Shrapnel.hitMaze` 事件级对拍；v161 的 `diff_shrapnel_no_bounce.js` 只是
  路径次数层面的回归，不是“是否当帧消失”的逐帧对照。

### 争议 13：`bulletPath` / `simulateNode` 在当前树上已无调用方

- `bulletPath`（`vantage_sandbox.js:2519-2531`）全仓只有定义与测试页调用；
  且它**不套弹种档案**（与 `getProjectilePaths` 行为不一致）。
- `simulateNode`（`2623-2665`）全仓只有导出与 `test_vantage_sandbox.html` 调用；
  它用旧 `bulletPosAt + checkDeath`，不读 track。
- ⇒ **未解决**：保留作测试 API 可以，但必须在文档/注释里明确“不是当前树主链”，
  否则后来者会按它理解弹道预测链（本项目已多次发生“文档/接口与主链脱节”）。

### 争议 14：沙箱没有任何一处复刻 `bounces.length>=5` 这条 `done()` 分支

- 原版 `done()` 含 `bounces.length>=timeoutBounceCount`（`418...js:4`）；
- `simulateBulletTracks` / `simulateFusedBatch` / Rust `rollout.rs` / `rescore.rs`
  都只有寿命/速度/破片判据，**没有 bounce 计数**（`vantage_sandbox.js:429-448`、`1727-1776`；
  Rust `rollout.rs:835-885`）。
- ⇒ 若争议 2 的“累计 5 次”读法成立，则等于沙箱**系统性高估**子弹寿命；
  若“35ms 抖动保护”读法成立，则影响很小。**未解决，依赖争议 2。**

### 争议 15：折线健康校验的“整条丢弃 + 纯直线 fallback”会绕过寿命/反弹

- `getProjectilePaths` 在健康校验失败时把 `path=[]`（`vantage_sandbox.js:2131-2133`）；
- `computeThreats` 随后用 `getProjectiles()` 的真实弹位姿造一条“当前位置→速度方向 × min(maxLen, speed*tHorizon)”
  的直线 fallback（`vantage_scoring.js:1556-1619`），`tEnd` 粗估为 `tIn+0.1`。
- 这条 fallback **不反弹、不看 lifetime**，只是一个“不让目标从视野消失”的兜底。
- ⇒ **未解决/需评估**：它是保守方向（多报威胁、偏安全），但会让“瞬态帧”的假威胁出现在评分里；
  是否值得、会不会造成树抖动，需要实测。

### 6.3 施工顺序建议（若哪天真要修）

1. **先做证据**：6.1 的 1/2/3/4 四项实机对拍，把“代码字面 vs 主人口径”钉死；
   这一步之前**不要改任何预测语义**。
2. **统一时间口径**：先把 6.1-8（帧长）和争议 10（墙钟接管）修掉，
   因为寿命/窗口/轨迹长度全部依赖时间。
3. **补弹种档案的执行层**：把 `_projProfile` 里现在只是注释的字段
   （`wall`、`steers`、`needsSweep`、霰弹标记）变成**JS track + JS 融合 + Rust** 三处都能读的显式输入；
   或删掉字段，避免再次“看名字猜语义”。
4. **补 lifetime 到折线**：在 `getProjectilePaths` 或 `computeThreats` 出口按剩余寿命×speed 截断，
   JS/Rust 同口径；同时决定 `bulletPath` 是否删。
5. **回归**：
   - 已有：`game_core/rust/diff_shrapnel_no_bounce.js` / `diff_shrapnel_wall_stop.js`
     （只覆盖破片路径/停墙，需补“当帧消失”的逐帧对拍）；
   - 必补：laser 半径 0、shotgun 0.7s、homing 无制导 vs 有制导、bounce 计数、qAge 三路对拍；
   - 对拍导出 JSON 时要包含：`anchorOffset`、`trackFrameDt`、`lifeLeft`、每弹 `isShrapnel`、
     `srcInfo`（real/track/path/approx）、每帧子弹位置。
6. **文档回写**：把本文 §五的 15 条逐条标“已定案/已实现/已回滚”，
   并同步到权威版；**不要只改代码不改文档**（本项目已经因此绕过一次大坑）。

### 6.4 一句话总结

**子弹弹道预测现在不是“一条链”，而是“三条不同精度的链”**：
折线（快、无寿命、只到 6 次命中）、track（准、只覆盖 4 种弹、按寿命断供）、
融合/Rust 圆弹（死亡权威、但缺激光扫掠/霰弹减命/导弹制导/bounce 计数）。
**要“一次性写对”，先定案争议 1/2/3/4，再统一时间口径，最后才动三处同改；
任何从函数名/字段名直接推语义的写法都会重蹈 `makeDeadlyToOwner` 的覆辙。**
