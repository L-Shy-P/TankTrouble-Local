# 踩坑记录：时间轴单位错位 + 刷新后真死回退缺失（2026-08-23）

> 本文件只记录已经复现、可验证的问题，与“待议/猜测”分开。

## 一、已确认：新弹死亡剪枝的时间轴单位错位（高置信，已用数值复现）

### 现象
- 树节点显示绿色（`fullDeathFrame=-1`），但实际执行中坦克死亡。
- 新弹有时像没被看见。
- 一局开局一段时间内正常，越往后越不稳定。

### 根因（代码级）
`game_core/js/vantage_tree.js` 中：

1. `nodeCoarseBox` 的节点时间窗使用**绝对时间**：
   ```js
   t0 = tree.rootAbsT + node.rolloutStartT
   t1 = t0 + maxK * FRAME_DT
   ```
2. `threatCoarseBox` 的新弹时间窗使用**相对时间**：
   ```js
   t0 = threat.anchorOffset
   t1 = t0 + track.length * FRAME_DT
   ```
   新弹 `anchorOffset = nowT - rootAbsT`，通常是当前段已执行的 0~0.6 秒。
3. `boxesOverlap` 把这两个不同单位直接比较。

### 数值证据
新弹在段开始后 0.2 秒出现，track 覆盖 9.5 秒：

| rootAbsT | node 窗口 | threat 窗口 | 重叠 |
|---|---|---|---|
| 0.5 | 0.5~0.9 | 0.2~9.7 | true |
| 5 | 5.0~5.4 | 0.2~9.7 | true |
| 10 | 10.0~10.4 | 0.2~9.7 | **false** |
| 20 | 20.0~20.4 | 0.2~9.7 | **false** |

结论：`rootAbsT` 超过约 9.5 秒后，新弹死亡剪枝的空间+时间粗筛会误判“时间不重叠”，
导致 `scanNodeDeath` 根本不会执行。

### 为什么以前没这么明显（推断，中等置信）
v54 之前，新弹 emergency 会执行全树 `rerouteTreeForCurrentThreats`。
即使死亡剪枝被这个单位错位跳过，全树重评分仍然会把当前提交节点和整条金线上的
死亡帧更新掉，等于变相补偿了这个错误。
v54 为性能把全树重评分换成惰性刷新后，这个被掩盖的错误暴露出来。
此推断符合“之前躲弹很强、改成惰性后明显变弱”的现象，但仍需修复后在长局中验证。

### 修复口径（已完成，tree v58）
- 比较前把 threat 粗包围盒平移到绝对时间：
  ```js
  tb.t0 += tree.rootAbsT;
  tb.t1 += tree.rootAbsT;
  ```
  或给 `threatCoarseBox(th, rootAbsT)` 增加根时间参数。
- 数值断言必须覆盖 `rootAbsT=20` 的新弹致死节点能被剪枝命中。

## 二、已确认：真死回退只在展开时判定，刷新后缺失（已用离线复现）

### 现象
- 看不到紫色节点。
- 新弹刷新后整层 9 个候选都变成 `fullDeathFrame=1`，父节点仍不是 `exhausted`。
- AI 有时拿着已知 1 帧内会死的操作继续走，像主动撞弹。

### 根因
`applyRetreatAfterExpand` / `isTrueDeadNode` / `pickRetreatLeaf` 都还在，但：
- 真死回退只在节点**刚展开 9 个候选**时执行一次；
- `ensureLayerFresh` 后来把候选刷新成整层真死时，没有重新执行真死判定。

### 复现结果
```text
before: parent.exhausted=false  retreats=0
after ensureLayerFresh:
children fullDeathFrame = 1,1,1,1,1,1,1,1,1
parent.exhausted=false
retreats=0
true-dead-retreat events=0
```

### 修复口径（已完成，tree v58）
- 把真死回退抽成可复用判定，`applyRetreatAfterExpand` 与 `ensureLayerFresh` 之后都调用；
- 整层 active 候选 `fullDeathFrame<=1` 时：
  - 父节点标 `exhausted`（变紫）；
  - `stats.retreats++`；
  - 记录 `true-dead-retreat`；
  - 走 3 层范围回退；
  - 父节点在 commitPath 上时清空相关展开切片；
- 需要递归保护，防止回退搜索内部刷新其他层时无限互相触发。

## 三、弹簧绳：已确认的部分与待议的部分（语气分档）

### 已确认
- 距离分符号原先接反：之前把危险分**加**进净分，已改为扣分。
- 开启弹簧绳时性能明显差，当前默认关闭。
- 当前可见图虽已按迷宫缓存，但查询仍慢，实测：
  - 27 墙：约 0.07~0.09ms/次；
  - 66 墙/219 角点：约 0.13~0.14ms/次；
  - 按 5 弹、9 操作、75 帧估算，可达上百 ms/轮。

### 待议 / 猜测（不确定，不要当成已定方案）
- 可见性表现在是“邻接数组 + 线性查找”，改成直接索引表可能显著提速；
- A* 每节点仍遍历全部候选点，可能用局部邻接进一步优化；
- `clearanceCap=8` 相对角度满分 39.5 偏小，AI 逃离感弱；是否调大需要实测；
- 建图本身在 219 角点时约 315ms，只发生一次，是否可接受待确认；
- 弹簧绳整体算法是否值得继续用 JS 做，还是留给未来高性能重写，暂不决定。

## 五、v60：绿节点但实际死亡的另一个高嫌疑根因（2026-08-23）
- 已确认：attachResults 新建节点 scoreCache=null，v54~v59 的 nodeIsStale
  一律把“无缓存”判为 stale；下一次 ensureLayerFresh 会用静态 checkDeath
  重算，覆盖融合世界传感器/CCD 给出的死亡结论。融合判死、静态漏判时，

- v60：保留融合死亡权威。威胁签名未变时，fused 新生节点视为 fresh；
  只有威胁集合变化后才允许重算，并标记 authority='computed'。

## 九、vt_score_paths 本轮踩坑（2026-09-07）

1. **WASM ABI 指针对齐**：
   `VantageRustBridge.scorePaths` 内存布局比 `rolloutBatch` 多了一个
   `op_moving` 字节数组。第一次实现把 `wallCountsBase` 紧挨着
   `opMovingBase + opCount` 放置，导致 `Uint32Array` 起始地址不是 4 对齐；
   `trackAlive` 字节数组之后同样忘了 8 对齐，`Float64Array` 起始地址不是
   8 对齐。报错都是 `start offset of Uint32Array/Float64Array should be a
   multiple of 4/8`。修复：`op_moving` 后 `align4`，`trackAlive` 后
   `align8`。
2. **别在超长 bash here-doc 里一次写大文件**：
   本轮多次出现 here-doc 被截断导致 Rust/JS 文件半截；分段写入并
   `node --check` / `cargo test` 能快速定位。
3. **Rust 评分路径必须保守**：
   `vt_score_paths` 只接受 lane=0 且弹簧绳关闭；lane>0/弹簧绳开启直接
   返回失败，JS 侧同时预检并返回 null。这样“Rust 失败自动回退 JS”的
   默认安全约定不会因配置组合而被绕过。

## 十、v79：树执行段死亡边界与权威标记漏洞（2026-09-07）

### 已确认并修复的四个问题

1. **差一帧执行到死**：
   `invalidateStaleNodes` 对新弹扫描当前执行节点时，原来只处理
   `newDeath < segmentFrames`，且把 `segmentFrames` 设成 `newDeath` 而不是
   `newDeath - 1`，也不更新 `tEndSec`/`fullDeathFrame`/权威来源。
   死亡帧语义是“第 k 帧是死态”，安全执行到 k-1 帧；差一帧会让节点
   多执行一个死亡帧。v79 统一 `safeFramesForDeath` 并补齐所有字段。

2. **回退路径把 Rust 物理候选误标为 JS 权威**：
   `refreshFusedLayer` 的 JS 回退结果只有 `rustPhysics` 标记，但
   `applyLayerResults` 只认 `rustCandidate`，导致 Rust 物理候选被标成
   `fused`，永不触发最终路线 JS 确认。v79 两个标记都识别为候选。

3. **全树更新后不确认当前执行节点**：
   emergency 全树 reroute 后，被选中的 next 会 JS 确认，但正在执行的
   `commitNode` 没有确认；若 Rust 对当前节点偏乐观，节点会继续执行。
   v79 在 reroute 后同 tick 内对 `commitNode` 做 JS 融合确认。

4. **刚性重摆后旧死亡结论仍然“保鲜”**：
   `rebaseSubtreeRigid` 平移/旋转整棵保留子树的 rollout 样本，但
   `freshSig` 只看子弹 ID/时间窗，不覆盖几何关系，旧死亡结论可继续
   被当作有效。v79 在重摆时清空被重摆节点的 `freshSig` 与 `scoreCache`。

### 确认口径
- 橙色/黄色节点可以执行，但实际执行帧数必须小于死亡帧；
- 绿节点 = 75 帧未死；橙节点执行到死、绿节点死都表示上述前提被破坏，
  而不是颜色语义本身允许。

### v79 诊断
- testbench 树详情新增 `Rust评分/回退` 与 `JS确认 提前/延后/清除` 统计。
- 如果 AI 回归与最终路线确认有关，可在战斗中直接看 `JS确认清除` 是否增长：
  - “提前” = JS 比 Rust 判死更早；
  - “延后” = JS 比 Rust 判死更晚；
  - “清除” = Rust 认为会死、JS 认为不会死。

## 十一、v80：软死执行时长收紧为死亡帧一半 + 每帧多层生长（2026-09-07）

### 用户定调
- 橙色节点不能“执行到接近死亡才换路”。只要 75 帧内会死，操作时长
  不得超过死亡帧的一半，保证 AI 尽量多换路、多苟活。
- 每帧只长 1 层太保守；增加“层/帧”滑块（1~6），每层仍是完整 9 候选分叉，
  用于测量节点数量对 AI 能力的影响。

### 实现
- `safeFramesForDeath` 增加 `deathDurationRatio`（默认 0.5）：
  - fd=1：仍只执行 1 帧；
  - fd>=2：`segmentFrames = min(fd-1, floor(fd*0.5), planned)`。
- `buildCandidate`、`applyRolloutScore`、`invalidateStaleNodes` 三处统一使用。
- `growStep` 融合路径每次最多生长 `growLayersPerTick` 层（默认 1），
  达到 `maxNodes` 或无可生长叶子时停止。
- testbench 新增“层/帧”滑块与 `setGrowLayersPerTick`；树详情统计继续显示。

## 十二、GPU 基准踩坑（2026-09-07）
- WebGPU 规范：`BufferUsage::MapRead` 只能与 `CopyDst` 同用，不能同时
  是 `Storage/CopySrc`。第一版把计算存储 buffer 直接设成
  `STORAGE | COPY_SRC | MAP_READ`，CreateBuffer 报错。
- 修复：计算写进 `STORAGE | COPY_DST` buffer，再 `copyBufferToBuffer`
  到 `MAP_READ | COPY_DST` 回读 buffer。
- WGSL 浮点取余 `%` 在部分实现会触发校验失败；normAngle 改为循环加减。
- 取消暂停时不再清空 `state.expandedSet`，折叠区展开状态在暂停/恢复间保留。

## 十三、v81：节点多但能力不提升的结构性根因（2026-09-07）

### 已确认
- 深层节点不延长决策时域：每个节点仍是独立 75 帧 rollout。
- 正常提交路径只认根层 `next`，而 `next` 由 `pickBestChildByRolloutTotal`
  只比较候选自身 75 帧总分；深层 `subtreeBest` 不参与。

### v81 实验开关

  - 开启后 `refreshCandidateScores` / 全树重路由 / 新叶展开改按 `subtreeBest`
    选 next；
  - commit 正常路径优先 `pickBest(prev.children)`；
  - 路线平均分分母改用实际 `segmentFrames`；
  - 记录 `commit-deep-select` 与 `deepSelects` 统计。

## 十四、v82：真死回退“只标记、不改道”的根因修复（2026-09-07）

### 已确认
- `applyRetreatAfterExpand` 在 v68 语义下虽然找到 retreat target，但返回值
  被调用方丢弃，既没有写回祖先 `next`，也没有提前结束当前段。
- 结果：真死节点只是变紫，当前路线仍沿着旧 next 走进死枝，直到自然提交
  才兜底；这就是用户观察到“遇到局部无解直接操作到死、没有重新找路”的
  结构性原因。

### v82 修复
- retreat target 写回 `rt.ancestor.next`，记录 `retreat-reroute`；
- 当前执行节点的下一层全真死时，同 tick 把当前 `commitNode.tEndSec` 设为
  当前时间并置 `_forcedReselect`，立即重选；
- 新增 `retreatReroutes` 统计与 testbench “回退改道”显示；
- 回归脚本 `rust/diff_tree_retreat_reroute.js`。

## 十五、v83：软死叶子被误判“不可生长”（2026-09-07）

### 用户实测现象
- AI 死亡时树图只剩一层节点，树图提示“软死2帧不可生长”。
- 表现为短视、无解、继续操作到死。

### 根因
- `status='dead'` 的语义是“计划段内会死”，并不等于终局；
- 但 `isGrowableLeaf` / `expandLeaf` / `attachResults` / `startExpandSlice`
  都直接禁止展开 `status='dead'` 的叶节点；
- 对 `fd=2` 的软死叶，实际安全执行帧数为 1，本应从该末帧继续展开
  下一层 9 候选，但旧代码直接停止生长；
- 当根层全为软死叶时，`tree.leaves` 也不收录它们，`pickGrowLeaf` 只能
  依赖回退搜索，导致树停在单层、无后续路线。

### v83 修复
- 新增 `isTerminalDead(n)`：只有 `fullDeathFrame<=1` 才视为终局；
- 软死叶（fd>=2）可从安全执行末帧继续展开 9 候选；
- `tree.leaves`、金线路径、展开入口同步允许软死叶；
- testbench 提示改为“软死@X帧（可续树）”，不再误导为不可生长。
- 新增回归脚本 `rust/diff_tree_soft_dead_growth.js`。

## 十六、v84：节点“不长”的三个可见原因与修复（2026-09-07）

### 用户现象
- 感觉树经常不生长；
- 操作执行到坍缩前后才恢复生长；
- 有时大量节点非坍缩消失。

### 代码确认
1. **节点上限 500**：`growStep` 达到 `nodeCount>=maxNodes` 直接停止生长。
   6 层/帧也会被 500 卡住；完整 3 层全分叉需 1+9+81=91，4 层 820。
2. **路径到视界直接停止**：`pickGrowLeaf` 的 v48.1 逻辑在当前路线到达
   8s 视界时直接 return null，不再长兄弟叶。用户看到的就是“本操作执行
   期间一直不长，直到坍缩后重新有预算/新路径”。
3. **非坍缩节点消失**：commit 时未选中的根层兄弟会转入 reserve，
   活动树视图不画 reserve，所以看起来是“非坍缩消失”。`reserveCount`
   现在直接显示在面板上；death-shorten 也会按新威胁提前剪枝。

### v84 修复
- `setMaxNodes(100~3000)` + testbench “节点上限”滑块；
- 路径到视界后不再直接停止，改为全局 fallback 继续生长尚未到视界的
  兄弟叶子；
- 面板显示 `节点/上限`、`储备`、`生长停` 原因统计。

## 十九、v86：节点上限开关没有穿透所有生长入口（2026-09-07）

### 用户现象
- 关节点上限、关视界上限、两个都关，活动节点都停在 420~500 左右；
- 设置开/关看起来效果相反或没区别。

### 根因
- `growStep` 顶层已经尊重 `nodeCapEnabled`/`refineBeyondLimits`；
- 但 `attachResults`、`expandLeaf`、`startExpandSlice`、commit 极端兜底
  仍然无条件检查 `tree.nodeCount + 9 <= tree.cfg.maxNodes`；
- 所以即使关掉节点上限，真正加节点时仍被 500 卡死；视界关闭后继续
  生长到接近 500 也停。用户看到的 420~500 就是这个硬检查。

### v86 修复
- 新增 `canAddTreeNodes(tree,count)` 统一判断：
  - 节点上限关闭 → 允许；
  - 超限细化开启 → 允许；
  - 否则按 maxNodes 判断。
- 四个加节点入口全部改用该函数。
- 新增回归 `rust/diff_tree_growth_switch.js`：节点上限关闭可长过 100，
  开启则停在 100 附近。

## 二十、v87：为什么“超强配置”看起来像唯一最优（2026-09-07）

### 用户实测最强配置
- 层/帧=1；
- 关节点限；
- 开视界限；
- 开超限细化；
- 开无弹生长。

任一改动都明显变弱。

### 代码解释
- `超限细化` 只在 `pickGrowLeaf` 找不到普通可生长叶时触发；
- `视界限` 开启时，当前路线到 8 秒后普通叶不可生长，才进入细化分支；
- 若关掉视界限，所有叶都可正常生长，`pickGrowLeaf` 不再返回 null，
  超限细化永远不会触发 → 看起来“关掉一个正向优化反而变强”；
- 关节点限让细化可以无限继续；
- 开无弹生长让战斗前就把细化链路预铺好；
- 层/帧=1 时每 tick 一次生长尝试，更容易频繁进入细化分支。

因此不是评分或开关反了，而是“细化触发条件与视界限强耦合”。

### 诊断
- 新增 `stats.refineSplits` 与面板“细化次数”；
- 面板新增当前生效配置行；
- 实验区新增“超强预设”一键恢复。

## 二十一、v88：持续细化独立触发 + 回退深度可调（2026-09-07）

### 用户要求
- “持续细化”不能依赖“没有普通叶可长”这个条件，也不能要求视界限开启；
- 回退量对 AI 强度重要，但目前没有动态调整方法，先做成可调常量。

### 实现
- 新增实验开关 `continuousRefine`（默认关），与 `refineBeyondLimits` 分开：
  - 有普通可生长叶时，正常生长照旧，额外再拆一次最长操作叶并展开前缀；
  - 没有普通可生长叶时，持续细化自己顶上，不需要“超限细化”开关；
  - 节点上限开启且已满时，持续细化也遵守上限；只有“超限细化”开启才穿透。
- 同一长操作叶只拆一次：拆完给原叶打 `_refineSplit` 标记，避免每 tick 对着
  同一个叶重复插前缀；真死叶不再参与细化。
- 新增实验滑块 `retreatDepth`（1~8，默认 3，面板“回退层”）：
  控制真死回退从第几层祖先开始找替代路线；数值越大越先看更高层/全局最优，
  数值越小越优先本地兄弟。若本层找不到活路，仍会继续向根搜索，避免完全不回退。
- 新增回归脚本：
  - `rust/diff_tree_continuous_refine.js`：开关关/开、正常叶仍在时也细化、
    同一长叶不重复拆；
  - `rust/diff_tree_retreat_depth.js`：回退 1 层选本地替代、回退 3 层选全局最优，
    以及 1~8 夹取。

### 已知边界
- 持续细化是每 tick 追加一次“拆前缀 + 展开 9 候选”，默认关闭；开启后
  计算量和节点增速都会明显上升，建议配节点上限或视界限一起用。
- 回退层目前只改变搜索起点，不硬性限制最大回退距离；“本层找不到就继续
  向根找”是故意的保命行为。

## 二十二、v89：Rust 物理默认开 + 无弹预热上限 + 回退量双单位（2026-09-07）

### 用户要求
- Rust 物理默认开启；
- 无子弹预热不能无限生长，否则开局等几分钟再发弹会非常卡；
- 回退滑块一拉就回弹，拉不到想要的值；
- 回退量要同时有“节点数”和“帧数”两个单位，帧数范围 10~200。

### 实现
- Rust 物理默认开启：
  - `VantageSandbox` 的 `RUST_PHYSICS_ENABLED` 默认改为 true；
  - 桥未就绪、任何 Rust 路径失败仍静默回退 JS 融合世界；
  - 死亡权威仍是 JS 融合世界最终确认，默认开启不改变这条链。
- 无子弹预热上限：
  - 新增 `warmupMaxNodes`（100~3000，默认 500），面板“预热上限”；
  - 只在该 tick 没有子弹、且开启“无弹生长”时生效；
  - 即使关闭“节点限”或开启“超限细化”，预热也不能突破这个上限；
  - 子弹一出现上限立即解除，恢复原有节点规则；
  - 生长停滞原因新增 `grow-warmup-cap`。
- 回退量双单位：
  - 原 `retreatDepth`（1~8 层）替换为 `retreatNodes`（1~32，默认 3）
    和 `retreatFrames`（10~200，默认 200）；
  - 每向上回退一个节点，就把该节点要撤销的段长累加到帧预算；
    先碰到节点上限或帧预算就从那里开始找替代路线；
  - 找不到替代路线时仍继续向根搜索，保留保命行为；
  - 旧 `setRetreatDepth` 保留为 `retreatNodes` 的兼容别名。
- 滑块回弹根因：
  - 新滑块只监听了 `change`，拖动中的 `input` 没有写回 `state`；
  - 面板每帧 `syncExpControls` 会把滑块值同步回旧 `state`，表现就是
    “一拉就弹回去”；
  - 修正：预热上限、回退节点、回退帧都增加 `input` 实时写回，和原有
    层/帧、节点上限滑块同一机制。
- 新增回归脚本：`rust/diff_tree_warmup_cap.js`、重写
  `rust/diff_tree_retreat_depth.js` 覆盖节点/帧两个单位。

### 默认值取舍
- 回退节点默认 3、回退帧默认 200，尽量贴近旧版“3 层”行为；
  帧预算拉到 200 等于默认不吃帧限制，用户需要时再往下调。
- 预热上限默认 500；超强预设也重置为 500，避免开局无限预热。

## 二十八、v96：预热上限误判“无子弹”，导致树卡在 10 节点
### 现场证据
- `测试反馈/vantage_tree_diag_1789370368599.json`：
  - 场上有 10 颗子弹；
  - 但 `growStalls["grow-warmup-cap"] = 537`；
  - 树只有 10 个节点、最大深度 1、`reuseCount=752`；
  - AI 表现为反复原地复用旧候选、不继续生长，看起来变蠢。

### 根因
- `warmupCapReached` 用 `tree.threats.length` 判断“有没有子弹”。
- `tree.threats` 只是树当前锚定的威胁集合，提交/重选过程中可能暂时为空；
- 预热上限因此被错误触发，把树按在 10 节点不让生长。

### 修复
- tick 每帧从 `adapter.getProjectiles()` 记录真实子弹数到 `tree._liveProjectileCount`；
- `warmupCapReached` 优先看真实子弹数，只在确实没有子弹时才启用预热上限；
- 新建树的第一个生长 tick 也会先记录真实子弹数；
- 回归 `rust/diff_tree_warmup_cap.js` 增加“tree.threats 为空但真实有弹”场景。
- 版本：tree v96、testbench v83、ai_vantage v8、local_patch v5、sandbox v35、index 同步。

## 三十四、v102：杀戮场其实一分都没进过选路（真 bug）+ 空场无梯度
主人实测反馈两条：“空场的开关貌似没用，没见到 AI 会提前走”“杀戮场的占比貌似有点弱”。

### 34.1 真 bug：杀戮场分被 0 乘没
- v100/v101 把杀戮场分挂在“混合选路”的加成函数 `targetMixBonus(node, scale)` 上，
  而那个 `scale` 只有在 `_targetMixEnabled && _moveTarget`（**有点击目标**）时才计算。
- 没有点击目标时 `scale` 恒为 0 → `0 × 杀戮场分 = 0`。也就是说：
  **两个开关（杀戮场引导、空场安全感知）看着有、面板也联动，但一分都没进过选路。**
- 这也是“空场开关没用”的第一层原因。
- 修法：目标分和杀戮场分的缩放基准拆开（`targetScaleOf` / `killfieldScaleOf`），
  杀戮场不再要求“有点击目标”才生效。

### 34.2 第二层原因：纯格子分没有梯度
- 静态杀戮场分只跟“死路惩罚 / 出口数 / 边界”有关。开阔地图里相邻格子分几乎相同，
  于是 9 个操作的安全分**完全一样**，argmax 只能退到平局规则（无弹优先静止）。
- 更关键的是：节点分只在节点末状态查表，而同一格子的 9 个操作末状态差别很小，
  等于没有可用的方向信息 —— 就算权重调到 400% 也只是把同一批数一起放大。
- 修法：
  ① 杀戮场构建时多做一次**多源 BFS**：从“安全格”（格子分 ≥0.7 或四面都通的格）
     出发算出每格到最近安全区的步数，归一化成 0~1 的距离分；
  ② 最终分 = 格子分 × 0.65 + 距离分 × 0.35（无安全区可达时退回纯格子分）；
  ③ 选路时用**“操作终点相对当前格子的安全提升量”**打分（`objectiveBonus` 里
     `there - here`）—— 静止永远是 0 分，AI 只有真的往安全地形挪才拿得到分。
- 副作用提醒：这条让 AI 在开“空场安全感知”时会主动从墙角/死路挪向开阔区；
  这是主人确认过的期望语义（“主动往开阔安全区挪，走到安全位置就停”）。

### 34.3 权重改 0~400%，默认 100%
- `killfieldWeight` 从 0~1 改为 0~4（面板 0~400%，默认 1.0）。
- 缩放基准明确为“一帧安全分”量级 (2π)² ≈ 39.4784，且不超过候选安全分实际跨度的
  一半：100% ≈ 最多一帧安全分的取舍空间（近似平局的地形偏好），
  400% ≈ 四帧；真安全分差大时杀戮场压不过它。
- 权重 0 = 完全不引导（但仍会走平局规则里的 `objectiveScore` 判据）。

### 34.4 显红语义纠正：不是“偏离默认就红”
- 主人的原话：“你还是没懂显红的意义，不是所有默认设置都不能动！而是有些设置会造成
  巨大影响，AI 能力大降之类的，有些设置是用于探索的，仔细看。”
- 旧的 `RISK_MAP`（偏离 DEFAULT_EXP 就红）整个作废，换成 `DANGER_RULES` 判定表，
  只有“危险取值”才红，而且红在控件本体上：
  | 控件 | 危险取值 |
  | --- | --- |
  | 仅操作时长评分 | 开（AI 变短视） |
  | 全局选路 | 开（当前版本极明显变呆傻） |
  | 死亡不扣分 | 取消勾选（评估重新加死亡惩罚，AI 过度保守） |
  | Rust 简化选路 | 开 |
  | Rust 物理预测 | 关 |
  | 预测时长上限 | 关（无限叠加节点导致性能雪崩） |
  | 无子弹预热 | 关（卡顿集中爆发在子弹出现时） |
  | 混合选路 | 关（只按安全分走，不靠近目标） |
  | 固定帧数滑块 | 偏离 25~200 区间 |
- **明确不红**（探索参数，随便调）：生长层数、预热上限、节点上限、预测时长数值、
  超上限细化、细化长路径、剪枝补偿、回退节点数/帧数、目标分系数、
  以及**杀戮场全家**（杀戮场引导、空场安全感知、杀戮场权重）——主人说暂时不标红。
- 提示改成“危险原因”文案，只在“安全值 → 危险值”那一下弹一次（固定浮层，不占布局）。

## 三十五、v103：空场为什么还是不动 + “发子弹卡一秒”的真凶

主人反馈：“开了空场之后，AI 依然不会在没子弹的时候主动移动，反而性能大幅下降，
每次我发子弹都能卡住一秒；如果只开杀戮场，有概率不怎么卡，也有概率依旧卡住一秒。”

### 35.1 真凶一：每帧一次全树重算（性能）
- 现象与根因链条：
  1. `clearMoveTarget()` 无条件写“目标已变”脏标记（`_moveTargetDirty`）；
  2. `syncKillfieldAutoTarget()` 在“不需要目标”时**每帧**调用它；
  3. tick 里看到脏标记就执行一次 `rerouteTreeForCurrentThreats`（全树重算）；
  4. 有子弹时，每次全树重算都要重算整棵树的死亡与评分 —— 树越大越慢，
     表现就是“发子弹卡一秒”。
- 只开杀戮场时也中招：空场关 → 不需要自动目标 → 每帧清一次 → 每帧全树重算。
  这也解释了“有时不怎么卡、有时卡一秒”：卡不卡取决于当时树的规模和弹数。
- 实测对照（同一场景 300 tick，13x11 房间）：
  | | 全树重算次数 | 平均帧耗时 | 最慢帧 |
  | --- | --- | --- | --- |
  | 修复前 | **300**（每帧一次） | 7.10ms | 16.7ms |
  | 修复后 | **0** | 1.85ms | 10.4ms |
- 修法（三条，缺一不可）：
  1. `clearMoveTarget()`：本来就没有目标 → 直接返回，不写脏标记；
  2. `setMoveTarget()`：目标没变 → 不重复置脏；
  3. `syncKillfieldAutoTarget()`：只在“确实有目标”时才清。
- 新增两个诊断量，以后再出现类似问题可以直接看：
  - `tree.stats.targetReroutes`：因目标变化触发的全树重算次数（正常只在
    用户点击/自动目标切换时 +1；每帧都在涨就是有人每帧重申目标）；
  - `VantageTree.getMoveTargetWrites()`：目标真正被写入/清除的累计次数。

### 35.2 真凶二：一段操作走不满一格，打分永远分不出胜负（行为）
- 一串操作通常只有 3~30 帧、坦克 4m/s，一段只走 2~6m，跨不过一个 10m 的格子。
  于是“操作终点格 − 出发格”恒为 0，9 个操作全 0 分 → AI 一动不动。
  这是 v102 加的空场距离梯度依然没效果的真正原因。
- 另一个结构性偏差：树里“静止链”越深安全分越高（静止操作会被反复延伸），
  实测 静止 11251 vs 其余 2961 —— 靠选路打分永远追不上，加成再多也没用。
- 修法：空场阶段不再靠打分，改为**给出一块“最安全地皮”当导航目标**，
  复用 `ai_vantage` 里“无弹点击寻路”这条已经跑通的通道（迷宫最短路 + 直接驾驶），
  走到就停。只有“无弹 + 无用户目标 + 开了空场安全感知”时才用，因此不影响躲弹。
- 杀戮场本身也重做成三个场（保证全图处处有梯度）：
  到最安全地皮的步数 40% + 离墙距离 40% + 基础质量 20%。
  距离用迷宫 BFS 算真实可走路径，不是直线距离。
- 锚点（最安全地皮）的选法也修过一次：最初只用“出口多 + 离墙远 + 基础质量”，
  在**单格宽走廊**里这三项对所有格子完全相同 → 锚点退化到最靠边的一格，
  AI 反而会主动往死路尽头走（实测：20 格走廊锚点落在 x=1）。
  现在加入“离危险格的距离”（危险格 = 死胡同或带死路惩罚的格，BFS 扩散），
  权重最高。修好后同一走廊锚点落在 x=9（正中），AI 从 x=0 走到 x=9。
  开阔房间里没有危险格，该项自动失效，锚点仍是中心。

### 35.3 顺带修掉的语义问题
- 用户点击目标接管时，作废我们的自动目标（保持“`_moveTarget` 是用户目标”的不变量）；
- 关杀戮场 / 关空场安全感知时，立刻作废自动目标（不用等下一帧）；
- 换局 reset 时清掉锚点、自动目标与写入计数。

### 35.4 新增：卡顿归因工具（面板导出即可定位）
- `VantageTree.getPerf()`：整帧平均/最慢、最近 60 帧平均/最慢，以及分阶段耗时
  （弹签名 / computeThreats / Box2D 轨迹 / 全树重算 / 层重算 / 提交切片 / 生长）；
- 自动记录最慢的 12 帧（>30ms），每帧带：当时的节点数、子弹数、威胁数、
  当前执行操作、死亡权威、待处理弹数、各阶段拆分；
- 面板“导出诊断 JSON”里已带上 `perf` 字段。
- 下次再出现“卡一秒”，直接看 `perf.worstFrames` 就知道是哪一段。

## 三十六、v104：提前走位 + 两个滑块分工

主人反馈三点：
① 「每帧全树重算？算的是哪个？」② 「杀戮场权重语义变了是什么意思？而且现在有两个滑块
（目标分系数 / 杀戮场权重），是不是同一个功能？」③ 「AI 有子弹时并不积极移动，子弹靠近才动，
我预期杀戮场会引导它提前走向更安全的地方，其他时候静止。」

### 36.1 先把「全树重算算的是哪个」说清楚（v103 那个真凶）
`rerouteTreeForCurrentThreats` 一次做四件事：
1. 先序遍历整棵树，收集所有「有孩子的活动节点」（父层）；
2. **重算所有脏候选的分数** —— 脏 = 节点的 `freshSig` 与当前子弹集合签名不一致。
   把这些节点的「75 帧逐帧分数 + 死亡帧」全部重算（Rust 批量 512 一批）。
   这是最贵的：O(脏节点数 × 75 帧 × 子弹数)；
3. 再遍历一遍，对每个父层重新选 next；
4. 后序回传 + 重数节点。
所以重算**不是寻路导致的，也不是杀戮场打分导致的**。它本来是「子弹变了 → 旧预测作废」
的核心机制（不能没有），真正的问题是**「目标变更」这个通知被每帧发了一遍**。
实测（Node，91 节点树，无 Rust/Box2D）：单次 8~24ms，每帧一次 → 帧率必崩。

### 36.2 两个滑块不是同一个功能
| 滑块 | 生效时机 | 作用 |
| --- | --- | --- |
| 目标分系数 | **有用户点击目标**时 | 多积极往用户点的格子靠 |
| 杀戮场权重 | **没有用户目标**时 | 地形偏好能压过多大的安全分差 |
两者互斥（有目标走目标分支，没目标走地形分支），但都加在同一个加成位置、量纲相近，
所以看起来像同一个东西。

### 36.3 v104 的分工（按主人要求）
- **杀戮场权重：只管有子弹时的行为**，含义改成「提前量」：
  `提前量 = min(4 秒, 权重 × 2.5 秒)`。
  权重 100%（默认）→ 2.5 秒；400% → 4 秒；0% → 不提前占位。
  它的意义是：「最近那颗会打到我的子弹还在 N 秒之外」时，让杀戮场先接管走位去占位；
  一旦进了 N 秒，立刻把驾驶权交回给树躲弹。
- **懒惰倾向（新增滑块）：只管没有子弹时的空场走位**。
  它是「当前格要比现在安全多少才值得挪窝」的门槛：0% = 只要不是最安全地皮就走，
  50% = 中等安全就不折腾，100% = 只有贴墙/死路才挪。
- ai_vantage v9：直接驾驶通道的放行条件从「只有无子弹」改为
  「无子弹 **或** 杀戮场判断子弹还在提前量之外」；用户点击的目标在有子弹时
  仍然只做平局裁决（不接管驾驶），保持原语义。

### 36.4 为什么「提前走位」以前做不到（两个原因）
1. **量级方向反了**：旧版按「候选安全分跨度的一半」缩放地形偏好。
   子弹越远 → 各操作安全分越接近 → 跨度越小 → 地形偏好被压得越小
   → AI 只有等子弹逼近（跨度变大）才肯动。
   改成固定用「一帧安全分」(2π)² ≈ 39.4784 做单位。
2. **一步之内分数不变**：一段操作只走 2~6 米，跨不过 10 米的格子，只查格子表
   的话一步之内分数完全不变。改成按**连续位置**双线性插值采样
   （`killfieldScoreAtPoint`），哪怕只挪 2 米，朝安全区的一步也会得分。
3. 附带发现：贴墙站立时，**转向类操作的安全分比静止低 132~300 分**
   （车体转向后被墙多挡一点；实测 2961 分制下 ±300）。所以光靠打分也掰不过，
   必须给它「直接接管驾驶」的通道 —— 这就是改成导航目标的原因。

### 36.5 提前量判据：两条一起用
- ① 威胁表的 `tIn`（首入圈时刻）：精确，但**只有子弹进了评分视界（约 3 秒）才算得出来**，
  视界外的子弹在表里是「无威胁」；
- ② 子弹当前位置/速度的几何估计（`geometricThreatEtaSec`）：粗但早，视界外也能看出
  「它在朝我飞」，危险距离取 30 米（3 格）。
- 取两者更保守的那个。实测踩过：只看 ① 时导航会一直开着，直到子弹进圈（滞后）——
  t409 才关；补上 ② 之后在「还剩 2.5 秒」处准时关闭（t263）。

### 36.6 四种场景实测（Node 诊断脚本 dbg_tree_tick.js）
| 场景 | 结果 |
| --- | --- |
| 无弹 + 空场关 | 静止（(1,5) → (1,5)） |
| 无弹 + 空场开 | 走去锚点（(1,5) → (4,5)，锚点 (5,5)） |
| 无关弹（横穿不会打到）+ 空场关 | 提前占位（(1,5) → (4,5)） |

## 三十七、v105：安全分与杀戮场分「连续共存」（主人定稿的语义）

主人的原话：「不应该用『接管』描述，而是连续的过程。安全分和杀戮场时刻共存，
子弹远的时候，安全分全一样、都很高，杀戮场引路；子弹近的时候，安全分都不高，
杀戮场小幅引导躲弹思路。这有个注意的点，两类分数的关系：子弹远，安全优先位置决策，
考虑大局；子弹近，安全分不高，杀戮场分更不能高，但也不能过低。」

### 37.1 「全树重算」的来源（主人问过，用提交历史回答）
| 部分 | 来自 | 评价 |
| --- | --- | --- |
| 全树重算（子弹变了就重算） | 老版本 v52/v68 | 必需，不能删 |
| 「目标变了也重算」 | 提交 `65ed7e6` = v98「点击后全树刷新重选」 | 设计合理（点击后确实该重选） |
| 「每帧触发一次」 | **v103 加空场自动目标时引入的 bug** | 错误，v103 已修 |

结论：不是混合选路（v94/v95）引入的；是 v98 那个新机制被 v103 每帧调用放大了。

### 37.2 为什么不能「交出驾驶权」
v104 曾让空场逻辑在「子弹还在提前量之外」时接管整帧驾驶（走迷宫最短路）。
主人指出风险：接管期间树完全不参与，判断失误就会完全不躲弹。
v105 改成两类分数在**同一次选路里**共存，任何一帧都还在躲弹。

### 37.3 定稿的算法
```
方向增益 = cos(本操作位移, 朝最安全地皮的方向) × min(1, 位移/6米)     // −1~1
安全性因子 = 0.15 + 0.85 × min(安全水平, 时间因子)
    安全水平 = 候选里最高安全分 ÷ 无威胁满分（评估帧数 × 39.4784）
    时间因子 = (最近那颗会打到我的弹还有几秒 ÷ 4秒)³
地形加成 = (无威胁满分 ÷ 4) × 杀戮场权重 × 安全性因子 × 方向增益
```
两个关键取值：
- **除以 4**：子弹远时地形加成 ≈ 740×方向增益，足以压过「转向被墙多挡」这类
  几百分的安全分差（实测 132~300）；子弹贴脸时只剩约 111 分，压不过真正的安全分差。
- **下限 0.15**：主人要求的「不能过低」——躲弹时仍保留一点方向偏好。

实测衰减（debugObjective 的安全性因子）：10 秒→1.000，4 秒→1.000，2 秒→0.256，
1 秒→0.163，0.3 秒→0.150（下限）。

### 37.4 三个踩到的坑
1. **方向增益恒为 0**：一开始用节点自身位姿算位移，而计划段常常只有 3 帧
   （坦克只挪 0.2 米）→ 增益≈0.0017，等于没有。改用 75 帧 rollout 末端。
2. **几何威胁判据过保守**：危险半径取 30 米，导致 25 米外横着飞、根本打不到的弹
   也被当成威胁，安全性因子被压到下限 → 「子弹远时该主导」变成「几乎不引导」。
   改成：先判「是否在接近」（不接近就跳过），危险半径缩到 12 米。
3. **同名函数覆盖**：v104 的 `terrainNavigationAllowed` 与 v105 的新版同名，
   JS 函数声明提升导致后面的旧版覆盖新版。删掉旧版。

### 37.5 两个滑块的分工（面板上各自紧挨着自己的开关）
- **杀戮场引导 + 强度**：只管**有子弹**时的行为。强度 = 地形能压过多大的安全分差
  （经安全性因子自动缩放）。
- **空场安全感知 + 懒惰倾向**：只管**没有子弹**时的空场走位（走导航目标通道）。
  懒惰倾向 = 「当前格要比现在安全多少才值得挪窝」的门槛（0% 最积极，100% 只在
  贴墙/死路才挪）。
- 面板顺序已调整成「开关 → 它控制的滑块」，关闭时滑块变灰。

### 37.6 诊断脚本的已知限制（别被误导）
`rust/dbg_tree_tick.js` 里「运行中新增子弹 → 树把该弹纳入威胁」这条链路**没有跑通**
（maxTreeThreats 恒为 0），原因在脚本自身的时序/stub，不是产品问题——
真实游戏导出的诊断 JSON 里 threats=10、threatIds 非空，链路是好的。
所以：空场行为用该脚本验证；有子弹时的分数配比用 `debugObjective` 的数值验证；
「子弹逼近时是否真的躲」必须到真实游戏里看。

### 38.1 录制器（主人要的工具）
- 面板「调试」栏：`● 记录`（点一次开始、再点一次停止）+ `导出录制`（下载 JSON），
  旁边显示「记录中 N 帧 / 未记录（环形缓冲 N 帧，死亡自动抓取 N 次）」。
- **逐帧记录**（每帧一条，最多 60 秒）：
  - 真实世界：坦克位姿、所有子弹的位置与速度、时间；
  - 树的决策：当前执行的操作、计划帧数/实际段长、段末时间；
  - **树的预测**：预测的段末位姿与时刻、预测的死亡帧、死亡权威来源、状态；
  - **段末对齐误差**：上一段「预测段末位姿」与「真实段末位姿」的位移/转角偏差
    （主人怀疑的「执行误差」直接可量）；
  - 树规模、威胁数、威胁签名、存活弹数、回退次数。
- **段末快照**（每次换执行节点记一条）：9 个候选各自的分数、死亡帧、状态、
  以及地形项拆分（方向增益、地形加成、安全性因子、当前格/锚点）。
  → 这样「预测到死亡为什么还选它」「有没有回退」「回退后是不是又选了会死的路」
    都能直接看出来。
- **死亡自动抓取**：不用一直开着录。内部有滚动环形缓冲，AI 一死就自动把
  死亡前 6 秒 + 死后 1.5 秒留档并停止。
- 导出格式：`{ meta, deaths, segSnaps, records }`，`meta` 里带全部开关与参数快照、
  最后一次死亡信息、最后一次树重置快照。

### 38.2 动作锁定（治「尝试一个操作后又退回去」）

  默认 5%（≈148 分，按无威胁满分算），面板可选 0~50%。
- **关键限制：只对方向相反的操作生效**（前进↔后退、左转↔右转，用两者 rollout
  位移向量的夹角 > 120° 判断）。第一版不分方向地对所有切换加滞回，结果 AI
  会一路直行撞到墙才停（实测 end tile 从 (4,4) 退化成 (1,4)）——转向去安全区

### 38.3 卡墙黑名单（治「贴墙不动被打死」）

  用「真实位移 < 1 米」判会把它误伤成卡墙 —— 实测后果是 AI 想转向去安全区却一直

  原来判不出来），惩罚 4 → 6。

## 三十九、v107：录制数据逐帧分析，抓到三个真 bug

主人录了 4 段关键场景（`测试反馈/vantage_record_*.json`）并说「AI 刚开始朝正确方向走，
后来突然朝危险方向移动」「应该没有明显误差，因为确实看到了极限擦边的操作」。
把每帧的「真实世界 × 树的决策 × 候选快照」摆在一起后，三个 bug 一目了然。

### 39.1 bug ①：安全性因子拿「含后代的分数」衡量「当前有多危险」
`terrainSafetyFactor` 原本取 `max(candidate.subtreeBest)` 当“安全水平”。
`subtreeBest` 含后代，于是一个**自身已经快死**的候选会被子树里的高分节点救活。

实测（`vantage_record_1789482367722.json`）：
```
t=10.15 选中「后右」  safety=3364.1  total=169.2  fd=7
t=10.27 选中「左」    safety=890.7   total=465.2  fd=25
```
`safety` 是含后代的 3364，而它**本段只有 169 分**（子弹贴脸、7 帧后就死）。
安全水平因此被判成 1.0 → 安全性因子 1.0 → 杀戮场加成 740 分全量生效 →
压过一切安全分差 → AI 朝“地形更好但会死”的方向走。

修：改用**本段自己的 75 帧分**（`fullRolloutTotalOf`）衡量安全水平。

### 39.2 bug ②：地形加成的量级不随安全水平缩放
固定上限 740 分 × 因子下限 0.15 = **111 分**。而子弹贴脸时各候选的安全分只剩
几分到几十分（实测 6.7 / 5.7 / 2.8）—— 地形加成比安全分本身大十几倍，
AI 在必死局面里还在朝“地形更好的方向”走，看起来就是“突然往危险方向移动”。

修：`地形量级 = min(满分/4, 候选里最高本段分 × 35%)`
| 当前最高本段分 | 地形加成上限 |
| --- | --- |
| 2960（无威胁） | 740 |
| 171（危险） | 60 |
| 6.7（贴脸） | 2.3 |

既保证“不能过高”（永远只是当前安全水平的零头），也保证“不能过低”（不归零）。

### 39.3 bug ③：几何威胁判据过灵敏，把杀戮场引导永久压死
`geometricThreatEtaSec` 只要「附近有弹在接近」（12 米内、接近速度 > 0）就返回 0 秒
→ 时间因子 0 → 安全性因子恒为下限 0.150。

实测（`vantage_record_1789482072281.json`）：从 t=89.5 起，**候选安全分满分 2960.9
（完全没威胁）时安全因子依然是 0.150**，一路到 t=99.2 都是 0.150
→ 杀戮场引导全程只有 0.15 的分量 → “提前走位”整个失效。

修：危险半径 12→5 米；要求「确实朝我飞」（接近速度占全速 > 50%，即夹角 < 60°）；
并且**安全分已接近满分（≥85%）时不再被几何估计压制**——几何估计只是
“安全分还没降下来时的提前感知”，不该盖过评分模块的权威判定。

### 39.4 顺带修掉的数据采集缺陷
`segEndErr`（预测段末位姿 vs 真实段末位姿的偏差）样本数一直是 0：它记在旧
commitNode 上，而 commit 之后 commitNode 就换新节点了。改成同时挂到 `tree._lastSegEndErr`。

### 39.5 本轮还没解决的

- `rust-candidate` 的死亡结论**在选路里被当真使用**（跳过这些候选），但它们
  从未被 JS 融合世界确认过（只有“被选中为执行路线”的那个才会确认）。
  如果 Rust 高估死亡，AI 的可选路线会被无谓砍掉。这条需要专门验证：
  在录制数据里对比「Rust 判死的候选」与「JS 融合确认的结果」。

## 四十、v108：贴墙宕机 + 跨局状态泄漏 + 懒惰阈值

主人这一轮反馈两条，并说「现在 AI 能力确实再次变强，几乎绝大多数时候都能做到提前
调整身位，十分活跃」——v107 的三个修复有效。剩下两个问题：

### 40.1 贴墙宕机（坦克正面垂直贴墙 = 必死）
现象：「按住前进键（能看到特效，所以不是静止），但实际坦克纹丝不动，身位规划完全
失效，随便一发子弹就能单杀。它甚至会退后一小步再前进顶住墙。」

录制数据（`vantage_record_1789487050730.json`）逐帧还原：
```
t     坦克位置        操作   预测死亡   实际单帧位移
7.89  (36.2, 3.1)   前左   -1       0.62   ← 顶到墙
7.91  (36.2, 3.1)   前左   -1       0.01   ← 有油门、没位移
...（连续 34 帧，位移 0.00~0.05）...
8.25  (37.0, 2.6)   前左   39       0.03   ← 树已经预测 39 帧后会死
8.49  (36.6, 2.4)   后     -1       0.27   ← 终于换操作回退
```
根因：**卡墙判定与重选都在段末**，而段长最长 30 帧（0.5 秒）。这半秒里树的
commitNode 不变，AI 无法改操作，只能顶着墙——表现就是「按住前进、有特效、不动」。
它确实会回退（v106 的卡墙黑名单+回退机制在工作），但要等段末，白送半秒。

修：新增**段内卡墙检测**（`checkStuckInSegment`，在每帧 tick 里跑）：
- 条件：当前执行的操作有油门（前进/后退），且连续 6 帧（0.1 秒）单帧位移 < 3cm
  （正常前进 ≈32cm/帧）；
- 动作：把该操作拉黑 45 帧 + 立刻把 `commitNode.tEndSec` 设为当前时刻
  （`_forcedReselect`）→ 当帧就重选。
- 反应时间 0.5 秒 → 0.1 秒；而且重选时该操作已被拉黑，不会又选回同一个。

### 40.2 跨局状态泄漏（同样配置每几局 AI 就变一个样）
现象：「25% 杀戮场强度、95% 懒惰，刚开始几局 AI 直接不动了；之后开局移动，
移动到某位置后开始后退+旋转原地转好几圈；再过了几局躲弹能力回归但极其活跃。
这期间我完全没动配置。」

根因：`reset()`（换局/重生调用）漏清了 v106 新加的状态：
- `_stuckOps`（卡墙黑名单）——上一局被拉黑的操作带进下一局，新局开局就有一批
  操作被禁选 → 「开局不动」「原地转圈」；
- `_stuckInSegFrames` / `_stuckInSegPos`（v108 新加的段内计数）同样要清。
现在 reset 里一并清干净。

### 40.3 懒惰阈值上限太低
现象：「惰性都 95% 了，开局还能跑大半个图。」

根因：阈值原本是 `懒惰 × 0.5`，即最高门槛只有 0.5 分。而安全分是 0~1 的无量纲量，
开阔地图里「贴墙角落 → 中心锚点」的安全分差本来就能超过 0.5 → 95% 懒惰照样走。

修：阈值改为 `懒惰 × 1.0`（0~1 全域）。实测（同一房间场景）：
| 懒惰 | 结果 |
| --- | --- |
| 0% | 走到锚点 (4,5) |

## 四十一、v110：遮蔽分机制被主人纠正 + 「安全裕度/动作成本」两项

### 41.1 先纠正我自己的错误结论
我说过「安全分只跟朝向有关（遮挡角）」——**完全错了**。主人指出：
「角度遮蔽的作用范围非常近，它基本只和子弹与坦克的相对位置有关，和朝向反而无关。」
读代码核实（`exactOcclusion` / `exactGeom`）：

| 量 | 值 | 说明 |
| --- | --- | --- |
| 角带半角 | `asin(1.75/D)`、`asin(2.625/D)` | 半宽/半高是**固定常量**，与朝向无关 |
| 角带中心 | `atan2(子弹-几何中心)` | 只由子弹相对位置决定 |
| 朝向的全部影响 | **0.375 m** | 仅几何中心沿朝向前移 `GEO_OFFSET` |
| 必死圈 R_ABS | **1.75 m** | 进圈 → free 为空、帧分 0 |
| 遮蔽成立条件 | `asin(1.75/D)+asin(2.625/D) ≥ 90°` | 只在 **D < 约 3.05 m** 时成立 |
| 超过 3.05 m | 不产生任何遮蔽 | **帧分恒为满分** |

所以分数 ≈ f(每颗子弹到坦克几何中心的距离)，朝向几乎不影响；
且作用范围确实极近（3 米外一律满分）——主人两条判断都对。

### 41.2 「大力出奇迹」的真正来源
1.75~3.05 米之间，帧分随距离**连续递减**（D=3.0m 时仍有约 71° 遮蔽弧，
D=2.0m 时约 122°）。于是：
- 「擦边躲开」（D≈3.0）→ 仍被扣分
- 「彻底走开」（D>3.05）→ 满分

**评分在奖励「越远越好」，而不是奖励「刚好躲开」**。而垂直于弹道移动能最快把
距离拉到 3 米外 → AI 就选它 → 表现为「大力转向」。它追求「最早脱离」没错，
错在这个「最早」被实现成「最远」。

### 41.3 主人对「操作成本」的关键洞察（本轮设计的前提）
主人原话：「这个操作成本本来是为了让AI尽可能走最优操作的，但实际上，在完全
安全后，每过一帧都叠加很多安全分，成本分根本拦不住，也就是说AI依旧会倾向于
操作很久。安全分和操作分的变化趋势是反的：越危险，安全分越低，越不阻拦过多
操作；越安全，越阻拦过多冗余操作。」

**完全正确**，而且是设计致命点：成本是固定量、安全分是累积量。
- 安全时：安全分每帧 +39.5，成本每帧 −2 → 成本被淹没 → 多余动作拦不住；
- 危险时：安全分接近 0，成本反而占主导 → 不敢动，与期望相反。

解法：**成本只在「这一帧已经完全安全」时计**（`safeFrame` = 该帧无任何遮蔽弧）。
于是危险帧不参与成本、全力躲弹；安全帧大家都是满分、成本成为唯一区分项。

### 41.4 本轮新增（三项默认全关，保持原行为）
面板「评分」栏：

| 控件 | 含义 |
| --- | --- |
| **角度遮蔽评分**（开关，默认开） | 关掉后帧分恒为满分。**只做对比实验**——有子弹时 AI 会失去躲弹梯度（杀戮场是静态地形，不知道子弹在哪）。 |
| **安全裕度**（0~4 米，默认关） | 超过它一律满分：「刚好躲开」与「躲很远」同分，大幅动作失去额外收益。建议试 2.0~2.5。 |
| **动作成本**（0~20 分/帧，默认关） | 转向/移动各算 1 分强度、同时踩两者算 2；只在安全帧计。建议试 2~4。 |

预期组合效果（安全裕度 + 动作成本）：AI 会选「略微偏移 + 移动，刚好躲开」而不是
「转到垂直再跑远」。

## 四十二、v111：安全过滤阈值 k（主人提的机制，取代 v110 的「安全裕度」）

主人原话：「我觉得可以再加个功能，过滤掉危险程度过低的情形，也就是把很接近安全的
情况视为安全。设单帧角度遮蔽分满分为a，实际本帧评分为b，则加了过滤后用的评分
b' = min(a*k, b)，其中k表示安全过滤阈值，范围0.1到1。这种简单的机制或许更利于分析。」

### 42.1 为什么它更好
- **直接作用在评分上**（一维可调），不改变遮蔽几何 → 好分析、好复现；
- **只截顶、不动危险区间的梯度**：b < a·k 的帧分原样保留，所以贴近子弹时该有的
  精细躲法不受影响；只有「已经足够安全」的帧被压成同一个值，
  「刚好够安全」与「非常安全」等价 → 大幅动作失去额外收益。
- v110 的「安全裕度（米）」已被它取代并删除（两套并存只会混淆）。

### 42.2 实测验证（子弹正对坦克，a=(2π)²=39.48）

| --- | --- | --- | --- | --- | --- |

| 2.0m | 2.29 | 2.29 | 2.29 | 2.29 | 2.29 |
| 2.5m | 5.20 | 5.20 | 5.20 | 5.20 | 5.20 |
| 3.0m | 9.43 | 9.43 | 9.43 | 9.43 | 9.43 |

## 四十三、v112：3.05m 断崖查清是**实现缺陷** + 杀戮场等比调整

### 43.1 断崖的真相：拷贝区 R_SEMI 取值与它自己的判据不自洽
主人问：「为什么在 3.05m 会有那么大的断崖？是错误还是函数确实在此处变化很快？」

查清是**实现缺陷**。机理：
1. `occlusionIntervals` 先用 `R_SEMI` 粗筛，只有圈内子弹才参与遮蔽计算；
2. 圈内子弹再过一个判据 `aW + aH ≥ 90°`（`aW=asin(EFF_HALF_W/D)`、
   `aH=asin(EFF_HALF_H/D)`），不满足就跳过；
3. 真正「不产生遮蔽」的边界应该由第 2 条判据自己决定：
   `asin(EFF_HALF_W/D) + asin(EFF_HALF_H/D) = 90°`
   → `sin(asin(EFF_HALF_W/D)) = sin(acos(EFF_HALF_H/D))`
   → `EFF_HALF_W/D = sqrt(1 − EFF_HALF_H²/D²)`
   → **`D = hypot(EFF_HALF_W, EFF_HALF_H) = hypot(1.75, 2.625) = 3.155m`**
4. 但拷贝区给的 `R_SEMI = hypot(rectHalfH, halfW) + bulletR = 3.059m` —— 用的是
   **未膨胀**的半宽/半高。3.059 < 3.155，于是 3.06~3.16m 之间本该正常计分的
   子弹被第 1 层粗筛提前当「无威胁」→ 直接返回满分。

实测（子弹在坦克正前方，坦克在原点）：
| 子弹 x | 到几何中心 D | aW+aH | 判定 | 帧分 |
| --- | --- | --- | --- | --- |
| 3.00 | 3.0233 | 95.6° | 算遮蔽 | **9.43** |
| 3.02 | 3.0432 | 94.7° | 算遮蔽 | **9.60** |
| 3.04 | 3.0630 | 93.8° | 被 R_SEMI 筛掉 | **39.48** ← 断崖 |
| 3.10 | 3.1226 | 91.3° | 被 R_SEMI 筛掉 | 39.48 |
| 3.20 | 3.2219 | 87.5° | （本就不该算） | 39.48 |

**2 厘米的差别 → 帧分 9.6 变 39.5（4 倍）。**

尝试过在**拷贝区之外**把粗筛半径改成 3.155：**实测无效**——`exactOcclusion`
内部还会用拷贝区自己的 `R_SEMI` 再筛一次，直接把结果置成满分。要真正修掉，
必须在拷贝区外复制一份矩形投影几何（约 80 行）；已记录，等主人决定是否值得。

当前实际影响（不大但要知道）：
- 威胁感知范围比理论小 **0.096 米**，且是**突变**的；
- **不会导致漏判死亡**——死亡判定走融合世界的 `checkDeath`，不走遮蔽分；
- 遮蔽分只是「偏好梯度」，所以断崖影响的是「AI 何时开始紧张、往哪偏」，
  不影响「会不会被判死」。

### 43.2 杀戮场等比调整（主人提的）
主人原话：「那个安全过滤会让安全分的最大值变小，导致潜移默化中杀戮场的权重也提升。
或许需要加一个等比例调整的开关，开启后，杀戮场的权重会等比缩减，和安全分的最大值的比例
保持不变。」

完全正确：`k` 把单帧满分从 `a` 压到 `a·k`，75 帧累计满分也等比缩小；但地形加成的
**固定上限**（`EVAL_FRAMES × 39.4784 / 4 ≈ 740`）原本不跟着缩 → 「地形 : 安全」
的比例被悄悄抬高，等于变相加强杀戮场。

新增开关「**杀戮场等比调整**」（默认开）：把固定上限按 `k` 等比缩减，
保持两者的比例关系不变。关掉即保留旧的比例。

## 四十五、性能问题定位（主人 2026-09-07 报 4 条）

主人原话要点：① 两个新滑块很难拖、严重回弹，暂停时不回弹；② 开任意一个新滑块
性能都显著下降；③「大力」操作依然存在；④ 性能很不稳定，半数情况发子弹帧率几乎不变，
少数情况（尤其子弹会打死 AI 正在执行的操作时）卡顿极明显，且**关掉杀戮场和混合寻路
几乎不省时间**，怀疑早期优化被弄没了。

### 45.1 实测：JS 评分路径比 Rust 全包慢 9 倍（问题②④的量级来源）
探针 `_probe_perf_paths.js`（真 Box2D + 真 WASM，同一局面，各跑 12 次取均值）：

| 场景 | JS 评分路径（9 操作×75 帧） | Rust 全包（vt_score_paths） | 倍数 |
| --- | --- | --- | --- |
| 远弹 | **10.83ms** | **1.19ms** | 9.1× |
| 横穿弹 | 9.84ms | 1.14ms | 8.6× |
| 迎面致死弹 | 2.39ms | 0.99ms | 2.4× |
| 激光（半径0，2帧就死） | 1.51ms | 1.10ms | 1.4× |

（近弹/激光两行帧数少是因为坦克很快就死了，帧数被截短，不代表便宜。）
注意这是**Node 里、同一台机器**的数字；浏览器里 JS 侧还要和渲染抢时间，只会更明显。

### 45.2 四个真凶（按影响排序）

**真凶①：提交心跳（commit）用的是 JS 评分，不是 Rust。**
`stepCommitSlice` 里那句是 `VantageScoring.scorePaths(...)` —— 一次把 9 个操作 ×75 帧
**用 JS** 算完（v42 为了位姿正确性故意「9 操作一次算完」）。它在这些时刻整体触发：
开局建树、**新弹把当前执行操作打死（commitHit）**、对齐大幅失败（alignHard）、
威胁签名变脏（threatDirty）。一次 ≈10ms（1 颗弹），正好对应主人说的
「子弹会导致 AI 正在执行的操作死亡时，卡顿极其明显」；而子弹没打死当前操作时，
走的是 Rust 批量重算（≈1ms），所以「半数情况几乎不变」。
**这条路从第一次提交起就是 JS，从来没接过 Rust** —— 不是被弄没，是一直没优化到，
树越大、弹越多越容易被看见。

**真凶②：开新滑块会关掉 Rust 重算通道，退回「逐层 JS」。**
`needsJsScoring()`（遮蔽关 / 动作成本>0 / k<1 任一成立）→ `tryRustRescoreBatch`
直接 `return null` → `rerouteTreeForCurrentThreats` 退化成**对每一层单独**
`refreshFusedLayer` → 每层一次 JS `scorePaths`（9 操作×75 帧 ≈10ms）。
10 层就 100ms+，这就是「卡一秒」的量级。另外段末的 `refreshCandidateScores`
也走同一条路 → 开着 k 时**每个段末**都多花一次 ~10ms。
**所以主人测 k 的那两次，性能对比其实是在比「Rust 批量 vs 逐层 JS」，不是 k 本身。**

**真凶③：生长路径（Rust）根本不认 k / 动作成本 / 遮蔽开关。**
`simulateTankBatchScored` 只把 `deathPenalty / stuckPenalty / stuckDistEps /
stuckRotEps / lanePenaltyRatio / springRopeEnabled` 传给 Rust（`vantage_sandbox.js`），
Rust 侧 grep 不到 `safeFilterK / actionCostPerFrame / occlusionEnabled`。
后果有两层：
- **k 现在只对「提交切片 + JS 重算 + JS 缓存路径」生效**，而生长探测（九操作 rollout，
  产出候选的 rolloutTotal/subtreeBest，选路主要看它）用的是**未截顶的原始分**。
  → 主人③「大力操作不治本」的根因之一：AI 实际比较的仍是原始分，越过 3.05m 断崖
  一次仍白拿 +30/帧的大奖。
- 因此 **k=0.4 的测试会半生效、结论不可信**（同一棵树里一部分节点被截顶、一部分没被截）。
  要真正测 k，必须先把 k 接进 Rust（和 JS 同样的 `b′=min(a·k,b)`，逐帧同口径）。

  **运行时实证**（`_probe_perf_paths.js`，同一局面，cfg 里塞 `safeFilterK:0.4,
  actionCostPerFrame:3`）：
  - Rust 生长路径：逐帧分数**完全相同**、总分**完全相同** → 完全忽略这两个参数；
  - JS 评分路径：总分从 `2960.9` 掉到 `1184.4`（截顶生效）。
  同一棵树里两条路给出**差 2.5 倍**的分数，这就是「k 半生效」的直接证据。

**真凶④：每帧的「诊断账」越攒越多。**
- `runDiagnostics()` 每帧都在跑：给**每颗子弹** push 一个对象进实际轨迹、再 push 一个
  进预测轨迹，各自最多保留 600 个（`d.bulletTracks`）；
- `_tree.diag.projectileSightLog` 每帧 push 一个对象 + 两个数组（保留 120 条）；
- 录制器的环形缓冲每帧再存一份（v106）。
这些不是「卡一秒」的元凶，但持续制造垃圾、抬 GC 压力，属于「老版本更稳」的一部分
（都是 v65~v67、v106 陆续加的，默认没关）。

### 45.3 核实「优化是不是被弄没了」
逐条查过，**都还在**：Rust 九操作评分（vt_score_paths）、Rust 增量重算
（vt_rescore_nodes）、批量合并（v72）、`_maxDepthCache`、惰性刷新（v54）、
「目标变更不每帧重申」（v103）。**没有发现被删掉的优化。**
主人感觉「老版本更稳」，最合理的解释是：老版本没有这两个新滑块（不会踩真凶②），
树也更小、没有 v106 录制器和逐帧轨迹存档（真凶④更轻）。

### 45.4 还需主人确认一件事（可能是最大的坑）
WASM 加载失败会**静默**退回 JS：`vantage_rust_bridge.js` 用相对路径
`js/wasm/vantage_core.wasm?v=10` fetch（文件在，201KB）。若加载失败，
`simulateTankBatchScored`/`rescoreTankSamples` 全部返回 null → **生长和重算全变 JS**
→ 那就是「1 颗子弹也卡」。请主人看浏览器控制台有没有
`[VantageRustBridge] ... failed` / `Rust init failed`，以及面板里
「Rust评分 N 回退M」的 M 是不是在飞涨。

### 45.5 滑块回弹（问题①）——已定位到两行代码
- 其它滑块的 `input` 处理里**同时写了 `state.exp.xxx`**（例：`targetMixRatio`、
  `emptyFieldLaziness`、`killfieldWeight`、`evalFrames`）→ 每帧 `syncExpControls()`
  写回的是同一个值 → 不弹。
- 这两个新滑块的 `input` 里**只改了数字文字**（`safeFilterKSpan` / `actionCostSpan`），
  `state.exp.safeFilterK/actionCost` 要等 `change`（**松手那一下**）才更新
  （通用分发在 `el.addEventListener('change', ...)`）。于是拖动过程中，
  每帧的 `syncExpControls()` 把**旧值**写回控件 → 拖动被每帧撤销 = 严重回弹。
  暂停时面板不刷新 → 不回弹（与主人观察完全一致）。
- 修法：两个 `input` 处理里补上 `state.exp.* = <新值>`（并可顺手实时调用
  `VantageTree.setSafeFilterK/setActionCostPerFrame`），与其它滑块完全一致。

### 45.6 建议的修法（按性价比，等主人拍板）
| # | 修法 | 收益 | 代价/风险 |
| --- | --- | --- | --- |
| A | 提交切片改走 Rust 批量（失败再回退 JS），被选中节点照旧由 JS 融合世界确认 | 单次提交 10.8ms → ~1.2ms（+确认 ~1.2ms），直接治④ | 触碰死亡权威：整条执行路线变「Rust 候选 + 选中节点 JS 确认」，需主人同意 |
| B | 两个滑块 `input` 补 state | 直接治① | 面板 4 行，无风险 |
| C | 把 k / 动作成本接进 Rust 评分 | 让 k 真正生效且不牺牲性能（治②③） | 要改 Rust + ABI + 双实现对齐 + 重跑回归 |
| D | 逐帧诊断轨迹只在录制/诊断开关打开时记 | 减 GC 压力 | 低风险 |
| E | 加计数器：提交切片 JS/Rust 调用次数、重算退回逐层次数，面板直接显示 | 下次一眼定位 | 低风险 |

### 45.7 本轮结论
- 性能问题**不是杀戮场/混合寻路**造成的（与主人实测一致），是提交心跳 + 新参数
  把 Rust 通道关掉、退回逐层 JS 造成的。
- 没有发现早期优化被删除；是「一直没优化到的路」被更大的树/更多弹放大了。
- **k=0.4 的测试先别做**：现在 k 半生效（生长路径不认），做出来会误导结论。

## 四十六、v114：提交切片改走 Rust（主人同意的 A）+ 修滑块回弹（B）

主人选择：「A 提交切片改走 Rust」+「B 先修两个滑块回弹」，并问了一句
「A 之前没做吗？我印象里老版本已经几乎全部 Rust 化了」。

### 46.1 先回答「A 之前做过吗」——没做过，证据三条
1. `git log -S "slice.adapter"`（提交切片里那句算分代码）：**只在最初导入那次提交
   出现过一次，之后再没改过** —— 说明它从没接过 Rust。
2. 仓库里留着主人早期的回滚备份 `game_core/_rollback_backup_v67/vantage_tree.js`
   （v67）：那份里的提交切片**同样是 JS `scorePaths`、同样是「9 操作一次算完」
   （`perTick = ops.length`）**，和现在一字不差。
3. 真正被搬进 Rust 的是**生长探测**（九操作 rollout），即那次
   「Move nine-op rollout scoring into Rust」（v78）—— 它只改了 `rolloutNine`，
   没碰提交切片。所以主人印象里的「几乎全部 Rust 化」指的是生长+重算，
   **提交切片是唯一被漏掉的那条**，而它恰好是「新弹打死当前操作」时必走的路。

### 46.2 A 的做法（两条纪律）
- 新增 `tryCommitSliceRust(tree, slice, subOps)`：提交切片先调
  `adapter.simulateTankBatchScored`（vt_score_paths，一次算完 9 操作）；
  任何不支持/失败/结果不齐都返回 null，**原样回退** JS `scorePaths`。
- **纪律①**：只在 `!needsJsScoring()` 时走 Rust。k / 动作成本 / 遮蔽开关目前
  只有 JS 实现认（见 §45.2 真凶③），走 Rust 会把这些设置**悄悄吃掉**。
- **纪律②**：死亡权威一点没动。Rust 结果标 `rust-candidate`，被选中为执行路线的
  节点仍由 `commit()` 里原有的 `confirmExecutionRoutePick` → JS 融合世界确认
  （`confirmExecutionNodeDeath`，会翻案、会改标 `fused`）。

### 46.3 实测收益（真 Box2D + 真 WASM）
| 场景 | 改造前（9 操作 JS） | 改造后（Rust 全包 + 选中节点 JS 确认） | 倍数 |
| --- | --- | --- | --- |
| 远弹 | 10.88ms | 1.33 + 1.47 = **2.80ms** | **3.9×** |
| 近弹（很快死，帧数被截短） | 2.58ms | 0.89 + 0.65 = 1.55ms | 1.7× |
单次九操作：JS 10.83ms vs Rust 1.19ms（9.1×）。确认那一步是必然开销
（主人定的规矩：执行路线必须 JS 融合确认），所以净收益是 3.9×，不是 9×。

### 46.4 B 的做法：滑块回弹
根因（§45.5）：这两个新滑块的 `input` 里只改了数字文字，`state.exp.*` 要等
`change`（松手）才更新，于是每帧 `syncExpControls()` 把旧值写回控件。
修法：两个 `input` 处理里补上 `state.exp.safeFilterK / state.exp.actionCost`
（与其它滑块完全一致，4 行）。效果：拖动过程不再被逐帧撤销，
设置仍在松手时生效（和其它滑块一致）。

### 46.5 新增计数器 + 回归
- `tree.stats`：`commitSliceRustBatches` / `commitSliceJsBatches` /
  `commitSliceRustFails`；面板树详情行显示「**提交切片 Rust N / JS M**」——
  以后「发子弹卡顿」一眼可见是走了哪条路。
- 新套件 `rust/diff_commit_slice_rust.js`，5 条断言：
  ① 默认设置必须走 Rust（JS 融合批量 0 次调用）；
  ② `k=0.4` 必须回退 JS；③ 动作成本>0 必须回退 JS；
  ④ Rust 误报死亡 → 被 JS 融合世界**翻案**（authority 变 `fused`、死亡帧清成 −1）；
  ⑤ Rust 漏报死亡 → 被 JS 补上（死亡帧变成 JS 说的第 2 帧）。
- 版本：tree v114、testbench v101、index 同步；scoring 未动（v36）。
  **23 个回归套件 + 82 个 Rust 测试全通过。**

### 46.6 本轮没做的（要主人另行拍板）
- **C（把 k / 动作成本接进 Rust）没做**：所以开着 k 或动作成本时，
  提交切片依然按纪律①回退 JS —— 那两种设置下的性能**没有变化**（还是慢）。
  A 帮到的是主人平时玩的那套默认设置。

## 四十九、多 AI 同场：融合世界缓存是**单槽**，两个 AI 每帧互相挤掉

主人实测：「K 和 V 同时在场时帧率大概减半，K 一死立刻流畅；而且 V 好像变蠢了
（能躲的子弹少了一些、失误变多）」。

### 49.1 根因（K 的加入暴露的老问题）
`vantage_sandbox.js` 的 `getFusedWorld(gameController, aiId)` 用的是**单槽缓存**
`_fusedCache`（命中条件 = 地图引用相同 且 aiId 相同）。于是：

1. V 调自己的适配器 → 建 V 的融合世界（缓存里是 V）；
2. K（走同一个 `VantageSandbox.createAdapter`）调自己的 → aiId 不同 → **未命中** →
   **重建整个 Box2D 融合世界**（含迷宫墙、候选车体、弹槽），把 V 那槽挤掉；
3. 下一帧 V 又未命中 → 再建一次……**两个 AI 每帧各重建一次整个世界**。

两个后果正好对上主人的观察：
- **帧率减半**：每帧多付两次世界重建；
- **V 变蠢**：V 的缓存每帧被丢，等于每一步都在付重建费、抢走它的时间预算
  （树生长/提交都在这点预算里），决策自然变差。

### 49.2 修法
缓存改成**多槽**（键 = aiId；换图时整体作废）：
`_fusedCacheSlots = {}` + `_fusedCacheMazeRef`；命中按 aiId 取，建好即入槽。
`clearCaches()` 一并清空所有槽。**30 个回归套件通过。**

> 教训：**任何"按 AI 实例缓存的全局单例"都是多 AI 同场的定时炸弹**。
> 以后新增缓存要么按 (地图, aiId) 分槽，要么明确写成单实例专用。

## 五十、K（Killfield）粗版的三个"不适应"与修法

主人实测：「能走能打、有躲弹能力，但明显不适应这个版本：躲弹下降、对着墙发子弹自杀
（可能它那个版本这样死不了）、稍微远点就原地抽搐不动；大图明显吃力」。

| 现象 | 根因 | 修法 |
| --- | --- | --- |

## 五十一、V 慢/变蠢的真根因：`MAX_WALLS = 1024` 让 Rust 评分整条失效（长期存在）

主人的控制台抓到关键一行：
```
[VantageSandbox] Rust 评分路径结果无效，回退 JS scorePaths: vt_score_paths returned failure (0)
```
而且**大量刷屏**。顺着查下去：

### 51.1 链条
1. `vt_score_paths` 开头有一串容量校验：`op_count > MAX_OPS`、`duration_frames > MAX_FRAMES`、
   **`wall_count > MAX_WALLS`**、`bullet_count > MAX_BULLETS`、`threat_count > MAX_SCORE_PATHS_THREATS`
   —— 任一超限就 `return 0`；
2. `MAX_WALLS = 1024`（`rollout.rs`）。**我们的墙是"格与格之间的薄墙段"**，
   一张大图（人多时自动生成的大图）墙段数**轻松超过 1024**；
3. 于是 Rust 每次返回 0 → JS 侧静默回退 `VantageScoring.scorePaths`（JS 融合路径）；
4. 后果：**生长探测（九操作）全程走 JS** —— 慢（实测 9 操作×75 帧 JS ≈10.8ms vs Rust ≈1.2ms），
   而且行为与 Rust 路径不同（更保守/更晚躲），看起来就是"V 变蠢 + 卡"，
   **新弹引发的重算/剪枝**又叠加在这条慢路径上（主人说的"射击的子弹导致大量剪枝时卡顿"）。

这是**长期存在**的问题，不是本轮外接 AI 工作引入的；只是"人多 → 图大"才把它逼出来。

### 51.2 修法（本轮）
1. `MAX_WALLS: 1024 → 8192`（这个常量只用于校验，世界是动态 `Vec` 建的，提高安全）；
2. **重建 wasm**（`build_wasm.sh`）——**必须**，否则 Rust 边还是旧上限；
3. `vantage_rust_bridge.js` 的 wasm URL `?v=10 → ?v=11`（否则浏览器继续用旧二进制）；
4. `vantage_sandbox.js` 的版本串升到 v36（主人看到 v35 会误以为没刷新）；
5. 新增 Rust 回归 `max_walls_covers_large_maps`：锁住 `MAX_WALLS >= 4096`，防止以后再被调小。

**83 个 Rust 测试 + 30 个 JS 套件全通过。**

### 51.3 还没做
- 同类上限还有两个：`MAX_BULLETS = 256`、`MAX_SCORE_PATHS_THREATS`。真机若再报
  `returned failure (0)`，先对照这两个值（我可以一起提）。
- **游客（G）与莱卡（L）的编号**：仍是游戏自己那套（按在场顺序），要统一成
  "id 编号 + 最小空号"，下一轮做。

## 五十二、v115（**已按主人纠正撤回**）：我误把“有解却操作到死”当成选路问题

> ⚠ 主人 2026-09-09 纠正：**设计文档写得很清楚——软死候选与存活候选在选路上一视同仁

主人第三轮反馈：① K+V 同场还是卡；② K 还是傻；③ **V 不稳定、又降智（不论 K 在不在），

### 52.1 ④的反常：关遮蔽 → 帧率降（机制确定，非猜测）
`needsJsScoring()` 在 `occlusionEnabled === false` 时为真 → **提交切片与重算整条退回 JS**
（JS 融合世界模拟：9 操作×75 帧 ≈10.8ms，Rust 只要 ≈1.2ms）。所以关遮蔽省下的那点
遮蔽计算，远抵不上丢掉 Rust 快路的代价 → **帧率下降**。这不是 bug，是“没接完的参数”
的已知代价（见 §47.2）。根治 = 把遮蔽开关接进 Rust（ABI 升版，即当初缓做的 C 项）。

### 52.2 ③+④的正解：「有解却操作到死」的选路缺陷（已用测试证明并修复）
两件事共享一个根因。**选路函数 `pickBestChildByRolloutTotal` 的“活>死”裁定只看
`c.status`（死亡发生在段内才算死），而段长中位数只有 4 帧** —— 于是“第 60 帧才死、
死前干净”的候选 status 仍是 alive，与“全程存活但被遮蔽压分”的活路按总分竞争：

| 候选 | 75 帧预测 | 总分 |
| --- | --- | --- |
| A（晚死） | 第 60 帧死，死前每帧都是满分（子弹在 3.05m 断崖外**看不见**） | 2765 |
| B（活路） | 全程存活，但 40 帧被三颗弹遮蔽压到 ~8 分/帧 | 1702 |

**旧代码选 A**（实测复现，`_probe_select` → 现为 `diff_tree_select_survival.js`）。

主人关遮蔽的实验恰好证实这条机制：关掉后 B 的总分 = 75×39.5 = 2961 > 2765 →
**活路必然赢 → V 躲得好**。也就是说：遮蔽分把活路的分压低了，而“晚死”不扣分
（noDeath 默认开，死亡只停止累计）→ 死路反超。V 的“不稳定”也由此而来：
压分是否越过那条线，取决于当时弹幕形状。

**修法（v115）**：把“活>死”裁定扩到 **75 帧全程**——只要有一个候选全程不死
（`status!=='dead' && fullDeathFrame<0`），其它 75 帧内会死的一律不选；
全都死才按总分（死得晚分高，天然胜出，符合原设计“双 dead 取活最久”）。
`pickBest`（深层选路）同样修了。回归套件四条断言：
有活路不走死路 / 全死取活最久 / 段内死仍被滤 / 高分活路照常赢。

**风险（说清楚）**：V 会更“惜命”——当活路都是烂位置（被弹幕围住的角）时，
它宁可选烂活路也不选“好看地死”。这正是主人关遮蔽实验里看到的行为（“躲得不赖”）。

### 52.3 K 的性能：视图每帧重建（已修）

## 五十四、v117：改面板参数后 V 变蠢（状态污染）+ K 远距抽搐

主人实测两件事：
1. **V**：把每帧生长层数 1→2 → 能力**大幅下跌**，明显有解却操作到死；**改回去也不好，
   刷新网页才好**。杀戮场权重拉到 200%+ 也有弱化版同样现象。
2. **K**：敌人稍微远点就完全傻掉，原地快速前后动（远距抽搐）。

### 54.1 V 的状态污染（根因 + 修法）
**根因**：面板改参数（`setGrowLayersPerTick` / `setKillfieldWeight`）只改 `cfg` 值，
**不重建树**。但：
- 生长层数变了 → 树的层结构/`next` 链/段末时序全按旧节奏建的，继续用就是"形状不自洽"；
- 杀戮场权重变了 → 所有节点的 `objectiveBonus` 全变 → 旧选路结果全部作废；
- 而且旧节点的 `freshSig` 只对威胁窗口做签名（不看配置）——威胁没变就视为"分数还有效"，
  实际上权重早变了。

改回原值也不恢复：因为树里已经挂着按中间值选出来的 `next` 链和段末对齐结果，
这些**不是"配置值"能复原的**——只有重建（reset）才能回到干净状态。

**修法（v117）**：`setGrowLayersPerTick` 和 `setKillfieldWeight` 检测到**值真的变了**就
调 `reset()`（等价于换局重开：树丢弃、下一帧重建、几帧内自愈）。
这符合"结构性参数一变就重建"的原则，与换局 reset 走同一条路。

> 以后凡是改了会影响**树结构**或**所有节点分数**的参数，都应该走这条路。
> 只影响单帧行为的参数（如 `actionCost`）不需要重建。

### 54.2 K 的远距抽搐（根因 + 修法）
**根因**：K 的评分里"靠近敌人"的**直线距离项**只在 BFS 距离表不可用时才算（`else` 分支）。
而 BFS 项在 12 帧前瞻（无弹时用短前瞻省性能）里**根本跨不出一格**——起点格 == 终点格
→ `d0 === d1` → 加 0 分。于是远距离时**所有移动候选同分**（前进后退都是"位移一样、
方向没差"）→ 平局乱选 → 主人看到的"原地前后抽搐"。

**修法**：直线"靠近敌人"项**永远算**（权重 12：靠近 = 正分，远离 = 负分），BFS 项叠加
在直线之上（跨格时额外 +60 × 步数差）。这样远距离时前进永远赢后退，方向感不会断。

tree v117（index 同步）。**30 套件 + 83 Rust 测试全通过。**

## 五十五、v118：**绿节点死亡**的真根因——新弹粗筛用"发射点"量距离（时间基准错配）

主人判据（**本项目的硬规则，记牢**）：
> 只接受两种死亡：① 贴着 AI 射击、1 帧死（来不及反应）；② **真死**（所有操作都活不了）。
> **AI 只应该死在红色节点**；死在橙色/绿色节点必然是错的——还有能活的时间，
> 操作更短时间就能多苟活一会。

### 55.1 录制实证（主人那份 `vantage_record_1789487050730.json`）
死亡 @t=7.85 前逐帧：

| 时刻 | 执行操作 | seg | `predDeathFrame` | 威胁数 | 威胁 id |
| --- | --- | --- | --- | --- | --- |
| 7.59 | 前右 | 14/14 | **-1（绿）** | 1 | `db-25d9-837`（**首次出现**）|
| 7.65 | 前右 | 14/14 | -1 | 1 | 同上 |
| … | … | … | … | … | … |
| 7.85 | 前右 | 14/14 | -1 | 1 | 同上 → **死亡** |

另一批死亡（橙色）：`predDeathFrame=4~5`、`seg=2/3` —— 也在 **橙色**节点死。

**结论**：执行节点在新弹出现后**从未被重算**（`predDeathFrame` 一直是 -1），
坦克把 14 帧段跑完，在段末被这颗弹打死。

### 55.2 根因：`bulletCannotReach` 的两个量时间基准不一致
链条：新弹出现 → `invalidateStaleNodes` 逐节点粗筛 → **`if (!hit) continue;`（跳过，永不重算）**
→ `if (node !== tree.commitNode) continue;`（只有执行节点做融合死亡扫描）
→ `scanNodeDeath` 才是真正的死亡判定。

**粗筛漏判 = 执行节点永不重算 = 绿节点死亡。**

而粗筛的 `bulletCannotReach` 是这么写的：
```js
var p0 = threatStartPoint(th);          // = track[0] = **子弹发射点**
var maxTravel = th.speed * (nb.t1 - _timeAcc);   // 从"现在"起还能飞的距离
return pointBoxDistance(p0, nb) - maxTravel > CONTACT_MARGIN;
```
- 距离从 **发射点** 量（很大）；
- 可飞距离从 **现在** 起算（很小）。

子弹飞了一半时必然误判"打不到"。**算例（就是主人的场景）**：
子弹 20 m/s 从 49 米外发射、已飞到距坦克 9 米处，段盒只剩 0.28 秒：
`49 − 20×0.28 = 43.4 > 4` → 判"打不到"；而实际它 **0.45 秒后命中**。

### 55.3 修法（语义修正，不动设计）
新增 `threatCurrentPoint(th)`：按 `_timeAcc - (rootAbsT + anchorOffset)` 把 track/path
推进到"现在"，取当前位置；`invalidateStaleNodes` 改用它量距离。两个量同基准。
（`track` 走下标，`path` 走弧长；都拿不到才退回发射点。）

### 55.4 回归 `diff_tree_coarse_reach.js`（三条断言）
1. 子弹已飞到 9 米外、0.45 秒后命中 → **必须判"能打到"**；
2. 远处背向的子弹 → 仍判"打不到"（不能矫枉过正）；
3. **守着旧写法会误判**（用发射点量距离 → 判"打不到"）——证明这条修的是真 bug。

另外导出 `VantageTree._coarse`（粗筛调试钩子），供回归直接验证。
**31 套件 + 83 Rust 测试全通过。** tree v118。

### 55.5 与「growLayers=2 更弱」的关系
主人观察到"预测量更高反而更容易死"。生长层数=2 时每 tick 建更多节点 →
**新弹到达时树里"待复核的节点"更多、而每个节点的粗筛/复核窗口更拥挤**；
再加上上面这条漏判，就更容易出现"执行节点被跳过复核"的组合。
v118 这条修好后，growLayers=2 应当不再反向。若仍有，下一步查
"`_pendingThreats` 在同一 tick 内是否可能被清空（导致粗筛 boxes 为空直接 return false）"。

### 55.6 同一个 bug 的**第二处副本**（一起修了）
`nodePossiblyAffectedByPending`（v71 的"节点是否可能被后补新弹影响"）里有**一模一样**的写法：
```js
var p0 = threatStartPoint(pending[bi]);
if (p0 && bulletCannotReach(pending[bi], p0, nb)) continue;
```
同样用发射点量距离 → 同样会漏判。已一并改为 `threatCurrentPoint`。
现在全文件里 `threatStartPoint` **只剩 `threatCurrentPoint` 的兜底调用**（无其他调用点）。

### 55.7 安全网：粗筛盒建不出来时不能静默跳过
`invalidateStaleNodes` 原来是 `if (!boxes.length) return false;` —— 有新弹却
建不出粗筛盒（track/path 都没有）时**静默跳过**，执行节点永不复核，还是"绿节点死"。
现在改成：记一条 `coarse-no-box` 结构事件 + 统计 `coarseNoBoxScans`，
并**只对正在执行的节点**做一次融合死亡扫描；若判死则夹取段长（`safeFramesForDeath`）
+ 置 `_forcedReselect`，同 tick 重选。

### 55.8 为什么它卡了三周（复盘）
主人的判断完全正确：**这个问题存在很久，而粗筛代码从来没被动过**，
所以**三周前的录制和现在的现象是同一个 bug**——这也解释了为什么
"改这改那都没用"：改的都是评分/选路/参数，而**执行节点在新弹出现时压根没进复核名单**。
线索一直都在（"绿节点死亡"= 预测说 75 帧不死却死），只是没人往"粗筛把节点滤掉了"这一层想。

### 55.9 回归（四条断言，两处副本全覆盖）
`diff_tree_coarse_reach.js`：
1. 子弹已飞到 9 米外、0.45 秒后命中 → 判"能打到"；
2. 远处背向 → 仍判"打不到"；
3. **旧写法（发射点）确实误判**（守住这条，防止有人改回去）；
4. **第二处副本**（`nodePossiblyAffectedByPending`）也必须判"受影响"。

## 56. 融合世界"静默丢弹"盲区（v119 修，v118 遗留）

### 56.1 现象
主人实测：**全橙死亡**——`predStatus=alive`、`fullDeathFrame=6`（橙色，≥2），
钳制后 `segmentFrames=3`，AI 就在这 3 帧"安全窗"里死了。
"预测 6 帧、3 帧就死"、"预测 5 帧、却操作了 5 帧"都是同一族的表症。

### 56.2 定位（9/19 录像 vantage_record_1789756723769.json）
- 死亡弹 `db-c79d-135`，执行节点 `fd=6 planned=4 seg=3`；段末预测坦克位姿
  与真实只差 **0.00~0.05 米**（说明**坦克侧与时间基准都是对的**）。
- 用真实位置/速度算几何接触 = `11.777`（报告帧 11.757 是覆盖到 11.777 的
  那一物理步 → 现实与几何一致）；融合世界预测 `11.817` → **弹药侧晚约 2 帧
  ≈ 0.68 米行程**。
- 也就是说：**权威对某颗弹的"位置/存在性"判断与现实不一致**，方向一律是乐观。

### 56.3 根因（代码事实，不是猜测）
`vantage_sandbox.simulateFusedBatch` 给弹摆位只有两条来源：
`th.track`（Box2D 逐帧轨迹）或 `th.path` 折线（还要 `(q+1帧)×speed ≤ 折线长`）。
两条都不满足时，代码是：

```js
if (!placed) { slot.body.SetActive(false); slot.lastRound = -1; continue; }
```

**一颗真实存在的弹就这样被从死亡权威里删掉了**——权威对它失明，于是判
"还活着/死得更晚"。另外 `scanNodeDeath(tree, adapter, node, pending)` 的
`pending` 形参**全程未被使用**（死参数），扫描只拿 `tree.threats`。

注意纠正一个早期误判：**不是**"新弹不在威胁表里"——`attachNewThreats` 会把新弹
并进 `tree.threats`（带 `anchorOffset` 与轨迹），`computeThreats` 还有 v28 兜底
"任何真实存在的 projectile 都不能从视野消失"。洞在**摆位**这一层。

### 56.4 修法（v119）
- 沙箱 v38：删除静默丢弃，改为"真实弹体位姿 + 真实速度"从**现在**前推到
  本节点起点（`advFrames = (tGlobal − nowTGlobal)/FRAME`）后摆进融合世界；
  无 `track` / 无威胁条目 / 近似也失败 → 分别计数，每秒最多一条响亮告警，
  并暴露 `getFusedDropStats()`。
- 树 v119：三处融合调用都传 `nowTGlobal`；`scanNodeDeath` 改用
  `unionThreats(tree.threats, pending)`（让死参数生效）；逐帧录制新增
  `fusedDrop`，`tree.stats` 累计 `fusedApproxPlaced / fusedNoThreat / fusedSkipped`。
- 回归：`diff_tree_grow_boost.js` 里加接线断言——静默丢弹的老写法必须不存在、
  统计与响亮日志必须存在、`nowTGlobal`/并集必须接管。

### 56.5 仍未定论（下一步的证据需求）
这颗录像里的致死弹**本来就在威胁表里**，所以它不能解释 56.2 那 2 帧晚点。
要分清"注入时就晚 2 帧"还是"中途发散（反弹/贴墙/步序）"，必须导出
**融合世界在被选中候选那次 rollout 里的逐帧坦克+每颗弹位置**，与真实轨迹
逐帧对拍（现有录制只记真实世界 + 段末预测，不记预测内部逐帧轨迹）。
先看 `fusedDrop`：若死亡瞬间它一直是 0，说明 56.3 不是该次死因，必须上逐帧轨迹导出。

### 56.6 铁律补记
**"看不见"必须等于"响亮出错"，不允许等于"当它不存在"。**
死亡权威内部尤其如此：任何"摆不进去就跳过"的分支，都是在制造橙色/绿色死亡。

### 56.7 第二轮实测（9/19 二次录像）把偏差钉死在"弹药侧落后 2~4 帧"
- 致死弹 `b-08eb-14` **一直在威胁表里**（不是 56.3 的静默丢弹）；
- 坦克当时静止十几帧，段末预测与真实差 0~0.06 米 → 坦克侧与帧基准都准；
- 用录像里的真实弹位/速度 + 原版车体尺寸（`createTankBody` 车体半长 1.5×2.0 米）
  做的几何核算：**接触时刻 ≈ 11.340，报告死亡 11.320（差 1 帧 = 物理步归属）**，
  即**现实与几何自洽**；
- 而树从头到尾稳定预测死亡绝对时刻 **11.38~11.42** → **比现实和几何都晚 2~4 帧**。
- 结论：**预测使用的弹药状态比真实物理慢约 2~3 帧**，方向恒为乐观（预测死得更晚）
  → 橙/绿节点死亡。这解释了为什么改评分/选路/参数全都无效：输入就差几帧。
