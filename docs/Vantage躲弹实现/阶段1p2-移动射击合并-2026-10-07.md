# 阶段 1′+2 合并实施（移动 + 射击一起学）— 2026-10-07

> 用户定案：「移动和射击**一起学**，因为怕学了移动之后很难再学会射击了」
> （原文档 §8 是把「移动」和「定点射击」拆开的，现改为并行。）

---

## 一、为什么合并（用户理由，已验证合理）

只学移动 → 策略收敛到「只会走」，**射击键的梯度信号被「走位已经能拿分」淹没**。
即使后面再单独训射击，已收敛的走位策略也会抵抗改变（灾难性遗忘）。

**所以：从第一个任务开始就让射击和移动同时存在。**

## 三、任务设计

**单一任务，同时考移动和射击：**

```
tank_a 随机传送到 A
tank_b（静止靶）随机传送到 B（与 A 保持最小间距）
→ 智能体必须【逼近 B + 转向瞄准 + 开火】
→ B 被击杀 或 用尽步数，episode 结束
```

**奖励：**

```
r = (prevDist - dist) / 10          # 移动塑形（势能，靠近为正）
  + 5.0   如果击杀 B                 # 射击奖励（终局）
  - 0.02  如果这一帧开了火            # 射击成本，防"无脑连按"
```

**为什么要有射击成本**：用户定案里有「轻罚：不达预期，例如非加特林连开很多帧」。
不加成本的话，最优策略是「永远按住 fire」——因为开火没有代价。加了成本才会
让网络学会「对准了才开火」。

## 五、动作空间 9 → 18

```
a ∈ [0, 17]
  move = a % 9      （静止/前/后/左/右/前左/前右/后左/后右）
  fire = a >= 9

__vtAct(a) 实现：
  var mv = a % 9, fr = a >= 9;
  c.fwd   = (mv===1 || mv===5 || mv===6);
  c.back  = (mv===2 || mv===7 || mv===8);
  c.left  = (mv===3 || mv===5 || mv===7);
  c.right = (mv===4 || mv===6 || mv===8);
  c.fire  = fr;
```

**为什么用 18 而不是「9 动作 + 1 个独立的 fire 头」**：
- 18 是**单个 categorical 分布**，PPO 实现不用改（`F.log_softmax` 直接可用）
- 独立头需要两个分布 + 联合 logprob，改动更大
- 代价：参数量 9×64 → 18×64（多 576 个），可忽略

## 六、网络

```
obs(15) → 64 → ReLU → 64 → ReLU → { logits(18),  value(1) }
参数量：15×64+64 + 64×64+64 + 18×64+18 + 64+1 = 1,024+4,160+1,170+65 = 6,419
```

（当前移动版是 5,642，加了 777 个参数。）

**注意**：这仍是「阶段任务的玩具网络」。真正的 Transformer（`d=256, L=3, 2.56M 参数`）
是**接回树之后**才用的。阶段任务用极简 MLP 是为了：
1. 快速验证奖励设计和训练管线
2. 快速迭代（几秒一轮，不是几分钟）

## 八、与树的关系（别忘了）

阶段 1′/2 是**技能预训练**，智能体直接输出 9（或 18）个操作，
**完全没有经过 Vantage 的树**。

这是有意的简化：
- 树负责物理模拟 + 增量预测，它的价值在**长时程规划**
- 而「走到目标 + 瞄准射击」是**短时程反射**，不需要树
- 等这些技能稳了，再把它们接回 `decide(ctx) → {growAt, select}` 契约

**阶段 8（真实对局）才是树 + 网络合体的地方。**
