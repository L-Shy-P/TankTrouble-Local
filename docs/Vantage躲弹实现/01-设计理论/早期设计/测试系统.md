## 〇、为什么测试要独立成系统

| 旧做法（test_vantage_sandbox.html 双按钮） | 问题 |
|---|---|
| 离线断言 = 硬编码场景 | 测的是"我编的场景"，不是"游戏里真实发生的局面" |
| 游戏内冒烟 = 一次性打印 | 看不到逐帧变化，子弹飞过来时评分怎么变的全靠猜 |
| 断言和渲染混在测试页里 | 换阶段就得重写，没法沉淀 |

新原则：**测试系统 = 时间控制器 + 探针 + 渲染器**，三件各自独立，
被测对象（评分/基准时间/沙箱）只被"读取"，测试系统不改它们的内部。

## 二、时间控制器：暂停 + 单帧递进（核心新设施）

### 2.1 游戏帧驱动链（已从源码挖出，非推测）

```
GameController.update()                          ← 每帧被 Phaser 状态驱动调用
  deltaTime = (当前真实时间 − 上次时间) / 1000     ← 用真实时钟算步长
  deltaTime = min(deltaTime, MAX_DELTA_TIME)      ← 钳制
  roundController.update(deltaTime)               ← 物理步进 + AI 更新全在这条链上
    → model.update → Box2D.Step → AI.update …
```

证据：`original_js/gamecontroller.js+gamemodel.js` 的 update 原文
（`var deltaTime=(time-this.lastUpdate)/1000.0 ... this.roundController.update(deltaTime)`）。

### 2.2 钩法（patch GameController.prototype.update，与 local_patch 同款手法）

```
原 update 被包一层：
  暂停中 → 不推进真实时间（lastUpdate 持续刷新成"现在"，
           这样恢复时 deltaTime 不会爆出一个大值），直接 return
  单帧递进被请求 → 放行一次，但把 deltaTime 强制换成固定帧时长（0.02 秒），
           走完一帧后重新落回暂停
  正常 → 原样放行
```

要点：
- **只包 update 入口，不动内部**——物理/AI/渲染全走游戏自己的链，
  单帧递进出来的画面就是真实一帧的结果（这正是"真实对局内验证"的保证）
- 暂停时 Phaser 渲染循环照常跑 → 画面冻结但 UI 还活着，渲染器可以继续画标注
- 固定步长 0.02 秒 = 沙箱的 FRAME_DT → 递进一帧 = 沙箱预测的一帧，两边对得上

## 三、探针：每帧采集被测数值（只读，不干预）

暂停或递进后，探针读一遍当前局面，产出"本帧测试快照"：

```
测试快照 = {
    帧号:            递进计数（暂停期间手动帧的序号）
    坦克位姿:        adapter.getTankState()
    子弹折线:        adapter.getProjectilePaths(...)
    威胁列表:        VantageScoring.computeThreats(...)   ← 每颗子弹倒计时/最近距离
    基准时间:        VantageScoring.computeBaseTime(...)  ← 基准帧数/基准子弹/密集权重和
    单帧评分:        VantageScoring.scoreFrame(...)       ← 分数/遮蔽角/剩余角区间
    一致性断言结果:  朝向是否在剩余角内 等（02 文档第三节末尾那两条）
}
```

规矩：探针**只调模块的公开接口**，不 import 内部函数——
模块接口一变，探针编译期就暴露，不会悄悄测错东西。

## 五、测试流程（主人视角的操作手册）

```
1. 启动游戏，正常开一局（1 player → 大厅 → Add Vantage → Local game）
2. 等 Vantage 进场，按 P 暂停
3. 按 V 打开渲染层 → 画面上出现折线/遮蔽扇区/基准子弹标注
4. 按 N 逐帧递进 → 每帧看：
   · 子弹沿折线走，倒计时数字递减
   · 遮蔽扇区随子弹逼近变大、单帧分下降
   · 基准时间随威胁临近缩短
5. 按 T 看分数曲线面板 → 目视判断"评分变化是否符合物理直觉"
6. 发现异常 → 记下帧号和快照（面板可导出当前快照 JSON）
```

**验收标准（真实对局内）**：
- 子弹直冲坦克 → 递进到相撞前一帧仍判存活、相撞帧判死扣 10 万
- 子弹擦身而过 → 最近距离小但倒计时已过 → 外圈/倒计时逻辑不把它当紧迫威胁
- 多弹齐至 → 密集权重和上升、基准时间明显短于单弹场景
- 全程一致性断言无失败（朝向始终在剩余角内，除非已判死）

### 8.2 补丁挂载点改 Classy `__methods`（修问题 2，核心）

```javascript
function patchUIGameState() {
    if (typeof Game === 'undefined' || !Game.UIGameState) return false;
    var klass = Game.UIGameState;                       // Classy 类对象
    if (!klass.__methods || !klass.__methods.update) return false;  // 挂不上→false，让重试继续
    if (klass.__methods._vtTimePatched) return true;
    var orig = klass.__methods.update;
    klass.__methods.update = function() {
        // ……暂停挂起 / 递进放行逻辑与原版相同（L72-90），原样搬过来 ……
    };
    klass.__methods._vtTimePatched = true;
    return true;
}
```
- GameController 同款：钩 `GameController.__methods.update`（GameController 也是 Classy 类）。
- tryPatch 成功后 `console.log('[Testbench] 时间钩已挂上: UIGameState+GameController (__methods)')`；
  600 次仍失败 → `console.warn` 明示（不再静默）。
- 暂停语义自动满足主人要求：挡住 UIGameState.update = 同时冻结 `AIs.update`（AI）
  与 `gameController.update`（物理），一停俱停。

### 8.3 单帧递进 dt 统一为 0.02s（修问题 7）

递进放行那一帧，调用 orig 前临时覆写 Phaser 时钟，返回后恢复：

```javascript
state.stepping = true;
var t = this.game && this.game.time;
var savedMS = t.physicsElapsedMS, savedS = t.physicsElapsed;
t.physicsElapsedMS = FRAME_DT_MS;        // 20
t.physicsElapsed = FRAME_DT_MS / 1000;   // 0.02
try { orig.apply(this, arguments); }
finally {
    t.physicsElapsedMS = savedMS; t.physicsElapsed = savedS;
    state.stepping = false;
}
```
依据：`AIs.update(this.game.time.physicsElapsedMS)` 的参数在 orig 内部求值 → 取到 20ms；
AI 内部若再读 `game.time.physicsElapsed` 也一致；GameController 侧沿用"拨 lastUpdate=now−20ms"。

### 8.4 快照冻结语义 + 帧号修正（修问题 3/4/5）

1. captureSnapshot **不再引用 AI 活数据**：threats / baseTime 一律暂停瞬间主动重算
   （`VantageScoring.computeThreats(adapter, tankState)` / `computeBaseTime(...)`）。
2. history 只在**真正递进后** push（togglePause 的"第 0 帧"基准采集不 push）；
   面板显示改为 `帧 K`，曲线点数 ≡ K。
3. 渲染器**去掉 250ms 轮询**：afterStep 之后画一次即可
   （Phaser 渲染循环本身在跑，Graphics 对象挂在场景里持续显示，冻结画面天然稳定）。

### 8.5 图例常驻（修问题 6）

### 9.2 「基准时间」中间值展开（需扩 computeBaseTime 输出，纯增量兼容）

接口扩展——`computeBaseTime(threats, cfg, consts)` 返回值追加 `details`：

```javascript
details: {
    outerRadius: cfg.outerRadius,          // ①外圈半径(m)
    perBullet: [                           // ①每颗子弹的过滤过程
        { id, countdown, closestDist, inCircle }
    ],
    tBaseRaw: tBase,                       // ②基准子弹倒计时(s)
    weights: [                             // ③圈内每颗非基准子弹的权重项
        { id, dt: tBase - countdown,       //   dt = tBase − 该弹倒计时 (≥0)
          weight: densityA * exp(densityB * dt) }
    ],
    composed: tBase / (1 + weightSum),     // ④合成值(钳制前)
    clampedLow: bool, clampedHigh: bool,   // ⑤是否触底/触顶
    defaultUsed: bool                      // 是否走了"圈内无子弹→默认值"分支
}
```

展开区逐行呈现（主人可手算核对）：
```
① 外圈过滤：N 颗子弹，M 颗入圈（半径 R m），未入圈：id…（最近距离 …m）
② 基准子弹 = ★id，倒计时 tBase = … s
③ 密集权重：id_A dt=… w=…；id_B dt=… w=…；合计 W = …
④ 合成 tBase/(1+W) = … s
⑤ 钳制 [baseTimeMin, baseTimeMax] → 终值 … s = … 帧
```

威胁表行点击 → 单弹中间值：折线采样过程（沿折线步进采样、坦克按净速度
`TANK_FORWARD_SPEED−TANK_BACK_SPEED` 前移、取距离最小点）→ countdown/closestDist 的来源。

### 11.1 遮蔽角 90° 偏移（已修复）

- 根因：拷贝区2 的弧段角是**前向轴在（x右/y下）atan2 系的角度**，≠ 游戏 rot。
  游戏 rot 的前向向量 (sin rot, −cos rot) 的 atan2 角 = rot − π/2，即 **rot = 弧段角 + 90°**，
  拷贝时漏了换算 → 全部区间偏 −90°；另回绕区间终点未按宽度重算 → 诡异扇形。
- 修复：exactOcclusion 输出前统一 +90° 并按"起点归一化+终点=起点+宽度"重算。
  算例验证：子弹正右 2.8m，四段遮蔽弧 +90° 后恰落在车体四角指向来弹的
  rot（57.7°/122.3°/237.7°/302.3°）。
