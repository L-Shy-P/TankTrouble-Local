# Vantage 双智能体架构（2026-10-02）

> 本文是**系统性整理**，不是时间线记录。前述讨论过程见《决策源接口架构-2026-10-02.md》。
> 本文以主人最终定案为准。

---

## 一、总览

```
┌─────────────────────────────────────────────────────────────┐
│ 规则系统（不是智能体，纯机械）                                  │
│   · 预测时长（树往未来铺多远）—— 纯性能调优，学习负担不该加在这 │
│   · 物理模拟（rollout：坦克轨迹 + 子弹弹道含反弹）              │
│   · 死亡判定（权威）                                          │
│   · 增量失效（新子弹出现 → 作废受影响的节点）                    │
│   · 段末重锚 / 对齐重建 / 节点预算 / 性能闸门                    │
│   · 两条硬检查（见第五节）                                     │
└─────────────────────────────────────────────────────────────┘
                              ↓ 摊开当前树 + 场面
┌─────────────────────────────────────────────────────────────┐
│ A 智能体 · 生长                                               │
│   只做一件事：决定「在哪些节点上继续展开」                       │
│   目标：长出的路尽量不用回退 → 换路少 → 坍缩浪费的节点少          │
└─────────────────────────────────────────────────────────────┘
                              ↓ 在哪长
┌─────────────────────────────────────────────────────────────┐
│ 程序：执行生长 → 树结构变了（多了新节点）                        │
└─────────────────────────────────────────────────────────────┘
                              ↓ 摊开更新后的树 + 场面
┌─────────────────────────────────────────────────────────────┐
│ B 智能体 · 操作                                               │
│   决定三件事：选哪条路 / 这段走多久 / 哪几帧射击                  │
└─────────────────────────────────────────────────────────────┘
                              ↓ 选路 / 段长 / 射击表
┌─────────────────────────────────────────────────────────────┐
│ 程序：逐项校验 → 合并成输入 → 交给游戏                          │
└─────────────────────────────────────────────────────────────┘
                              ↓
                        游戏执行本段
                              ↓ 段末
                        回到帧开头，重新开始
```

**为什么是两个智能体而不是一个**（主人定案）：

> 「分了模块说不定还能优化，每个都做好自己的分工。就像大语言模型也由好几个小的模块组成一样，
> 我们看的是**总时间、总的参数量**……**分工还能防止灾难性遗忘**，
> 一个只负责预测、长节点，一个只负责玩游戏、操作。」

一个"什么都管"的模型必须足够大才能都管好；两个"只管一件事"的各自可以很小，**总账可能更省**。

## 二、每帧的完整时序

```
①  更新场面数据（保证智能体看到的永远是最新的）
        ↓
②  树把「当前节点集合 + 场面」摊成观测
        ↓
③  调用 A：输出「在哪些节点长」
        ↓
④  程序执行生长 → 树多出新节点
        ↓
⑤  树把「更新后的节点集合 + 场面」摊成观测   ← 与 ② 不是同一份
        ↓
⑥  调用 B：输出「选哪条路 / 段长 / 射击表」
        ↓
⑦  程序逐项校验（格式 + 语义）——不合法则【本帧重试】
        ↓
⑧  合并成输入（移动 + 射击）→ 交给游戏
        ↓
⑨  执行本段（段长由 B 定）
        ↓
    段末 → 回到 ①
```

**关键点**：
- ③ 和 ⑥ 是**两次独立调用**（两个智能体，不是同一个跑两次）
- ⑤ 的观测**包含 ④ 长出来的新节点** → B 才能选到"这一帧刚长出来的路"
- ⑦ 的校验失败 → **本帧重试**，非法输出永远到不了树

## 三、输入输出契约

### 3.1 A 的输入

| 内容 | 说明 |
|------|------|
| 树的节点集合 | 每个节点一份**摘要**（见 3.3） |
| 当前场面 | 坦克位姿、子弹位置/速度、迷宫 |
| 自己的记忆（可选） | A 上一帧存下的东西，原样归还（不透明） |

### 3.2 A 的输出

| 内容 | 说明 |
|------|------|
| **在哪些节点长** | 节点编号列表。**不限于叶节点** |
| 记忆（可选） | 不透明 |

**注意**：**A 不输出"长几次"**——长几次就是它列出的节点个数。
极端情况是它啥都不列（0 个节点），这是合法的。

**也不输出预测时长**——那是规则系统的事。

### 3.3 节点摘要（A 和 B 看的一样）

每节点约 12 个数：

| 字段 | 说明 |
|------|------|
| 编号 / 父节点 | |
| 来路操作 | 9 种移动操作之一 |
| 段长 / 深度 / 到根累计时间 | |
| 末态位姿 | 相对当前位置的位移 x、y + 朝向变化 |
| 死亡帧 | −1 表示活满 |
| 是否失效 / 有没有子节点 | |

原始逐帧轨迹**不发**——留在树内部。

### 3.4 B 的输入

与 A 相同（更新后的树 + 场面），但调用发生在生长之后。

### 3.5 B 的输出

| 内容 | 格式 | 说明 |
|------|------|------|
| **选哪条路** | 一个节点编号 | |
| **段长** | 一个整数（帧） | **不能乱来**——撞墙、被打死都在这里 |
| **射击表** | **稀疏表**（哪几帧射击） | 大部分帧不射击，所以只列表态的那些帧 |
| 记忆（可选） | 不透明 | |

**射击表的格式**：

```
{ 第 5 帧: 射击, 第 12 帧: 射击, 第 13 帧: 射击 }
```

合法性条件只有两条：帧号在本段内、不重复。
**"按下/松开必须交替"这个约束不存在。**

**执行层负责把稀疏表变成按键状态**：连续出现的帧 = 按住；中间断开 = 自动松开。

## 四、程序侧的四类处理

| 类型 | 什么时候 | 做什么 |
|------|---------|--------|
| **格式校验** | 每包输出 | 类型对不对（生长必须是编号数组、射击表必须是编号到布尔的映射…） |
| **语义校验** | 格式过了之后 | 编号找得到吗、是不是真死、选路是不是当前决策点的候选 |
| **帧内重试** | 校验失败 | **本帧重新调用同一个智能体**，并把"哪一项非法、为什么"作为反馈带进去 |
| **兜底** | 重试用尽 | 放弃本帧，树走规则逻辑保证能继续跑 |

### 为什么"帧内重试"和"非法惩罚"都要有

| 机制 | 目的 | 归属 |
|------|------|------|
| **帧内重试** | 让**树**拿到可用的结果 | 执行层（可靠性） |
| **非法惩罚** | 让**智能体学会一次给对**，省掉重试开销 | 训练（性能） |

**重试不是免费的**——每次重试 = 一次完整推理。所以非法输出虽没生效到树上，
**但它消耗了算力**，惩罚就是为这份消耗定价。

## 五、三条不变量（执行层强制，智能体无权覆盖）

| # | 内容 |
|---|------|
| **一** | 真死（能走一步就死）的节点，**不能作为生长的父节点** |
| **二** | **有非真死候选时，不选真死路线** |
| **三** | **射出瞬间（0 帧）就打死自己的射击，绝对不选** |

**口径统一**："真死"不论凶手是谁——敌人的弹、自己的弹、反弹回来的，一视同仁。

**第三条的范围要精确**：只有 **0 帧自杀**是绝对错误。
后续帧被自己的子弹打死、或被自己的子弹逼死，**都不判错**——
只把**死亡时间**作为观测告诉智能体，让它自己权衡（射出的子弹能干扰对手、封锁走廊）。

## 六、惩罚

### 6.1 四级

| 级别 | 范围 |
|------|------|
| **重罚** | 结构性非法：引用不存在的节点、跨层选路、在真死节点生长、选真死路线 |
| **中罚** | 动作无效 |
| **轻罚** | 数值越界；**以及"不达预期"**（见 6.2） |
| **不罚** | 资源限制导致的拒绝 |

### 6.2 射击的"不达预期"

射击被简化成逐帧二值之后，**"非法操作"这个类别基本消失了**。剩下的只有：

| 情况 | 处理 |
|------|------|
| 不会发射加特林（加特林要按住蓄力，点射打不出来） | 轻罚 |
| 想射 5 发，只打出 1 发（点击频率过高被判为按住） | 轻罚 |

**判断依据**：直接看当前持有的物品——非加特林武器却连续很多帧射击，不符合它的预期。

### 6.3 分级的原则

| 级别 | 为什么 |
|------|--------|
| 结构性错误重罚 | 很快学会不编造、不跨层 |
| 数值越界轻罚 | 不会因为"层数给大了 1"就被吓得不敢生长 |

**一律重罚会让智能体学会"什么都不做"——因为不动就不会违规。**

## 七、缓存

### 7.1 物理缓存的失效条件（已有机制）

新子弹出现且与节点时空盒相交 / 段末重锚 / 对齐超差 / 节点被剪枝。

**这是固有的刷新**——规则版也是这样，一有新子弹就刷新。
规则版还有一堆吃性能的评分，所以这个开销不用担心。

### 7.2 思维缓存（可选，且是非线性的）

主人的方案：

> 离现在越远，预判中的可能性越低，思维价值越低，所以**缓存的大小就要越小**。

| 距离 | 策略 |
|------|------|
| 0 ~ 15 帧 | 全精度，可每帧更新 |
| 15 ~ 40 帧 | 中精度，只在物理缓存失效时更新 |
| 40 ~ 75 帧 | 低精度，或被访问时现算 |
| > 75 帧 | 不存 |

**理由不只是省空间**：越远的节点，到达它时真实状态早已不同，树会重锚、重选路，
那个评估大概率被真实信息覆盖——**精算它是浪费算力**。

### 7.3 缓存接口是不透明的

两种智能体的"思维状态"形态完全不同（网络的中间层激活 vs 果蝇的 82 个发放率）。
所以树**不解释缓存内容**，只负责保存、归还、以及"这个节点失效了"的通知。

**没缓存也照样能选**——场面数据是现成的。

## 八、训练课程

> **【2026-10-06 修正】** 本节的课程顺序已改：**阶段1（移动）与阶段2（定点射击）改为并行喂同一个网络**，
> 不再串行（避免"学会移动后射击学不动"）。完整定案见
> **`智能体架构定案-2026-10-06.md` §三**。


| 阶段 | 内容 | 练什么 |
|------|------|--------|
| **1** | **移动**：地图上随机给可达位姿，尽可能短时间内贴合 | 走位精度 + 效率 |
| **2** | **定点射击**：不能离开本格，射击可达的目标位置 | 瞄准 + 反弹几何 |
| **3** | **躲弹**：射击源随机移动并发射不同弹种，存活越久分越高 | 纯躲弹 |
| **4** | **移动射击**：先移动到目标格，再射击目标位置 | 走位 → 射击的衔接 |
| **5** | **躲弹射击**：躲弹的同时射击目标位置 | 边躲边打 |
| **6** | **移动目标躲弹射击**：同 5，但目标是会移动的真实坦克 | 预判移动目标 |
| **7** | （可选）道具操作专项 | 道具运用 |
| **8** | **真实对局** | 全部整合 |

**前置**：预训练——**不渲染但保留完整游戏逻辑**（关的只有画面和 UI），
智能体随机操作树，先学会合法操作。因为不渲染，速度会快得多。

**课程设计的三个优点**：
1. 每阶段只引入一个新变量 → 出问题能定位
2. 前面阶段的技能被后面复用
3. 阶段 1、2 完全不需要对手 → 训练极快

## 九、明确不做的事（避免重走）

| 不做 | 原因 |
|------|------|
| 让智能体输出"评分"，算法拿分去搜最优路径 | 会导致**越深的路线分数越高**，必然偏向深路线 |
| 把对手预判塞进 rollout | 对手不确定且不可分离，偏离即全量作废 |
| 用"数对手存活操作个数"做进攻节奏 | 那是对时间余量的离散采样，是感知层且贵 9 倍 |
| 让 A 管预测时长 | 预测时长只为省性能，**没必要为省性能给它加学习负担** |
| 射击用"按下/松开事件列表" | 格式太硬（必须交替） |
| 射击用"逐帧位" | 绝大多数帧不射击，稀疏表更省 |
| 一律重罚 | 会教出"什么都不做" |

## 十、第三轮审查的回应与定案（2026-10-02）

> 子代理第三次审查提出了一批问题。以下逐条记录主人回应与最终定案。

### 10.1 定义缺口（全部定案）

#### ① "长一个节点" = **展开成一层**（定案）

主人：

> 「同样是长 9 个节点，每次长一个的话节点位置可以自由支配，节点利用率更高。
> 但是**一次性长一层的性能要比连长 9 轮单个节点的性能好很多**，
> 因为前者**只需要选择在哪里长、操作多久**就行了，直接就长 9 个。
> 而后者还得选长哪种操作，长 1 个节点比长 1 层节点甚至更费性能。
> 所以或许应该考虑一次长一层吗？**应该是。**」

所以：

```
A 说"在节点 X 长"
   ↓
程序把 X 展开成 9 个子节点（对应 9 种移动操作）
   ↓
A 不需要指定用哪种操作 —— 9 个一起长
```

**收益**：A 的输出维度恒定（就是"长哪些节点"），不用挑操作。

#### ② A 和 B **都是每帧调用**（定案）

主人：

> 「**绝对都是每帧调用**，因为环境每帧都变，**即使选的路不变，它也得重新选一次完全一样的**。」

#### ③ 操作时长归 **A**（定案，且修正了 §1 的分配）

★ 主人发现的关键约束：

> 「**只有全新长出的节点才需要给操作时长。老的操作时长不能动，
> 一动树就塌**，因为**树的节点本身就是在上一个节点操作结束后执行的。**」

这条直接否掉了"B 管段长"：

```
节点 = 上一个节点执行完之后才开始的
   → 老节点的时长一动，它后面所有节点的绝对时间全部错位
   → 树塌

所以：时长必须在【新建节点时】一次性分配
   → 这是 A 的活（和"在哪长"强绑定）
```

主人对"给 A 还是给 B"的判断：

> 「给 A 的话有点让 A 玩游戏的感觉，它可能不够擅长；给 B 的话好像也不是很贴合它的工作，
> 难道需要再来一个专门给操作时长的智能体？
> **我觉得还是应该给 A，因为操作时长和建立节点是强绑定的，有新节点就有新时长，不论新节点在哪。**」

**所以 A 的完整职责 = 在哪长 + 新节点的操作时长。**

**B 的职责 = 选哪条路 + 射击表。**（段长不再是 B 的）

#### ④ "0 帧自杀"的语义（待实现时钉死）

主人：

> 「我不确定，反正就指的就是**最快速度的自杀，坦克炮管紧贴着墙壁发射**。」

→ 实现时定义为：**子弹射出瞬间就命中自己**（炮管贴墙发射、立刻反弹回来）。
**不能实现成"段帧号 0"**，否则把自爆安排在第 1 帧就绕过了不变量三。

#### ⑤ 失效节点 **不给智能体看**（定案）

主人：

> 「何为失效？坍缩掉的？**失效的我觉得智能体根本就不需要能看见它，也没必要让它能被选。**」

→ 观测里**不出现**失效节点；语义校验里"选到失效节点"这个类别**不存在**。

### 10.2 归因问题（定案）

子代理指出：A 没长出某个动作 → B 被迫在残缺集合里选 → B 挨罚，是归因错误。

主人回应：

> 「那有什么办法呢？**我们无法检测某次死了到底是 A 的锅还是 B 的锅，
> 只能一起扣分**，让 A 尽可能长出好的，B 尽可能在 A 长的里选出最好的。」

**定案：不做信用分配，联合惩罚。** 接受这是不完美但唯一可行的做法。

### 10.3 段长与末态的矛盾（定案：不可达问题）

子代理说 B 要管段长但观测只有全长摘要。主人指出这本身是**循环依赖**：

> 「你这本身就是个**不可达问题**，因为**要想让智能体知道操作末态的精确物理状态，
> 就得提前让树知道智能体要操作多久；要想有操作时长必须有选中的路；
> 要想选路就必须知道操作完的物理状态。这不就循环了吗，自相矛盾。**
> 所以只能是**让它自己感知操作完会怎么样**，我们给它的辅助工具已经够多了，
> **它自己感知这一点不是多大的事**。」

**这正好解释了为什么时长必须由 A 在新建节点时分配**（见 10.1 ③）：
A 分配时长时，"操作完会怎样"由树的模拟算出来，不需要智能体自己推。

### 10.4 段内盲飞（定案：接受）

子代理说 B 选的 12 帧路线，对手第 3 帧开火、第 9 帧命中，段内没法重规划。

主人回应：

> 「**对手开火那我们树也没有任何办法啊，那是薛定谔的子弹，不是固定的子弹，
> 我们没法确定**，我们能做的只有**在新子弹登场后立即刷新**。
> **智能体的工作就是预判对手开火，尽可能不被打死。**」

**定案**：段内盲飞是物理限制，不是设计缺陷。
树管"已知子弹"，智能体管"预判对手"。

### 10.5 关于"不预测对手"的准确表述（修正措辞）

主人：

> 「**不是不预测对手，是我们根本就无法做到预测。**
> 只能**由智能体去预测**，而且那也**只是种感知，并不是确定的**。」

## 十一、B 的观测基准 = 「本段操作结束时」

### 11.1 主人定案

> 「注意，**如果操作时长由 A 给出，那么 B 就能得到操作完的状态了**，
> 而且**它看的也应该是操作完的状态**，而不是预测时长末尾的状态，
> 因为**看那个预测时长末尾的状态没有任何作用，反正也根本不会有操作到那里的情况**。」

### 11.2 为什么这条很重要

```
树的 rollout 一直跑到【预测时长末尾】（75 帧）——那是为了评估
但 B 只需要知道：【这一段走完之后】世界是什么样
```

**两者的区别**：

| | 预测时长末尾（75 帧） | 本段操作结束时（段长帧） |
|---|---|---|
| 谁用 | 树的评估（判断这条路通往哪里） | **B 的观测** |
| 有意义吗 | 是"评估用的推演" | **是"B 下一步决策的真实起点"** |
| 为什么 | — | 因为**根本不会有操作到 75 帧的时候**——下次决策早就在段末发生了 |

**所以**：给 B 的节点摘要里，**位姿/子弹等状态一律取"本段末"**，不是"75 帧末"。

### 11.3 这条把 §10 的一个循环依赖解开了

之前子代理指出："B 要管段长，但观测只有全长摘要"——那确实是死循环，因为：
要让智能体知道末态 → 得先知道时长 → 但时长要有选中的路 → 选路要知道末态。

**现在解开了**：

```
A 在【新建节点时】同时给出「在哪长」和「操作时长」
   ↓
树按这个时长把节点模拟出来
   ↓
B 拿到的就是【该时长末尾】的状态   ← 不再循环
```

**顺序上是自洽的**：时长由 A 在建节点时定，B 继承已建好的结果。

## 十三、A/B 互通 · 性能闸门 · 编码修正（2026-10-02 定案）

### 13.1 ★ A/B 互通：双份记忆 + 程序直传"干了什么"

#### 记忆部分（主人方案）

> 「我觉得**必须得有一些 AB 互通数据的渠道**，不然两个东西独立工作很容易出问题。
> 我想了一个，就是**双份记忆，但是双方都能看到，自己只能改自己的记忆**。」

```
记忆区 A：只有 A 能写，A 和 B 都能读
记忆区 B：只有 B 能写，A 和 B 都能读
```

**它有个天然的时序性质**（这是它能成立的原因）：

```
第 N 帧：
   A 先跑 → 读 B 的记忆（上一帧写的）、写自己的记忆
   B 后跑 → 读 A 的记忆（这一帧刚写的）、写自己的记忆
   ↓
B 能立刻看到 A 这一帧的意图
A 只能看到 B 上一帧的意图
```

**所以这是"跨帧通信"，不是同步通信——没有竞争条件。**
B 比 A 多知道一帧，符合分工（A 布局、B 执行）。

#### 事实部分（主人修正）

主人指出：

> 「你的补充那个**不是智能体行为，而是它干了什么**，
> **可以直接程序处理，传递给下一个智能体**。」

所以**"A 实际做了什么"不该由 A 输出，而是程序直接传给 B**：

```
A 说：在节点 X、Y、Z 长
程序执行：X 成功、Y 因为真死被拒、Z 因为预算被拒
   ↓
程序把【这个事实】直接塞进 B 的输入
   （属于 §12 的"第一类数据"，不是智能体的输出）
```

**区分**：

| | 属于 |
|---|------|
| "我想在哪长" | **智能体的输出**（A 的职责） |
| "实际长成了什么样" | **程序的事实**，直接传 |

### 13.2 性能闸门：数量上限 + 到顶就不调用生长

主人：

> 「性能闸门的话，可以参考一下现在的思路，**可以加数量上限，
> 长到数量上限后，不再调用长节点的智能体**。」

```
节点数 < 上限  → 正常调用 A
节点数 ≥ 上限  → 【不调用 A】，只调用 B（让树继续被使用）
```

**为什么这样可以**：树到顶之后不再长大，但已有的节点仍然是有效的决策依据，
B 照样能在里面选路。**停止生长不等于停止工作。**

### 13.3 编码修正：弹种与操作类型直接用数字

上一版我建议"弹种/操作类型用嵌入向量"，**主人否决了**：

> 「我觉得**弹种和操作类型就应该用简单的数字**，我不认为网络无法区分。」

**按此定案**：弹种、操作类型等类别量**直接用整数**。

### 13.4 时间上限与节点上限（主人定案）

> 「目前节点是有双重上限的，一个时间一个数量，都比你这多。
> 我倾向于**节点数量不限或者几乎不限，时间限制 10 秒**，
> 也就是**游戏中生命周期最长的子弹**。」

| 维度 | 上限 |
|------|------|
| **时间** | **10 秒**（子弹最长寿命——之后世界就"清空"了，再远没有意义） |
| **节点数** | 几乎不限（但配合 §13.2 的数量闸门） |

### 13.5 失效节点：停用而不是剪掉（主人方案）

主人指出一个白剪问题：

> 「在新弹或者护盾更新树时，会剪掉那些**新致死后方的节点**。
> 但是**如果未来树再变了，那些节点就不一定致死了，就白剪了**。
> 我想到的就是**死亡以后的节点不剪，缓存着，但是暂时停用**。
> 几乎所有树操作都不会看这些停用的节点，除非树更新了，
> 导致原本死的节点重新活了，就**再把停用的启用**。
> 反正缓存一些节点也吃不了几个内存……而且**停用的节点在被坍缩掉后，
> 就是真的报废了，不会一直占用**。」

**采纳，并补一条让恢复变便宜的做法**：

```
失效时，记下【失效原因】——因为哪颗子弹 / 哪次护盾变化
   ↓
树更新时，按原因批量恢复：
   那颗子弹自然消失了 → 它导致的失效全部恢复
   护盾状态变了       → 护盾导致的失效全部恢复
   ↓
不用逐节点重新扫描
```

**内存账**：节点就是几十个字段，几百个节点几十 KB ~ 几 MB。
而**坍缩后停用节点真正报废**——保证停用区不会无限增长。
