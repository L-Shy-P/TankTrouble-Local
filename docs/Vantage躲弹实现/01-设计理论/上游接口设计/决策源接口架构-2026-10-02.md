# 决策源接口架构（2026-10-02）

> 目的：把 `vantage_tree.js` 里的**判断**抽成可替换插槽，让规则版 / 果蝇版 / NN 版
> 换着插，而**树的结构一行不改**。
>
> 本文只定接口，不含实现。实现分 B1 / B2 两步（见 §9）。

---

## 1. 为什么切

现在树里所有判断都焊死在函数体里。例如 `pickBest`（`vantage_tree.js:4904`）：

```js
var cScore = c.subtreeBest + objectiveBonus(c, ...);   // ← 判断焊死在这
if (cScore > bScore) { best = c; }
```

要换成网络出的分，只能改这行——但没有地方"插"。

**切的目标**：把 `cScore` 这一行的来源变成可替换的，**调用者（树）不动**。

---

## 2. 核心原则

| 原则 | 说明 |
|---|---|
| **只出数字** | 插槽吃数据、吐数字。**禁止碰 `gameController`、禁止碰树的内部结构、禁止改 `inputState`** |
| **物理归物理，判断归判断** | 树继续跑 rollout/判死/粗筛；插槽只回答"这些结果各值多少分" |
| **缺省即回退** | 插槽不存在或抛异常 → 自动退回规则版，不中断对局 |
| **统一形式** | 全部是「给候选打分 → 执行层 argmax」，没有 one-hot、没有排名输出（主人 2026-10-02 定案） |

## 4. 接口契约

### 4.1 决策源对象

```js
var DecisionSource = {
    name: 'rule',                       // 'rule' | 'fly' | 'nn'，只用于日志/面板显示

    // —— D1 候选评分（B1 唯一要实现的）——
    //   ctx   : 上下文（见 4.2）
    //   rolls : rolloutNine 现有的物理结果数组（见 4.3），长度 = 9
    //   返回   : 同长度数组，元素必须是 rolls[i] 本身或其副本，且 totalScore 已填好
    scoreOps: function (ctx, rolls) { return rolls; },

    // —— 以下为 B2 预留，不实现时树用原规则 ——
    segFrames:  function (ctx, op) { return null; },   // 返回帧数；null = 用原规则
    growLeaf:   function (ctx, leaves) { return null; },// 返回选中的叶；null = 用原规则
    growLayers: function (ctx) { return null; },       // 返回层数；null = 用原规则
    boostLayers:function (ctx) { return null; },       // 返回补偿层数；null = 用原规则
    staleNodes: function (ctx, node, proj) { return null; } // 返回是否作废；null = 用原规则
};
```

**约定**：任何插槽返回 `null` / `undefined` / 抛异常 → 树回退到原规则。
这样"只实现一部分"也是合法的中间状态。

### 4.2 上下文 `ctx`（树侧构造，插槽只读）

```js
ctx = {
    tree:     <树对象>,          // ⚠️ 只读；插槽不得写入
    adapter:  <沙箱适配器>,       // ⚠️ 只读
    simState: <当前坦克状态>,     // {tank, tGlobal, ...}
    threats:  <子弹威胁数组>,     // VantageScoring.computeThreats 的输出
    ops:      <OPERATIONS>,      // 9 个操作，顺序即下标
    frames:   <EVAL_FRAMES>,     // 75
    cfg:      <treeScoringCfg(tree)>,
    slow:     <bool>             // 是否处于性能熔断（插槽应降低工作量）
};
```

### 4.3 `rolls` 元素结构（树要求的字段）

树后续只依赖这几个字段（`buildCandidate` 3869 / `applyRolloutScore` 2528 消费）：

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `totalScore` | number | ✅ | **唯一被决策消费的字段** |
| `perFrameScores` | number[] | ✅ | 逐帧净分，长度 = frames |
| `samples` | 数组 | ✅ | 逐帧位姿采样（渲染/粗筛复用） |
| `dead` | bool | ✅ | 是否死亡 |
| `deathFrame` | number | ✅ | 死亡帧（-1 = 未死） |
| `opIndex` / `opName` | number/string | ✅ | 与 OPERATIONS 对应 |
| `deathAuthority` | string | ⭕ | `'fused'` / `'rust-candidate'` / `'computed'` |

> **插槽的自由度边界**：果蝇版/NN 版**可以改 `totalScore`**，
> 但 `samples` / `dead` / `deathFrame` **必须来自树的物理模拟**——那是权威，不可覆盖。
> 也就是说：**网络决定"哪个好"，物理决定"会不会死"。**

### 4.4 执行层硬约束（插槽无权覆盖）

| 约束 | 位置 | 说明 |
|------|------|------|
| **红（fd≤1）绝对不选** | `isTerminalDead` 3931 + `pickBest` / `enforceNonRedPrefer` 4984 | 主人反复确认的不变量，不可学习 |
| 段长 ≤ `evaluatedFrames` | 段末调度 | 不能超出实际模拟范围 |
| 粗筛只许假阳不许假阴 | `threatCoarseBox` 2057 等 | `最终作废 = 几何粗盒 ∪ 插槽判定`（只能追加，不能免除） |
| 节点预算 | `canAddTreeNodes` 3635 | 性能闸门 |

## 7. 验证标准（"零回归"的定义）

**不是"胜率差不多"，是逐帧一致。**

```
同一批固定种子跑 N 局：
  切缝前记录：每一帧的 commitNode.opIndex 序列
  切缝后记录：同一序列
  要求：完全一致（包括 tick 数、节点数）
```

任何一处不一致 = 切口错了，回滚。

## 9. 实施步骤（与 §12.4 一致）

```
B0  四个基本操作的接口（生长 / 评分 / 回退 / 更新）
    · 规则版 = 现有逻辑原样搬进去，含全部补偿机制，先不动
    · 逐帧验证零回归（不是"胜率差不多"，是决策序列完全一致）
    · 切口只落在树内部调用这几个操作的地方，其它一律不碰

B1  把乙类补偿逐个卸掉，每卸一个跑一次基准
    · 顺带量出每个机制到底值多少胜率
    · 卸完还能保持强度的，说明它本来就没用

B2  果蝇 / 神经网络实现自己的评分
```

**为什么先做 B0 再做 B1**：B0 是纯搬运，零行为变化，可逐帧验证；
B1 每一步都改变行为，必须有 B0 建立的对照基线才能判断是变好还是变坏。

## 12. 参数面要不要接口化（2026-10-02 修订，主人定案）

### 12.1 先纠正上一版

上一版（已废弃）把树里全部 62 个可调项都列出来要接口化。
**主人指出这是过度设计**——那些可调项里的大部分，是在给"固定算法的 Vantage"打补丁，
不是树本身需要的东西。有了神经网络或果蝇之后，不再需要这么多复杂机制。

### 12.2 按"它在补什么"分三类

**甲类 · 树的骨架（保留）**

| 机制 | 作用 |
|------|------|
| 时间刻度 | 每帧多长、向前预测多少帧、视界多长、段长上下限 |
| 节点预算 | 最多允许多少节点、要不要限、每帧最多长几层 |
| 性能闸门 | 最多评估几颗子弹、每 tick 算几个操作、卡顿时优先保谁 |
| 几何口径 | 死亡按什么时长判、接触余量、危险半径 |

这些不是"决策"，是**资源的度量单位**。换什么决策源都要用。

**乙类 · 为规则算法的弱点而存在的补偿（该退役）**

| 机制 | 它在补什么 |
|------|-----------|
| 剪枝补偿、回退补偿、生长层数加成 | **规则评分会选错路** → 靠多长几层、多补几帧来救 |
| 杀戮场开关与权重 | 手工价值函数 ← 正是要换成网络的那部分 |
| 目标混合开关与比例 | 手工价值函数 |
| 车道压分 | 手工价值函数 |
| 空场懒惰 / 空场安全 | 手工价值函数 |
| 超限细化、持续细化、最小生长间隔、只算计划操作、深选开关 | **规则评分不够细** → 靠额外细化、改评分口径来救 |
| 弹簧绳相关 | 物理修复阶段的规避 |
| 段末软对齐容差、硬对齐容差、锚点最大偏移 | **规则预测会漂移** → 靠对齐与整树重建来救 |
| Rust 最小决策开关 | 规则版的实现细节 |

**规律**：凡是名字里带"补偿 / 加成 / 细化 / 对齐 / 回退"的，
本质都是**在弥补规则决策的偏差**。决策准了就不需要。

**丙类 · 正确性不变量（不是"机制"，不能和乙类一起砍）**

| 不变量 | 砍了会怎样 |
|--------|-----------|
| 红过滤：只走一步就会死，就绝不选它 | 主人反复确认过的死规矩 |
| 粗筛只许假阳不许假阴 | 一旦假阴，就会跳过本该做的死亡重扫 |
| 新弹增量失效 | "绿节点死亡"那场事故就是这么来的 |
| 融合世界权威判死 | 上面三条的最终兜底 |

**这四条不是补偿，是让树说真话的东西。**
网络可以决定"选哪个"，**不能决定"死了不算死"**。

### 12.3 最终接口：智能体直接接管树的操作（2026-10-02 主人定案）

#### 为什么不能"评分 + 算法找最高分"

主人指出的关键问题：

> 不能让智能体给节点评分，然后我们用算法直接找分最高的路径，
> **因为那样子会导致更深的路线分数更高，很容易选到更深的路线。**

现有树里那套"子树最优 = 本段分 + 取(延伸, 基线)的最大值"的递归写法，
**存在的唯一理由就是压住"越深分越高"**。而它一直很脆
（历史上为它反复改过好几版口径）。

**让智能体直接选路，这个问题从根上消失**——不需要分数沿路径累积，就不存在累积偏差。

#### 最终形态

> 分数都在智能体"脑子里"。树最多只需要**缓存它的思维结果**（数据类型不确定，
> 见下面的"私有数据槽"）。

**树 → 智能体（只读）**

| 提供什么 | 说明 |
|---------|------|
| 节点集合 | 每个节点的来路操作、父节点、段长、模拟位姿轨迹、有效/失效标记、真死标记 |
| 当前物理状态 | 坦克、子弹、迷宫——与现有树看到的一致 |
| 私有数据槽 | 智能体上一帧自己挂上去的东西，原样还给它 |

**智能体 → 树（只有两件事）**

| 输出 | 说明 |
|------|------|
| **在哪长节点、长几个** | **不限于叶节点**——想在哪长就在哪长 |
| **选哪条路** | **直接给，不是打分** |

**执行层强制（只有两条）**

1. **禁止在真死的节点上生长**（只走一步就会死的节点不能当生长父节点）
2. **有非真死的路线时，不选真死路线**

> 逻辑异常简单。除此之外智能体想干什么都行。

#### "回退"不再是独立操作

主人指出：回退是**为"走错路时及时止损"而设的补丁，本身机制不够完善**。

在最终形态里它被完全吸收：

- 想换个地方长 → 直接在别处长
- 想换条路 → 直接选别的
- **不需要"限制只有真死才回退"**——智能体自己知道是不是选错了

所以接口里**没有回退这一项**。

### 12.4 与现有机制的关系（★ 修正口径）

> ⚠️ **不是删掉，是做成可拆卸模块。**
> **选择纯算法模式时，那些机制一点不变，行为与现在完全一致。**
> 我们做的只是**智能体接口**。（主人 2026-10-02 明确）

结构分三层：

```
┌─ 树核心（不可拆卸）──────────────────────────────┐
│  · 节点结构与父子关系                            │
│  · 前向模拟（rollout）                           │
│  · 权威判死（融合世界）                          │
│  · 新弹增量失效                                  │
│  · 节点预算 / 性能闸门                           │
│  · 两条不变量（见 12.3）                          │
└──────────────────────────────────────────────────┘
              ↑ 挂在核心上的可拆卸模块 ↓

┌─ 可拆卸模块（默认【全部装载】= 纯算法模式）────────┐
│  · 评分模块（含杀戮场 / 目标混合 / 车道压分…）     │
│  · 选路模块（取最高分 + 子树最优递归折算）         │
│  · 回退模块                                      │
│  · 补偿模块（剪枝补偿 / 回退补偿 / 生长加成）      │
│  · 生长模块（叶优先、固定层数）                   │
│  · 段长模块                                      │
└──────────────────────────────────────────────────┘

┌─ 智能体模式 ─────────────────────────────────────┐
│  · 卸载上述模块                                  │
│  · 由智能体直接提供「在哪长节点、长几个」和「选哪条路」│
└──────────────────────────────────────────────────┘
```

**所以每一条现有机制都要保留成可独立开关的模块**——纯算法模式下开关全开、
行为逐帧不变；智能体模式下可以整组关掉，也可以只关一部分让它接管。

### 12.5 实施顺序（★ 修正）

```
B0  两条不变量显式化
    └─ 现状里它们隐含在选路逻辑中，要提出来单独成条、并前移到生长阶段

B1  把现有机制逐个包成可拆卸模块
    └─ ★ 默认全部装载，逐帧验证零回归
    └─ 这一步【不改变任何行为】，只是把开关位置造出来

B2  智能体接口
    └─ 允许卸载任意模块 + 由智能体提供「在哪长」「选哪条路」
    └─ 规则版填进去，仍然零回归

B3  果蝇 / 神经网络实现这两件事
```

**B1 是纯重构，B2 才是新功能。** 分开做，每步都能逐帧验证。

### 12.6 一个副产品

模块化之后可以做**单模块消融实验**：

```
关掉「回退补偿」→ 跑基准 → 强度掉了多少？
关掉「杀戮场」  → 跑基准 → 掉了多少？
```

**这是第一次能算清楚每个机制到底值多少胜率。** 以前它们缠在一起，没法单独评估。
而且这个实验**不改任何默认行为**——只是开关拨一下。

## 13. 两个适配器（神经网络 / 果蝇大脑）

> 主人 2026-10-02 提醒：**"智能体"指的是神经网络或果蝇大脑，两者要分别做适配。**
> 它们共用同一个树侧接口，但内部形状差别很大。

### 13.1 共同点

两者都要**实现同一组树侧输出**：

```
① 在哪长节点、长几个
② 选哪条路
```

### 13.2 差异

| | 神经网络 | 果蝇大脑 |
|---|---|---|
| 中间是什么 | 可训练的网络 | **冻结的 LIF**（3508 神经元 / 11.5 万条边） |
| 能不能吃节点列表 | ✅ 可以（变长节点集合 → 定长张量编码） | ❌ 只能吃固定维度的注入电流 |
| 输出形状 | ✅ 可直接输出"选哪个节点" | ⚠️ 只有 82 个连续发放率，**与节点数量无关** |
| 需要几段可学模块 | 1 段（整个网络） | **2 段**：编码器 + 读出头，中间冻结 |
| 训练方式 | 端到端梯度 | 两端可学、中间不动，中间那层的语义要另外定 |

### 13.3 果蝇适配器的关键难点

**82 个连续通道 ↔ 动态数量的树节点**，这个映射不是固定的。
所以必须有一个**解释规则**，把 82 维发放率翻译成树操作：

```
物理状态 ──编码器(可学)──→ 注入电流 ──冻结LIF──→ 82个下行发放率 ──读出头(可学)──→ 树操作
```

解释规则可以有好几种做法（**这部分是要设计、要学的**）：

| 做法 | 说明 |
|------|------|
| 分组解释 | 把 82 维分成几组，分别解释为"往哪长"和"往哪走"的倾向 |
| 特征 + 小网络 | 把 82 维当特征，接一个小网络输出树操作 |
| 再经一层 LIF | 让下游也用同一套脉冲机制 |

**注意**：编码器和读出头都是"接法"，都属于要学的东西，
而中间的连接组是**冻结**的——这正是最早那个假说的形式。

### 13.4 神经网络适配器相对直接

```
节点集合 + 物理状态 ──编码──→ 定长张量 ──策略头──→ 树操作
```

变长的节点集合用固定特征 + 补齐（padding）压成定长张量即可
（这与既有的外接 AI 观测构造是同一套思路，见《外接AI接入方案-Hybrid》）。

### 13.5 ★ 一个必须分清的区别

主人指出"不能让算法用分数找最高分，会偏向深路线"。这里要分清两件事：

| | 能不能做 |
|---|---|
| ❌ **算法沿路径累加分数、再取最大** | **不行**——越深累积越多，必然偏向深路线 |
| ✅ **智能体内部对当帧候选打分、自己取最大** | **可以**——每个候选独立评估，不跨深度累积 |

所以：**打分可以存在，但只能存在于智能体内部**，而且它的作用域是"当前这一批候选"，
不能变成"算法拿它去做全局路径搜索"。

### 13.6 对实施顺序的影响

```
B0  两条不变量显式化
B1  现有机制包成可拆卸模块（默认全开，零回归）
B2  树侧接口（在哪长 / 选哪条路）+ 规则版填充
B3a 神经网络适配器
B3b 果蝇适配器（多一层：82 维 → 树操作的解释规则）
```

两者可以并行，但**神经网络那条要等训练环境**（既有卡点），
果蝇那条可以先做（数据与引擎已就绪）。

## 15. 果蝇接入方案（研究）

### 15.1 核心矛盾

| | 形状 |
|---|---|
| 果蝇能给 | **82 个连续发放率**（运动指令：往哪走、使劲多大） |
| 树要的是 | **一个节点 id**（离散，且数量每帧都在变） |

**中间必须有一层"解译"**，这是接入的全部难点所在。

### 15.2 三个要解决的问题

1. **编码**：物理状态 → 注入电流。注到哪些神经元？
2. **解译**：82 维 → 树操作。节点数动态、通道数固定。
3. **学习**：编码器与解译器都要学，中间的连接组冻结。

### 15.3 方案 A 被否决（主人 2026-10-02）

上一版方案 A（82 维 → 2D 运动指令 → 选子节点）**不行**，主人指出：

> 你这 A 就不行，果蝇只做了个选路，其他树操作一点没干。

具体问题两条：

1. **信息损失巨大**：82 个通道压成 2 个数，果蝇几乎全部输出被丢掉
2. **只驱动了一个操作**：树的三个操作（在哪长 / 长几次 / 选哪条路）只驱动了最后一个

根因是**假设果蝇要"直接输出选哪个"**——但果蝇只有固定 82 维，
而树的节点数每帧都在变，这个映射根本不存在。

### 15.4 ★ 关键认识：树的决策空间是【固定维度】的

主人 2026-10-02 指出：**如果果蝇只干了个评分或类似的事，那就是不完善的，
没有用到这么丰富的接口的价值，它就应该操控整个树。**

上一版"输出一组权重、给候选节点打分"**仍然是"另一种评分方式"**——
算法还是主角，果蝇只贡献了一个打分函数。已否决。

**关键认识**：`OPERATIONS` 恒为 9 个，而树的每一层天然就是这 9 个分支，
所以树的每一个决策都是**固定维度**的：

| 决策 | 候选集 | 维度 |
|------|--------|------|
| 选哪条路 | commit 节点的 9 个子节点 | **9 选 1** |
| 在哪长 | commit 节点自己 + 它的 9 个子节点 | **10 选 1** |
| 生长层数 | 0 ~ 8 | 标量 |
| 段长 | 若干帧 | 标量 |
| 回退深度 | 退几层祖先 | 标量 |

**"在哪长"限在 commit 节点及其子节点**，就覆盖了"不必长在叶上"这个要求
（可以在 commit 节点本身长，而不是只能在叶子长）。

### 15.5 ★ 果蝇输出的是【指令】，不是【评分】

```
82 个下行神经元发放率
   ↓ 映射层（先手写，后训练）
   ├─ 10 个值 → 在哪长     → 取最大
   ├─  9 个值 → 选哪条路   → 取最大
   ├─  1 个值 → 生长层数   （0~8）
   ├─  1 个值 → 段长       （几帧）
   └─  1 个值 → 回退深度   （退几层祖先）
   ────────────────────────
   共 22 个输出，全部固定维度
```

**和"评分方式"的区别**：

| | 评分方式（已否决） | 指令方式（本方案） |
|---|---|---|
| 果蝇产出 | 一组打分 | **具体的动作指令** |
| 主角 | 算法（拿分去搜） | **果蝇** |
| 树的角色 | 搜索器 | **执行器** |

### 15.6 每个指令怎么被树消费

| 指令 | 树怎么执行 | 现有对应 |
|------|-----------|---------|
| 选哪条路 | 直接作为 `select` 传给接口 | `pickBest` / `pickBestChildByRolloutTotal` |
| 在哪长 | 直接作为 `growAt` 的父节点 | `pickGrowLeaf` |
| 生长层数 | 作为 `growTimes` | `growLayersPerTick` |
| 段长 | 覆盖本段计划帧数 | `segmentEndDue` / `tEndSec` |
| 回退深度 | 退到第 N 层祖先，作废其下路线 | `pickBestChildByRolloutTotal` 重选 + `invalidateDescendants` |

**回退**这一条是本方案新增的：本来回退是"走错路时的补丁"，
现在变成**果蝇可以直接下的指令**（退几层）——正合主人说的"回退也是不完善的机制"。

### 15.7 映射层：先手写，后训练

| 阶段 | 做法 |
|------|------|
| 第一版 | 手写线性映射（82 → 22），先把链路跑通 |
| 第二版 | 把这层变成可学参数，用胜负信号训练 |
| 始终 | 中间的连接组**冻结** |

**编码器（物理状态 → 注入电流）同理**：先手写，后训练。

### 15.8 已知的坑

| 坑 | 说明 |
|---|---|
| 82 个通道大部分是 0 | 实测只有 17~29 个通道有信号，映射要容忍大量零 |
| 输出尺度要标定 | 22 个输出里既有"9 选 1"又有"层数 0~8"，量纲不同，要分别标定 |
| 左右未必真对称 | 连接组里"同名"的左右神经元功能不一定对称，需实测 |
| 池化时长 | 发放率是窗口统计量，窗口长短直接决定反应快慢 |
| **真死不可覆盖** | 果蝇可以下任何指令，但**真死判定必须由树的物理模拟说了算** |
| 回退深度的安全边界 | 退得太多会把树退空，要夹紧 |

### 15.9 接入步骤

```
1. 手写编码器：子弹几何 → 8 通道 → 注入电流
2. 写映射层：82 维 → 22 个指令（先手写）
3. 接成 FlyAgent（decide 返回 growAt / growTimes / select / segFrames / retreat）
4. 对比：果蝇版 vs 规则版 vs 随机版
```

## 16. 射击接口 · 智能体观测范围 · 第三条不变量（2026-10-02 主人定案）

### 16.1 射击是致命遗漏

主人指出：**树现在根本没有射击接口，不管怎么搞，最后出来的都是个躲弹机器人。**

射击的结构和移动**完全不同**：

| | 移动 | 射击 |
|---|---|---|
| 形式 | 9 个操作选一个 | **逐帧的二值状态** |
| 段内 | 整段恒定 | **可在任意位置切换** |
| 与对方 | — | **与移动互相独立** |

所以射击**不进树的节点结构**，是一条独立通路：

```
树       → 移动输入（前 / 后 / 左 / 右）
智能体   → 射击输入（每帧一个值）
               ↓ 合并
          最终输入
```

### 16.2 边沿约束由执行层负责

主人的两条约束：

> 松开时无法再松开，射击（键按下）时无法再射击。

所以智能体输出的是**"这一帧想不想开火"**，
执行层拿它和上一帧比较，**只在变化时产生动作**。

**这条逻辑不交给智能体**——否则它得自己记住上一帧状态，是无谓负担。

### 16.3 ★ 智能体观测范围（纠正上一版）

上一版说"只看当前一层"是**错的**。主人指出：

> 智能体怎么可能只看一层，不然如何对树进行管理？

**智能体必须看到整棵树。** 数据量的问题不在"发多少个节点"，
而在**每个节点发什么**——不是每节点 75 帧原始轨迹，而是**每节点一个摘要**：

| 字段 | 个数 |
|------|------|
| 编号 / 父节点 / 来路操作 | 3 |
| 段长 / 深度 / 到根累计时间 | 3 |
| 末态位姿（相对当前位置：位移 x、y + 朝向变化） | 3 |
| 死亡帧（-1 = 活满） | 1 |
| 有效/失效标记 / 有没有子节点 | 2 |
| **每节点合计** | **≈12** |

节点上限几百个 → 总输入**几千个数**，属于可处理量级
（参照：Hybrid 的观测是 1028 个数）。

**结论**：不是"让它少看"，是**把每帧的原始轨迹压成摘要**——原始轨迹留在树内部。

### 16.4 ★ 第三条不变量：自杀子弹

主人定案：

> 只需要在沙箱模拟这个子弹射出后的结果就行了，如果被自己子弹打死了，绝对不选。
> 如果受自己子弹影响死了，看情况决定。

```
每个候选的模拟里，额外模拟"如果开火会射出的那颗弹"
   ↓
得到"被自己子弹打死的帧"
   ├─ ≤ 1（真死） → 【绝对不选】（有别的可选时）
   └─ 只是"受它影响而死" → 交给智能体权衡
```

**与已有两条不变量是同一模式**：

| # | 不变量 |
|---|--------|
| 一 | 真死的节点不能当生长父节点 |
| 二 | 有非真死候选时，不选真死路线 |
| **三** | **被自己射出的子弹打死的候选，绝不选** |

统一口径：**"真死"不论凶手是谁**——敌人的弹、自己的弹、反弹回来的，
一视同仁。

而"受自己子弹影响"（被迫走位、被逼进死角）**不算硬拒**——
那本来就是要智能体去权衡的事。

### 16.5 遗漏清单（审查结果）

| 项 | 判断 |
|----|------|
| **射击** | ✅ 必须补（本节） |
| **自杀子弹** | ✅ 升为不变量三 |
| **智能体观测范围** | ✅ 更正为"整棵树 + 每节点摘要" |
| 武器切换 | 游戏里武器是**排队自动切换**的，暂不需要接口 |
| 目标选择 | 1v1 不需要；多人局再议 |
| 每帧算力预算 | 可作为智能体的一个输出，也可固定 |

### 16.6 还需要主人确认的一点

射击通路是**每帧**问智能体一次，还是与树的段同步（段内不重新问）？

这决定智能体被调用的频率，也决定"射击输入"是逐帧独立还是跟着段走。

## 17. 惩罚项 · 思维缓存的正确形态（2026-10-02 主人定案）

### 17.1 惩罚项（共四条）

| # | 惩罚 | 性质 |
|---|------|------|
| 1 | 已经按下射击键却再次尝试按下 | 动作无效 |
| 2 | 没子弹却尝试射击 | 动作无效 |
| 3 | **射击在沙箱里导致死亡** | 动作有效但后果坏 |
| 4 | （沿用）被自己射出的子弹直接打死 → **绝对不选** | 硬拒，见 §16.4 |

**第 1、2 条**：执行层仍然要忽略非法输入（否则游戏会崩），
但**智能体要挨罚**。这是标准做法——**动作无效 + 罚分**，
而不是把约束藏起来不让它知道。

**第 3 条**：沙箱里模拟出"这一枪导致死亡"就给惩罚信号，
比 §16.4 的硬拒范围更广（硬拒只挡"直接被自己子弹打死"，
惩罚覆盖"因这一枪而死"的各种情形）。

### 17.2 ★ 纠正：思维缓存不能镜像物理缓存

上一版（已废弃）说"思维结果的缓存应当镜像物理缓存的生命周期"。**错了。**

主人指出：

> 不是的，只有固定的弹道的未来才是固定的。而智能体的思维缓存肯定会变，
> 比如没预判到对手。

差别在哪：

| | 为什么它**能**缓存 |
|---|---|
| **物理缓存** | 弹道是**确定的**——出了膛，未来就定死了 |
| **思维缓存** | ❌ 不成立——**对手不确定**。智能体可能没预判到对手，它的判断就变了 |

所以物理缓存的失效规则（新弹相交 / 段末重锚 / 对齐超差 / 剪枝）
**不能直接搬到思维缓存上**。

### 17.3 ★ 解法：非线性缓存（距离衰减）

主人给的方案：

> 但貌似可以做非线性缓存，离现在越远，预判中的可能性越低，
> 思维价值越低，所以缓存的大小就要越小。

展开成可执行的形态：

| 距离（帧） | 缓存策略 |
|-----------|---------|
| 0 ~ 15（近） | **全精度**，可以每帧更新 |
| 15 ~ 40（中） | 中等精度，只在物理缓存失效时更新 |
| 40 ~ 75（远） | 低精度（降维 / 量化存储），或只在被访问时现算 |
| > 75（超出视界） | **不存** |

**为什么这样合理**——不只是"省空间"，而是**远处的评估本来就不值得精算**：

- 越远的节点，到达它时**真实状态早已与模拟起点不同**
- 树会重锚、会重选路，那个节点的评估**大概率会被真实信息覆盖**
- 所以**精算它是在浪费算力**

**这是个通用策略**：近处精算、远处粗算。树的物理模拟其实已经在这么做了
（粗筛先、精算后），思维缓存只是把同一原则用在"思考"上。

### 17.4 推论：也许不需要"缓存格式"这个设计

| 智能体评估成本 | 做法 |
|---------------|------|
| 便宜（小网络，几十微秒） | **不缓存**，需要时重算 |
| 昂贵 | 按 §17.3 的非线性方案缓存 |

**先测一次评估要多久**。不贵的话，这件事根本不存在，
也就不用设计任何缓存格式。

### 17.5 若要缓存，接口应当是不透明的

两种智能体的"思维状态"形态完全不同：

| 智能体 | 它的"思维状态"是什么 |
|--------|-------------------|
| 神经网络 | 中间层激活 / 它对每个节点的估值。形状由网络定 |
| 果蝇 | 那 82 个发放率本身就是它的状态，但它是**每帧变化的**，不是每节点一份 |

所以缓存接口必须做成**不透明的**：

```
树   →  智能体："这个节点失效了，通知你一下"
智能体 →  树  ："我存了什么、什么时候用，我自己决定"
```

树不解释缓存的内容，只负责发失效通知。

## 18. 非法操作全景与惩罚设计（2026-10-02）

### 18.0 三种处理方式，别混为一谈

| 方式 | 什么时候用 | 树的行为 |
|------|-----------|---------|
| **拒绝** | 动作会破坏树的结构完整性 | 忽略，不执行 |
| **夹紧** | 数值越界 | 收到合法范围，照常执行 |
| **罚分** | 给智能体的训练信号 | 前两者都可以同时罚 |

**原则**：执行层必须保证"无论智能体多离谱，树和游戏都不崩"；
同时**智能体必须知道自己错了**（挨罚），不能把约束藏起来。

### 18.1 ~~公平性前提~~（已作废）

上一版写了"要区分智能体的错和树自己的变化"。**主人指出这个前提不存在**：

> 那个"上一帧"问题根本不存在，不可能会有它看着过期的数据做决断的情况，
> 因为每一帧都是先更新完数据再调用智能体的。它看到的永远是最新版。

**调用时序保证了智能体永远看到最新状态**，所以引用不到已消失的节点
只可能是它自己编的 → **一律罚，不需要区分。**

### 18.2 逐操作清单

#### ① 在哪长节点

| 非法情况 | 处理 | 罚 |
|---------|------|----|
| id 不存在（且不在上次观测集里） | 拒绝 | **重罚** |
| id 不存在（但在上次观测集里） | 拒绝 | 不罚 | 见 §18.1 |
| 指定的节点是真死（走一步就死） | 拒绝 | **重罚** | 不变量一 |
| 指定的节点已失效 | 拒绝 | 不罚 | 树自己标的 |
| 指定的节点已耗尽（9 个候选全死） | 拒绝 | 轻罚 |
| 指定的节点**已经长满 9 个子节点** | 拒绝 | 轻罚 |
| 一次给了多个节点，部分非法 | 合法的照做，非法的拒绝 | 按条计 |
| 生长会超出节点预算 | 拒绝 | 不罚 | 资源限制不是它的错 |

#### ② 长几次

| 非法情况 | 处理 | 罚 |
|---------|------|----|
| ≤ 0 | 夹紧到 1 | 轻罚 |
| 超过单帧上限（8） | 夹紧到 8 | 轻罚 |
| 超过节点预算剩余 | 夹紧到剩余额度 | 不罚 |

#### ③ 选哪条路

| 非法情况 | 处理 | 罚 |
|---------|------|----|
| id 不存在（不在上次观测集里） | 拒绝 | **重罚** |
| id 不存在（在上次观测集里） | 拒绝 | 不罚 |
| **跨层选择**：所选节点不是当前决策点的候选 | 拒绝 | **重罚** | 这是结构错误 |
| 所选节点是真死 | 拒绝 | **重罚** | 不变量二 |
| 所选节点已失效 / 已耗尽 | 拒绝 | 不罚 |

#### ④ 段长

| 非法情况 | 处理 | 罚 |
|---------|------|----|
| ≤ 0 | 夹紧到 1 帧 | 轻罚 |
| 超过可模拟范围（超出实际模拟的帧数） | 夹紧 | 轻罚 |
| 超过视界 | 夹紧 | 轻罚 |

#### ⑤ 射击

| 非法情况 | 处理 | 罚 |
|---------|------|----|
| 已经按下，却再次尝试按下 | 忽略（保持按下） | **罚** |
| 已经松开，却再次尝试松开 | 忽略（保持松开） | **罚** |
| 没子弹却尝试射击 | 忽略 | **罚** |
| 武器冷却/蓄力中尝试射击 | 忽略 | 轻罚 |
| 指定的射击帧超出当前段范围 | 夹紧到段内 | 轻罚 |
| **射击在沙箱里导致死亡** | 照做，但记录 | **重罚** | §17.1 第 3 条 |

### 18.3 罚分分级

| 级别 | 适用范围 | 理由 |
|------|---------|------|
| **重罚** | 结构性非法：编造 id、跨层选择、在真死节点生长、选真死路线、射击致死 | 违反了不变量或树的本质约束 |
| **中罚** | 动作无效：重复按/松射击键、没子弹射击 | 没有违反结构，但动作毫无意义 |
| **轻罚** | 数值越界：层数、段长、射击帧 | 夹紧后照常执行，只是"手抖" |

**不罚**：树自己的变化导致引用失效（§18.1）、资源限制导致的拒绝。

### 18.4 为什么要分级而不是一律重罚

一律重罚会让智能体**学会"什么都不做"**——因为不动就不会违规。
分级之后：

- 结构性错误重罚 → 很快学会不编造、不跨层
- 数值越界轻罚 → 不会因为"层数给大了 1"就被吓得不敢生长

**这是训练能不能收敛的关键细节之一。**

## 19. 修正与预训练方案（2026-10-02 主人定案）

### 19.1 "长几次"不是独立输出（修正 §18.2 ②）

上一版把"长几次"当成一个标量输出。**主人指出它不存在**：

> 长节点不会出现小于 0 的情况，因为只需让它输出长的节点的配置就行了，
> 不需要额外备注几个。极端情况就是它啥都没输出，0 个节点，不会为负数。

所以：

| 旧 | 新 |
|----|----|
| 输出「在哪长」+「长几次」 | **只输出「在哪些节点长」的配置** |
| 长几次 = 一个标量，可能越界 | **长几次 = 输出的节点数**，不可能为负 |

**极端情况**：啥都不输出 → 0 个节点 → 合法。

**§18.2 ② 那张表整张作废。**

### 19.2 射击致死：告知，但不惩罚（修正 §17.1 第 3 条）

主人定案：

> 射击致死这个或许不一定要惩罚，但是必须让智能体知道致死了。
> 因为我想到，有些极端情况下，几乎已经快输了，只能用这种射击来换取同归于尽，
> 不应该扣分。智能体知道射击会致死，自然就会避着。这是为了拦截失误。

**为什么惩罚会误伤**：惩罚会教会智能体"永远不要冒险开枪"，
而"同归于尽"在某些败局里是正确决策。**它该自己权衡，不该被一刀切。**

修正后的处理：

| | 处理 |
|---|---|
| **告知** | ✅ 必须——把"这一枪会致死"作为观测/信号给智能体 |
| **惩罚** | ❌ 不罚 |
| **硬拒** | 仅在"直接被自己子弹打死"时仍然不选（§16.4 不变量三保留） |

**注意区分**：
- **不变量三**（不选）是**本帧选择时**的硬约束——因为选了就是立刻自杀，没得商量
- **不惩罚**是针对**训练信号**——它可以在后续局面里学着接受这种代价

### 19.3 ★ 预训练方案：先学会合法操作，不接游戏

主人提出：

> 我觉得可以先不把智能体接入游戏什么的，节省性能，先预训练，
> 让它随机操作树，先学会合法操作再说，因为不跑游戏，应该训练非常快。

**为什么这个思路对**：

如果一上来就端到端训练，智能体绝大部分时间在输出非法操作，
**真正的胜负信号会被"违规惩罚"淹没**——它还没学会走路，就被要求跑步。

**预训练循环**：

```
1. 建一棵树（用假环境或录制的局面快照，不需要完整游戏）
2. 智能体输出操作
3. 树按 §18 的规则处理：合法 → 执行；非法 → 拒绝/夹紧 + 标记
4. 训练信号 = 合法性（合法 +，非法 −）
5. 循环
```

**不需要的东西**：渲染、UI、网络、完整对局。**只需要树的物理模拟。**

**产出**：一个"永不违规"的策略 —— 之后端到端训练时，
它已经不用再浪费探索在"什么操作合法"上。

### 19.4 课程顺序（修订）

```
阶段 0  预训练：学会合法操作                不跑游戏，极快
阶段 1  学会别自杀                        沙箱模拟自己射出的子弹
阶段 2  学会躲弹                          真实对局
阶段 3  学会赢                            真实对局 + 对手
```

**每一阶段只加一个新变量**，这样出问题时知道是哪一步坏了。

## 20. 修正与训练课程（2026-10-02 主人定案）

### 20.1 射击致死：只有"0 帧自杀"才算绝对错误（修正 §16.4）

主人指出：

> 射击致死不好评判。什么叫"直接"被自己打死呢？现在设定，
> **只有 0 帧自杀才算绝对错误的射击**。其他的都有可能对，
> 因为会对对手造成干扰什么的，**只需把死亡时间丢给智能体，它自然会知道好坏。**

| 情况 | 处理 |
|------|------|
| **射出瞬间（0 帧）就打死自己** | **绝对错误 → 不选** |
| 后续某帧被自己子弹打死 | **不判错** → 把**死亡时间**作为观测给智能体 |
| 被自己子弹影响而死（走位被逼等） | **不判错** → 同样告知 |

**为什么必须放宽**：自己射出的子弹会**干扰对手、封锁走廊、逼对方走位**。
一刀切成"错"会让智能体不敢开枪。**只有立刻自杀才是毫无争议的错误。**

**观测内容**：死亡时间（第几帧死）。**智能体自己会判断这代价值不值**——
这正是"拦截失误"该有的形态：给它事实，不给它结论。

### 20.2 预训练不能拆环境（修正 §19.3）

主人指出：

> 预训练也不能把环境全拆了，只不过是不渲染游戏画面什么的提升性能，
> **但是游戏逻辑还在，它也在真实的游戏里，会做出真实操作。**
> 只不过当前不对游戏进行引导，只让它学会操作树。

| 旧（错） | 新 |
|---------|-----|
| 用假环境 / 快照，只要树的物理模拟 | **完整的真实游戏逻辑**，只是**不渲染画面** |
| — | 关掉的只有：画面渲染、UI |
| — | **保留**：物理、子弹、迷宫、坦克、全部游戏逻辑 |

**关键**："它也在真实的游戏里，会做出真实操作"——所以学到的东西能直接用。

**"不对游戏进行引导"** = 这一阶段不追求打赢，只追求**合法操作**。

### 20.3 ★ 训练课程（主人给的 8 阶段）

| 阶段 | 内容 | 练什么 |
|------|------|--------|
| **1** | **移动**：地图上随机给可达的位姿，智能体要在尽可能短时间内尽可能贴合目标位姿 | 走位精度 + 效率 |
| **2** | **定点射击**：让智能体不能离开本格，射击可达的目标位置 | 瞄准 + 反弹几何 |
| **3** | **躲弹**：射击源随机移动并发射不同类型的子弹，存活越久分越高 | 纯躲弹 |
| **4** | **移动射击**：先移动到目标格子，再射击目标位置 | 走位 → 射击的衔接 |
| **5** | **躲弹射击**：躲弹的同时射击目标位置 | 边躲边打 |
| **6** | **移动目标躲弹射击**：同 5，但射击目标是**真实坦克**、会移动（比如 Vantage 躲弹） | 预判移动目标 |
| **7** | （可选）**道具操作专项**：武器箱 / 地雷等 | 道具运用 |
| **8** | **真实对局** | 全部整合 |

**课程设计的三个优点**：

1. **每阶段只引入一个新变量** —— 出问题时能立刻定位是哪一步坏的
2. **前面阶段的技能被后面复用** —— 不是八个独立任务，是一条阶梯
3. **阶段 1、2 完全不需要对手** —— 训练极快；阶段 6 才需要"陪练"，
   而陪练正好是 **Vantage 躲弹 AI**（也解释了为什么它要有单独的训练阶段）

### 20.4 与接口的关系

这 8 个阶段**全部跑在同一套树 + 智能体接口上**，
区别只在于**环境给的训练信号不同**：

| 阶段 | 训练信号 |
|------|---------|
| 1 | 到目标位姿的时间 / 误差 |
| 2 | 命中率 |
| 3 | 存活时长 |
| 4、5 | 到达 + 命中 |
| 6 | 对移动目标的命中率 + 存活 |
| 8 | 胜负 |

**所以接口不需要为不同阶段做任何改动。**

### 22.4 ★ 唯一保留待观察的点：生长的学习信号

不是"值不值"那个框架的问题，而是一个很实际的归因问题：

```
智能体决定了"往这几个节点长" → 树长出来了 → 它选了其中一条走 → 结果决定胜负
                     ↑
        那些"长了但没走"的节点，它怎么知道自己当时该不该长？
```

**主人的回答是**："走错了就赢不了，自然就学到了。"
**这在长期是对的。**

**但有个现实困难**：如果它长了 A、B、C 三个分支，走了 A 并死了——
它**无法区分**是"不该长 B、C"还是"长了但没走 A"。中间隔了一层。

**处理方式**：不立刻解决，**留档观察**。
如果训练后期发现"生长那一头学不动"，**这是第一嫌疑**。

#### 22.4.1 主人补充：这个问题早就讨论过，靠"坍缩"解决

> 「你那个"长了没走"的问题很实际，是我很早以前就讨论过的。
> **树会坍缩**（不懂就查定义），**坍缩掉的分叉越深，惩罚越高**。
> 但由于**坍缩频率极高，每帧 1 次**，所以单次惩罚实际上数值是很小的。
> 这个也确实不是当下的问题，训练不动了才考虑这个。」

**坍缩的定义**（见 `03-树结构.md`）：
提交节点升为新根、旧根的 8 个兄弟**离开活动树**。
**离开的那批，正是"长了但没走"的分叉。**

所以"该不该长"这个问题的答案已经内建在机制里：

| 机制 | 作用 |
|------|------|
| **坍缩** | 没走的兄弟离开活动树 → 它们的"生长"被判定为浪费 |
| **按深度惩罚** | 分叉越深，坍缩时罚得越重（浅分叉浪费的算力少） |
| **高频摊薄** | 每帧坍缩一次 → 单次惩罚数值很小 → 不会压过胜负信号 |

**这就是"生长"的学习信号来源**——不是靠"值不值"的显式目标，
而是靠**坍缩这个结构性事件**自然产生。

**当前不作为问题处理**，训练不动了再回头看这条。

## 23. 每帧一套完整输出 + 帧内重试（2026-10-02 主人定案）

### 23.1 主人定案

> 「还需要个逻辑，就是目前暂定**智能体每帧进行完整的 1 套有效操作**，
> **这一次输出所有结果**，包括缓存、生长、选路等，所以**有非法输出时，
> 得在本帧重新让它输出，直到每种数据都获取到 1 个，并且合法**。」

### 23.2 这解决了什么

之前 §21.3 B 说"优先采样前屏蔽非法动作"——但没说**怎么做到**。
本节给出了做法：**帧内拒绝采样（rejection sampling）**。

| 旧方案 | 新方案 |
|--------|--------|
| 输出非法 → 接受 + 惩罚（污染训练信号） | 输出非法 → **本帧重试，直到全合法** |
| 夹紧 → 执行的动作 ≠ 输出的动作 | **执行的动作 = 输出的动作**（不合法就不采纳） |

**关键性质**：**非法输出永远到不了树**——它不会污染训练信号里的"动作后果"。
（注意：这不等于不用罚——非法输出消耗了重试算力，**仍要罚**，见 §23.6。）
- 训练信号里不会出现"执行了一个非法动作"这种事
- 但**重试次数要记下来**，它是"这个策略爱犯错"的度量，也是惩罚依据

### 23.3 一套完整输出包含什么

每帧智能体输出**一个包**，包里每一项都要合法：

| 项 | 说明 |
|----|------|
| **记忆** | 智能体自己的思维缓存（**不透明**，树不解释内容，只负责保存与归还） |
| **生长** | 在哪些节点继续展开 |
| **选路** | 选哪个节点作为执行路线 |
| *（后续）* | 段长、射击帧 |

### 23.4 帧内流程

```
本帧调用智能体
   ↓
拿到一包输出 → 逐项检查合法性
   ├─ 全部合法  → 采纳，进入执行
   └─ 有非法项  → 记录是哪些项、为什么
                   ↓
              【本帧重新调用】把它重新输出
                   ↓
              ... 直到全部合法，或达到重试上限
```

### 23.5 三个必须定死的细节

#### ① 重试上限（必须）

**没有上限 = 可能卡死一整帧。** 建议先给 **3~5 次**，
实测一帧预算内能跑几次再调。

#### ② 超限之后怎么办（必须）

```
超过重试上限 → 兜底
   ├─ 退回规则逻辑（树能继续跑，但这一帧智能体没起作用）
   └─ 记录"本帧放弃"，供统计
```

**绝不能既不合法又硬用**，也绝不能无限重试。

#### ③ 重试时要不要告诉它哪里错了（建议要）

```
第二次调用时附上：
   { 第几次: 2, 非法的项: ['选路'], 原因: '选了真死路线' }
```

**这能大幅提高收敛速度**——它不用猜为什么被拒。
而且**它不违反"不给结论"的原则**：告诉它"这条违规了"是**事实**，
不是替它决定该选哪条。

### 23.6 ★ 帧内拦截与非法惩罚，两者都要有（主人更正）

上一版写"非法输出不罚（它没生效）"——**错了**。主人指出：

> 「不，**非法惩罚和这个都要有**，惩罚的目的是让智能体**学会一次性输出对**，
> **节省性能**；单帧拦截的目的是让树**拿到可用的结果**。」

两者的目的完全不同，所以**必须都有**：

| 机制 | 目的 | 归属 | 不做会怎样 |
|------|------|------|-----------|
| **单帧拦截（重试）** | 让**树**拿到可用的结果 | 执行层（可靠性） | 树拿到非法结果，跑不了 |
| **非法惩罚** | 让**智能体学会一次给对** | 训练（性能） | 每帧反复重试，前向成本翻倍 |

**关键认识**：**重试不是免费的**——每次重试 = 一次完整前向。
所以"非法输出"虽然没有直接生效到树上，但它**消耗了算力**。
惩罚就是为这份消耗定价。

#### 罚什么、罚多少

| 罚的对象 | 说明 |
|---------|------|
| **输出非法** | 每有一次非法项，罚一次 |
| **重试次数** | 重试越多罚越多（直接对应算力浪费） |
| **本帧放弃**（重试用尽） | 罚最重——这一帧智能体完全没起作用 |

**量级要小心**（呼应 §18.4）：

- **太小** → 它不在乎，每帧重试两三次也无所谓，性能白烧
- **太大** → 它学会"什么都不做"来避免违规

**目标是让它"一次给对"，不是让它"不敢给"。**

### 23.7 性能提醒

每次重试 = **一次完整前向**。所以要一起看：

```
每帧耗时 = 前向次数 × 单次前向耗时 + 树的模拟耗时
```

如果一帧内平均要重试 2 次，**前向成本就翻倍**。
这也是为什么 §17.3 的"非线性缓存"和 §20.2 的"不渲染"很重要——
省下来的都要留给重试。

## 24. 射击简化 + 两阶段分工是"两个智能体"（2026-10-02 主人定案）

### 24.1 射击只有一个操作：逐帧二值

主人定案：

> 「只有一个射击操作，如果**连续很多帧都射击，那就视为按住了**。
> 也就是说，**射击只需要一个键**，下一帧要是没继续射击，**程序自动处理松开**。
> 游戏本身也本来就是这样的，射击有 1 帧后摇，点击频率不能过高，否则视为按住。
> 也就是说**这样子就不可能有不合法操作**。」

所以：

```
智能体每帧输出一个二值：这一帧要不要射击
        ↓
执行层负责：
   · 连续帧都输出"要" → 视为按住
   · 下一帧输出"不要" → 自动松开
   · 后摇/点击频率限制 → 由游戏本身处理
```

**关键收益**：**"重复按下/重复松开"这类非法操作根本不存在了**。
§18.2 ⑤ 那张表里的一半条目直接作废。

### 24.2 剩下的只有"不达预期"，用轻罚

没有非法操作，但有两类"它想要的和实际发生的对不上"：

| 情况 | 说明 | 处理 |
|------|------|------|
| **不会发射加特林** | 加特林需要一直按住（蓄力），点射打不出来 | 轻罚 |
| **想射 5 发，只打出 1 发** | 点击频率过高被游戏判为"按住"，实际只算一发 | 轻罚 |

**判断依据**：**直接看当前持有的物品**。

```
持有的是非加特林武器，却连续很多帧都在射击
   → 这不符合它的预期（点一次和按住没区别）
   → 轻罚
```

主人原话：「这和点一次射击没区别。」

### 24.3 ★ 两阶段 = 两个智能体，不是"一个智能体的两次调用"

主人进一步明确：

> 「分了模块的话，说不定还能优化呢，每个都做好自己的分工。
> 就像大语言模型也由好几个小的模块组成一样，**我们看的是总时间，
> 总的参数量或是规模什么的和一个万用智能体一样或者更省就行了**。
> 现在分两阶段，意思就是**给智能体加明确的分工**，
> 而不是一个万能的智能体两件事都干了。」

**分工方案**：

| | 职责 | 它需要什么 |
|---|------|-----------|
| **智能体 A** | **预测 + 长节点** | 看树、看场面，判断"哪里值得继续算" |
| **智能体 B** | **玩游戏 + 操作** | 看树、看场面，决定"选哪条路 / 走多久 / 怎么射击" |

**主人给出的额外理由——防灾难性遗忘**：

> 「分工还能防止灾难性遗忘，**一个只负责预测、长节点，一个只负责玩游戏、操作**。」

这是个重要论点：如果塞进一个网络，两件事的梯度会互相干扰；
分开之后**各学各的，不会互相冲掉**。

### 24.4 性能账的算法要改

主人指出：

> 「多次调用智能体是会增加时间，但是分了模块的话，说不定还能优化呢……
> **我们看的是总时间，总的参数量**……」

所以**不能按"调用次数"算成本**，要按**总时间 + 总参数量**：

| 方案 | 调用次数 | 总耗时 | 总参数量 |
|------|---------|--------|---------|
| 一个万能智能体，跑 2 次 | 2 | 2 × 大模型 | 1 份大的 |
| **两个专用智能体，各跑 1 次** | 2 | **各自都小，可能更快** | **两份小的，总量可能更少** |

**关键**：一个"什么都管"的模型必须足够大才能都管好；
两个"只管一件事"的模型各自可以很小。**总量可能反而更省。**
（这也是主人举"大语言模型也是好几个小模块组成"的例子想说的。）

### 24.5 关于"同一个智能体、两组输入输出"

主人表示不确定如何实现。补充说明：

**技术上**：共享一套底层（读树、读场面），上面接两个输出分支。
**问题在于**：两件事的梯度会写进同一套底层参数 → **互相干扰**。
这恰恰是主人说的"灾难性遗忘"的另一面。

所以：

| 方案 | 优点 | 缺点 |
|------|------|------|
| 共享底层 + 两个输出头 | 底层理解共用、样本共用 | **梯度互相干扰** |
| **两个独立智能体**（主人倾向） | 各学各的、互不冲掉、各自可以很小 | 各要自己的样本 |

**按主人的理由，两个独立智能体更稳**——尤其"预测"和"操作"这两件事的目标根本不同
（前者是预测未来，后者是赢）。

## 25. 射击格式修正 · A/B 职责明确化（2026-10-02 主人定案）

### 25.1 射击输出不是"逐帧位"，是【稀疏表】

上一版（§24.1）和更早我推荐的"逐帧二值"**被否决**。主人指出：

> 「注意，**智能体不输出每一帧的情况**，因为**绝大多数帧都没在射击**，
> **只需要指定某帧射击即可，一个字典的事**。」

所以格式是：

```
{ 第 5 帧: 射击, 第 12 帧: 射击, 第 13 帧: 射击, 第 20 帧: 射击 }
```

| | 逐帧位（已否决） | **稀疏表（采用）** |
|---|---|---|
| 输出长度 | 固定 30 位（大多是 0） | **只列真正射击的帧** |
| 信息密度 | 极低（绝大多数是"不射击"） | 高 |
| 表达 | 每帧都要表态 | **只表态要射击的那些帧** |

**合法性条件只剩两条**：帧号在本段内、不重复。
（"按下/松开必须交替"这个约束依然不存在。）

**执行层负责把稀疏表变成按键状态**：
连续出现的帧号 = 按住；中间断开 = 松开。

### 25.2 A 的职责与目标（明确化）

主人定案：

> 「对，**A 的职责就是生长出尽可能不用回退的路，也就是它换路更少，
> 系统坍缩浪费的节点更少**。」

所以 A 的目标是**可度量的**：

| 指标 | 含义 |
|------|------|
| **换路次数** | 越少越好 |
| **坍缩浪费的节点数** | 换了路 → 没走的那些兄弟离开活动树 → 全是浪费 |

**这个目标不依赖"预测未来"**——它是"**别让已经算出来的东西白费**"。
（这比 §22.4 里我写的"预测未来"准确得多，**以此为准**。）

### 25.3 职责划分的最终版

| | 谁管 | 说明 |
|---|------|------|
| **生长**（在哪长） | **A** | 目标：少换路、少浪费坍缩节点 |
| **选路** | **B** | |
| **操作时长**（段长） | **B** | ★ 主人强调："**操作时长真不能乱来**" |
| **射击** | **B** | 稀疏表 |
| **预测时长**（树往未来铺多远） | **规则系统** | ★ 不由智能体管，见下 |

#### 为什么预测时长不给智能体

主人原话：

> 「目前**不需要 A 管理预测时长**，但**需要 B 管理操作时长**。
> 因为**预测时长的管理仅仅是为了省性能，没必要为了省性能给它加学习负担**。
> 而**操作时长真不能乱来**。」

两者的区别：

| | 预测时长（树铺多远） | 操作时长（这段走多久） |
|---|---|---|
| 影响什么 | 只影响**算力消耗** | 影响**实际执行的成败** |
| 错了会怎样 | 算得慢一点而已 | **撞墙上、被弹打死** |
| 该谁管 | **规则系统**（纯性能问题） | **B**（真会影响胜负） |

**所以：能用规则解决的事，不要给智能体加学习负担。**
