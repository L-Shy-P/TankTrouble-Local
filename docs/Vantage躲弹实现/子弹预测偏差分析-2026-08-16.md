> 2026-08-23 口径更正：文中“恢复段末删除未来 8 兄弟”等坍缩描述是当时针对
> 重建风暴的临时方案。最终口径是：换路线不删节点，未执行分支保留复用；
> 只有被新弹真正判死或极端结构失效才允许局部作废。
> 本文关于 path[0] 活引用、折线漂移、Box2D 轨迹替代 raycast 的技术结论仍然有效。



数据文件：`game_core/测试反馈/vantage_tree_diag_1786964490980.json`（3.3MB，tNow=29.533s，5颗弹）。

## 结论一句话

预测误差不是单一“时间锚点”问题，而是三层叠加：

1. **折线 path[0] 是活引用**：`B2DUtils.calculatePath` 把 `b2body.GetPosition()` 原对象直接 `path.push(position)`，没 `Copy()`。锚定后 body 继续运动，path[0] 每帧跟着真实子弹跑，导致“锚定折线预测”在第一次反弹前就以 **2 倍真实速度**漂移。
2. **raycast 折线与 Box2D 圆弹碰撞不一致**：折线按“中心射线撞墙面”反射，真实弹是“圆半径撞墙+Box2D 接触法线”反射。第一次反弹就产生约 0.35m 的平行偏移，角弹差异更大。
3. **树把一张旧折线锚了 4 秒不换**：`rootAbsT` 停在 25.5667s，而真实子弹在此期间反弹 7 次；预测后段穿墙/停住，最终同帧误差 17.61m。

## 逐条证据

### 1. path[0] 活引用 → 反弹前 2 倍速漂移

以 `b-9b24-31` 为例（真实速度 18.0m/s，v=(-12.06,-13.36)）：

| 预测时刻 | 预测位移/帧 | 真实位移/帧 |
|---|---|---|
| 23.150→23.233 | (-2.019,-2.235)/0.0833s = 24.2, 26.8 m/s | (-1.009,-1.118)/0.0833s = 12.1, 13.4 m/s |

预测轨迹的形状完全贴着真实轨迹，但速度正好是 2 倍。等价关系：

`pred(t) ≈ actual(t_anchor + 2·(t - t_anchor))`（第一次反弹前成立）。

代码定位：`game_core/js/b714588...js` 内 `B2DUtils.calculatePath`：

```js
path.push(position);   // position = b2body.GetPosition()，活引用，未 Copy()
...
path.push(closestPoint.Copy());  // 后续点才是快照
```

Box2D 的 `GetPosition()` 返回内部 `b2Vec2` 引用，子弹每帧运动都会改它。锚定后：

`bulletPosAt(path, 18, relT)` = 活 path[0]（已是当前真实位置）再沿旧第一段前进 `18·relT`，
总位移 ≈ 真实位移 + 预测增量 = **2 倍真实速度**。

原版 AI 每帧重算路径所以从不暴露；Vantage 树把路径锚定跨 0.1~0.2s 使用，问题必现。

### 2. 第一次反弹：中心射线 vs 圆弹接触

`b-9b24-31` 真实第一次反弹：

- t=24.5833，pos=(14.04, 0.76)，vy 从 -13.36 翻成 +13.36。

raycast 折线在墙面 y=0.4 就反射（中心射线撞面），真实圆弹中心要到 y≈0.65~0.76 才反弹。预测反弹点比真实早约 0.36m。

反弹后的对齐残差（把重锚跳跃去掉后按最近真实点比较）稳定在 **0.34~0.40m**，与半径偏移完全同量级。之后每次反弹该偏移还会累积/换向，角弹（如 `b-9b24-28` 在 24.28s 双分量翻转）误差更大。

### 3. 旧折线锚 4 秒，误差从米级长到 17.6m

最终导出时：

- `rootAbsT = 25.5667s`
- 5 颗弹的 `threats[].x/y` 都等于各弹在 t=25.5333 的真实位置（例：`b-31` (18.72,13.45)）→ 锚定本身还带 2 帧陈旧。
- 事件日志里 26.02→29.53 有 24 次 commit，但 `rootAbsT` 一直没变：正常坍缩的 `hasKids` 分支保留旧 threats，弹已反弹 7 次也没换锚。

结果：

- `b-9b24-31` 最终预测 (24.53, 47.71)，真实 (32.16, 31.84)，同帧误差 **17.61m**。
- 25.58~26.3 期间预测点停在真实第三次反弹点附近不动（折线在反弹瞬态被 raycast 成短路径/端点），而真实弹已飞出 20m+。
- 相同弧长 65.3m 处：预测 (29.31,45.56)，真实 (28.15,36.27)，路线已经分叉，不是单纯时间差。

### 4. pathBounces=5 的作用（次要但存在）

锚定 25.533→29.533 这 4 秒内 `b-9b24-31` 真实反弹 7 次。`pathBounces:5` 在第 5 次反弹后不再反射，后续段必然穿墙。它不是首个 1m 误差的来源，但当前“长锚定 + 5 跳”组合下误差会被无上限放大。

### 5. 新弹漏锚

`missingBullets` 显示每颗新弹出现后有 3 帧（约 0.05s）真实存在但树未锚定：`b-16/21/22/23/28/29/30/31/32` 全部如此。

## 三轮：融合世界为什么“看起来和原版一样”还会坏 + v19 处置

- 旧融合世界不是原版模拟：它在一个世界同时放 9 个候选坦克 + 共享子弹克隆。每个候选的物理边界条件已经与原版不同。
- 真正的幽灵弹根因（代码级）：
  1. tGlobal>0 时只把子弹**位置**摆到 raycast 折线未来点，速度仍是当前真实速度——折线一旦预测过反弹，子弹就以错误方向从墙边起飞；
  2. 槽位按数组复用，bullet(0.25m)/shotgun(0.1m) 混用同一 body，半径错；
  3. SetActive 后未 SetAwake，速度写入不唤醒；
  4. 共享子弹与 9 候选在同一世界，哪怕传感器不反弹，接触/冲量状态跨轮复用。
- v19 处置：融合世界改为**纯坦克候选世界**（9 个候选只撞墙，不创建子弹体）；子弹轨迹由 v18 bullet-only 世界独立预测，死亡判定旧 checkDeath 权威。两个世界各管一件事，可分别验证。
- FUSED_ENABLED 默认恢复 true；旧 `setFusedEnabled(false)` 仍可关。
- 树生长随之恢复融合节奏：每 tick 同步扩一层，短段不再只 1 层。

## 四轮：架构澄清 + 宕机根因 + 节点只增不减（v29）

### 现在的“融合版”到底是什么

- 游戏真实世界：从不 step、从不 clone 修改，只读。
- 预测侧有两个独立私有世界：
  1. **坦克候选世界（融合版）**：迷宫墙 + 9 个候选坦克体，只算坦克运动，不创建任何子弹体；
  2. **子弹轨迹世界（bullet-only）**：迷宫墙 + 当前弹道型子弹体，只录未来轨迹，不创建坦克体。
- 死亡判定：旧 `checkDeath` 迷你世界（Box2D 静态重叠），输入 = 坦克候选位姿 + 子弹轨迹点。
- 所以它是“魔改的预测沙箱”，但每个子世界只做一件事；物理建体和 Step 参数全部复用原版函数。

### 躲几波后宕机的根因

- 树正常坍缩且已有预览子树时，`rootAbsT`/threats 会长期保留旧锚（这是刻意复用子树）。
- v28 给子弹 track 的长度只按 horizon+EVAL≈4.5s 生成；锚龄超过 4.5s 后
  `threatBulletPos` 对整段 track 越界返回 null → 预测世界里所有子弹消失 →
  9 操作同分 → `pickBest` 平局选静止 → 坦克原地不动，表现为“躲几波后宕机”。
- v29 把 track 长度改为 `max(horizon+EVAL, 10s弹寿命)=500 帧`，子弹真实寿命内
  预测世界不再空；新子弹出现仍走 emergency 重建（旧树进历史，不删）。

### 节点只增不减策略（v29）

- 正常提交不再删除未来 8 兄弟；旧根（已执行过的过去备选）进 `tree.retired` 历史。
- 节点数只增不减，直到 `maxNodes=500`。
- 满 500 后只回收**最老的历史根**腾预算（`recycle` 事件）；当前根的未来候选永不剪。
- `diag.shapeHistory` 每次 commit 记录 `{t,nodeCount,activeDepth,retiredCount}`，导出 JSON 可画曲线验证。

## 六轮：新弹局部失效 + 节点动态上限解释 + 卡墙惩罚（v31/tree，v20/scoring）

### 新弹不再整树清零

- 新弹出现：以 `anchorOffset = now - rootAbsT` 追加进 `tree.threats`，旧树不动。
- `invalidateStaleNodes`：对每个未来节点，用其已存的 `rolloutSamples` 重扫
  “当前 threats 下是否比建节点时更早死亡”；只剪受影响节点及其子树。
- 只有 `commitNode` 本身被判定提前死亡（=受影响链就是整条活链）才根层重选。
- 段末心跳继续重扫（`_hasOffsetThreats` 期间），处理“远弹后来逼近”的迟到影响。

### 节点动态上限的机制

- 节点数 ≈ `horizonSec / 段长 × 每层候选数`。
- 远弹/无威胁：probeSegment 找不到分数分歧 → 段长=tMax30帧(0.6s)，3s视界只有
  约5层 → 约41节点。
- 子弹接近：9操作分数分歧早 → 段长压到3帧(0.06s)，同样视界约50层 → 节点暴涨。
- 所以“上限41→65→接近时暴涨”是段长自适应在起作用；`maxNodes=500` 只是极端保护。
- 主人不喜欢被限制，v31 已把 `horizonSec 3.0→8.0`：远弹场景从5层变约13层，
  节点更多；近弹仍由500上限兜底。

### 卡墙惩罚（killfield 式）

- 新增 `stuckPenalty=4.0/帧`、`stuckDistEps=5cm/帧`、`stuckRotEps=0.05rad/帧`。
- 只对非静止操作的 75 帧模拟生效：连续两帧位姿几乎不变（顶墙/被墙吸住）就扣。
- 75帧全卡最多扣300，足以压过“倒车进墙角”的短期收益，逼 AI 面向子弹换位。

## 七轮：新弹反应变慢的原因与修复（v32/tree，v21/scoring）

- 现象根因：v31 局部失效只做“提前死亡剪枝”，不更新 9 候选分数。
  新弹出现时若没造成提前死亡，当前段继续跑完，下一段候选还是旧弹评分，
  新弹影响要等金线慢慢长出才能传到 argmax —— 表现就是“子弹贴脸才动”。
- 修复：
  1. `scoreRollout`：不重新模拟坦克，直接对节点已有 rolloutSamples 重算
     75 帧总分（含新弹轨迹/车道/卡墙）。
  2. 新弹出现 → 刷新当前 commitNode 下一段 9 候选的 subtreeBest →
     强制当前段提前结束（跳过段末对齐，因为不是自然段末）→ 同一 tick
     提交换操作。
  3. 结构剪枝仍只按“提前死亡”执行；分数刷新不重建节点。
- 卡墙惩罚不会误伤正常移动：阈值是位移<5cm 且转角<0.05rad/帧；
  正常前进≈32cm/帧、倒车≈26cm/帧、原地转≈0.1rad/帧。
- 静止没有惩罚；但新弹出现会立即刷新移动候选分数，静止只有在
  “严格更好”时才继续赢。

## 八轮：分数割裂、地图轨迹不一致、暂停逐帧卡顿（v33）

- 分数割裂根因：v32 `refreshCandidateScores` 改了子节点 subtreeBest 后没有
  backpropBest 回传父链，父节点/根仍显示旧链累计高分（“静止上万、其他两千”）。
  已补回传。
- 轨迹不一致根因：新弹强制提前提交是半途截断，旧节点的 rolloutSamples 仍从
  预测段末出发；AI 实际从当前真实位姿出发。v33 在强制提交后沿新 argmax 链
  `rebaseCommitPath` 逐节点从上一节点末态重摆 rolloutSamples/末态，地图金线
  与 AI 实际执行一致。
- 暂停逐帧：提前提交后的链重摆是本次最重路径，已加 try/catch 防异常导致
  tick 中断；若仍卡，导出 JSON 看 `shapeHistory` 和事件日志里是否有连续
  fresh/commit 循环。

## 二十一轮：真根因实锤——发射源混入布位 + 间距死循环防护（training v45）

- **探测工具链重建**（`_probe_maze.js` / `_probe_rebuild.js`）：
  - `_maze_pkg.txt` 旧版与打包文件不一致且手术正则漏替换 createSymmetric 分支，
    历史“wall 0.95 死循环”结论系误判；
  - 现从 `418577fd210ad079ea3d1e5e04050fe0.js`（mod_pagespeed 多段字符串打包）
    逐段 unescape 还原真实 Maze 源码再手术，实测数据全部以真实源码为准。
- **真根因**（真实源码 + 迭代计数实测）：
  - 引擎 `initializeRound` 用 `gameMode.getMaze(getActivePlayerIds(), …)` 生成地图，
    发射源伪玩家也在 playerIds 里（`replaceEmitters → ensureEmitterPlayers` 已入 model）；
  - `createTrainingMaze` 原样转发给 `Maze.createRandom`（open 空旷场走此路径）；
  - `createRandom` 按切比雪夫间距 `MAZE_MINIMUM_TILES_BETWEEN_TANKS=4` 逐个放坦克，
    放不下就 `while(true)` 整图重来。实测 10×8 图：≤6 坦克稳定、8 坦克需 291 次重试、
    14 “坦克”（12 发射源+人类+AI）20 万次重试撞上限 → 网页未响应实锤；
  - standard/dense 走 `createSymmetric`（坦克位置由首坦克镜像生成、无间距检查），
    天然免疫——所以卡死集中在 open 场景模板（precision/surprise/positioning）。
- **修复①：createTrainingMaze 过滤发射源伪玩家**——`isEmitterId` 的 ID 不参与
  坦克布位，多源模板不再挤占布位容量；引擎只按 `maze.tankPositions` spawnTank，
  发射源坦克改由 `trainingAfterInitializeRound` 正常生成路径补齐
  （复用 `spawnTrainingTanksForFixedMaze`，配置坐标优先/幂等跳过已有坦克）。
- **修复②：非对称路径容量预检自动降间距**——坦克数超过
  `ceil(W/(d+1)) * ceil(H/(d+1)) + 2` 时自动收紧 `minTilesBetweenTanks`（4→3→2→…），
  实测 d=2 时 10×8 图 14 坦克 2 次迭代即成；`applyTrainingMazeConstants` 的
  overrides 新增 `minTilesBetweenTanks` 联动写入 `Constants`。
- **模板参数澄清**：dense 的 wall 0.95/tile 0.65 经真实源码验证**安全**（对称路径
  sqrt 概率 + 强制打通 + 镜像布位），无需下调；open 场景 wall=0/tile=1 本身安全，
  卡死全部来自布位容量而非墙概率。

## 二一轮：高频死亡恢复 + 弹消失不清树 + 基准全部短爆发（tree v36 / bench v13）

- 九候选被高频死亡剪光时，只重建当前根层；节点满等极端失败走 freshRoot
  兜底，避免 commitNode 永远卡在同一操作。
- 所有基准模板统一加 applyBurstProfile：
  普通/双管：10发@0.05s，停14s；
  加特林：30发@0.04s，停18s；
  霰弹：5发@0.08s，停16s；
  追踪：4发@0.12s，停20s。
  即“极短时间大量放弹 → 长停歇”，给树充分重建时间。

## 二二轮：取消新弹强制提前提交（tree v37 / ?v=43）

- 根因判断：树图频闪、1-2层反复、旧节点连线被拉长，基本都来自
  “每颗新弹强制把当前段提前结束并重摆 argmax 链”。爆发期几十发弹 =
  每帧一次坍缩/重摆，树永远长不起来。
- 现逻辑：新弹只做三件无损的事：
  1. 追加 threat；
  2. 剪掉真正提前死亡的节点；
  3. 刷新当前根下一段候选分数。
  当前段自然结束才提交。
- 增加 prune/fresh 事件细节：导出 JSON 可看到每次清空的具体原因
  （newBulletCommitDead / noCommitNode / align / 节点满兜底）。

## 二三/二四轮：新JSON定位——清空主要是段末对齐失败（tree v38 / training v46）

- 新诊断显示：子弹发射期与发射结束后都出现密集 fresh；而事件里
  prune/newBulletCommitDead 很少，stats.alignFails 高（第一份18/16s，
  第二份40/48s）。结论：清空主要不是新弹剪枝，而是**段末硬对齐失败**。
- 修法：
  1. 软对齐：偏差 <3m 且 <20° 只记录 align 事件，保留整棵树继续运行；
     只有超过硬阈值才 freshRoot。
  2. 发射源坦克取消与玩家/AI坦克的物理推挤：预测沙箱没有发射源体，
     现实中发射源推挤 AI 必然造成无意义对齐偏差。
- 之前已取消新弹强制提前提交；新弹只局部追加/剪真正提前死亡节点。
- shapeHistory label 现在会记录 fresh 的具体原因（alignHard/commitDead/
  newBulletCommitDead/initial），下份 JSON 可直接定位。

## 二五轮：安全后树突变+全静止死亡的解释与保护（tree v39）

- 症状解释：突发清空往往发生在空旷期 freshRoot 后；新根无威胁时九操作
  同分，argmax 自然选 OPERATIONS[0]=静止，且 probeSegment 给长段(30帧)。
  下一波子弹贴脸时，如果当前段还没结束，AI 会静止到段末。
- 保护：仅当 commitNode 是静止、且后补新弹 tIn 即将进入威胁圈时，
  提前结束该静止段；其余新弹仍不强制提交，保持树稳定。

## 二六轮：静止死亡保护 + 提交候选诊断（tree v40 / ?v=46）

- 有 tIn 即时威胁时，如果 argmax 选静止，则改从“存活且可动”的候选中
  重新 argmax；只有所有可动候选都死才允许静止。
- commit 时记录 `diag.lastCommitInfo`：威胁数、每候选 op/status/seg/score/death。
  下次导出 JSON 可直接看死亡前最后一层为什么静止。

## 二七轮：「无」模板选项 + 地图缓存防白屏（training v47 / bench v14）

- **「无」模板选项**（bench）：
  - 维度下拉新增 `0 无（保留普通训练）` 并设为默认；
  - 面板构建不再自动应用 precision 模板——普通训练模式不再被基准接管；
  - 选「无」时 `applyFromDimension` 早退（不替换发射源/地图/设置），
    需要跑基准时主人主动选维度或点「跑基准」。
- **白屏根因**（实测）：
  - 地图参数面板的 `fixedWidth/fixedHeight` 手输框允许 `0`/负数直通
    `createTrainingMaze` → `Maze.createSymmetric(0,0,…)` 在空 block 上
    无限 continue（实测 20 万次迭代撞上限）；
  - 生成无结果校验、无异常保护、无兜底：一张 null/半成品图流入引擎
    `setMaze` 后 `getTankPositions()` 即崩，模型卡 BETWEEN_ROUNDS
    （betweenRoundsDuration=1e6 永不开局）→ 白屏。
- **修复①：createTrainingMaze 全参数 clamp**——尺寸夹 [6, MAX]（6×6 实测安全，
  0/负/过小一律回退按玩家数推算）、概率夹 [0,1]、间距 ≥0；
  生成过程 try-catch + 结果校验（tiles 非空 + tankPositions ≥ 真实玩家数），
  失败返回 null 交给上层降级。
- **修复②：地图缓存机制（优先用做好的地图）**——`getOrGenerateTrainingMaze`
  四级策略：
  1. `fixedMazeData`（显式固定关卡）优先；
  2. 参数指纹命中缓存（`mapGenCacheKey`=生成参数+真实玩家列表，发射源剔除）
     → 直接复用做好的地图（基准多局同图=公平；调整配置 key 变化自然失效）；
  3. miss → 按当前参数随机生成，成功后写入缓存（data+tankPositions，
     withObject 不重建布位，故缓存需一并存取）；
  4. 生成失败 → 回退旧参数缓存图（宁可用旧图不白屏）→ 仍无 → 引擎原生
     getMaze（vanilla 常量官方参数）兜底，四级策略保证永不白屏。
- 挂点统一：`installTrainingGetMazeHook`（实例级）与
  `BootCampGameMode.getMaze` patch（类级）均改走 `getOrGenerateTrainingMaze`；
  两层 fallback 链（实例 prev → 原生）无递归风险。
