## 二、改动（带行号）

### 2.1 核心：`game_core/js/vantage_tree.js:1774-1801`（`reanchorThreatsAtCommit`）

```js
// 旧（v167，:1775/:1795）
var shift = Math.max(0, _timeAcc - oldRootAbsT);       // 本次 commit 的间隔
if (old && old.track && old.track.length >= needFrames && shift <= 1.0) {
    th.track = old.track; ... th.anchorOffset = (old.anchorOffset || 0) - shift;

// 新（v168，:1797-1801）
var newOffset = old ? (old.anchorOffset || 0) - shift : 0;   // 复用【之后】锚点相对新根的偏移
if (old && old.track && old.track.length >= needFrames && Math.abs(newOffset) <= 1.0) {
    th.track = old.track; th.trackSource = ...; th.anchorOffset = newOffset;
```

- 语义等价性：`|newOffset| = -anchorOffset + shift = Δ`（锚点年龄）。
  因为 `abs0 = rootAbsT + anchorOffset`、`rootAbsT_new = _timeAcc = rootAbsT_old + shift`，
  所以 commit 那一刻 `Δ_after = _timeAcc − abs0_new = −newOffset`。⇒ 新门 = **「Δ ≤ 1.0s」**，正是
  `:1785-1787` 注释的原意（防"累积过大→最深未来查询越界"）。
- 数量级自洽：修后实测最深节点 `horizon ≈ 8.1s`、轨迹覆盖 `len·tdt ≈ 9.37s`，
  `Δ ≤ 1.0` ⟹ 最深节点查询落在 `1.0 + 8.1 = 9.1s < 9.37s` 内，**刚好不再越界**（与注释里 480 帧/9.6s 的算账一致）。
- 未改：`track.len >= needFrames` 那一条（保留），`else` 分支（重模拟 + `missingIds`）一行未动。

## 三、反例实验：修前取位失效 / 修后恢复（**同一探针、同一场景对拍**）

探针：`node _tools/headless/_probe_reanchor_fix.js --frames=900`
（场景：无头 Chrome + 虚拟时钟，1 具脚本人操 `tank_a`（每 40 帧转一次 + 持续开火）+ 1 Laika + 2 vantage；

`px` = **产品自己的 `trackPosAt(th, relTime)` 的"现在"取位**、`rx/ry` = 真实弹位；

- 上表 after1~3 的 Δmax（2.3~5.7s）与 null 计数里，**取位 null 的样本全部落在 `cover<1s` 的「寿命截断型」轨迹上**
  （能拆分的两次跑实测：`afterA` = 156/156、`v168-gate` = 0/0——后者根本没有短轨迹样本）
  这类轨迹 `len<needFrames` ⟹ **每次 commit 都被重模拟**（Δ≈0），它 null 是因为
  "一个 commit 间隔内 Δ 就超过了这条只有 0.03~0.2s 覆盖的轨迹末端"——**既有机制，与本次的门无关**。
- 修后仍有 `len=562` 的 Δ 越界到 **1.10~1.22s**：门只在 **commit 那一刻**取界，
  commit 之间 Δ 继续按时间增长（`Δ = Δ_commit + 段内已过时间`）。属门语义的固有边界（注释按 480 帧/9.6s 算的余量足够）。

### 3.3 判死侧的后果（为什么要修）

Δ 越过覆盖后，报的 §3.5 清单里这几条同时成立（都在产品函数里）：
`trackPosAt`/`threatPosAtTree` 返回 **null**（本实验直接测到 344 次）⇒「弹在树里消失」；
`threatCoarseBox` 的时空窗 `[abs0, abs0+len·tdt]` 整体落到过去 ⇒ 节点粗筛判"时空不相交" ⇒ 跳过死亡重扫 ⇒ **假绿**；
`threatCurrentPoint` 钳到轨迹末帧 ⇒ 幻影静止弹 ⇒ **假红**。
修后满窗口型的取位 null = 0、深节点查询重新落在覆盖内 ⟹ 这一族后果被掐掉。

### 3.4 方向性自检（游戏常识）

- 弹的 `BULLET_MAX_LIFETIME = 10.0s`，而轨迹覆盖 9.37s ⟹ **满寿命弹的锚点年龄本来就会超过覆盖**，
  这与"轨迹长度按 `horizon+EVAL` 截断"是同一个数量级 ⟹ 必须靠门拦住，不能靠子弹自然死亡。
- 修后 Δ≤1.0s 换来的是"最多多看 1 秒的陈旧轨迹"（轨迹保真度：修前 Δ 大时的取位误差 med 0.88m / p90 21.97m / max 49.37m，
  那是"用 20 秒前的预测当现在"；修后 Δ≤1.2s，误差回到 1m 量级）。

   ⚠️ **我没有确证**（探针拿不到 `ai._vantageAdapter`：本轮场景里它是 undefined，`_dbg_gate3` 打点失败）。
   **建议**：下一轮在该早退处加只读计数（并在 `hasKids===false` 分支给锚点归零前加断言），定位后再决定。
   **这一条要不要改，请主人拍板——它超出"改一处门"的范围。**
2. **寿命截断型轨迹（`len<needFrames`，覆盖 0.03~0.2s）的取位 null**：修前修后都在（那些轨迹每次 commit 都重模拟），
   修后实测仍有 156~193 个这样的样本。**不在本次范围**，但它是"Δ 超过覆盖"的第二个来源，建议单开一项核算。
3. **只有 1 局实战录像**（368 个 Δ 样本、只有 BULLET 一族）：激光/导弹/破片/霰弹/加特林的 Δ **一个样本都没有**。
   要它只能专门录一局用这些武器的实战（《锚点年龄Δ实战复算》§五.1 的老问题）。
4. **无头环境的 `_timeAcc` 与泵帧数不同步**：本轮 900 帧走到的树时间 ≈30s（≈2×），
   **【推断】**`resolveWorldDt` 在无头下吃到真实墙钟步长（~34ms）而不是虚拟 16.67ms。
   ⇒ **Δ 的绝对秒数在无头场景里偏大**；但 Δ 与覆盖是**同一把尺**（取位 null 的边界实测 9.366 vs 覆盖 9.37 精确对齐），
   §三/§四结论不受影响。要把"秒"写进定案时请留意。
5. §四的"重模拟 1.2~2.1×"是**场景总量**（被寿命截断型弹主导）；单看满窗口型是 0.18/s → 3.6~5.5/s。
   若要"全弹轨迹每 1 秒一次"的干净数字，需把两类弹分开统计后再重录一局。
