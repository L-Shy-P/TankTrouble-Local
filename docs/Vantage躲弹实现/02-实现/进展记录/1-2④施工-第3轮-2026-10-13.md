## 一 本轮做完的：「下一格表」预计算（**已实测 PASS**）

### 1.1 它是什么（已批准的 ABI v12 前置件）

```
Uint8Array( w*h * w*h )   下标 = fromIdx*(w*h) + toIdx（idx = y*w+x）
  值 = 「下一格」下标；255 = 该格对不需要/不可算
       （from/to 非 reachable、或 4 连通距离 ≤1 ⟹ 真游戏走 tank-exact、不查最短路）
```

* **距离口径 = 4 连通 BFS**（`maze.getDistancesFromPosition/getDistanceToPosition`）；
  **下一格 = 8 连通 jKstra 双向 Dijkstra 的首步**（用**游戏自己的 API** 算，不在 Rust 复刻）。
* **一局一次**（16×10 迷宫 = 25.6 KB），`maze_id` 变则重建 = 失效机制；实测建表 **< 0.01 ms**（7×4 / 650 格对）。

### 1.2 独立验证（三条互相独立的判据，`_probe_next_tile_table.js`）

```
建表: {"ok":true,"w":7,"h":4,"pairs":650,"computed":650,"skipped":0,"ms":0}
对拍: {"n":28,"nz":650,"eq":650,"neq":[],"walkOk":650,"walkBad":[],"sentinelOk":134,"sentinelBad":0}
★ 判定: PASS（表 == 游戏API；行走法全部到达；哨兵全对）
```

1. **逐格对拍** 650/650 —— ⚠️ 与建表同源 ⟹ **只证明"我没写错索引/循环"，不是语义证明**（诚实标注）。
2. **★ 行走法（真独立）**：从任意格沿表连续走，每步用**我自己按 `_createGraph` 的 8 连通墙条件重写**的判据
   独立判定合法性 ⟹ **650/650 都能走到目标（或按设计停在离目标 1 格处）** ⟹ 表的**语义**成立。
3. **哨兵** 134/134：不该有值的格对恰好是 255，0 错。

### 1.3 过程中的坑（纪律④的又一例）

行走法第一版把"走到 255"当**失败** ⟹ 650 个格对全 FAIL。**真相**：表**本来就不该**覆盖"离目标 1 格"
（那是 tank-exact 分支）⟹ **255 是设计行为**。**先验自己的判据**，别先怀疑产品。

## 二 ★★ 三条结构性事实（全部带 `文件:行`，这是本轮真正的产出）

### 2.1 事实①：JS 融合世界 = **一颗共享弹体 + 9 个候选** ⟹ 制导必须 N 弹体（**已批准，未施工**）

* `vantage_sandbox.js`：`fc.bulletSlots` 是**共享**子弹槽；候选是 `fc.candidates[i]`（9 个）**在同一个 Box2D 世界里**。
* 死亡判定（同一文件，接触循环）只读 `sensorUd.opIndex`，**不辨是哪一颗弹** ⟹ 多弹体不配对就会**假死/假活**。
* 激光之所以可以共享：**激光与目标无关**（纯弹道）⟹ 一颗共享弹体对 9 个候选同时成立。
* 制导弹不行：瞄准点 = "朝**目标（=候选）当前格**的下一格" ⟹ **候选不同 ⟹ 弹道不同**。

### 2.2 事实②：**Rust rollout 与 2.1 同构**（更正我第 2 轮的错误陈述）

* `rollout.rs:789-790`：一个世界里 `for op_index in 0..MAX_OPS { candidates.push(create_fused_candidate(...)) }`（9 个候选 body）。
* `rollout.rs:1271-1299` 死亡扫描：只取 `FixtureKind::TankSensor { op_index }` + `other_cat == CATEGORY_PROJECTILE`
  ⟹ **同样不辨弹**；子弹槽 `fc.bullet_slots` 也是共享的。
* ⟹ **选项 A 的 N 弹体 + 配对过滤要在 JS 融合与 Rust rollout 两处各做一遍。**

### 2.3 事实③（新，**必须拍板**）：**Rust rescore 根本不跑物理** —— 它是**折线回放**

* **【代码原文】**`rescore.rs:1101 verify_death_for_node`：对每帧、每个威胁，
  `let pos_k = threat_bullet_pos(th, t_k);`（≈`:1158`）；而 `threat_bullet_pos`（同文件，注释原文
  "Threat bullet position (exact JS `threatBulletPos` semantics)"）的取位是
  **`th.track`（预计算折线）按 `q/FRAME_DT` 取下标**，退化时走 **`th.path`（直线折线）**；
  帧间速度 `(vx,vy)` 是**相邻两点差商**（`:1181` 附近）。**全程没有 Box2D 步进弹体。**
* ⟹ **rescore 是纯几何回放**："沿给定折线飞"。而**制导弹的轨迹依赖坦克轨迹**
  （每个 node 的 `node.samples` 不同）⟹ **固定折线在结构上装不下制导**。
* 旁证：同一函数开头（`rescore.rs:1112`）本来就有 `TODO(阶段1-2ab收尾)`：
  「只喂 path（无 track 折线回退）时会沿折线飞过销毁点（59/28 vs -1）；修它需 ABI 弹种 + 销毁状态跨帧持久，**属设计变更**」
  —— **本次的制导弹是同一族问题**，不是新怪癖。
