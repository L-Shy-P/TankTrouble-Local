## 一 ★ 你要我"先验"的那个前提：**路线 B 能不能把 th.track 喂给 rescore？**

### 1.1 内容层：**能**（制导轨迹可以按 node 算出来）

* 制导每帧是**纯确定运算**：`(导弹状态, 该帧坦克位姿, 迷宫表)` → 下一帧速度
  （依据：实测《导弹制导实测-2026-10-13》§2.3——逐帧逐分量 **172/174、164/169 bit-exact**）。
* 而 **rescore 的每个 node 自带 `node.samples`（该 node 的坦克逐帧位姿）**（`rescore.rs:1101 verify_death_for_node`
  的参数 `node: &RescoreNodeInput`）⟹ **给定 node，JS 完全能算出一条制导轨迹** ✓
* 【推断】JS 侧生产者可复用与融合世界**同一个 `steer()` 步进函数** ⟹ **一份实现两处用**
  （这正是你选 B 的理由："JS 融合本来就要模拟制导 ⟹ 理论上可以共用同一份模拟"）✓ **成立**。

### 1.2 投递层：**装不下** ⛔（这就是"格式装不下"，我按条件③停下来报告）

* **【代码原文】**`vt_rescore_nodes` 的威胁形参（`lib.rs`）：`threat_track_counts: *const u32`
  + `track_x/track_y/track_alive: *const f64/u8` —— **长度按 `threat_count`**（每威胁**一条**），
  而 node 是 `node_count` 个**共用这一组威胁**。
* **【代码原文】**`rescore.rs` 取位：`let t_k = node.start_t + k*dt; let pos_k = threat_bullet_pos(th, t_k);`
  —— **同一威胁、不同 node、同一个 `t_k`** ⟹ 若 track 只有一条，**所有 node 会被喂同一条制导弹道**，
  而正确语义要求 **每个 node 一条**（导弹追的是"那个 node 的坦克"）。
* ⟹ **现有 ABI 布局无法表达「node × threat」的轨道** ⟹ **路线 B 需要先解决"投递"，二选一：**

| 选项 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **B1（改 ABI）** | `vt_rescore_nodes` 加一段「**每 node 的制导弹道**」尾参（`node_count × threat_count` 展开，配 per-threat 的长度游标；非导弹 threat 传 0 长度） | ~150 行（lib.rs + bridge + JS 生产者） | 中（新布局要钉死） |
| **B2（不改 ABI，改调用形状）** | **bridge 在"有制导弹威胁"时按 node 逐个调用** `vt_rescore_nodes`（1 node/次），每次带该 node 算好的 track | ~60 行（bridge 循环拆批）+ JS 生产者 | 低（Rust 一行不改）；代价=多次调用（rescore 本来只在刷新时跑） |

* **【我的建议】B2**：Rust 侧 0 行（正是你选 B 的初衷），且**不需要动 ABI 布局**；
  唯一代价是"有制导弹时 rescore 调用次数 = node 数"，而它只在**刷新**时发生、且导弹在场才有。
  **但这属于"改调用形状"，按条件③我停下来等你一句话**（要不要按 B2 拆批，或走 B1 加尾参）。
