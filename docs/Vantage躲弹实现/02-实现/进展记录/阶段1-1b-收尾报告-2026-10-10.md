**新采样顺序**（`vantage_tree.js:7179–7235` 的逐行逻辑）：

1. 先用 `gc.lastUpdate`（`Date.getTime()` 或 number）当**去重键**——同一个 `lastUpdate` = 这一帧没有 update，不采样（原逻辑保留）；
2. 墙钟差分照旧算出来（`(Date.now()-ms)/1000`，`cap*1.5` 拒绝口径与 `resolveWorldDt:1481` 一致），**但只进交叉校验**；
3. 主样本：`dPerf = (performance.now() − 上一次采样时的 performance.now()) / 1000`，同样过 `cap*1.5` 口径；
4. `performance.now()` 不可用时（老环境/离线沙箱）才退回墙钟样本（来源标 `wall(无performance.now)`）。

**为什么"自分差"就等于游戏的 dt**（这是本修正的关键前提，**用探针实测过**，见 §三.1）：
树 tick 由 `ai_vantage.js:93` 在**坦克 update 里**触发，而 `GameController.update()` 的 `roundController.update(deltaTime)` 在它之后 ——
事件序实测是 `tick → upd_in → upd_out`（同一帧、位置固定）。
⟹ 相邻两次 tick 的 `performance.now()` 之差 ≈ 相邻两次 `gc.update` 入口之差 = 游戏喂给物理的 `deltaTime`（见 `_p11b_pnow_analysis.jsonl`）。

**三条边界处理**（每条都写进代码注释了）：

1. **第一个 perf 样本没有基线** ⇒ 返回 `null`（不硬凑）。代价：切稳定值从第 4 帧推迟到**第 5 帧**
   （改前 f4 切、改后 f5 切；仍 ≤ 权威版 §7.10 G.2 的"K 例如 5"）。
   【推断】我**没有**拿第一帧的墙钟样本去凑（那会把一个量化样本混进中位数窗口）——如果你更想要"第 4 帧就切"，把
   `vantage_tree.js:7224` 的 `if (prevPerf === null) return null;` 换成"用 wall 兜第一帧"即可（会引入 ±1ms 的量化样本）。
2. **基准无论如何都推进**（`_frameDtLastPerfMs = pnow` 在 return 之前）——否则掉帧/长停顿后的下一帧会被算成"两帧间隔"。
3. **没改** `applyFrameDtSample`（5% 抖动带 / K=4 / 中位数 / 去掉 `[0.015,0.03]` 钳位全部原样），
   **没改**训练模式优先级（`rm._ttStepCount / _ttLastStepDt` 仍然最优先），**没动** `resolveWorldDt`（含保护行 `vantage_tree.js:1466`）。

## 三、验证证据（全部可复跑，命令见 §六；日志在 `_tools/headless/prof/_p11b_*`）

### 3.1 探针：树 tick 的时钟结构（`_probe_p11b_pnow.js`，**新增**）

把 `VantageTree.tick` / `gc.update` 在**页面内只读包一层**（不改文件、不改参数），记录每次调用的 `performance.now()` / `Date.now()` / `gc.lastUpdate`：

```
hook: gcPatch=instance-ok tickPatched=true pnow=function
ticks=60 upd_in=60
dPerf(ms) 中位=16.6667 范围=[16.6667,16.6667]      ← performance.now() 自分差：精确等于 __vt.dt = 1000/60
dWall(ms) 中位=17      范围=[16.6667,17.3333]      ← 老口径 now−lastUpdate：被整数毫秒量化
dLu(ms)  中位=17       范围=[16,17]                ← lastUpdate 自身差分（Date，整数毫秒）
前 12 tick 事件序：tick@2383.333 upd_in@2383.333 upd_out@2383.333 tick@2400.000 upd_in@2400.000 …
```

**两条结论**：

1. **`performance.now()` 自分差没有量化**（60fps 恒 16.6667ms，浮点）；老口径恒在 16/17/17.33ms 之间跳。
2. **树 tick 发生在 `gc.update()` 之前**（`tick → upd_in → upd_out`，同一帧、相对位置固定）⟹ 自分差 ≈ `deltaTime`，
   所以"用 perf 自分差当校准样本"在时序上是成立的（这不是我猜的，是探针打在事件序上的）。

## 四、没解决 / 拿不准 / 请拍板

1. **【推断】performance.now() 采样点假设**：我把"树 tick 在 `gc.update()` 之前、位置固定"当成前提（探针在本 build 实测成立）。
   若以后有人把树下 tick 的位置挪到 `gc.update()` **之后**，perf 自分差会变成"帧内耗时"（≈0）而不是帧长——
   那时 `crossMiss` 会立刻爆表 + 响一次 warn，**这就是我保留交叉校验的主要理由**。
   ⚠️ 另外：多辆 vantage 车时，`_frameDtSampleKey` 去重保证一帧只采一次，但"哪辆车的 tick 先跑"若换序，
   自分差会额外带上两辆车 tick 间隔的抖动（【推断】量级 <1ms，且会被 5% 抖动带吞掉）。本机只测了 1 辆 vantage 车。
2. **【推断】首帧放弃**（§2.1 边界 1）：代价是掉帧矫正从"第 4 帧"挪到"第 5 帧"。文档给 K=3~5，仍在范围内；
   想回到第 4 帧就用墙钟样本兜第一帧（一行改动，见 §2.1）。**请拍板**要哪种。
3. **交叉校验容差 1ms** 是"Date 量化上限"（严格 <1ms）；正常运行时 `crossMaxMs` 会稳定在 0.5~1ms 量级（本例 0.667）。
   若真机上看到 `crossMiss` 偶发 +1（比如浏览器把 `performance.now` 降到 2ms 精度，Firefox RFP），
   **不代表故障**，那正是这条校验该暴露的"两个时钟不再同源"。

   真机掉帧时自分差的抖动分布。**【推断】只会更好**（真机 perf 精度 ≥ 虚拟时钟），但没有实测数据。
