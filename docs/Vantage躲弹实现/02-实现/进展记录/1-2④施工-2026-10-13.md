## 三 ★ 新发现的结构性冲突：**融合世界是"一颗弹体 + 9 个候选"，制导弹装不进去**

> 这是我准备动手做 JS 融合路径时，读 `simulateFusedBatch` 内部才发现的 —— **四条 D1~D4 决策都没覆盖它**，
> 所以我停下来报告，没有自己发明。

### 3.1 事实（代码原文）

* `vantage_sandbox.js` 的融合世界：**候选坦克**有 N=9 个（`fc.candidates[i]`，每个 = 一种操作序列的未来位姿），
  但**子弹只有一套**（`fc.bulletSlots`，body 共享）；死亡判定是"**这颗共享弹体** 碰到 **候选 i 的 sensor**" ⟹ `dead[i]=true`。
* 激光为什么可以这样？因为**激光与目标无关**（纯弹道）⟹ 一颗共享弹体对所有候选都成立 ✓。
* **制导导弹不是**：`HomingMissile.update` 的加速方向 = "**朝迷宫图下一格**"，而"下一格"取决于
  **目标（=我方坦克）当前在哪一格** ⟹ **候选 i 的轨迹不同 ⟹ 导弹的轨迹也不同**。
  ⟹ 一颗共享弹体**在数学上不可能**同时对 9 个候选成立。
* 而且现有代码里"共享弹体"还会**互相污染**：`dead[op]` 的判定只看"有没有 PROJECTILE 撞到候选 op 的 sensor"，
  **不区分是哪一颗弹**（`vantage_sandbox.js` 接触循环里只读 `sensorUd.opIndex`）；
  多放几颗弹体的话，A 弹的命中会算到 B 候选头上。

### 3.2 三条可选路线（**我建议 A，但请拍板**）

| 选项 | 做法 | 代价 / 风险 |
|---|---|---|
| **A（我建议）每候选一颗弹体** | 导弹在融合世界里开 `N=9` 个同起点弹体，每个朝自己的候选制导；接触判定加"**只认同 op 的那一颗**"（给 fixture userData 加 `homingOp`）；滚弹子/寿命/反弹记账同步 per-copy | 改动集中在 `acquireFusedBullet` + `simulateFusedBatch` 内循环 ≈150 行；**性能 ×9（仅导弹）**；风险=接触配对过滤写漏就会造**假死/假活**（必须配 2×2 退化对照） |
| **B 只算"追我方那一颗"** | 融合世界里保持 1 颗，但制导目标改用**真实世界那辆坦克当前所在格**（不是候选未来） | 便宜，但**对 9 个候选是同一个轨迹** ⟹ 与"给定候选轨迹能精确算"的定案（§12.16 表）**冲突**，等于把 D4 的相位差问题放大成结构性错误 |
| **C 暂时不进融合世界** | 导弹保持 v172 的"普通圆弹近似"，只在文档/audit 里标 `missileApprox=true` | 不改结构，但**明知不对**（轨迹差），且违反你批准的"落融合世界逐帧制导" |

### 3.3 ★ 另一个必须一起定的 ABI 细节：**别在 Rust 里复刻 Dijkstra**

我本来打算"D3 方案 A：Rust 内自建 BFS"，读代码后发现**不能**：

* **目标选择**用的是 `maze.getDistancesFromPosition()` = **4 连通 BFS 距离**（`_traverseCloseTiles`）——这个**可以**在 Rust 忠实复刻（无平局问题）✓
* 但**瞄准点**用的是 `maze.getShortestPathWithGraph(start, end)[0]` —— 那是 **jKstra 的
  `Dijkstra.shortestPath`**，而它是 **【双向】Dijkstra**（`2e2acf87850d72356447904f0853591b.js:1`：
  `outIteraror` / `inIterator` 轮流推进、`_hasBeenReachBothWays` 相遇即停），
  且**允许 4 个对角方向（cost √2）**。**平局时走哪条最短路 = 该库实现的细节**，Rust 侧复刻它的堆行为**既贵又脆**。

**⟹ 我建议（D3 的修正版）**：ABI 里传一张 **"下一格表"**（JS 用**游戏自己的 API** 预计算，
`w*h × w*h` 个 u8；16×10 迷宫 = 25.6 KB，**一局一次**，Rust 按 `maze_id` 缓存），
Rust 只做**查表 + 4 连通 BFS（算距离）**，**不实现 Dijkstra**：

```
vt_set_maze(maze_id: u32, w: u32, h: u32,
            flags: *const u8,       // 每格 1 字节：bit0=reachable(distances!==null) bit1=leftWall bit2=topWall bit3=floor
            next_tile: *const u8)   // w*h*w*h：由 JS 用游戏 maze.getShortestPathWithGraph 预计算；255=无
   → 返回已缓存/新缓存；两个批处理入口都带 maze_id，id 变了就重建（= "maze 变了"的失效机制）
```
这样**忠实性由构造保证**（同一张表就是游戏自己算的），且**平局行为不可能分叉**。
