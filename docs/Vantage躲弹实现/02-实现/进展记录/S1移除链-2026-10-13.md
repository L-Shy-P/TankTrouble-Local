## 一、一句话结论

> **§12.3 的三件事里，② 摘除本来就有半边（槽按真实弹列表逐轮 acquire + 未被 acquire 的 body 停用），
> ① 识别 与 ③ 更新受影响帧的生死 完全缺；本轮把三件事补齐并证明了它们真的生效：**
> **子弹因"有人非正常退出"被移除 ⟹ 融合世界的槽 `retired=true / bodyActive=false / hasProjObj=false`（槽真的空了），
> 且被它判死的帧经纯函数放活 `dead:true(0) → dead:false(-1)`，`monotoneOk:true`（不重跑任何物理/接触）。**
> **假阳率**：同一轮里 3 颗弹消失，其中 **2 颗是正常消失（1 超时 + 1 撞掉）**——
> **naive 口径（只看"id 从列表消失"）会对这 2 颗全部误报（假阳率 2/3 = 66.7%），
> 本实现 0/3 = 0%**（因为它按**游戏自己的事件**分类：有 `PROJECTILE_TIMEOUT`/`PROJECTILE_DESTROYED` = 正常；
> 只有"踢人"那条路才无事件、并带 `TANK_CHICKENED_OUT` 名单）。
>
> ⚠️ **一条需要主人/父代理裁的事实**：`§10.2` 写"非正常消失 = **击杀对手** / 有人非正常退出"，
> 但**本仓 `RoundModel` 源码里"击杀"那条路只删坦克、不删弹**（见 §二.4 原文）⟹
> "击杀对手 → 他的子弹全消失"**在这份 build 里不成立**（本轮实测也确认：踢人路径删弹、击杀路径不删）。

## 二、现状到底覆盖到哪（**施工前读码结论**，别信 `v136` 注释）

### 2.1 【有】② 摘除：**半边已经存在**（按真实弹列表逐轮重建 + 未用的槽停 body）

`【读码】` `vantage_sandbox.js`：
- `:2085-2088`（`simulateFusedBatch` 摆弹入口）**枚举的是真实弹表**，不是树给的威胁表：
  ```js
  var projectiles = gameController.getProjectiles();
  for (id in projectiles) { … var slot = acquireFusedBullet(fc, pr, operations.length); … }
  ```
- `:1722 acquireFusedBullet()`：按 `lastRound !== fc.round` **轮询复用**槽；本轮被 acquire 的槽才有 `lastRound = fc.round`。
- `:1802 parkUnusedFusedBullets(fc)`：**本轮没被 acquire 的槽 ⟹ `body.SetActive(false)`**（制导弹的 N 个副本一起停）。

⟹ **结论**：真实世界里没了的弹，**下一批就不会再进融合世界**；它的 body 会被停用。
**这半边本来就是对的**——所以"消失的弹继续在融合世界里判死"这个隐患**不存在**（`v136` 注释担心的"在它仍存活的那几帧里整颗消失"是**另一件事**：
那是 `slot.active` 被 `lifeLeft<=0` 关掉造成的 **placement 期**误关，`v137` 已修，与"移除链"无关）。

### 2.2 【无】① 识别：沙箱**从来没有**"这颗弹不该再存在了"的显式信号

`【读码】` 沙箱里只有**放置类**的记账（`_fusedDropStats`：`approxPlaced / noThreat / skipped / droppedTargetOther`），
**没有任何"移除/消失"的计数器或名单**。唯一做识别的地方在**树**里（`vantage_tree.js:8180`：
`removedIdsBetween(oldSig, sig)` + `:8183 removeThreatsByIds(_tree, removedIds)`）——
它只把 threat 从树里摘掉，**不碰已算出的生死**，而且那份识别没有和"这是正常消失还是非正常消失"分开。

### 2.3 【无】③ 更新树里受影响帧的生死：**完全没有**

`【读码】` `simulateFusedBatch` 的产出只有 `{samples, hitWall, dead, deathFrame}`；
**没有任何"这颗弹是凶手"的溯源**（几处死亡点只写 `dead[op]=true; deathFrame[op]=k`）。
⟹ 就算知道某颗弹被移除了，**也没法知道哪些帧是被它判死的** ⟹ 无从"放活"。

### 2.4 【口径】"弹为什么会没"——以**游戏自己的代码**为准（这是本轮判据的根据）

`【读码】` `_tools/headless/_i4_tmp/_i4_game_roundmodel.js`（美化副本；原文件 `game_core/js/46989e39….js`）：

| 路径 | 源码位置 | 是否派发事件 | 语义 |
|---|---|---|---|
| `timeoutProjectile(id)` | `:750-760` | ✅ `PROJECTILE_TIMEOUT` | **寿命到了 = 正常** |
| `destroyProjectile(id)` | `:738-748` | ✅ `PROJECTILE_DESTROYED` | **撞掉/被吃掉 = 正常**（调用点：`roundcontroller:125/159` 的接触处理） |
| `removeTank(playerId)` | `:230-254` | ❌ **没有任何 `PROJECTILE_*` 事件**；只把该玩家**所有弹**塞进 `destroyedProjectileIds`（随后 `_removeDestroyed()` `:944-949` `delete this.projectiles[...]`），并派发一个 **`TANK_CHICKENED_OUT`**，载荷 `ChickenOut.getProjectileIds()` | **§10.2 的"有人非正常退出 → 他的子弹全消失"** |
| `killTank(kill)` / `destroyTank(playerId)` | `:641-649` | 只有 `TANK_KILLED` / `TANK_DESTROYED`；**玩家**进 `destroyedPlayerIds` | ⚠️ `_removeDestroyed()` `:920-943` **只删坦克 body / weapon / upgrade，不删弹** ⟹ **击杀不会让他的弹消失** |

⟹ **本文档的"非正常"判据 = 弹没了、但既没有 `PROJECTILE_TIMEOUT` 也没有 `PROJECTILE_DESTROYED`**（或直接收到 `TANK_CHICKENED_OUT` 的名单）。
这条判据是**零歧义**的（正常路径必派事件），所以**假阳率可以做到 0**（§四.2 实测）。

### 2.5 §12.3 的"移除类是单调的 ⟹ 不用重检"这个论断，代码能不能直接支持？——**能，且这正是本轮实现方式**

`【读码】` 死亡帧的唯一来源是**已记录的接触/几何/扫掠命中**（`:2749` 接触、`:2466` 几何、`:2510` 扫掠），
`deathFrame[op] = k` = **第一次**命中帧。把某些"凶手"剔掉之后：
- 若还有别的凶手 ⟹ 取它们里**最早**的帧 ⟹ **只可能 ≥ 原帧**（更晚）；
- 若凶手全被剔掉 ⟹ 该 op **回到活**。
两个方向都**不需要重跑 Step**（信息在记录里），且**不可能出现"活→死"或"死得更早"** ⟹ 单调 ✓。

## 三、改了什么（**三件事各一处**；行号 = 改后）

### ① 识别 —— `scanProjectileRemovals(gameController, liveProjectiles)`（`game_core/js/vantage_sandbox.js:3535`）

- 新增一个**独立订阅式账本** `_vtEnsureProjectileLedger(gc)`（`:3501`，挂在 `GameController.addRoundEventListener` 上，
  与 2-2 死亡采集器**同一个成熟机制但不同 handler** ⟹ 不挤占它的 `subCount===1`）：订阅
  `PROJECTILE_TIMEOUT` / `PROJECTILE_DESTROYED` / **`TANK_CHICKENED_OUT`**（`ChickenOut.getProjectileIds()`）/
  `ROUND_CREATED`（**换局清账**：上一局的弹全没了是正常的，不许记成移除）。
- 逐批对比真实弹列表：`消失 = 上批见过 − 这批还在`，然后**按事件分类**：
  `normalTimeout` / `normalHit` / `abnormalExit`（踢人名单）/ `abnormalNoEvent`（无事件且残寿未尽）/ `heuristicNormal`（无事件但残寿 ≤1.5 帧）。
- 累计账 `getRemovalStats()`：`seenTotal / vanishedTotal(=naive 口径) / normalTimeout / normalHit / abnormalExit / abnormalNoEvent / roundResets`。
- 只读：不碰任何 body、不改任何判死结论。

### ② 摘除 —— `retireFusedBulletSlots(fc, removedIds)`（`:3625`，批次里自动调用点 `:2361`）

- 对"已被判为非正常移除、且本轮没被 acquire"的槽：`retired=true`、`removedReason='abnormal-removal'`、
  `active=false`、**`projObj=null`**、清 `bounces/hitThisFrame/sweepPrev`、`body.SetActive(false)`、制导副本一起停。
- 只做**显式化 + 清残留**（这些槽本来就不会再进判死）；`getFusedBulletSlots()` 把它们暴露出来供自证。

### ③ 更新受影响帧的生死 —— 死因溯源 + `releaseDeathsAfterRemoval(deaths, removedIds, causesTable)`（`:3661`）

- **溯源**：三处死亡点各记一条 `{frame, bulletId, src}`（`contact` / `geometry` / `sweep`）到 `_lastDeathCauses`（`:1538`，带批次号 `_lastDeathCauseSeq`）。
  ⚠️ 接触那处**必须问"这个刚体本轮是谁"**（新增 `_vtFusedBodyPid(fc, body)`，`:3611`）——
  槽是轮询复用的，融合体 `userData.gameObject` 是**建体那一刻的老弹**，直接读它会**张冠李戴**（探针第一版实测抓到）。
- **放活（纯函数，不重跑死亡检测）**：把归因表里"凶手是被移除的弹"的原因剔掉，取剩余原因的最早帧；
  没有剩余 ⟹ `dead=false, deathFrame=-1`；**归因不明（无记录）⟹ 保守不动**。
  返回 `{results, released, moved, kept, unattributed, monotoneOk, usedOwnCauses}` —— 自带**单调性自检**（`deathFrame` 只许变大、不许"活→死"）。
- ⚠️ 归因表必须与 `deaths` **同一次批次**：缺省用"最近一次批次"，两次之间跑过别的批次时必须**显式传**（探针第一版就踩了这个）。

### 4.2 【假阳率】"弹没了"在**正常消失**时会不会被误报？

| 用例 | 怎么造 | naive 口径（只看 id 从列表消失） | **本实现** |
|---|---|---|---|
| FP-1 正常**撞掉** | 调游戏自己的 `destroyProjectile(id)`（`roundController:159` 那条路） | 会说"移除" ✗ | `normalHit=[id]`、**`abnormal=[]`** ⟹ **不报** ✓ |
| FP-2 正常**超时** | 什么都不做，等它自己到寿命（实测 `age` 到点后消失） | 会说"移除" ✗ | `normalTimeout=[id]`、**`abnormal=[]`** ⟹ **不报** ✓ |

**全轮累计账（`getRemovalStats()`，J 步）**：
```
seenTotal=6  vanishedTotal=3  normalTimeout=1  normalHit=1  normalHeuristic=0
abnormalExit=1  abnormalNoEvent=0  roundResets=0  errors=0
```
⟹ **naive 口径假阳率 = (3−1)/3 = 66.7%**（2 个正常消失全被误报）；
**本实现假阳率 = 0/3 = 0%**（唯一那次"非正常"被 `CHICKENED_OUT` 名单零歧义命中，`abnormalNoEvent=0` ⟹ 连启发式兜底都没用上）。
**注意分母是"这一轮真发生的消失次数"**，不是"人工构造的用例数"——2 个正常用例就是这一轮里真实的正常消失。

### 4.3 【单调性】移除只会让帧**从死变活 / 死得更晚**，绝不反向

| 用例 | 构造 | 结果 |
|---|---|---|
| **C**（上表） | 唯一凶手被移除 | `dead:true → false`、`fd:0 → -1`、`monotoneOk=true` ★ **死→活** |
| **G** | 两凶手（早到 + 晚到）+ 一颗无关弹 | 移除**早到**那颗 ⟹ `released=1`（`dead:true → false`）、`monotoneOk=true` ★ 方向正确（死→活） |
| **H** | 移除**无关**那颗（不在任何死因表里） | `kept=1, released=0, moved=0`；`{dead:true,fd:0} → {dead:true,fd:0}` ⟹ **一个字节都没动** ★ 负例 |
| **I** | 两颗凶手**都**移除 | `released=1` ⟹ `dead:false` ★ |

**单调性自检**：上面每一步 `monotoneOk` 都是 `true`（函数内部逐条断言：`dead` 不许 false→true；`fd` 不许变小）。

> ⚠️ **诚实登记（未演示到的那一支）**："移除早到的凶手 ⟹ `deathFrame` **变大**（死得更晚）"这一支本轮**没能在真局面里演示**，

> 实测证据：F 步 `causes` 只有早到那颗（`{frame:0,bulletId:早}`）；晚到那颗确实被正确摆进了融合世界

> ⟹ 这是**"死因溯源只覆盖首个凶手"这一已知限制**，见 §六.1（要补则需把记录扩到第 2/3 个凶手，属下一步）。
