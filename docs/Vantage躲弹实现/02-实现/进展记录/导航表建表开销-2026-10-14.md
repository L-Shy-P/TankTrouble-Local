## 一 一句话结论

1. **反证成立、但适用条件要说清**：页内 `performance.now()` / `Date.now()` **在虚拟钟下被接管**，
   **同一次 eval 内的同步计算不会让它们走**（20 000 000 次循环：页内 delta **0 ms**，同一循环 Node 侧 **8.68 ms**）
   ⟹ **"在某一次 eval 内部测同步耗时"一律无效**；而 **跨 eval/跨帧打的时间戳仍然有效**（虚拟钟在帧间会走）。
2. **但 `117 ms` 不是页内测的**：它在 `_probe_missile_perf.js`，用的是 **Node 侧 `process.hrtime`（2 处）、0 处 `performance.now`**，
   只是它跑的是一个**探针里的假迷宫**（`makeMazeFake`，非游戏 jKstra）+ **30 次热均值**。
   ⟹ `117 vs 652` 的差**不是**计时器问题，而是 **假迷宫 vs 真迷宫 + 热均值 vs 冷首发**（见 §三-1）。
3. **真迷宫上的产品数字**（Node 侧墙钟）：小迷宫（6×4，504 格对）**冷 5.0 ms / 热 ~3 ms**；
   `16×10`（13.1k 格对）**冷 292 ms**；`20×12`（48.6k 格对）**冷 2812 ms** ⟹ **大迷宫红线确认**（§三-2）。

## 二 ① 反证核实

### 2.1 最小实验（`_probe_navtab_cost3.js`，一次运行内完成）

```js
// 页内（同一次 eval）
var p0 = performance.now(), d0 = Date.now();
var s = 0; for (var i = 0; i < 20000000; i++) s += (i & 7);
var p1 = performance.now(), d1 = Date.now();
```

| 观测量 | 值 | 说明 |
|---|---|---|
| `perfDelta`（页内） | **0** | 同步循环期间 `performance.now()` 完全不走 |
| `dateDelta`（页内） | **0** | `Date.now()` 同样不走 |
| 同一个循环 Node 侧 `process.hrtime` | **8.68 ms** | 循环确实耗时（对照）⟹ 页内 0 是**时钟**问题，不是"循环被优化掉" |
| `perf0 % 1 !== 0` | **true**（`2383.333333333334`） | 真 `performance.now()` 通常有小数，这里的小数来自**虚拟钟**（= `window.__vt.t`） |
| `date0 % 1 !== 0` | **true**（`1791803149326.3333`） | 真 `Date.now()` 是**整数**；这里带小数 ⟹ **已被接管** |
| `window.__vt.t` | `2383.333333333334` | **与 `perf0` 完全相等** ⟹ 两者同源（同一个虚拟钟） |
| `typeof window.__vtStep` | `function` | 虚拟钟的步进器在场 ✓ |

**结论（精确表述）**：
* **无效**：在**一次 eval 内部**给同步计算计时（`t0=performance.now(); work(); t1=performance.now()`）⟹ 恒为 0。
* **有效**：**跨 eval / 跨帧**的时间戳（例如 `_probe_multiai_clock.js` 每帧读 `Date.now()`）；
  以及 **Node 侧**包 `m.eval` 的墙钟（`process.hrtime`）。⚠️ 后者含 CDP 往返（~1-3 ms），
  **所以小块操作要放在同一个 eval 里循环 N 次再除以 N**（`_probe_missile_perf.js` 正是这么做的 ✓）。
* **半有效**：`new Date().getTime()` 在本环境返回整数（`newDateFrac=false`），但它同样来自虚拟钟 ⟹ 仍是冻结量。

## 三 ② 建表开销

### 3.1 `117 ms` vs `652 ms` 的差 = 三个因素叠加（不是计时器问题）

| 因素 | 那个 117 ms | 我的 652 ms |
|---|---|---|
| 迷宫 | **假迷宫**（`makeMazeFake`，BFS+手工回溯；无 jKstra 堆/双向迭代器） | **真游戏迷宫**（`Maze.createRandom` + 游戏 jKstra） |
| 统计口径 | **30 次热均值**（前 3 次预热丢弃） | **best-of-3 冷**（含 JIT 预热） |
| 规模 | 表 `160×160=25 600` 格位；实际"需算格对"取决于可达性 | 13 110 / 21 366 格对（不同随机迷宫可达性不同） |

**⟹ 对产品有意义的数是「真迷宫 + 冷首发」**，因为表**只建一次**（按 maze 对象缓存，`vantage_sandbox.js`
`getMazeNavTables`），那一次就是**冷的**。`117 ms` 低估了约 **5 倍**，且**低估的原因是假迷宫**。

### 3.2 真迷宫上的分解（Node 侧墙钟，本轮实测）

| 迷宫 | 需算格对 | 第 1 次（冷） | 热（3~5 次） | 备注 |
|---|---|---|---|---|
| 6×4（本轮真实局） | 504 | **5.0 ms** | 2.9 / 3.0 / 3.1 / 3.3 / 3.6 ms | **当前游戏实际尺寸 ⟹ 无感** |
| 6×5（上轮） | 648 | 9.4 ms（best-of-5） | — | 同上 |
| 10×6 | 3 406 | 53.6 ms | — | |
| **16×10** | **13 110** | **292 ms** | 310 / 415 / 784 | 与 `652 ms`（21 366 格对）同量级 ⟹ **每格对 ~22–30 µs** |
| **20×12** | **48 606** | **2 812 ms** | 1 356 / 1 517 / 2 387 | 与 `4 772 ms`（56 764 格对）同量级 ⟹ **每格对 ~58–84 µs** |

**增长律**：格对数 ∝ `(w·h)²`，单格对 Dijkstra ∝ `(w·h)·log(w·h)` ⟹ **总开销 ∝ `(w·h)³·log`**。
【推断】外推：`24×14`（336 格）≈ **8~15 s**；`30×20`（600 格）≈ **40~70 s**。

### 3.3 红线（按你要求明确写）

🔴 **`20×12` 量级（≈2 000 万格位表 / 5 万格对）已是 1.4~2.8 s 的一次性阻塞**，
**`30×20` 量级【推断】≈ 40~70 s** ⟹ **该实现在大迷宫上不可用**。
⚠️ 但这**不影响当前产品**：游戏实际迷宫是 5~8 × 4~5（20~40 格），实测 **3~10 ms** ⟹ 现状可接受。
（另：表内存 = `(w·h)²` 字节 —— 16×10 = 25.6 KB ✓；30×20 = 360 KB ✓；**内存不是瓶颈，时间才是**。）

## 四 优化建议（**只建议，未动手**）

| 方案 | 做法 | 省多少 | 代价/风险 |
|---|---|---|---|
| **A. 换图时就建**（最省事） | 把建表从"第一次见到制导弹"挪到**换图/开局**（那时本来就重） | 不省时间，只**挪走"正被打时卡 0.3~2.8 s"这个最坏时刻** | 无（纯时机）✓ **建议至少做这个** |
| **B. 只建用到的 `from` 行**（懒建） | 制导弹每帧只查**它当前所在格**那一行（一行 = `w·h` 个格对） | 16×10：21 366 → **160 格对 ≈ 3000 倍**（单行 ~3 ms） | ⚠️ **只在 JS 融合路可用**（那里知道每候选的弹在哪格）；**Rust rollout 里弹的格由 Rust 决定**，JS 拿不到 ⟹ **救不了 Rust 路** |
| **C. 分摊到多帧** | 每 tick 建 k 行，建完前 Rust 侧该弹**按直飞**（无制导） | 消除卡顿 | 🔴 **语义变化**（短暂近似）——**要拍板**，且会给"假死/假活"开口子 |
| **D. 反向 Dijkstra（`n` 次代替 `n²` 次）** | 对每个**目标格**跑一次反向最短路，得到"所有 from 的下一格" | 16×10：21 366 → **160 次**（≈100 倍） | 🔴 **要么在 Rust 里复刻最短路的平局行为**（当初 D3 就是为避开它才改传表），**要么**用游戏图但自写 Dijkstra ⟹ **忠实性要重新论证** —— **要拍板** |
| **E. 超预算就降级**（兜底） | 建表耗时预估 > 阈值（如 50 ms）就**本局停用制导**并响亮告警 | 防呆 | 语义变化（但比卡 2 s 好）；**建议作为安全阀** |
| **F. 缓存跨局复用** | 同尺寸/同主题迷宫表复用 | 取决于重复率 | 迷宫每局重生成 ⟹ 命中率低，**不建议** |

**我的建议**：**A + E 立刻可做（无忠实性风险）；B 只在 JS 融合路补一刀；C/D 若将来真出大迷宫，作为一个
"带 2×2 忠实性对照的设计变更"来做**（正因为它涉及"近似/平局"，不宜顺手改）。
