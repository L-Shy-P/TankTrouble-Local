## 一、一句话结论

1. **`RoundModel._EVENTS` 是 41 项，不是 40**（全文 `_EVENTS:{…}` 逐项枚举见 §二）。任务书那句「40 个事件」**少算了 1 个**；清单在 §二，41 行一个不少。
2. **A3-O1 的四件套（节点 token / 子弹 token / 根滞后 / 上帧计划）没有一项需要事件总线**：
   - 节点 token 12 维**全部来自树侧**；
   - 子弹 token「**必须独立从 `gc.getProjectiles()` 抓**」（`阶段2冻结点…:198` 原文）⟹ 不订 `PROJECTILE_CREATED/DESTROYED/TIMEOUT`；
   - 根滞后是我们自己的两个时钟相减；
   - 上帧计划是 B 的**输出**（事实直传）。
   ⟹ **事件总线上真正「非订阅不可」的只有【死亡事件】一族（属〔其它〕已定来源）。**
3. **死亡事件里真正非订阅不可的只有 4 个**：`TANK_KILLED`（**唯一**带 killer/弹种）、`TANK_DESTROYED`（毒雾与出生区致死的**唯一**出口）、`TANK_DEADLY_COLLISION`（**唯一**带精确接触点 `data.collisionPoint`）、`TANK_ZONE_COLLISION`（毒雾致死的上游）。**其余 37 个都能轮询替代**（§二逐行给了理由）。
4. **不 wrap `RoundController.killTank` 也能拿到死亡位置。** 机制（§三.2）：`killTank` 只把 pid 推进 `destroyedPlayerIds`，**不删坦克**；删坦克是 `_removeDestroyed()`，而它在 `RoundModel.update()` 里排在**事件派发之后**（`[RM]行1@26346` 那一行的语句顺序）⟹ **在 `TANK_KILLED` / `TANK_DESTROYED` 回调里 `gc.getTank(pid)` 必定还在**。先例 `training_mode.js:4828-4851` 就是这么写的，而且是在 `origKill.call` **之前**读。
5. **wrap 的唯一增量**是「同一行里同时拿到 `kill` 与 tank」以及能在 `RoundController` 层拦截；**代价是产品路径风险**（本项目最痛的那类坑）。⟹ **建议：主业用订阅；wrap 做成可选、缺省关、只在无头/训练显式开**（§三.4）。
6. **顺序问题不要靠注册顺序解，要靠「两个回调都同步抓 + 按 pid 先到先写」解**（§三.5）。理由：本地模式下弹杀**只发** `TANK_KILLED`、毒雾杀**只发** `TANK_DESTROYED`，两者互斥；只有「同帧又中弹又踩毒雾」才可能同帧两条，**此时顺序由 Box2D 接触表次序决定、我们不可控**。
7. **毒雾致死绝对不能靠 wrap `killTank`**——它根本不走 `killTank`（§三.6）。它走 `TANK_ZONE_COLLISION`(STORM) → `RoundController.destroyTank(pid)` → `TANK_DESTROYED(pid)`；**没有 killer、没有弹种**，位置同样在回调里 `gc.getTank(pid)` 拿。
8. **订阅口用 `gc.addRoundEventListener(cb, ctx)`（`[GC]行1@20488`），不要用 `rc.addEventListener`。** 因为 `_createRoundController`（`[GC]行1@12194`）会把 `gc.roundEventListeners` **自动重挂到每回合新建的 RoundController 上** ⟹ **回合重启不需要重订阅**；要清的是**我们自己的每回合死亡缓存**（`endRound` 会 `this.tanks={}`）。
9. **三个已埋着的坑**（§四、§五逐条给对策）：
   - `_notifyEventListeners` **用 `try/catch` 吞异常**（`[RM]行1@31585`）⟹ 我们的回调抛错**不会炸游戏、只会静默丢数据**；
   - 回调签名是 **`(self/ctxt, gameId, evt, data)`**——**第 3 个参数才是 evt**，第 2 个是 gameId；
   - `VantageTree.noteDeath(kill)`（`tree:8178`）**已经存在**、且**会 `_frozen = true`**（`tree:8190`）把树定死 ⟹ 我们的采集器**必须纯读、绝不碰 `VantageTree`**。
10. **A3 边界**：死亡事件的**采集**（谁死 / 位置 / 角度 / killer / 弹种 / 毒雾）/ `TANK_KILLED` 抓取方案 / 订阅生命周期 / 防重复 —— **一律不取决于 A3，现在就能做**（§五 W1~W4）。**只有「死亡事件进不进观测、以什么 token 形式进」取决于 A3**（A3-O1 四件套里没有「事件」这一项，`阶段2-1取数清单…:145` 也这么写）⟹ 见 §六。

### 3.2 回调内读 tank——**那个时刻 tank 还没被 delete**（这是本方案的地基）

**`RoundModel.update(deltaTime)` 的语句顺序**（`[RM]行1@26346`，逐句原文顺序）：

```
update:function(deltaTime){
  if(!this.running){return;}
  this.cachedRoundState=null;
  this._removeDestroyed();                  // (a) 删【上一帧】排队的
  this.b2dworld.Step(deltaTime,10,10);      // (b) PreSolve 在这里生成 collisionEvents
  this._filterAndDispatchCollisionEvents(); // (c) ← 事件在这里派发；killTank/destroyTank 在这里
  this._removeDestroyed();                  // (d) ← 坦克在这里才被 delete
  for(var tank in this.tanks){ this.tanks[tank].update(deltaTime); }  // (e) ← tank.x/y/rotation 在这里刷新
  ...
}
```

**三条结论**：

1. **在 (c) 的任何一个回调里，`gc.getTank(pid)` 必定返回坦克对象** —— 删掉它的是 (d)，而 (d) 排在 (c) **之后**。`destroyTank/killTank` 自己只做 `destroyedPlayerIds.push`（`[RM]行1@20417` / `@20587`）。
2. **绝不许把读位置推迟到回调之后**（`setTimeout` / `Promise.then` / 「等这帧结束再读」）—— (d) 就在同一个 `update()` 里，晚一步就是 `undefined`。
3. ⚠️ **读到的是【上一帧末】的位姿，不是本帧接触瞬间的位姿。** 因为 (e) 才是 `tank.x/y/rotation` 的刷新点（`[TK]行3@7184`：`update:function(deltaTime){this.x=this.b2dbody.GetPosition().x; this.y=...; this.rotation=this.b2dbody.GetAngle(); ...}`），而 (e) 排在 (c) 之后 ⟹ **(c) 时刻读到的 `tank.getX()` 是【第 N−1 帧 Step 完之后】的值**（body 已经是第 N 帧的了）。**滞后 1 帧**。

**三种「死亡位置」的取法对比**（都要在 (c) 的回调内同步取）：

| 取法 | 代码 | 精度 | 需要 wrap 吗 | 备注 |
|---|---|---|---|---|
| **A. 读 Tank 缓存**（**推荐·最简单**） | `var t=gc.getTank(pid); t.getX()/getY()/getRotation()` | **上一帧末位姿**（滞后 1 帧）；`rotation` **弧度** | **不需要** | 先例 `training_mode.js:4837-4843`（在 `origKill.call` **之前**读）。⚠️ 与「判死/树」的帧号口径要对齐——本项目已有「时间基准三层」的血泪（`方针:1-1 补记`） |
| **B. 读 b2dbody（本帧）** | `t.getB2DBody().GetPosition().x/.y`、`t.getB2DBody().GetAngle()` | **本帧 Step 后**（更接近接触瞬间） | **不需要** | 读的是 Box2D 活 body；**世界系 = 米**。⚠️ 若坦克在 (d) 被 `DestroyBody`，**本帧内**读仍安全（(d) 还没跑）【推断】 |
| **C. 读接触点（最准）** | 在 `TANK_DEADLY_COLLISION` 的 `data.collisionPoint`（`[CO]行5@49693`，`worldManifold.m_points[0].Copy()`，米） | **精确接触点**（在坦克**边缘**，非质心） | **不需要 wrap `killTank`**，但需要**订阅 `TANK_DEADLY_COLLISION`**（同一总线） | 同时有 `data.collisionNormal`（法向）；且 `data.projectile` 指向**还没被销毁**的弹（`destroyProjectile` 在 `killTank` **之后**才调，`[RC]行1@5132`）⟹ 还能拿弹的 `getX/getY/getSpeedX/getSpeedY/getType` |
| （D. wrap 后读） | wrap `RoundController.killTank` 里读 | 同 A/B | **要** | **增量只有「同一行拿到 kill+tank」**；信息量不比 A/B/C 多 |

### 3.4 ⚠️ 开关怎么设计（**产品路径绝不能装上**）

**推荐设计（照抄 `training_mode.js` 的 opt-in 风格，但**只做实例级**）**：

```js
// 位置建议：vantage_sandbox.js 内部（或先放 _tools/headless 里，产品零风险）
// —— 三条硬纪律 ——
//   ① 缺省【不装】：没有任何显式开关 ⇒ 一行都不执行

//                ＋ 环境白名单（window.__VT_HEADLESS===true || /[?&]vt=1/ || navigator.webdriver===true）
//   ③ 【实例级】而不是 prototype 级：只动 gc.roundController 这一个对象
var _installed = null;   // {gc:..., uninstall:fn}；模块级只留一个

function installDeathHook(gc, opts) {
    opts = opts || {};
    if (!gc) return false;
    var want = (opts.enabled === true)
            || (typeof window !== 'undefined' && window.__VT_DEATH_HOOK__ === true);
    if (!want) return false;                                   // ← 产品路径在这里就 return
    var envOk = (typeof window !== 'undefined') &&
        (window.__VT_HEADLESS === true ||
         /[?&]vt=1(?:&|$)/.test(window.location.search || '') ||
         window.navigator.webdriver === true);
    if (!envOk) return false;                                  // ← 第二道门
    if (gc.__vtDeathHooked) return false;                      // ← 幂等：自己的字段名

    var rc = gc.roundController;
    if (!rc || typeof rc.killTank !== 'function') return false; // RC 未就绪 = 本回合不装（见下）
    var orig = rc.killTank;                                     // ★ 存 orig，不假设它是原版
    rc.killTank = function (kill) {
        // ↓↓ 只做「读」。绝不改参数、绝不改返回值、绝不吞异常、绝不调 VantageTree
        try { if (collector) collector.onKill(this, kill, /*during*/'pre'); } catch (e) { collector.selfLog(e); }
        var res = orig.apply(this, arguments);                  // ← 原样转发
        try { if (collector) collector.onKill(this, kill, /*during*/'post'); } catch (e) { collector.selfLog(e); }
        return res;                                             // ← 原样返回
    };
    gc.__vtDeathHooked = true;
    _installed = { gc: gc, rc: rc, orig: orig, uninstall: function () {
        if (rc.killTank === wrappedRef) rc.killTank = orig;      // 可逆
        try { delete gc.__vtDeathHooked; } catch (e) {}
    } };
    return true;
}
```

**必须写进代码注释的四条**：
1. **实例级，不是 prototype 级** —— 绝不碰 `RoundController.prototype.killTank`；避开 `_trainingKillPatched`（`training_mode.js:4825`）与 `_vtbKillWrapped`（`vantage_training_bench.js:564`）这两个**别人的**标记字段，用 `__vtDeathHooked`。
2. **叠加安全** —— 那两个 wrap 可能已经先装/后装，`orig` 可能不是原版；只 `apply` + `return`，不要再解析参数。
3. **wrap 必须在 `ROUND_CREATED` 之后装**（`[RM]行1@31869` 时 `gc.roundController` 已存在）——**最好干脆不装 wrap**，因为**订阅已经够了**（§3.1~3.2）。若一定要装，把 `installDeathHook` 放在 `ROUND_CREATED` 的回调里，并且**每回合重装一次**（RC 每回合新建，实例级 wrap 会随旧 RC 一起丢弃）。
4. **`killTank` 有静默门**：`[RC]行2@14548` 的守卫 `model.getStarted()` 为假时**只 log.error、不发事件** ⟹ **wrap 与订阅在这点上行为一致**（都收不到），不会因此产生差异；但**不要**在 wrap 里额外判 `getStarted()`（多一个判据就多一个差异源）。

**若主人要求「死亡位置必须是精确接触点（collisionPoint）」，wrap `killTank` 帮不上忙** —— 那时要挂的是 `TANK_DEADLY_COLLISION`（订阅即可，§3.2 表 C），**仍然不需要 wrap**。真正「只有 wrap 才能拿」的东西，本方案**找不到** ⟹ 这是本方案与「架构 AI 建议 wrap」的**唯一实质分歧**，标 `【推断】`，请主人裁（§六-1）。

### 3.5 `TANK_KILLED` 与 `TANK_DESTROYED` 的【顺序】怎么保证

**先把事实摆清（本地/无头 = 我们的训练环境）**：

| 死法 | 上游 | 发出的事件 | 两条会不会同时出现 |
|---|---|---|---|
| 被弹打死 | `TANK_DEADLY_COLLISION`（`PreSolve@3809`）→ `[RC]行1@5132` → `killTank` | **只有 `TANK_KILLED`** | ✗（本地不会再来 `TANK_DESTROYED`） |
| 毒雾致死 | `TANK_ZONE_COLLISION`(STORM)（`PreSolve@5927`）→ `[RC]行1@6050` → `destroyTank` | **只有 `TANK_DESTROYED`** | ✗ |
| 出生区致死 | `TANK_ZONE_COLLISION`(SPAWN) → `[RC]行1@5967` → `destroyTank` | **只有 `TANK_DESTROYED`** | ✗ |
| 联机 | 两条服务器消息 | 两条都可能有 | ✓（顺序由服务器/消息到达次序决定，**本地不可控**） |
| **同帧既中弹又踩毒雾** | Box2D 接触表里两个接触都在 | **两条都发** | ✓ **同帧**，顺序 = `this.collisionEvents` 的压栈次序（Box2D 决定）【推断】 |

⟹ **「靠注册顺序保证 `TANK_KILLED` 先抓」在本项目里既不可靠也不必要。** 正解是三条：

1. **两个回调里都同步抓位置**（都在 (c) 内，坦克都还在，见 §3.2-1）⟹ **谁先到都能拿到**。
2. **按 `victimPlayerId` 建 key，先到先写、后到不覆盖**：
   ```
   if (!deathByVictim[pid]) deathByVictim[pid] = rec;   // ← 不是赋第二个值
   ```
   ⟹ 无论谁先到，第二条只是补齐「cause/killer」这类字段，**位置不会被后到的（更差的）来源覆盖**。
3. **每回合（`ROUND_CREATED`）清空 `deathByVictim`** ⟹ 不会把上一回合的死因带到下一回合（§四-2）。

**顺带一条验证纪律**：本项目的 `_filterAndDispatchCollisionEvents`（`[RM]行1@27149`）会在**同一帧内**把 `TANK_DEADLY_COLLISION` 按 `data.tankA` 去重成 1 条 ⟹ 「同一帧被两发打死」只记 1 次 kill，**这是游戏自身语义，不是我们的 bug**；不要为了「记全」去 wrap。

### 3.6 毒雾致死（**只走 `TANK_DESTROYED`**）怎么办

**链路（逐句可查）**：

```
b2dworld.Step()
  └ RoundModel.PreSolve  [RM]行1@3372

      └ _notifyEventListeners('tank zone collision', data)       @28518

                        └ _notifyEventListeners(TANK_DESTROYED, pid)   @20519
```

**结论 4 条**：

1. **毒雾位置怎么拿**：在 **`TANK_DESTROYED` 回调内** `var t = gc.getTank(pid); t.getX()/getY()/getRotation()`。**和弹杀同款**（同一段 (c) 内、坦克还在）。
   ⚠️ 若还想更准，**订阅 `TANK_ZONE_COLLISION`**：它的 `data.zone` 给出**毒雾区对象**、`data.tankA` 给出坦克、`data.collisionPoint` 给出**接触点**。
2. **毒雾绝对不能靠 wrap `killTank`** —— 它根本不经过 `killTank`（`destroyTank` 是另一条链，见 §3.1 末）。谁要是只 wrap 了 `killTank`，毒雾致死就是**100% 静默漏记**，而且**不报错**（`_notifyEventListeners` 的 try/catch 只管我们自己的异常，管不了我们没订阅）。
3. **毒雾没有 killer、没有弹种**：`Kill` 根本不生成（`[RC]行1@5857` 那一段不建 `Kill`）。⟹ 要 killer 只能自己造约定（比如 `killerPlayerId = null` / 特殊哨兵值）。**这条属于「进观测」范畴 ⟹ 等 A3/主人（§六-2）**。
4. **`TANK_DESTROYED` 也用于出生区（SPAWN zone）致死**（`[RC]行1@5967`）—— 别把它当成「毒雾专用」事件；判因要读 `cause`（我们在 `TANK_ZONE_COLLISION` 里能看到 `data.zone.getType()`；只订阅 `TANK_DESTROYED` 时**拿不到** zone 类型）【推断】。

## 四、订阅时机与生命周期

### 4.1 什么时候订阅

**结论：用 `gc.addRoundEventListener(cb, ctx)` 订阅一次，越早越好；不要在 `rc` 上订阅。**

| 候选时机 | 评价 |
|---|---|
| 页面加载时 | ❌ 太早：`GameManager.getGameController()`（`c63a12f5…js@3648`）那时是 null。⚠️ 而且 `training_mode.js`/`vantage_training_bench.js` 已经证明「页面加载就装」会装到产品页上 |
| **`createVantageAdapter(gc, aiId)` 里**（`[SB]:2746@127863`） | ✅ **推荐**。此时 `gc` 已知；每个 `VantageAI` 构造时调一次（`[AV]:25@1839`） |
| `GameController` 建好时 | ✅ 等价（`UILibraryState._createLocalGame` / `local_patch.js:1542` / `training_mode.js:4296` 三处 `GameController.create`） |
| **回合开始时（`ROUND_STARTED` / `_initializeRound`）** | 🟡 **不必要**：RC 每回合新建，但 `gc` 会在 `_createRoundController`（`[GC]行1@12194`）里**自动把你重挂到新 RC 上** |

**为什么用 `gc` 而不用 `rc`**（这是本节的核心理由，务必写进代码注释）：

- `rc`（`RoundController`）**每回合新建**：`GameController._createRoundController()`（`[GC]行1@11617`）里 `this.roundController = RoundController.create(...)`，而 `RoundController` 的构造里 `RoundModel.create(...)`（`[RC]行1@1575`）——**每回合一个全新的 `RoundModel`，`eventListeners` 零开始**。
- 你在旧 `rc` 上订的监听器，**随旧 RC 一起消失** ⟹ 下一回合你什么都收不到。
- `gc.addRoundEventListener` 把 `{cb,ctxt}` 存进 **`gc.roundEventListeners`**（`[GC]行1@20488`），并且：
  - 当前有 RC → **立刻**挂上去；
  - 之后每次 `_createRoundController` → **`for(...) roundController.addEventListener(roundEventListeners[i].cb, .ctxt, this.id)`**（`[GC]行1@12194`）⟹ **自动重挂**。
- ⚠️ 但 **`gc` 本身也是每「一局」新建的**（`GameController.create(...)`）⟹ **`gc` 换了，订阅就没了**。所以订阅函数必须是**幂等的 `ensureSubscribed(gc)`**，并在 adapter 创建时调用（每次 `VantageAI` 构造都会调，天然覆盖「新一局」）。

### 4.2 回合重启后要不要重订阅（⚠️ `endRound` 会清 `tanks`）

**结论：监听器【不需要】重订阅；但要清【我们自己的每回合缓存】。**

| 对象 | 回合重启（`ROUND_ENDED` → 下一局 `_initializeRound`）后的命运 | 对策 |
|---|---|---|
| `RoundModel.eventListeners` | **整个 RoundModel 被换掉** ⟹ 监听器没了 | **不用管**：`gc` 会自动重挂（§4.1） |
| `gc.roundEventListeners` | **不清空**（`endRound`（`[GC]行1@15841`）只调 `roundController.endRound`） | 不用管；但也**容易重复 push** ⟹ 见 §4.3 |
| `RoundModel.tanks` | 🔴 **`endRound` 里 `this.tanks={}`（`[RM]行1@32037`，与 `ROUND_ENDED` 同一句）** | 🔴 **我们缓存的 `tank` 对象/`deathRecord` 必须在这个时候失效**：否则会拿着**上一局**的坦克引用去读位置 |
| `RoundModel.projectiles/traps/collectibles/weapons/upgrades/counters/zones` | 同上，`endRound` 里全清 | 同上（子弹 token 每帧重建 ⟹ 天然没事） |
| `endedPlayerIds` / `destroyedPlayerIds` | `endRound` 里 `destroyedPlayerIds=[]` | — |

**因此**：在 `ROUND_CREATED`（`[RM]行1@31869`）**或** `ROUND_ENDED`（`[RM]行1@32112`）里清 `deathByVictim` / 缓存。
**推荐用 `ROUND_CREATED` 清**（「新局开始前一定清干净」比「旧局结束时清」更稳：`ROUND_ENDED` 之后还可能插 `CELEBRATION_*`，而 `ROUND_CREATED` 是新局的第一声）。

⚠️ **`ROUND_ENDED` 回调里禁止读坦克**：`endRound` 在派发 `ROUND_ENDED` **之前**就把 `started=false;running=false` 设好、**派发之后立刻** `this.tanks={}` ⟹ 在 `ROUND_ENDED` 回调里读坦克还来得及（同一句内、`tanks={}` 在后面），但**没有任何理由在这里读**；要做也是在 `TANK_KILLED`/`TANK_DESTROYED` 里做完。

### 4.3 怎么防「重复订阅」

**已知事实（逐条带引用）**：

| 点 | 事实 | 后果 |
|---|---|---|
| `RoundModel.addEventListener` | `eventListeners.push({cb,ctxt,gameId})`，**没有任何去重**（`[RM]行1@31249`） | 挂两次 = 回调跑两次 |
| `RoundModel.removeEventListener(cb,ctx)` | 按 `cb===callback && ctxt===context` 找**第一处**并 splice（`[RM]行1@31369`） | 能用，但**必须传同一个函数引用**（匿名箭头函数每次都是新引用 ⟹ 删不掉） |
| `GameController.addRoundEventListener(cb,ctx)` | **只 push `roundEventListeners`，不看重复**（`[GC]行1@20488`） | 同一个 `gc` 上调两次 = 下一回合被挂 **两次** ⟹ **回调跑两次** |
| `GameController.removeRoundEventListener(cb,ctx)` | 只从 `roundEventListeners` 里 splice（`[GC]行1@20687`），🔴 **不摘当前 `roundController` 上已挂的那一份** | **`remove` 之后当前回合仍然会收到事件**（本项目的既有小缺口，登记在 §七） |
| `RoundController.addEventListener/removeEventListener` | 纯转发到 `RoundModel`（`[RC]行2@22194` / `@22300`） | — |

**防重复的推荐做法（三层）**：

```js
// ① 模块级：单例订阅器（同一个函数引用，才能 remove）
var _evCb = null;                       // 固定引用，不要写 function(){...} 字面量
// ② 实例级：在 gc 上打自己的标记（别用别人的字段名）
function ensureSubscribed(gc) {
    if (!gc) return false;
    if (gc.__vtEvHooked === true) return false;    // ← 幂等闸门
    if (typeof gc.addRoundEventListener !== 'function') return false;
    if (!_evCb) { _evCb = function (self, gameId, evt, data) {   // ★ 3 参是 evt、4 参是 data
        try { collector.handle(self, gameId, evt, data); }
        catch (e) {
            collector.selfErr(e);      // ★ 必须自己记！外层只会 console.log（[RM]行1@31585）
        }
    }; }
    gc.addRoundEventListener(_evCb, /*ctx*/ collectorCtx);
    gc.__vtEvHooked = true;
    return true;
}
// ③ 不变量自检（可选，强烈建议）：订阅后断言「GC 里只有 1 份」
function assertSubscribedOnce(gc) {
    var n = 0; var a = gc.roundEventListeners || [];
    for (var i = 0; i < a.length; i++) if (a[i].cb === _evCb) n++;
    return n === 1;                    // 期望恰好 1
}
```

**另外两条**（都是本项目踩过的形状）：
- ⚠️ **不要用匿名函数订阅**（`gc.addRoundEventListener(function(self,id,evt,data){...}, this)`）：`remove` 时 `cb===` 比不中，且你无法自检「有几份」。
- ⚠️ **`_evCb` 必须是同一份**：`VantageAI` 的 `reset()`（`[AV]:152@50563`）会把 `_vantageAdapter=null`；如果那里顺手重新 `createAdapter`，**必须**走 `ensureSubscribed` 的幂等闸门，否则 `gc.roundEventListeners` 会一份一份涨。
