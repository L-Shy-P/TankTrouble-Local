## 二、场景定义（"多场景、除 `DM`"）

**每局随机（训练集）**：
- **玩家数 `2 ~ 8`**：我方 **`Vantage × 1`**，其余全是 **`Laika`**
  （**依据**：`LOCAL_MAX_TANKS = 8`，来自 `game_core/js/` 的 `Constants`）
- ⭐ **地图大小：交给游戏【原版建图逻辑】** —— **人数变 ⟹ 地图自动变尺寸**
  - ⛔ **不自己指定迷宫尺寸、不覆盖建图代码**
  - 我们只随机"人数 + 随机种子"；**每局记录"人数 + 实际地图尺寸"确认联动成立**
- **道具**：按 `Constants.GAME_MODE_INFO[模式].DEFAULT_AVAILABLE_CRATES` 的可用集随机组合
- **毒雾**：`storm` / `stormOn` 随机开关

**评测集**：固定 `30` 场景（覆盖 `2/4/8` 人 × 毒雾开关 × 道具开关），**每次评测用同一批**、保证可比。

### ⭐⭐ "地图尺寸随人数变化" —— **已独立核实（拿到了原版公式）**

**出处**：`game_core/game_modes_decoded.js`（`BootCampGameMode.getMaze`，**反混淆后的原版代码**）
逐字：
```js
getMaze: function(playerIds, theme) {
  return Maze.createRandom(
    Math.min(C.MAZE.MAX_WIDTH,
      Math.floor((C.MAZE.BASE_WIDTH  + C.MAZE.WIDTH_FOR_PLAYERS[playerIds.length])
                 * (Math.random()*(C.MAZE.MAX_RANDOM_WIDTH_MULTIPLIER-1.0)+1.0))),
    Math.min(C.MAZE.MAX_HEIGHT,
      Math.floor((C.MAZE.BASE_HEIGHT + C.MAZE.HEIGHT_FOR_PLAYERS[playerIds.length])
                 * (Math.random()*(C.MAZE.MAX_RANDOM_HEIGHT_MULTIPLIER-1.0)+1.0))),
    playerIds, theme);
}
```
**常量实测值**（同文件）：
```
WIDTH_FOR_PLAYERS : [0, 2, 4, 6, 8, 9, 10, 11, 12]   ← 下标 0..8，含 8 人
HEIGHT_FOR_PLAYERS: [0, 1, 2, 3, 4, 5,  5,  6,  6]    ← 下标 0..8，含 8 人
BASE_WIDTH = 2 · BASE_HEIGHT = 2
MAX_WIDTH  = 16 · MAX_HEIGHT = 10
MAX_RANDOM_WIDTH_MULTIPLIER = 1.5 · MAX_RANDOM_HEIGHT_MULTIPLIER = 1.5
```

**⟹ 三条结论**
1. ⭐ **"人数 ⟹ 地图尺寸"成立**：**`尺寸 =（`BASE` + `*_FOR_PLAYERS[人数]`）× `U(1,1.5)`、再被 `MAX` 截断** ✓✓
2. ⭐⭐ **同人数下还有 `1.0~1.5` 倍随机** ⟹ **"随机人数"已经同时带来了"随机尺寸"**（**主人的话得到确认**）✓
3. ⭐⭐ **`8` 人在表内（下标 `8` 存在）⟹ 不会越界成 `NaN`** ✓✓

**推算出的尺寸范围（供 `G2` 对照）**：
| 人数 | 宽 | 高 |
|---|---|---|
| `2` | `6 ~ 8` | `4 ~ 5` |
| `4` | `10 ~ 12` | `6` |
| `8` | `14 ~ 16`（截断）| `8 ~ 10`（截断）|

⚠️ **由此新增一条风险**：**`8` 人局地图明显更大 ⟹ 回合可能更长 ⟹ 一晚局数会低于 `1,700` 的估计** ⟹
**`G4` 冒烟时要分别量"`2` 人 / `8` 人"的局均帧数** ✓✓

### ⭐ 实现要点：`2~8` 人怎么凑（**已查清**）

**事实**（出处见下）：
- ⭐ **`match.js:63-96`** 的 `open({humanIds, aiCount, vantCount})`：

**⟹ 结论**：**要凑到 `8` 人，必须用"多个 `Laika` 实例"**（多个 playerId、同一套 `Laika` traits）。

**⚠️ 一个必须绕开的坑**（`game_core/js/local_patch.js:1106-1112`）：

## 七·五、⭐ 父代理拍板（`2026-10-17` 夜，供训练器/服务端实现遵循）

### 裁决 `A`：**`v` = `out[0]`**
- 依据：`net_v2_fixed.py:32` 返回 `(head_node, head_fire, head_fail, logp_all)`；
  `head_node` = **池化表示过 `Linear(D,1)` 的【每样本标量】** ⟹ **它就是价值头的位置**（`head_fire`/`head_fail` 是别的用途）。
- ⭐ **口径统一**：**服务端与训练器一律取 `out[0]` 当 `v`**（**`policy_server.py:33` 那个 `out[1]` 是旧的、作废**）✓✓
- ⚠️ **注**：**模型目前没有显式命名的 `head_value`**；**本轮先沿用 `head_node` 的位置**，
  **若日后要改名/加头，须同步改"服务端 + 训练器 + 录图验收"三处** ✓

### 裁决 `B`：**探索随机性 —— 种子由载荷提供**
- 现状：两处服务端**每请求 `manual_seed(12345)`** ⟹ **同一观测永远抽到同一分位点** ⟹
  **探索噪声被钉死、`entropy`/`ratio` 失真**（`G4 缺口 P0-5`）✓✓
- ⭐ **裁决**：**由载荷带 `seed`（建议 = `f(局号, 帧号)`）**；**服务端 `manual_seed(seed)`**；
  **载荷没给 `seed` ⟹ 用服务端自身递增计数器**（**保证"同一帧可复现、不同帧不同**"）✓✓
- ⛔ **不许**"全局随机"（那样回放无法复现）；⛔ **不许**"继续用固定 `12345`"（那样探索死掉）✓

### 裁决 `C`：**观测回传走"近线 `buffer`"（路线 `C`）**
- 理由：**全存观测 = `226 GB`，而 `D:` 只有 `17 G`**（`G4 §二` 实算）⟹ **路线 `B`（重放重建）不划算** ✓
- ⭐ **落地**：**`RAM` 里留一个 `rollout` 窗口 → 更新完即弃**；**磁盘只留小记录 + `ckpt`** ✓✓

### 🔴 裁决 `D`：**今晚的训练预算 —— 训练是瓶颈，不是采集**
**⚠️ 这是本轮最重要的算术**（依据 `G4 §二` 的实测吞吐）：
```
采集：8.08 ms/帧   ⟹ 8h 可采 ~1,129 局（~357 万帧）
训练：138.9 样本/s ⟹ 8h 只能过 ~400 万【样本·次】
```
**⟹ 若"采满 + `PPO` 跑 `4` 个 `epoch`"，需要 `4 × 357 万 / 138.9 ≈ 28.6` 小时 —— 一晚装不下** ✓✓

**⭐ 所以今晚的形态定为「少采多训、多轮循环」**：
| 项 | 建议值 | 依据 |
|---|---|---|
| **每轮采集 `M`** | **`80 ~ 150` 局**（≈ `1` 小时以内）| 让"训练完"能跟上"采集" |
| **每轮 `epochs`** | **`2 ~ 4`** | `PPO` 常规 |
| **一晚轮数** | **`3 ~ 5` 轮** | 每轮都存 `ckpt` + 评测 ⟹ **明早有 `3~5` 个点可画趋势** ✓✓ |
| **评测间隔** | **每轮末一次**（`30` 局 ≈ `8.8 min`）| `G4 §三` 的成本估计 |

⛔ **不要"先采满一晚再训"**（**那样明早只有一个 `ckpt`、看不出趋势**）✓✓
⭐ **并且**：**第一轮先用 `10` 局做端到端冒烟**（`G4`），**确认 `ckpt` 能存能读、`ratio` 不再是 `1`**，**再放量** ✓✓
