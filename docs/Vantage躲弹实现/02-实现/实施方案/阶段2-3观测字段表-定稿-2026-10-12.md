### 1.2 争议 1（**本表唯一需要主人一句确认的地方**）：`uid` 要不要进 token？

**两处定案互相顶：**

| 出处 | 原话 | 结论 |
|---|---|---|
| `权威版:3081`（§16.4 #1） | 「**父节点下标** int **数组里的位置。不用全局 id** —— 整树重建会重置 id，**会串味**」 | 用**数组下标**，**不要** id |
| `权威版:4546`（§8.1 #8，另一份草案） | 「⚠️ 现在给的是全局 id（**整树重建会重置为 1** → 记忆键串味）」 | 同上，嫌 id 会重置 |
| **`方针:102`（阶段 2-4，**列在路线图里的施工项**）** | 「**节点出生 UID（单调计数器，重建不重置），观测与输出统一用它**」 | 用 **UID**，且**观测与输出共用同一套** |
| `权威版:222`（2026-10-12 裁决） | 「直接【**子节点 + 自己来源的操作类型**】就行了」 | **节点自身身份**是输出定位的一半 |

**施工侧判读（不改一行代码，先说清楚）**：
- `§16.4` 嫌 id 的两个理由（**"重建会重置"**、**"记忆键串味"**）**已经被 2-4 的"单调计数器、重建不重置"直接消灭** —— `tree:3741` 是 `tree.nextNodeId++`，**本来就不重置**（只有 `nextNodeId` 不是 number 的老路径才退回 `nodeCount`）。
- 真正必须含 `uid` 的理由是**功能性的，不是偏好**：**A/B 的输出格式是 `(子节点ID, 反向相对帧)`**（`权威版:205-208` 定案），**上帧计划**（`方针:101`）也是 `(nodeUID, back)` 对 —— 网络**必须能从 token 里读出"这个 token 对应哪个 ID"**，否则它输出的 ID 无法回指。
- `§16.4 #1` 想要的是「**父引用用一个小而密的整数**」，这与「**每个 token 额外带一个自身 UID**」**不矛盾**：`parentIdx` 仍是数组下标（稠密、好算注意力），`uid` 只是输出空间的锚。

**⟹ 建议（本表的默认取值）：两者都留 —— `parentIdx` = 数组下标，`uid` = 阶段 2-4 出生 UID。**
**⟹ 代价**：`+1 维/节点`（@N=1000 ⟹ +1000 维/帧，占总量 ~9%）。
**⟹ ⚠️ 如果主人裁定"不要 uid"**：则 **A/B 的输出 ID 必须改用"数组下标"**，阶段 2-4 的"UID"降级为内部映射，`上帧计划` 的 `nodeUID` 同步改成下标 —— **这是一处联动，改一处要改三处**（token / 上帧计划 / 输出契约）。**请主人一句：留 uid，还是 token 内不带 uid？**

### 1.3 `hasGrown`（是否生长过）—— **为什么它不能"从现有字段推出来"**（★ 本表的核心发现）

主人的逻辑表（`权威版:3106-3120`）：

| 情形 | 有分支？ | **生长过？** | 结论 |
|---|---|---|---|
| 生长过 + 有活路 | ✅ | ✅ | 正常 |
| **生长过 + 全真死** | ❌ | ✅ | ⭐ **真死（确定）** |
| **没生长过** | ❌ | ❌ | ⭐ **不确定（还没探）** |

**⟹ 判据字面是「无分支 + 生长过 ⟹ 真死」。那能不能用 `n.children.length === 0` 当"没分支"、用"曾经有过子节点"当"生长过"？**

### ⛔ **不能。** 有三处代码会把**已经生长过的节点**的 `children` **清空**：

| # | 位置 | 干了什么 | 后果 | `hasGrown` 应该 |
|---|---|---|---|---|
| ① | `tree:2667`（`invalidateStaleNodes` 提前死亡剪枝）**该节点自己**因新弹提前死 | `while (node.children.length) detachChild(...)` ＋ `node.exhausted = true` ＋ 改写 `fullDeathFrame/segmentFrames/tEndSec` | 曾经 9 个子 → **0 个子**；节点**真的死了** | **保持 1** ✅（生过 + 无分支 = 真死，**判据正确**） |
| ② | `tree:2756`（`applyRolloutScore`）**段长被新威胁缩短** | `if (actual < planned && node.children.length) invalidateDescendants(tree, node)` ⟹ `tree:2710-2729`：所有后代 `invalid = true` 并 `detachChild` | 曾经 9 个子 → **0 个子**；**但节点自己还活着、还能重长** | ⛔ **必须复位成 0** —— 否则会被误判成"真死"，把**当时死、现在活**的位置**永久堵死** |
| ③ | `tree:3588`（`markReserveInvalid` → `discardReserveSubtree`）结构性失效 | 标记 `invalid` + 删除未来子树 | 同上 | ⛔ **复位成 0** |

**⟹ 三条硬结论：**
1. **`children.length === 0` 是一个二义量**（"从没长过" 与 "长过但被摘空了"）⟹ **不能拿来当 `hasGrown`**。
2. **`n.exhausted` 也不是它**：`exhausted` 只在 `applyRetreatAfterExpand`（`tree:5930`，"9 候选全 1 帧死"）与上面 ① 两处被置 `true`，**全仓没有任何一处把它置回 `false`**（`grep 'exhausted = false'` 只有 `tree:1427` 建节点、`tree:6788` 新建树）⟹ **它是"一旦真死就永久"的旧口径**，与主人新口径「**没生长 = 不确定**」**方向相反**（旧口径会把"其实没探过"的当成"已确认真死"）。
3. **`hasGrown` 必须是【新增的、独立的、可复位的】节点字段。** 这是本表**最实的一条前置缺口（G2）**。

**⟹ 写死的写入点 / 复位点（第二步施工按这个改，别处不许动）：**

| 动作 | 位置（建议） | 值 |
|---|---|---|
| **置 1** | `expandLeaf` 成功产出**≥1 个**子节点之后（`tree:4262` 一带，`child.opName = ops[opIdx].name` 附近） | `parent.hasGrown = true` |
| **复位 0** | `invalidateDescendants(tree, node)` **入口**（`tree:2710`）—— 覆盖上面 ② | `node.hasGrown = false` |
| **复位 0** | `markReserveInvalid` / `discardReserveSubtree`（`tree:3588+`） | 对受影响的 `node` 复位 |
| **⛔ 不复位** | `tree:2667` 提前死亡剪枝（情形 ①）—— 那里 `hasGrown` 必须**保持 1** | — |
| **建节点初值** | `createTreeNode`（`tree:1410-1430`） | `n.hasGrown = false` |
| **整树重建/坍缩** | 保留层数沿用旧节点 ⟹ **值跟着节点走，不用重置**；新树新节点自然是 `false` | — |

> ⚠️ **一个必须说清的边界**：复位时机若**过宽**（例如每帧无条件复位），`hasGrown` 就退化成恒 `0` 的**死字段**（本项目老坑）；若**过窄**（只置不复位），就会退化成旧的 `exhausted`。**⟹ 第二步必须做【配对实测】：造一个"先探过全死、后被新威胁判活"的真局面，证明该字段能 `1 → 0`。**

### 1.4 节点 token 的两个"防坑"说明

   **`exhausted` 节点【不过滤】** —— 主人裁决恰恰要**让智能体看见"生过 + 无分支"**（那就是真死信号）。

### 2.1 ★★ 两个 `atan2` 约定：**选哪个 + 为什么**（**写死，不许改**）

**事实**：`Projectile` **没有角度字段**（`418577fd…js:行4`：`id/playerId/type/x/y/speedX/speedY/lifetime/timeoutWindow/timeoutBounceCount/timeAlive/deadlyToOwner/initialSpeed/stopped/bounces[]`；建体处 `fixedRotation=true` 且**没有 angle 赋值**，`冻结点:283-284`）⟹ **角度只能由速度派生**。

**两个候选（⚠️ 不是一套，差一个符号 + 一次轴交换）：**

| 约定 | 公式 | 含义 | 与游戏的关系 |
|---|---|---|---|
| **(A) 数学/速度方向** | `θ_A = atan2(speedY, speedX)` | 速度矢量相对 +X 轴的标准极角 | **游戏里没有任何东西用这个约定** |
| **(B) 坦克 `rotation` 约定** ✅ | `θ_B = atan2(speedX, −speedY)` | 与 `Tank.getRotation()` 同一个角 | **游戏自己的约定**：`Tank.update` 每帧写 `SetLinearVelocity(sin(rot)*speed, −cos(rot)*speed)`（`AGENTS.md` 原版事实纠正 #2）⟹ **前向 = `(sin θ, −cos θ)`** |

**验证（B 的自洽性，可当单测）**：把 `vx = sin(θ)·s`、`vy = −cos(θ)·s` 代进 (B)：
`atan2(sin θ · s, −(−cos θ · s)) = atan2(sin θ, cos θ) = θ` ✅（`s > 0`）

### ✅ **选定 (B)：`θ = atan2(speedX, −speedY)`**

**理由（按分量排序）**：
1. **观测里已经有一堆 (B) 约定的角**：自己坦克的 `rot`（`adapter.getTankState().rot = tank.getRotation()`，`sandbox:3435`）、对手的角度（§16.3 对手段）**全是 (B)**。**选 (A) 就等于让网络在同一份输入里学两套角约定** —— 而本项目已经为"同一概念两套口径"付过代价（`权威版 §26.1` 的"时间基准三层"、"`q` vs `qAge`"）。
2. **"会角弹"要的正是 (B)**：判断"这颗弹是不是朝我飞来"要拿**弹的航向**和**坦克朝向**比；判断"会不会打到我的侧后方"也是。**同一个约定 ⟹ 可以直接相减**，不用先转一次。
3. **(B) 可被游戏自身对拍**：`p.getB2DBody().GetAngle()` 是 Box2D body 角 = (B) 约定 ⟹ **第二步自证可以用它当参照做独立核验**（⚠️ 只做**诊断对拍**，**不写进 token**，因为 body 是 `fixedRotation`、它的角不随速度变）。
4. **(A) 的唯一优势是"mathtext 习惯"**，对本项目**无收益**。

⚠️ **⛔ 禁令**：**全仓只许存在一个子弹角约定**。第二步落代码时，`θ` 的计算必须**只在一处**（唯一真源 + golden vector 对拍，`权威版:4459` §8.0 第 3 条），**别在编码器/调试页/探针里各写一遍**。
