## 一、观测张量（A 和 B 共用同一套）

### 1.1 形状总览

```
观测 = 全局段 + 节点段
       ├─ 全局段：固定 G 个数
       └─ 节点段：最多 N 个节点 × 每节点 K 个数
```

| 常量 | 值 | 理由 |
|------|-----|------|
| `N`（节点槽位） | **256** | 超过 256 取"离根最近的 256 个"（近处更重要） |
| `K`（每节点字段） | **16** | 见 1.3 |
| `G`（全局字段） | **48** | 见 1.2 |

**总维度** = `48 + 256 × 16` = **4144**

### 1.2 全局段（48 个）

| 段 | 个数 | 内容 | 编码 |
|----|------|------|------|
| 自身坦克 | 6 | x / y / 朝向 sin / 朝向 cos / 速度 x / 速度 y | 见 1.4 |
| 当前段已走帧数 | 1 | 本段已经执行了多少帧 | ÷ 10 秒 |
| 节点数量 | 1 | 实际有多少个真节点（其余槽位是补齐） | ÷ N |
| 失效节点数 | 1 | | ÷ N |
| 残留算力预算 | 1 | 本帧还能跑多少 rollout | ÷ 预算上限 |
| 本帧是第几次重试 | 1 | 0 = 一次就过 | ÷ 最大重试次数 |
| 上一帧的射击状态 | 1 | 按住 / 松开 | 0 / 1 |
| 当前武器类型 | 1 | **整数**（主人定案：类别量用数字） | 整数 |
| 当前武器剩余弹药 | 1 | | ÷ 弹药上限 |
| 时钟 / 剩余时间 | 2 | 本局还剩多久、当前是第几秒 | ÷ 10 秒 |
| **道具位置** | 最多 8 × 3 = 24 | 每个道具：x / y / 类型 | 坐标归一，类型整数 |
| 保底位 | 8 | `⚠️ 待定` | |

### 1.3 节点段（每节点 16 个）

| # | 字段 | 编码 | 说明 |
|---|------|------|------|
| 1 | 编号 | **位置索引，不是原始 id** | 见 1.5 |
| 2 | 父节点编号 | 同上，根为 −1 | |
| 3 | 来路操作 | **整数 0~8** | 主人定案：类别量用数字 |
| 4 | 段长 | ÷ 10 秒 | |
| 5 | 深度 | ÷ 最大深度 | |
| 6 | 到根累计时间 | ÷ 10 秒 | |
| 7-8 | 末态相对位移 x / y | ÷ 地图尺寸 | **本段末**，不是预测时长末 |
| 9-10 | 末态朝向 sin / cos | −1~1 | 同上 |
| 11 | 死亡帧 | −1 表示活满；否则 ÷ 视界 | |
| 12 | 是否失效 | 0 / 1 | |
| 13 | 有没有子节点 | 0 / 1 | |
| 14 | 是不是根 | 0 / 1 | |
| 15 | 是不是当前提交点 | 0 / 1 | |
| 16 | `⚠️ 待定`（预留给"该节点的子弹摘要"） | | |

### 1.4 编码规则（修正版）

| 类型 | 编码 |
|------|------|
| 坐标 | ÷ 地图尺寸 → 0~1 |
| **时间** | ÷ **10 秒**（子弹最长寿命，物理上限） |
| 朝向 | **sin / cos 两个数**，不是角度 |
| 速度 | ÷ 子弹速度上限 |
| **布尔** | **0 / 1** |
| **弹种 / 操作类型等类别量** | **直接用整数**（主人否决了嵌入向量） |

### 1.5 节点编号的处理（关键）

**不把原始 id 喂给网络。** 理由：重锚/重建后编号会变，网络会学出"编号 → 语义"的伪相关。

做法：

```
每个节点在观测里占一个【位置索引】（0 ~ 255）
节点段里出现的"编号"字段，填的是【位置索引】，不是原始 id
程序内部维护 位置索引 ↔ 原始 id 的映射表
智能体输出的是位置索引 → 程序翻译回原始 id
```

**这样编号永远稳定**，且"第 5 槽位的节点"这一概念对网络是可学的。

## 二、动作空间

### 2.1 A 的动作（生长）

| 输出 | 形状 | 合法条件 |
|------|------|---------|
| **在哪些位置生长** | **256 个 0/1**（每个槽位一个开关） | 该槽位有节点、且该节点不是真死、未失效、未耗尽 |
| **每个新节点的操作时长** | **256 个标量**（帧数） | 夹到 `[3, 30]` 帧 |

**为什么用 256 个 0/1 而不是"变长列表"**：定长输出才能用固定形状的网络。
"列表长度"由输出里有几个 1 决定（**不需要"长几次"这个输出**，主人定案）。

### 2.2 B 的动作（操作）

| 输出 | 形状 | 合法条件 |
|------|------|---------|
| **选哪条路** | **256 个分数**（取最大 = 选哪个槽位） | 该槽位是当前提交点的子节点、非真死、未失效 |
| **射击表** | **256 个 0/1** | 位置 i 表示"本段第 i 帧射击"；帧号 < 段长、去重 |
| 记忆 | 由各自网络决定 | 不透明 |

**为什么射击表用定长 256 位**：段长上限 30 帧，所以 30 位就够，256 是富余。
主人定的格式是"稀疏表（哪几帧射击）"，**在张量里就是这 30 位的展开**——
输出层用 30 个 sigmoid，取 > 0.5 的就进稀疏表。

> ⚠️ **待定**：射击表到底是"网络的 30 路 sigmoid 输出"还是"别的机制"。
> 本文按 30 路 sigmoid 设计，因为它最兼容定长网络。

### 2.3 记忆

```
记忆 A：形状由 A 的网络决定（建议 64 维浮点）
记忆 B：形状由 B 的网络决定（建议 64 维浮点）
双方都能读，自己只能写自己的
```

## 三、网络结构（第一版：小、能跑通）

### 3.1 共享底层 + 各自的头（推荐第一版）

```
观测（4144）
   ↓
共享底层：Linear(4144→512) → ReLU → Linear(512→512) → ReLU
   ↓
   ├─ A 头：Linear(512→256) 特征  →  sigmoid  → 256 个生长开关
   │        Linear(512→256) 特征  →  sigmoid×27+3 → 256 个时长
   │
   └─ B 头：Linear(512→256) 分数  →  softmax  → 选路
            Linear(512→30)        →  sigmoid  → 射击表
```

**参数量**：4144×512 ≈ 2.1M + 512×512 ≈ 0.26M + 头 ≈ 0.4M ≈ **2.8M**

> **注意**：架构文档的定案是 **A 和 B 是两个独立智能体**（防灾难性遗忘）。
> 但第一版用"共享底层 + 两个头"更省事，且可以先跑通链路。
> **最终形态应是两个独立网络**——见 §6 的迁移说明。

### 3.2 为什么第一版可以先用共享底层

因为第一版的目标是**验证链路能通**，不是出强度。
两个独立网络只是把"共享底层"复制一份、各自训练，结构上等价。

## 四、训练流程

> **【2026-10-06 修正】** 阶段 1 与阶段 2 改为**并行**训练，不串行。
> 完整定案见 **`智能体架构定案-2026-10-06.md` §三**。


### 4.1 阶段 0（预训练）：学会合法操作

**目标**：让智能体输出的动作**一次就合法**，不靠重试。

**数据从哪来**（不需要跑完整游戏）：

```
1. 用合成器生成随机的"树状态"：
     随机节点数、随机父子关系、随机标记哪些是真死/失效/耗尽
2. 对每个状态，随机生成一批"候选动作"
3. 程序判定每个动作的合法性（这是标签）
4. 训练网络：输入树状态 → 输出动作 → 与"合法动作"对齐
```

**损失**：

```
生长开关：BCEWithLogitsLoss（合法 = 1，非法 = 0）
         ← 网络学"哪些位置可以长"
选路：   交叉熵（正确的 = 合法的里随机挑一个）
         ← 网络学"在合法的里选"
射击表： BCE（帧号越界 = 0）
时长：   MSE（夹紧到合法范围）+ 越界惩罚
```

**关键**：这一步**不需要游戏**，只需要"树的形状 + 合法性规则"。
所以可以极快（几千次迭代几秒钟）。

## 五、导出格式（给 JS 用）

> **【2026-10-06 修正】本节的导出格式已作废。**
> 旧格式基于「4144 维扁平输入 + 全连接」，已被证明有结构性问题：
> ① 输入层吃掉 75.9% 的参数；② 无权重共享，同一件事要学 256 遍；
> ③ 硬编码 256 个节点槽位，泛化不到别的树大小；
> ④ 每个节点看到的是同一份全局摘要，无法做节点间相对比较（"盲人摸象"）。
>
> **新格式：Transformer Encoder（自注意力）+ 指针式逐层输出**，
> `d=256, L=3` → **2,562,849 参数（Hybrid 的 11.2 倍）**，
> 输入投影只占 0.7%，92.4% 用在注意力+FFN。
> 完整定案见 **`智能体架构定案-2026-10-06.md` §二**。


第一版**不引入 WASM 或 Rust**，直接导出成 **JSON + 平面数组**：

```json
{
  "format": "vantage-nn-v1",
  "obsDim": 4144,
  "layers": [
    { "name": "trunk0", "shape": [512, 4144], "bias": [512], "act": "relu" },
    { "name": "trunk1", "shape": [512, 512],  "bias": [512], "act": "relu" },
    { "name": "A_grow", "shape": [256, 512],  "bias": [256], "act": "sigmoid" },
    { "name": "A_len",  "shape": [256, 512],  "bias": [256], "act": "sigmoid" },
    { "name": "B_pick", "shape": [256, 512],  "bias": [256], "act": "none" },
    { "name": "B_fire", "shape": [30, 512],   "bias": [30],  "act": "sigmoid" }
  ],
  "weights": { "trunk0": [ ... 平面数组 ... ], ... }
}
```

**为什么用 JSON + 平面数组**：浏览器里 `Float32Array` 直接读，不依赖任何库。
体积估计：2.8M 参数 × 4 字节 ≈ **11 MB**（gzip 后约 3~4 MB）。
> 后续若要压体积，再上量化或二进制格式。

## 六、实现顺序

```
1. 写观测编码器（JS）：树状态 → 4144 维张量
2. 写动作解码器（JS）：网络输出 → 接口要的格式（growAt / select / 射击表）
3. 写合成器 + 训练脚本（Python）：生成阶段 0 的数据并训练
4. 导出权重 → JS 加载 → 接进接口 → 在游戏里验证"不违规"
5. （后续）真实环境到位后，训练阶段 1~8
```

**第 1、2 步是纯数据变换，可以用合成数据在 Node 里单独测；不需要游戏。**
