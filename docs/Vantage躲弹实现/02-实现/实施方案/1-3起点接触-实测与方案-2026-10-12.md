## 一、一句话结论

> **【实测】Rust 物理核心从来没有漏判「起点即接触」。**
> 把弹摆在坦克**中心 / 体内 0.5m / 贴边（相切）**，**raw ABI**（`vt_rollout_batch` 与 `vt_score_paths`，
> 不经过任何 JS 消费层）全部返回 **`dead=true`、`death_frame=0`**；8m 外对照两边逐帧一致。
>
> 旧实测看到的「**JS 9/9 报 df=0、Rust 9/9 报 alive**」是 **JS 消费层的 sink**：
> v172 之前 `simulateTankBatchScored` 把 Rust 结果映射成 **`dead: r.deathFrame > 0`**，
> 合法的 `fd=0` 被改写成 `dead=false`，探针再按 `dead ? deathFrame : -1` 读，就成了 `-1`。
> 该 sink 已在 v172 修为 **`dead: r.deathFrame >= 0`**（当前 `game_core/js/vantage_sandbox.js:2722`）。
>
> ⟹ **① 不该往 Rust 加「起点重叠检查」（物理上没缺）**；Rust 侧无需改、JS 主修已落。
> **残留同类洞只有一处**：`game_core/js/vantage_tree.js:3000` / `:3021` 的
> `mergeIncrementalRescoreDeath` 仍用 `>0` 丢掉增量重评分的 `fd=0`（**JS 单侧即可修，与 Rust 无关**）。

**对旧 audit 数字的修正（重要）**：《JS-Rust判死频率-2026-10-11》里的
**「JS 多判死 8.3%、其中 85% 是 df=0」这条头条是被上述 sink 抬出来的**——
- `df=0` 的「JS 判死 & Rust 判活」在旧探针口径下**必然**长这样（Rust raw 的 0 被吞）；
- **D 桶（把车直接摆到弹上）`1251/1251` 是 100% sink 伪影**（G4 实测：同一条 `>0` 映射一贴，9/9 全变 -1）；
- C 桶的 `108` 个 `df=0` 无法重跑（旧 wasm 没了），**【推断】绝大多数同因**；
  ⟹ **8.3% 这个头条不可再引用**。真实「JS 多判死」数量**无法从旧样本反推**：若那 108 个 df=0
  全是 sink 伪影，则 **≈19/1539 = 1.23%**；若它们全是真的，则仍是 127/1539；
  无论哪种，本报告能钉死的只有「**D 桶 1251/1251 是伪影**」与「**起点接触物理层没漏**」；
- B 桶 3 个 JS-only（`df=75/75/45`）与反向 `10/1539=0.65%` **不受该 sink 影响**（df>0 能穿过去），继续有效。

## 三、改法方案（不是实现）

### 3.1 结论：**Rust 侧不需要加「起点重叠检查」**

理由（每条都有实测/代码支撑）：

1. **物理层已经抓到**：raw ABI 三类局面 `dead=true/df=0`（§2.4）；`box2d.rs` 自 10-02 未变。
2. **加了会重复**：Rust 的接触扫描与 JS 的接触扫描同语义；再加一个几何检查是在同一条路上叠一层。
3. **加错位置会直接打破 `diff_rollout_bridge 0.0`**：若在 k=0 的 Step **之前**置 `dead`，
   下面这句会把速度清零（`rollout.rs:1066-1071`）：
   > 【代码原文】`if dead[i] { speeds[i]=0.0; rot_spds[i]=0.0; continue; }`
   ⟹ 候选在 k=0 不动，轨迹与 JS 分叉。JS 侧自己就吃过这个亏：
   > 【代码原文】`vantage_sandbox.js:1936-1937`：「立刻置 dead 会把候选停车，使 JS/Rust 轨迹分叉
   > （实测 `diff_rollout_bridge` 会因此报 **0.32m** 轨迹偏差）」。
4. **旧实测量级不足以支撑这个改动**：修掉 sink 后，起点接触类分歧的实测反例已经归零（D 桶与定点复现都是伪影）。

**因此推荐落法：Rust 一行不改；JS 消费层按 v172 保持 `>=0`；把「起点接触」纳入回归守卫（§四）。**

### 3.2 如果指挥官仍要「Rust 侧防御性兜底」——唯一安全的精确设计

> 这一节是**方案**，不是建议落地；只有在 fuzz 出「接触路径真的漏」之后才有必要。

- **加在哪**：放在 `rollout.rs` 主循环**每次采样之后、`if k >= duration { break; }` 之前**，
  只记录 `start_geo_hit[op] = k`（与现有 `sweep_hit` 同位），**绝不在循环内置 `dead`**；
  循环结束后在 `:1307-1313` 那段「扫掠回溯合并」旁边做同样的回溯合并（取更早者）。
- **对哪些弹种**：**全部**活跃弹槽（用 `slot.radius`，与 JS `geoHit` 逐槽遍历一致），
  **不许只对激光**——起点接触与激光扫掠无关；激光/霰弹/破片/普通弹在 JS 侧都吃同一个 `geoHit`。
  （`radius=0` 的激光在 JS 融合侧已被 `acquireFusedBullet` 回退到 0.05，Rust 收到的是同一个 0.05。）
- **代价**：若只查 `k==0`：每批 9 op × 活跃弹数（≤256）一次「fat-AABB 门 + 圆 vs sensor 多边形」，
  µs 级、每批一次；若逐帧镜像 JS `geoHit`（k=0…duration）：75 倍，仍是小量但非可忽略，
  且需要在 Rust 新写一个圆-多边形最近距离 helper（现有只有激光用的线段扫掠 helper）。
- **会不会改变 `diff_rollout_bridge` 的 `0.0`**：
  - **回溯式（推荐形态）⟹ 不会**：samples 逐帧不动，位置误差保持 0.0；只可能在「接触漏判」的场面
    把 Rust 的 `dead/df` 改成与 JS 一致，**只会让该对拍更绿**。
  - **内联式（循环内置 dead）⟹ 会，而且必坏**：见 3.1③。
- **JS 融合侧要不要同步加**：**不要**。JS 已经有 `geoHit`（`:1938-1958`）且覆盖所有 k；
  同步加只会重复。真正要同步的是**消费层口径**（`>=0`），那已在 v172 落了。

### 3.3 JS 侧**残留必改点**（与 Rust 无关）：增量 rescore 的 fd=0 仍被吞

【代码原文】`game_core/js/vantage_tree.js:2996-3024`（**修前行号**；本文件已于 §8.2 修好，行号/内容以 §8.2 为准）`mergeIncrementalRescoreDeath(c, r)`：

```js

var newFd = (r && typeof r.deathFrame === 'number') ? r.deathFrame : -1;
var mergedFd = oldFd;
if (newFd > 0 && (oldFd <= 0 || newFd < oldFd)) mergedFd = newFd;   // ← :3000 吞掉 newFd=0
...
} else if (mergedFd === newFd && newFd > 0 && Array.isArray(r.perFrameScores)) { ... } // ← :3005 同理
...
    dead: mergedFd > 0,                                             // ← :3021 吞掉 mergedFd=0
```

- **可达性**：`vt_rescore_nodes` 的 v172 注释（`rescore.rs:1361-1365`）明确说
  「`death_frame==0` = 起手第 0 步就撞上……旧代码 `> 0` 会把激光扫掠的首帧命中直接丢掉」，
  说明 fd=0 在增量路径**确实会返回**；沙箱 `:2895` 也已改成 `dead: rn.deathFrame >= 0`，
  **但树这一层又把 fd=0 丢了** ⟹ 同一个 bug 只修了一半。
