## 一、输出形态定案：**每帧重新生成整条路线**

### 用户原话

> 「LLM 是不能撤回 token，但这我们这也不是撤回 token，而是**每帧重新生成一句话**，
> 即使生成出来的话和上一帧的完全一样，也要再生成一遍。
> 至于生成具体的句子的时候，肯定还是一个 token 一个 token 吐的。」

### 准确模型（两层时间尺度）

```
【帧内】token by token
    从当前 root 出发，沿父子边一个节点一个节点地吐
    step 1: 在 root 的子节点里选 → 节点A
    step 2: 在 节点A 的子节点里选 → 节点B
    step 3: 在 节点B 的子节点里选 → 节点C
    ... 直到吐出结束符 或 到达叶子
    → 得到【一条完整路线】

【帧间】整句重新生成
    下一帧，世界已经推进（车动了、子弹飞了），从【新的 root】重新吐一遍
    即使吐出来的路线和上一帧一模一样，也重新生成，不缓存、不复用
```

### 关键推论 1：**深度偏差在结构上不可能出现**

因为帧内沿父子边生成 → **每一步的候选永远只可能是"上一个节点的子节点" → 永远是同层兄弟之间的比较**。

```
❌ 会出深度偏差的：把不同深度的节点放一起比 / 沿路径累加分数
✅ 这里的做法：   每一步只比"当前节点的 9 个子节点"
```

用户此前否掉的正是前者：
> 「不能让智能体给节点评分，然后我们用算法直接找分最高的**路径**，因为那样子会导致**更深的路线分数更高**。」

**结论**：用户当时的判断是对的，而本架构天然不触发它。

### 关键推论 2：**不是"撤回 token"，所以没有抖动问题**

上一版文档里担心的「第1帧选左、第2帧选右、第3帧又选左 → 车原地抽搐」是**错误类比**：
- 帧内生成是**连贯的**（相邻 token 必然沿父子边）
- 帧间重生成时**世界已经推进**，是从新状态重新规划，不是原地反复横跳
- 帧间不做任何"跨帧一致性"约束，也不需要记忆去压抖动

### 关键推论 3：**候选集 = 整棵树的合法节点，但生成路径是逐层的**

「智能体想选哪就选哪」指的是**起点自由**（任意合法节点都可以作为路线起点），
不是「一帧之内在所有深度里乱跳」。生成仍然是逐层的。

## 二、网络架构定案：Transformer Encoder + 指针式输出

### 为什么不用"共享节点编码器 + 全局摘要"（上一版方案，作废）

用户原话：
> 「选每层节点的时候，肯定得看到整棵树，不然纯盲人摸象。」

上一版把整棵树压成一个全局摘要，**所有节点看到的是同一份摘要**，
节点 A 无法知道节点 B 长什么样 → 无法做"我比它更安全"这类相对比较 → 盲人摸象。

**自注意力直接解决这个**：每个节点 attend 到其他所有节点的**原始特征**。

| 需求 | 自注意力 |
|---|---|
| 树大小可变 | ✅ 不依赖固定槽位 |
| 置换不变（节点顺序无意义） | ✅ 天生 |
| **每个节点看到整棵树** | ✅ 这就是它的定义 |
| 节点间相对比较 | ✅ 注意力权重就是"我跟谁最相关" |

### 结构

```
输入
  ├─ N × 16   节点特征（每个节点：x, y, 深度, 是否真死, 段长, 子树评估, ...）
  └─ 1 × 48   全局（地图、我方位姿、子弹、上一帧选谁、A/B 双份记忆）
                 ↓ 线性投影到 d=256
                 ↓ + 深度编码 + 节点/全局类型编码
      ┌──────────────────────────────────────┐
      │  Transformer Encoder × 3 层           │
      │  d=256, 8 heads, FFN 4×               │
      │  （节点 token 之间全连接自注意力）      │
      └──────────────────────────────────────┘
                 ↓
  ┌──────────────┼───────────────┬────────────────┐
  ▼                      ▼                   ▼                ▼
A_grow 头             A_len 头            B_pick 头        B_fire 头
逐节点 → 1            逐节点 → 1          逐节点 → 1       全局 token → 30 帧
"这能长吗"            "这段多长"          "选它"           射击表
                                        ↓
                              沿父子边逐层生成，softmax over
                              当前节点的子节点 → 吐一个 token
                              直到结束符 → 输出整条路线
```

### 参数量（实测计算）

| 配置 | 注意力+FFN | 输入投影 | 各头 | **合计** | /Hybrid |
|---|---|---|---|---|---|
| d=64, L=3 | 149,952 | 4,224 | 31,713 | 185,889 | 0.8× |
| d=128, L=4 | 793,088 | 8,448 | 67,745 | 869,281 | 3.8× |
| d=192, L=4 | 1,779,456 | 12,672 | 116,065 | 1,908,193 | 8.4× |
| **d=256, L=3** | **2,369,280** | **16,896** | **176,673** | **2,562,849** | **11.2×** |
| d=256, L=4 | 3,159,040 | 16,896 | 176,673 | 3,352,609 | 14.7× |
| d=256, L=6 | 4,738,560 | 16,896 | 176,673 | 4,932,129 | 21.6× |

**定案：`d=256, L=3` → 2,562,849 参数（2.56M）**

### 为什么不缩到 200K

用户原话：
> 「比 Hybrid 小我觉得不太行，因为那个本身接收的量就小，我们给的操作更多，有更多输入，权重不更大不合理。」

**同意。** Hybrid 是 228K，但它的输入维度和任务复杂度都远低于我们（9 操作 + 整棵树 + 四个头 + 射击表）。
按"输入更多、操作更多 → 容量应当更大"的外推，2.5M 量级是合理的。

### 同样 ~2.5M，钱花在哪 —— 这才是本次改动的实质

```
文档旧架构（扁平 4144 长向量）
    输入层   2,122,240   75.9%   ← 全喂给没有权重共享的平铺输入
    真正的脑子   672,030   24.1%

Transformer d=256 L=3
    输入投影     16,896    0.7%   ← 输入只占这么点
    注意力+FFN 2,369,280   92.4%   ← 几乎全在真正的大脑
    合计      2,562,849
```

**不是"把模型变小"，是"同样大小但不再浪费"。**

### 数据需求（@ 8 路并行 / 19 倍实时 / 每 10 帧一次决策 ≈ 912 样本/秒）

| 模型 | 参数 | 样本需求（10~100×） | 估算耗时 |
|---|---|---|---|
| Hybrid 参照 | 228,280 | 2.3M ~ 22.8M | 0.7 ~ 7.0 小时 |
| 旧扁平架构 | 2,794,270 | 27.9M ~ 279.4M | 8.5 ~ 85.1 小时 |
| **Transformer L=3** | **2,562,849** | **25.6M ~ 256.3M** | **7.8 ~ 78.1 小时** |

## 三、训练课程定案（修正 §8）

### 用户原话

> 「初期肯定分阶段啊，我分得清清楚楚，看文档。**先让智能体学会合法操作，然后学习移动**
> （**移动和射击或许可以一起学，因为怕学了移动之后很难再学会射击了**）」

### 修正

原 §8 把「移动」（阶段1）和「定点射击」（阶段2，不能离开本格）拆开。
用户指出风险：**只学移动会让策略收敛到"只会走"，射击键的梯度信号被淹没**。

**定案：阶段 1 与阶段 2 并行喂同一个网络**（交替采样两个任务），
阶段 4「移动射击」由并行训练自然合并，而不是重新学一遍。

| 阶段 | 内容 | 练什么 | 相对原文 |
|---|---|---|---|
| **前置** | 随机操作树，学会合法操作（不渲染但保留完整游戏逻辑） | 合法性 | 不变 |
| **1′** | **移动 + 定点射击 并行**（两个任务交替喂） | 走位精度 + 瞄准/反弹 | **原 1、2 合并** |
| **3** | 躲弹：射击源随机移动并发射不同弹种 | 纯躲弹 | 不变 |
| **4** | 移动射击（自然合并，非重学） | 衔接 | **由 1′ 直接产出** |
| **5** | 躲弹射击 | 边躲边打 | 不变 |
| **6** | 移动目标躲弹射击 | 预判移动目标 | 不变 |
| **7** | （可选）道具操作专项 | — | 不变 |
| **8** | 真实对局 | 整合 | 不变 |
