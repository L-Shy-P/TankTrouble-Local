## 二、逐条展开（含结构说明）

### 2.1 地图与配置

**对称**：`GameController` 构造函数接 `symmetric` 参数并存成字段（[GC]行1@731 字段块、构造函数 `this.symmetric=symmetric`）。
`_initializeRound()` 里 `this.gameMode.setSymmetric(this.symmetric)`（[GC]行1@14907 附近）→ `GameMode.getMaze()` 按它选 `Maze.createSymmetric` / `Maze.createRandom`（[GM]行47、行49 的 `getMaze`）。
**注意**：`Maze` 自己**不保存**"我是不是对称生成的"（[MZ]行2 的 `Maze.fields` 里没有 symmetric 字段）⟹ **对称性只能从 `GameController`/`GameState`/`GameMode` 读，不能从 maze 读**。

**毒雾开关 vs 毒雾实体**：`getStorm()` 只说明**本局允许风暴**；真正出现与否看 `getZones()` 里有没有 `ZONE_TYPES.STORM` 的 zone（[GM]行47@46154 经典模式 `roundDuration>=Constants.CLASSIC_STORM_APPEAR_DURATION(60s)` 时才 `StormZone.createInitialZoneState`；[GM]行49 的 DM 是加时后 30s）。**开关开着也可能还没出现。**

**可刷新道具类型**：`crateTypes` 是构造参数 → `GameController.crateTypes`（字段）→ `_initializeRound()` 灌进 `gameMode.crateTypes`（[GC]行1@14907）。**两边都没有 getter**（全仓 grep `getCrateTypes` 只命中 `CreateGameMessage`，[GM]行32@16571，那是**网络消息**，不是 `GameController`）。
刷新的实际逻辑在 [GM]行45/行49 的 `update()`：`if(this.crateTypes.length>0){…Math.random()*this.crateTypes.length…}`，刷新上限 `Constants.MAX_CRATES=3`（[CO]行1@3950）。

**玩家上限**：`getMaxActivePlayerCount()`；`_initializeRound()` 用它决定激活几个排队玩家（[GC]行1@9567 附近的 `while(this.model.getActivePlayerCount()<this.model.getMaxActivePlayerCount()…)`）。
另有常量口径 `Constants.GAME.MAX_ACTIVE_PLAYERS=8 / SYMMETRIC_MAX_ACTIVE_PLAYERS=4`，以及 `GAME_MODE_INFO[mode].MIN_PLAYERS`（开一局的门槛，[CO]行1@9807）。

**地图本体**（`Maze`，[MZ]行2）可用方法：`getTiles()`（三维数组 `tiles[x][y]`，`[0]`=是否有地板、`[1]`=上墙、`[2]`=左墙，见 [MZ]行2 顶部注释）、`getWidth()/getHeight()`、`getTileBounds()`、`getTheme()`、`getWalls()/getBorders()/getFloors()/getSpaces()`、`isPositionInsideMaze(position)`、`getRandomUnusedPosition(roundState, minDist)`、`getCrateSpawnPosition(roundState)`、`getTankSpawnPosition(roundState)`、`getStormExpansionSequence()`。

### 2.2 玩家与战绩

- 列表：`getActivePlayerIds()`（在局中的）、`getQueuedPlayerIds()`（排队的）、`getAllPlayerIds()`。
- 对象：`getActivePlayer(pid)` / `getQueuedPlayer(pid)` → `Player`（[CO]行7）：`getId()`、`getTeam()`、`getEnqueueTime()`。
- **战绩**：一局里每个玩家有两条 `Score`（`SCORE_TYPES.KILL=0` / `VICTORY=1`，在 `BootCampGameMode.getScoreStates` 建立，[GM]行45）。取值：
  `getScoreByPlayerIdAndType(pid, 0).getValue()` / `…(pid,1).getValue()`；或 `getScores()` 拿全表再按 `getType()` 分。
- 徽章（连杀/连胜的 UI 状态）：`getEmblems()` / `getEmblemByPlayerIdAndType(pid, EMBLEM_TYPES.TERMINATOR=0|DOMINATOR=1)`。

### 2.4 对手坦克（**含"按键"这条**）

一次拿全对手信息的最小调用链：

```

tank.getX() / getY() / getRotation()                // [TK]行3
tank.getForward() / getBack() / getLeft() / getRight() / getFireDown()   // [TK]行3（默认 getter）
tank.getLocked() / getSpeed() / getRotationSpeed()  // [TK]行3

```

**★ 按键（最关键那条）**：**能读到，且对手和自己走的是同一个 `Tank` 对象、同一套字段**。
`Tank.fields` 直接有 `forward/back/left/right/fireDown/locked`（[TK]行3@4622），`Tank.setTankState` 把它们从 `TankState` 拷进来（[TK]行3 `setTankState:function(tankState){…this.forward=tankState.getForward();…}`）。
⟹ `getTank(任意 playerId).getForward()` 就是那个玩家的"前进键是否按下"。

**三个必须知道的坑（都是代码原文可证的）**：
1. **`locked` 会吞掉按键**：`getForward/getBack/getLeft/getRight/getFireDown` 全是
   `if(this.locked){return false;}`（[TK]行3@6208 等）。`locked` 由武器决定：`_updateWeaponLockingAndFiring()` 里 `tanks[tank].setLocked(weapon.movementLocked())`（[RC]行2）。
   ⟹ **读到的 `false` 可能是"被锁定"而不是"没按"**；要区分必须同时读 `tank.getLocked()` 和 `tank.fireDown` 的**原始字段**——注意 **`fireDown` 本身没有 getter 直读**，`getFireDown()` 同样会被 locked 吞。
   【我的解释】训练沙箱若关心"AI 对手到底按没按"，**`getLocked()` 必须一起进观测/一起判**，否则会把"开火时被锁"误读成"没开火"。
2. `TankState` 里也有同样 6 个布尔（[RM]行17），所以 `getRoundState(true).getTankStates()` 是**另一条等价路径**（但受 expanded 位影响，见 §三）。
3. **在线模式的可用性未验证**：`RoundController.setRoundState()` 对**本地玩家**会跳过 tank state（`Constants.getMode()!=MODE_CLIENT_ONLINE||localPlayerIds.indexOf(...)==-1||…`，[RC]行1），而 `TankStateMessage`（[GM]行6）确实把整份 `TankState`（含按键）发给客户端。**但本套代码里没有实测**在线对局下 `Tank` 的按键字段是否被填满 ⟹ 见 §六。

**携带道具 / 剩余子弹**：
- 当前武器 = `getActiveWeapon(pid)`（栈顶，`playerIdOtherWeaponIds` 的最后一个，[RM]行1@21230）；
- 排队武器 = `getQueuedWeapons(pid)`（[RM]行1@21477）；
- 弹药：所有武器类都是 `_xxx` 私有字段 + `getField(name)`（[MZ]行12@83896：`getField:function(fieldName){if(this.classs().hasOwnField("_" +fieldName)){return this["_" +fieldName];}…`；Weapon/Counter/Upgrade/Zone 里是同一段代码，如 [TK]行5@10624）：
  - 子弹枪 `_numBullets`（=初始 5，`Constants.BULLET_AMMO_COUNT`）、已打 `_bulletsFired` ⟹ **剩余 = `numBullets-bulletsFired`**【我的解释，未在代码里找到现成的"剩余"getter】
  - 双管 `_numBullets`（**直接递减，就是剩余**，[TK]行11）、霰弹 `_numBullets`（[TK]行12）、地雷 `_numMines`（[TK]行15）、加特林 `_numBullets`（[TK]行17）

**存活**：`getTank(pid)` 返回 `undefined` 就是死了 —— `_removeDestroyed()` 会 `delete this.tanks[playerId]`（[RM]行1@28780）。

### 2.8 毒雾（`StormZone`）

`getZones()`（[RM]行1@22298）→ `{id: Zone}`；`Zone`（[TK]行36）有 `getId()/getType()/getTiles()/getB2DBody()/getField()/getZoneState()`。
毒雾专属字段（[TK]行40@39100）：
`_expansionTime`（距下次扩张的剩余秒）、`_expansionSequence`（**扩张序列数组**，元素 0/1/2/3 = 右/下/左/上）、`_tileBounds`（`{minX,minY,maxX,maxY}`）、`_expansionSide`（本帧正在扩的边；`-1` 表示"不在扩张动画中"）、`_expansionTilesRight/Bottom/Left/Top`（已扩格数）。

- ⚠️ **`Maze.getStormExpansionSequence()` 不是缓存的**（[MZ]行2）：方法体里用 `Math.random()` **现算一个新序列**（`result.push(Math.random()<0.5?0:2)` 等）。游戏只在 `StormZone.createInitialZoneState(id, maze.getStormExpansionSequence(), maze.getTileBounds())` 时调一次（[GM]行47@46154 / 行49）。⟹ **要"提前知道下次方向"，必须从已存在的 `StormZone` 读 `_expansionSequence`，不能自己调 `Maze` 的方法**。
- 碰到风暴 = 死：`TANK_ZONE_COLLISION` → `case ZONE_TYPES.STORM: self.destroyTank(...)`（[RC]行1@6013）。

### 2.9 时间（剩余 / 模式 / 加时）

游戏里**没有"全局计时器"对象**，时间由 **Counter** 实体 + **GameMode 自己的字段**两套拼出来：

| 模式 | 计时实体 | 依据 |
|---|---|---|
| 经典 / 新手营 | **没有回合倒计时**（只有"剩 ≤1 辆坦克后再等 `ROUND_FINISHING_DURATION=3s` 结束"） | [GM]行47（Classic 只创建风暴）、[GM]行45@41218 `roundFinishingDuration=Constants.ROUND_FINISHING_DURATION;` |
| 死斗（DM） | `TimerCountdownCounter`（60 → 0），到 0 且无赢家 → 换成 `OvertimeCountUpCounter`（从 0 往上加） | [GM]行49@54449（ROUND_STARTED 建倒计时）、[GM]行49@51244 `this.roundDuration=Constants.DEATHMATCH_ROUND_DURATION;`、@57121（建加时计数） |
| DM 加时且**只剩 1 个赢家** | 再建一个 `TimerCountdownCounter`（`ROUND_FINISHING_DURATION=3s`）收尾 | [GM]行49@51471 `overtimeCountdownDuration=Constants.ROUND_FINISHING_DURATION;` |

读法（唯一通用入口）：`getCounters()` → 按 `counter.getType()` 分：
- `COUNTER_TYPES.TIMER_COUNTDOWN=0` → `getField("currentTime")`（剩余秒）、`getField("startTime")`（初始值）
- `COUNTER_TYPES.OVERTIME_COUNT_UP=1` → `getField("currentTime")`（**已加时秒数**）
【我的解释】"不限"= 这两种 counter **一个都不存在**且 `getState()=="in round"`。

### 2.10 回合状态（倒计时 / 结算中）

- **快照状态**：`getState()` ∈ `{"between rounds","counting down","in round","ended"}`（[GC]行3）。
- **开局倒计时**：默认 `COUNTDOWN_START_VALUE=3`、每 `COUNTDOWN_DURATION=0.5s` 一格（[CO]行1）；`GameController.update()` 里 `countDown(this.countDownValue)` 后自减（[GC]行1@15471 区）。

- **"结算中"**：代码里**没有**这个状态名。最接近的三个可读量：
  ① `getState()==="between rounds"`（回合已结束 / 庆祝阶段）；
  ② `getBetweenRoundsDuration()`（已等待时长；`BETWEEN_ROUNDS_DURATION=1.0` + `CELEBRATION_DURATION=7.0`，[CO]行1）；

### 2.11 死亡事件（★ 结论：**有事件，但事件里没有位置/角度**）

**订阅**：
```js
gameController.addRoundEventListener(function(ctx, gameId, evt, data){ … }, ctx);   // [GC]行1@20488
```
回调签名 `(context, gameId, evt, data)`（[RM]行1@31585 `_notifyEventListeners:function(evt,data){…this.eventListeners[i].cb(this.eventListeners[i].ctxt,this.eventListeners[i].gameId,evt,data);`）。

**两个事件，语义不同**：

| 事件 | 字符串 | `data` | 何时发 |
|---|---|---|---|
| `TANK_KILLED` | `"tank killed"` | **`Kill` 对象** | 被子弹打死（`TANK_DEADLY_COLLISION` → `Kill.create` → `killTank`） |
| `TANK_DESTROYED` | `"tank destroyed"` | **playerId（字符串）** | 掉进风暴/出生区（[RC]行1@6013）、玩家主动退出等 |

`Kill`（[TK]行42）**完整字段**：`victimPlayerId / killerPlayerId / experience / deadlyId / deadlyType`，
getter 齐全（`getVictimPlayerId()` @43534、`getKillerPlayerId()`、`getExperience()`、`getDeadlyId()`、`getDeadlyType()` @43746）。
`deadlyType` 是 `Constants.WEAPON_TYPES`（`BULLET:-1,LASER:0,DOUBLE_BARREL:1,SHOTGUN:2,HOMING_MISSILE:3,MINE:4,GATLING_GUN:5`，[CO]行1@2931），`deadlyId` 是那颗子弹的 id。
自杀也是 `TANK_KILLED`，此时 `killerPlayerId===victimPlayerId`（`BootCampGameMode` 里 `if(data.getKillerPlayerId()!=data.getVictimPlayerId())` 才加分，[GM]行45@43134）。

**❗位置 / 角度取不到（事件里没有）**：
`Kill` 里**没有任何坐标字段**。可行做法只有：
**(a)** 在**回调里**用 `getTank(victimId)` 读位置 —— 此时 `delete` 还没发生（`_removeDestroyed` 下一帧才跑，[RM]行1@20587 vs [RM]行1@28600 `_removeDestroyed`）；
**(b)** 在 `RoundController.killTank` 上打一层 wrapper，**先**取 `getTank(victim).getX()/getY()/getRotation()` 再调原函数 —— **本项目已有现成先例**：`game_core/js/training_mode.js` 的 `wrapTrainingRoundController()`（函数在**行111**；取位姿在**行127**，调原函数在**行134**：`var deadTank=this.getTank(victim); …deathPose={x:deadTank.getX(),y:deadTank.getY(),rotation:deadTank.getRotation()}; var result=origKill.call(this,kill);`）。
【我的解释】训练侧如果用 (a)，**必须保证"事件回调 → 读 tank"发生在同一帧、且没有中间 `update()`**；(b) 更稳。

**被毒雾/出生区杀死的**走 `destroyTank`（不是 `killTank`）⟹ **既没有 killer，也没有武器**，也没有位置（只有 playerId）。
**"被谁用什么武器"只有 `TANK_KILLED` 有**；`TANK_DESTROYED` 只有 playerId。

其它相关事件：`TANK_CHICKENED_OUT`（玩家退出时，`data` = `ChickenOut`，含 `playerId/projectileIds/trapIds`，[TK]行57 / [RM]行1 `removeTank`）。

11. **`getRoundState()` 的"缺段"风险**：`RoundState` 只有 `TankStates/ProjectileStates/CollectibleStates` 是**始终有**的，`Trap/Weapon/Upgrade/Counter/Zone` 五段**只在 expanded 时才有**（[RM]行1@18340 `if(expandedState){this._getExpandedRoundState(rs);}`；[RM]行28 `isExpanded()`）。

    【我的解释】沙箱**不要依赖 `getRoundState()` 取这五类**，直接 `getTraps()/getUpgrades()/getZones()/getActiveWeapon()`。
12. **`Maze` 里"我是不是对称地图"** —— 没有这个字段（[MZ]行2 的 `Maze.fields`）。
13. **`Maze.getStormExpansionSequence()` 的"确定性"** —— 它是 `Math.random()` 现算（[MZ]行2），**不是缓存的序列**；序列只存在于 `StormZone._expansionSequence`。

## 五、【我的解释】（**均未验证，别当定论**）

1. 【解释，未验证】`getTank` 的按键字段是**输入快照**而不是"当前按键的物理真值"：`Tank.setTankState` 从 `TankState` 拷入，`TankState` 只能来自 `InputState`（本地玩家）或网络包（在线）。所以**只要该玩家这一帧没有新的 input/tankstate，字段就是上一帧的值**（不会自动清 false）——对训练沙箱而言，"上一帧输入"与"当前按键"的差别要注意。
2. 【解释，未验证】`getLocked()` 是**读按键时最容易踩的坑**：locked 时 5 个按键 getter 全返回 `false`（[TK]行3@6208 等），所以"对手没开火"和"对手被武器锁定"在只读 `getFireDown()` 时**无法区分**。
3. 【解释，未验证】"时间"最稳的读法是**按 counter 类型**而不是按模式名：经典模式没有 counter，DM 有时是 `TIMER_COUNTDOWN`、有时是 `OVERTIME_COUNT_UP`（加时后），加时且只剩 1 个赢家时又变成 `TIMER_COUNTDOWN`（3s）。判别式 = `type → currentTime`。
4. 【解释，未验证】`MINE_DETONATED` 之后 `_detonationTime` 每帧减 `deltaTime`，`released()` 为真时破片才生成（[RC]行2 的 update 扫 `traps[..].released()`）⟹ "已触发未爆"窗口 ≈ 0.4s，**读到的概率不高**，必须订阅事件而不能靠轮询。
5. 【解释，未验证】`RoundModel._EVENTS.TANK_KILLED` 在 `killTank()` 里**先 push `destroyedPlayerIds` 再发事件**（[RM]行1@20587），所以事件回调里 `getTank(victim)` **仍返回旧对象**、`getX/getY/getRotation` 是**死亡瞬间**的值（这是"事件里拿位置"可行的原因）。**但我没有实测**——建议沙箱侧用一次真死亡打日志确认。
6. 【解释，未验证】"结算中"我倾向指 `getState()==="between rounds"` 之后的窗口（含庆祝 7s），但**这只是命名猜测**。
7. 【解释，未验证】两侧文件在训练环境里是 **`MODE_CLIENT_LOCAL`**（本地跑完整服务器逻辑），所以 `RoundController._modelEventHandler` 才会挂上（[RC]行1 里 `if(Constants.getMode()===MODE_SERVER||MODE_CLIENT_LOCAL)`），死亡事件才会在本地产生。**在线模式**下同一事件走 `TankKilledMessage`（`game_core/js/5be42e11…js` 里 `_tankKilledMessageHandler`）。
