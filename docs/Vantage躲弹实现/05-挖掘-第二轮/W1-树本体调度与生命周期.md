## 一、职责

### 1.1 它是谁、谁在调它

- **模块级单例**：`var _tree = null;`（`vantage_tree.js:6781`）。整个 AI 一局一棵树，跨 tick 存在。
- **唯一驱动入口**：`function tick(ai, dt)`（`vantage_tree.js:7127`）。调用方是 `ai_vantage.js`：

  【代码原文】`game_core/js/ai_vantage.js:89-95`
  ```js
  if (typeof VantageTree === 'undefined' || !VantageTree.tick) return false;
  try { VantageTree.tick(this, (deltaTime || 20) / 1000); } catch (eT) { ... }
  ```
  （注释在同处说明：Phaser 的 deltaTime 是毫秒，tick 契约是秒，必须 /1000。）

- **树对游戏的唯一输出**：`getDesiredOperation()`（`vantage_tree.js:7571-7577`），返回 `{inputs, opName}`；`ai_vantage.js:96-106` 把它写成 `InputState`。

  【代码原文】`vantage_tree.js:7571-7577`
  ```js
  function getDesiredOperation() {
      if (!_tree || !_tree.active || !_tree.commitNode) return null;
      return {
          inputs: _tree.commitNode.inputs,
          opName: '树:' + (_tree.commitNode.opName || '?')
      };
  }
  ```

- **树不负责驱动坦克**：没有逐帧 advance/step 节点执行的代码；执行 = 游戏按 `commitNode.inputs` 操作，树的 `rolloutSamples` 是**预先算好的**。

### 1.2 它的状态由谁保管

| 状态 | 存在哪里 | 生命周期 |
|---|---|---|
| 树本体 | 模块级 `_tree`（`6781`） | `createTree()` 建立（`7292-7304`），`reset()` 置 null（`7726`） |
| 全局时间轴 `_timeAcc` | 模块级（`1413`） | **跨树不清零**（`createTree` 只把它抄进 `tree.tNow` / `tree.rootAbsT`）；`reset()` 会清零（`7728`） |
| 帧步长 `FRAME_DT` | 模块级（`790`） | 被 `calibrateFrameDt` 逐帧平滑（`7115-7123`）；`reset()` 强制回 0.02（`7738`） |
| 跨局黑名单 `_stuckOps` 等 | 模块级（`859-867`） | `reset()` 清空（`7757-7760`） |
| 事件/性能/录制环形缓冲 | 模块级（`1416`、`6943`、`875-894`） | `reset()` 清（`7747`、`7761`） |

### 1.3 树**不做**什么（与智能体版改造直接相关）

- **树里没有"射击"这件事**。【代码原文】全文件 8,344 行中 `fire/射击/shoot` 只出现在一条无关注释里（`vantage_tree.js:1965`）；接口的 `validateDecision` 也只认 `growAt / growTimes / select / memory` 四个字段（`vantage_tree_interface.js:113-123`）。射击在 `ai_vantage.js` 自己的 action 系统里（不在树内）。
- **树不自己算物理**：所有物理/死亡都委托给 `VantageScoring.scorePath(s)`、`adapter.simulateTankBatch(Scored)`、`adapter.rescoreTankSamples`、`adapter.simulateBulletTracks`（调用点见 3.1-D6）。
- **树的 `next`/`commitNode` 是"预测"，不是"命令"**：`getDesiredOperation` 只读 `commitNode.inputs`。

## 五、切片机制：`_commitSlice` / `_expandSlice`

两套切片都是"把一批 9 操作评分摊到多帧"的性能手段，但**目的、粒度、完成语义、当前实际上是否跨帧**完全不同。

### 5.1 `_expandSlice`（预览展开切片）

- **声明**：`tree._expandSlice = null`（`createTree` `1647`，注释：`{leaf, adapter, threats, idx, results}`）。
- **开**：`startExpandSlice` `5571-5584`：拒绝 `!leaf / isTerminalDead(leaf) / leaf.children.length>0`；`canAddTreeNodes(tree, 9)` 不够也拒绝；否则建 `{leaf, adapter, threats, idx:0, results:[], computeMs:0}`。
- **推**：`stepExpandSlice` `5587-5637`：每 tick 算 `perTick = heavy ? TREE_OPS_PER_TICK_HEAVY(1) : TREE_OPS_PER_TICK(3)`（`5591-5592`，`heavy = 威胁数>6`）；优先 `VantageScoring.scorePaths`（`5597-5600`），失败则逐操作 `scorePath`（`5612-5619`）；`idx` 走满 9 后 `attachResults` → 记 `growMs` → `computeMs>60` 置 `_growSkip` → `tree._expandSlice = null` → `_lastGrowAt = performance.now()` → `applyRetreatAfterExpand`（`5628-5635`）。
- **被谁推**：`growStep` 第一句 `if (tree._expandSlice) { stepExpandSlice(tree, adapter); return; }`（`5878-5881`）；以及 `startExpandSlice` 成功后同帧先切一片（`6044-6046`）。

### 5.2 `_commitSlice`（提交重选切片）

- **声明**：`tree._commitSlice = null`（`createTree` `1648`，注释：`{adapter, threats, realTankState, idx, results}`）。
- **开**：`startCommitSlice` `6655-6668`：`if (!realTankState || tree._commitSlice) return false;`；建 `{adapter, threats, realTankState, freshRoot, idx:0, results:[], computeMs:0}`。

- **被谁废**：`tick` `7372`（`_commitSlice` 进行中又出新弹：`tree._commitSlice = null`，继续走 emergency 分支重建）。

### 5.3 两者怎么交互

1. **顺序固定**：`tick` 里 `_commitSlice` 的处理（`7370-7377`）在 `growStep`（`7558`）之前；`_commitSlice` 完成时 `tick` 直接 return（`7397`/`7552`）→ **这一帧 `_expandSlice` 不会被推**。
2. **互相作废**：`commit()` 内部两处都把 `_expandSlice = null`（`6344`、`6605`）——提交会作废预览切片；新弹 emergency 也显式作废（`7386`）。
3. **没有互斥断言**：两个字段可以同时非 null（`startCommitSlice` 不检查 `_expandSlice`；`startExpandSlice` 也不检查 `_commitSlice`）。实际路径上靠 tick 的先后顺序避免（见 U12）。
4. **`_expandSlice` 是回退路径**：默认融合世界开着（`vantage_sandbox.js:622`），走的是 `growStep` 的 `fusedBatchReady` 分支（`5978-6038`，每 tick 最多 `growLayersPerTick` 层**同步**整层展开）；`_expandSlice` 只在融合不可用时启用。

### 5.4 生长路径的"闸门"顺序（`growStep` 全文骨架）

### 6.3 "根 = 现在"这条不变量在代码里怎么维持

【代码原文】`tree.rootAbsT` 的全部写点：`1626`（createTree）、`6319`（正常坍缩提升 prev）、`6455`（根层重选兜底再写一次 `_timeAcc`）、`6595`（freshRoot）。**四处都等于当时的 `_timeAcc`**。
【代码原文】`tree.root.simState` 的全部写点：`1615`（createTree，`{x,y,rot}, tGlobal:0`）、`6320-6323`（坍缩提升 prev，`{真实位姿}, tGlobal:0`）、`6590-6593`（freshRoot，`{真实位姿}, tGlobal:0`）。

**结论（代码事实）**：
- "根 = 现在"**不是每帧维持的，而是每个 commit 点维持一次**：只有 `tick` 里走到 `commit` 的分支（`7397`/`7540`/`7552`）才会重写根。段内（两段之间）`root.simState` **不更新**——`buildAgentCtx` 的注释（`3780-3785`）正是为此：智能体的 `tank` 改为优先取 `adapter.getTankState()` 的真实位姿，而不是 `tree.root.simState`（原文："它只在【建树 / 坍缩 / 新根】时被写，**段内不更新** → 最远是 13 帧前（≈3.4 单位）的位姿"）。

## 八、【解释】

> 以下**全部是我的推断**，不是代码原文，也未经运行验证。格式统一为「【解释，未验证】」。
