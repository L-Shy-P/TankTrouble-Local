## 一、⭐ 一句话：4 人局 70% 未决的主因

> **主因 = 「4 人局要 3 次击杀才能分出胜负」× 「评测 `cap=3000` 太紧」**——
> 7 场未决**全部**是"帧数撞 `cap`（`frames=3000`、`truncated=true`、`result=timeout`）"，**没有一场 `dbl_death`**、**没有一场是崩溃/卡死**（`step_err=null`、`server_errors=0`、`nodeid_oob=0`、`lp_finite=2999/2999`、`wall/frame` 与已决局一致）；
> 而这 7 场里 **2 场是纯粹被 `cap` 砍掉的**（同一场景类别在 `cap=3600` 的旧 run 里分别在 **`3333` / `3584` 帧**分出了胜负），**3 场是连 `3600` 帧都分不出的真僵持**，**2 场是同场景类别在旧 run 里 `1943` / `1259` 帧就分出**（⟹ 地图随机带来的差）。
> **最关键的一句**：**把旧 run 也按 `cap=3000` 折算后，4 人局未决率是 `70%`（旧）vs `70%`（新）—— `A 相修复`对 4 人局未决率【零改善】**；真正改善的是 **8 人（`80%`→`60%`）**和 **2 人（`20%`→`10%`）**。
> ⟹ **"4 人 70%"不是 A 修复留下的新问题，也不是"4 人最痛"的新发现，而是一个一直在、且被 `cap` 放大了的结构现象。**

**③ 存活时间？** 🔴 **字段缺失，读不到。** 没有逐坦克 `alive`/坐标/死亡帧。

## 三、⭐ 3 条原因假设 + 怎么验证 / 要改什么

### H1（最可能）**`cap=3000` 对 4 人局太紧 + 4 人局"解决时间"是重尾**
- **证据**：① 7 场未决里 **2 场**在 `cap=3600` 的旧 run 里分别在 `3333`/`3584` 帧分出胜负；② p4 已决局里 **`2/8 = 25%`** 需要 `>3000` 帧（p2 只有 11%）；③ **同口径折算后 A 修复前后都是 70%** ⟹ 与策略无关，与"需要多少次击杀"有关。
- **怎么验证**（只跑评测，不动代码）：`node _tools/eval/run_scenes_30.js --only p4_ --cap 6000 --out D:/vt_run/eval`，看这 7 场里有多少在 `3000~6000` 之间结束。**判据**：若 ≥4/7 在 6000 内结束 ⟹ H1 成立（主因是 cap）；若仍 ≤2/7 ⟹ 主因是 H2。
- **要改什么**：`run_scenes_30.js:258`（`cap` 按人数分档：p2 3000 / p4+p8 6000）；评测报告**不再只报"未决率"**，改报 **"解决时间 中位数 + p75 + >cap 占比"**（现在 `frames` 已经在 jsonl 里，纯报告口径改动）。

### H2 **4 人局"多 bot 僵持"：不是慢，是根本不死（缺"收束机制"）**
- **证据**：① **3/7 连 `3600` 帧都分不出**；② 解决时间**双峰**——已决局 `{623,846,1191,1259,1577,1943}` 与 `{3333,3584}`，**`1600~3000` 之间零样本**（"要么很快结束、要么永不结束"）；③ 毒雾**在场（`100/100`）却不致死**；④ 4 人局 `dbl_death = 0` ⟹ 不是"同时死光"，是"死不够"。
- **怎么验证**（只改评测埋点，不动产品代码）：把 `run_scenes_30.js:205` 已经拿到的 `snap`（`m.snapshot()`，含 `tanks`）与 `roundEnded.playerIds` **落盘**：每 60 帧记一次 `{f, alive:[pid...], nAlive}`，收尾记 `winner/playerIds`。
