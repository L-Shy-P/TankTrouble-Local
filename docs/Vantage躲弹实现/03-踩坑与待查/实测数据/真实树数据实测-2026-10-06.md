## 二、★★ 最重要的发现：**阶段 0（合法操作）不成立**

### 2.1 没有负样本

带对手（Laika）跑了 9000 帧、采 400 条：

| 指标 | p50 | p95 | p99 | max |
|---|---|---|---|---|
| **真死节点占比**（fd ≤ 1） | **0** | **0** | **0.0099** | 0.0129 |
| `invalid` 占比 | 0 | 0 | 0 | **0** |
| `exhausted` 占比 | 0 | 0 | 0 | **0** |

**一半的样本里一个非法节点都没有；99% 的样本里真死节点不到 1%。**

`fullDeathFrame` 的实际取值分布：

```
-1        : 162,011 次     ← 不死
然后直接跳到 10,11,12,13,15,16,19...
```

**没有任何 0 或 1。** 即：节点要么不死，要么死在第 10 帧以后——「0 帧/1 帧必死」这种真正需要拦截的情况几乎不出现。

**结论：网络只要学会「永远说合法」就能拿 100% 准确率。这个任务没有训练价值。**

### 2.2 无对手时更极端

`aiCount: 0` 时：

| 指标 | 值 |
|---|---|
| 真死节点占比 | **0**（全部记录） |
| invalid / exhausted | **0** |

因为没有子弹 → 树里永远不会死。**采集必须带会开枪的对手。**

## 三、树的形状与规模

| 指标 | 值 | 说明 |
|---|---|---|
| **节点总数** | **恒为 496**（中位数=p99=max） | `maxNodes: 500`，**树永远长到上限** |
| 深度 | p50=10, p95=29, p99=31, **max=31** | 不是文档里拍脑袋写的「1~20」 |
| 子节点数 | p50=**0**, p95=**9** | **双峰**：要么叶，要么满 9 叉 |
| 叶节点占比 | **88.9%** | |
| 内部节点 | 16,068，其中**满 9 叉 = 100%** | |
| 段长 | 3 ~ 23 帧，p50=13 | |
| **段长是否兄弟共享** | **是**（深度0 全是 13；深度1 全是 13；深度12 全是 13） | 验证了子代理的判断：`probeSegment` 算一次，9 个兄弟共用 |
| `tEndSec` | 0.28 ~ **85.7 秒** | **这是绝对时刻，不是相对时间**（子代理警告属实） |

### 3.1 由此推翻的旧假设

| 旧假设 | 实际 |
|---|---|
| 「深度 1~20，归一化 /20」 | 实际到 **31**，`Embedding(32)` 刚好卡在边缘 |
| 「节点数 1~512，pad 到 512 浪费 80%」 | **恒为 496**，pad 到 496 **零浪费**（这条虚惊一场） |
| 「tEndSec /10」 | 实际最大 **85.7 秒**，/10 会溢出 8 倍 |
| 「invalid / exhausted 是有效字段」 | **恒为 0，是死字段**，不该占观测维度 |
| 「合成树能代表真实树」 | 合成树是 0~9 加权随机子节点；真实树是**满 9 叉 + 兄弟共享段长** |

## 四、对设计的直接影响

### 4.1 阶段 0 的处理

| 原计划 | 改为 |
|---|---|
| 训练「合法操作」 | **删掉**（没有负样本） |
| `A_grow` 头（哪些节点能长） | **重新定义**——见 4.2 |
| `A_len` 头（段长多长） | **删掉**（无接口通道 + 兄弟共享 + 标签=输入） |
| `B_pick`（选路） | 合法性由**掩码**结构性保证，不需要学 |

### 4.2 「在哪生长」这件事本身要重新想

**树永远在节点上限（496）。** 这意味着：

- 生长请求**几乎总是被资源上限拒绝**（`canAddTreeNodes` 返回 false）
- 被拒绝属于「不罚」（用户定案：资源上限拒绝不罚）
- **所以 `growAt` 在当前配置下几乎没有决策空间**

要么：
- (a) 把 `maxNodes` 调小，让生长成为真实的取舍
- (b) 承认 A 的职责其实是「**在坍缩释放出名额后，优先长哪里**」，而不是每帧都想长

**这是需要用户拍板的设计问题。**

### 4.3 观测字段的修正（必须）

| 字段 | 处置 |
|---|---|
| `invalid` / `exhausted` | **删**（恒 0，死字段） |
| `tEndSec` | 改**相对量**（减去 root 的绝对时刻），或干脆用 `depth × 段长` |
| `fullDeathFrame` | 保留，但注意它**可能是 Rust 候选值而非 JS 确认值** |
| `段长` | 保留（同一深度内确实有 3~23 的变化） |
| `深度` | 归一化改 /31 |

## 六、★★★ 攻克「坦克不动」—— 整轮训练的最大阻塞

### 症状

批量 rollout 里动作序列完全正常（`[5,2,4,1,8,8,1,0,5,6,2,5,1,7,5,5]`），
但 16 步（=256 帧）的累计位移只有 **0.1~1 像素**，奖励恒在 ±0.01。

按 `Constants.TANK.FORWARD_SPEED = 15.95 单位/秒`，256 帧该走 ~68 单位。**差 60 倍。**

### 对照实验（决定性）

同样 4 段 × 16 帧，理论位移 17 单位：

| 泵帧方式 | 位移 | 帧/秒 |
|---|---|---|
| A `for` 循环里连续 `window.__vtStep(1)`（同步紧循环） | **0.42** | ~2500 |
| B 16 次独立 `Runtime.evaluate`，无睡眠 | 0.85 | ~1500 |
| C 16 次独立 evaluate + 每帧真实睡眠 4ms | **3.99** | ~165 |
| D 睡 30ms 后一次性 `__vtStep(16)` | 1.23 | — |
| **E 页面内 `async`，帧间 `await setTimeout(0)`** | **6.28** | **166** |
| F 同上但 `setTimeout(8)` | **12.62** | 81 |

### 根因

**纯同步紧循环把浏览器的事件循环堵死了。**

游戏（或者它依赖的 Phaser / Box2D 链路）需要**页面事件循环真的转起来**——
浏览器要处理 task queue、microtask、内部计时器——物理与输入链才正常推进。
`window.__vtStep` 只驱动了 rAF 回调队列，**驱动不了事件循环本身**。

### 修复

把页面内 rollout 改成 **async**，每帧之间 `await` 一次让出事件循环：

```js
window.__vtEpisodeAsync = async function (net, A, B, steps, seg, temp, yieldFn) {
  ...
  for (var s = 0; s < steps; s++) {
    ...决策...
    for (var zf = 0; zf < seg; zf++) {
      window.__vtStep(1);
      await yieldFn();          // ★ 关键：帧间让出事件循环
    }
    ...
  }
};
```

**副产品**：整个 batch 只需要**一次 CDP 往返**（让出真实时间在页面内完成），
而不是每帧/每段一次。

### 效果

| | 修复前 | 修复后 |
|---|---|---|
| 平均每局位移 | 0.55 像素 | **4.85 像素** |
| 平均每步奖励 | ±0.0005 | **±0.01** |
| 训练奖励曲线 | 恒定 | **+0.0098 → +0.0187（翻倍）** |

### 还没解决的

**吞吐只有 5~10 样本/秒**（8 页并行时预计 40~80）。`await` 本身的调度开销是新的瓶颈，
不是睡眠时长（`setTimeout(0)` 和 `setTimeout(4)` 帧率几乎一样）。
下一步要查为什么 `awaitPromise` 的 evaluate 有这么大开销。但**信号已经正确，可以训了**。

## 七、★★★ 根因实锤：`new Date()`（2026-10-07 子代理攻克）

### 结论（一句话）

**`GameController.update()` 用的是 `var time = new Date()` —— `Date` 构造函数，不是 `Date.now()`。**
而 `clock.js` 只接管了 `Date.now()` / `performance.now()`，**没接管 `Date` 构造函数**。

于是物理 `dt` = **两帧之间的真实墙钟耗时**：

- 一次 evaluate 里紧循环 `__vtStep(1)` → 帧间真实耗时≈0 → **dt≈0 → 坦克不动**
- 每帧 CDP 往返 / 页面内 `setTimeout` 让出真实时间 → dt>0 → 会动，但**速度由真实时间决定，非确定**

**我上一轮那个「让出事件循环」的修法是错的绕路。** 它不是「事件循环被堵死」，只是碰巧提供了真实时间。

### 证据

页面内运行时把 `window.Date` 换成虚拟时间做 A/B（同一长走廊、同样的 tight 单次 evaluate）：

| 条件 | Σ `world.Step(dt)`（60帧） | 左转 30 帧 Δrot |
|---|---|---|
| 不接管 `Date` | **0.2890s**（= 真实渲染耗时） | **-0.7300**（= 5rad/s × 0.146s 真实时间） |
| **接管 `Date` 后** | **1.0000s**（精确） | **-2.5000**（精确 = 5rad/s × 0.5s） |

修复后四时钟严格同步：`new Date` / `Date.now` / `performance.now` / `__vt.t` 推进 60 帧 = 1000ms。

### 修复（`_tools/headless/clock.js`，唯一必需改动）

```js
const RealDate = Date;
function VirtualDate() {
  if (!(this instanceof VirtualDate)) return new RealDate(state.epoch + state.t).toString();
  if (arguments.length === 0) return new RealDate(state.epoch + state.t);
  return Reflect.construct(RealDate, arguments);
}
VirtualDate.prototype = RealDate.prototype;
VirtualDate.now = () => state.epoch + state.t;
VirtualDate.parse = RealDate.parse;
VirtualDate.UTC = RealDate.UTC;
try { window.Date = VirtualDate; } catch (e) {}
```

### 效果

| | 修复前 | 修复后 |
|---|---|---|
| 前进 20 帧 | 1.55 单位 | **5.31**（理论 5.317）|
| 左转 20 帧 | -0.270 rad | **-1.665**（理论 -1.667）|
| 单步奖励量级 | ±0.01 | **±0.34** |
| 每步位移 | ~0.5 像素 | **15~18 像素** |
| 吞吐 | 9.7 步/秒 | **315.6 步/秒**（6 页）|

### 附带修复：`__vtReady` 原本是坏的

旧代码查 `gc.model.getStarted/getMaze`，但 `gc.model` 是 `GameModel`，**没有这两个方法** →
两个 `typeof` 检查全部落空 → **永远返回 true**。回合 60s 结束后传送/输入会被静默丢弃。

改为查 `gc.roundController.model` + `gc.model.getState() === GameModel._STATES.IN_ROUND`，
并在 `__vtBatch` 里加回合就绪等待（跨过 `BETWEEN_ROUNDS(8s) + COUNTING_DOWN(2s)`）。

### 教训

只接管 `Date.now()` **不够** —— 代码里可能用 `new Date()` 取当前时间。
虚拟时钟必须同时接管：`performance.now` / `Date.now` / **`Date` 构造函数**。
