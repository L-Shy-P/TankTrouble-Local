## 一、一句话结论 ×2

### ① 反弹上限：`35` **就是 35 毫秒**（≈2.1 帧）；而"反弹满 5 次消失"**不是"总共弹 5 次"**，
### 它是**"最近 35 ms 内累计 ≥5 次接触就当作卡住、直接销毁"**的去抖保护。
### ⟹ 正常飞行**永远不触发**（实测：普通弹弹了 **21 次**，一直在飞，最后是**寿命到**才消失）。

**【实测】**长走廊里朝侧墙垂直打一发普通弹（弹速 18 m/s）：

* 逐帧读 `Projectile.bounces` 数组本身：**600 帧里 `bounces.length` 最大只有 1**（撞墙前是 0，第 1 次撞墙之后恒为 1，21 次撞墙一次也没堆起来）；
* 21 次撞墙事件全部被记录，**相邻两次间隔恒为 29 帧 ≈ 483 ms**；
* 弹**活满 600 帧（`timeAlive = 10.0s = lifetime`）才消失**，`stopped=false`；
* 最后一条撞墙记录在被删前最老撑到 **-467 ms**（是 35 ms 的 13 倍）—— 说明"过期"根本不是按时间清空的。

⟹ **判据命中第一支**：它反弹远超 5 次才消失 ⟹ "反弹满 5 次消失"在正常对局里等于死代码。
**但"35 不是毫秒"这个推论是错的**：断言语是 `new Date().getTime()`（毫秒），剪枝也确实按 **35 ms** 生效
（见 §二.4 的定量卡尺：每帧 1 次接触时数组稳定停在 3 条 —— 恰是 0/16.7/33.3 ms，**50 ms 那条被删**）。

### ② 激光撞墙**会反弹**，而且是**标准镜面反射**：速度方向反了、**大小不变**，之后**继续飞**，
### 既不消失也不停下；它最后是**寿命到（`LASER_MAX_LIFETIME = 0.8 s`）**才消失的。

**【实测】**朝走廊尽头打一发激光（`WEAPON_TYPES.LASER = 0`，半径 0，速度 180 m/s = **3.0 m/帧**）：

* 第 1 次撞墙那一帧：`v = (-180, 0)` → `(+180, 0)`，`|v|` 仍是 `180`；接触点 `x = 0.4044`（墙面在 0.4）；
* 第 2 次撞墙（另一头）：`v = (+180,0)` → `(-180,0)`；接触点 `x = 69.5956`（墙面在 69.6）；
* `stopped` 全程 `false`，`|v|` 全程**恒为 180**（48 帧里只有一个取值）；
* 第 49 帧消失，最后一帧 `timeAlive = 0.8 s` = `LASER_MAX_LIFETIME`。

⟹ **沙箱档案 `LASER:{bounces:0, wall:'vanish'}` 是错的**，要改成"和普通弹一样的反弹"。

## 二、实验 ①：普通弹在长走廊里反复反弹

### 1. 场地与设置（`probe_bl_v4.log:30-33`）

```
迷宫 7x4，可达 24 格
水平走廊(两侧封死) = {"x0":0,"y0":0,"len":1,"horiz":true}   ← 格 (0,0)：上下都是墙
tank_a 就位 @(5,5) rot=0（rot=0 → 朝 -y），正对侧墙
开火后场上弹数=1；立刻把 tank_a 挪到 (65,35)（不同列，不在弹的弹道上）
```

* 弹种：普通弹 `WEAPON_TYPES.BULLET = -1`，`BULLET.SPEED = 360px/s = 18 m/s`。
* 弹在 y 方向纯一维来回：**实测每帧位移 0.3 m**（f150 `y=1.6` → f153 `y=0.7`，3 帧走 0.9 m = 18 m/s × 1/60 × 3）。
* 两侧墙面：撞墙点 y 恒为 **0.4025** 与 **9.5975** ⟹ 两墙面相距 9.195 m
  （格高 10 m − 墙厚 0.8 m = 9.2 m，与 `MAZE_WALL_WIDTH = 16px = 0.8m`、`MAZE_TILE_SIZE = 10m` 完全吻合）。
* 弹心在两墙间走 8.7 m = 18 m/s × 0.483 s = **29 帧一次往返** ⟹ 与实测间隔 29 帧一致。

**这三列本身就是判据：**

1. **第 1 次撞墙 `nb=1`、后面每次 `nb=2`** ⟹ 撞墙那一瞬间数组里是 `[上一次的旧时间戳, 本次]`，
   而**同一帧稍后**（采样时）又变回 1 ⟹ **剪枝确实每帧都在跑，而且每次都删掉了那条旧的**。
2. 每帧的 `contactEvents`（本帧有几次撞墙）实测分布：**21 帧为 1，其余 579 帧为 0** ⟹ 一帧最多一次接触。
3. 相邻撞击间隔 **29 帧 = 483 ms ≫ 35 ms** ⟹ 这个场景里**根本凑不出"35ms 内 5 次"**。

### 4. 剪枝窗口到底是多大？——用"饱和长度"当卡尺（**这一段是本次实测最硬的一把尺**）

**先把代码原文摆出来**（`418577fd…js` / `Projectile`，逐字照抄，只在换行处断开）：

```js
update: function (deltaTime) {
  this.timeAlive += deltaTime;
  var currentTimeout = new Date().getTime() - this.timeoutWindow;
  for (var i = 0; i < this.bounces.length; ++i) {
    if (this.bounces[i] >= currentTimeout) { this.bounces.splice(0, i); break; }
  }
  if (Math.abs(this.b2dbody.GetLinearVelocity().LengthSquared() - this.initialSpeedSquared) > 0.01) { … 归一化回 initialSpeed … }
  …
},
hitMaze: function () { this.bounces.push(new Date().getTime()); },
hitShield: function () { this.bounces.push(new Date().getTime()); },
done: function () { return this.timeAlive >= this.lifetime || this.stopped || this.bounces.length >= this.timeoutBounceCount; }
```

**【代码原文】它后面挂的是 `new Date().getTime()`（毫秒）** ⟹ `timeoutWindow` 的单位只能是毫秒。
**【代码原文】而且剪枝有"粘性"**：只有在数组里**找到第一条"新"记录**时才 `splice(0,i)`；
如果**全部都是旧的，`if` 一次都不成立 ⟹ 一条都不删**。（这一点和"保留最近 35 ms"的直觉不一样，必须照抄。）

**用实验④A 量这个窗口**（合成场景：把弹直接种在墙面正中，速度给到 ~0，让它每帧都产生 1 次接触）：

| 帧 | timeAlive(s) | 本帧接触数 | 采样到的 `bounces.length` | ages(ms) |
|---|---|---|---|---|
| f825 | 0.016 | 1 | 1 | [-0.67] |
| f826 | 0.033 | 1 | 2 | [-17.33, -0.33] |
| f827 | 0.050 | 1 | **3** | [-34, -17, 0] |
| f828 | 0.066 | 1 | **3** | [-33.67, -16.67, -0.67] |
| …（一直到 f864 都停在 3） | | 1 | 3 | [-34, -17, 0] 循环 |
| 逐帧 push 后/prune 前的 `nb` | | | **最大 4** | （即 0 / 16.7 / 33.3 / 50 四条，最小那条被删） |

* **每帧 1 次接触时，稳态长度 = 3** ⟹ 留下来的三条年龄是 0 / 16.67 / 33.33 ms，
  **被删掉的那条是 50 ms**。
* ⟹ **窗口 W 满足 33.33 ms ≤ W < 50 ms**，与代码常量 **35** 完全吻合；
  **不可能是"2 帧"（=33.3ms 会卡在边界）、也不可能是"35 帧/秒/其他单位"**。
* ⟹ **结论：`PROJECTILE_BOUNCE_TIMEOUT_WINDOW = 35` = 35 毫秒 ≈ 2.1 帧**。

**【实测】规则到底能不能触发？（能做，但只在"卡在几何里"时）**

实验④B：把同一颗弹种在**两面墙的内角交点**上（同时压住两个不同的墙体 fixture）→ **每帧 2 次接触**：

| 帧 | timeAlive | 本帧接触 | push 后 nb | 采样到的 nb | ages(ms) |
|---|---|---|---|---|---|
| f868 | 0.017 | 2 | 1 → 2 | **2** | [-0.33, -0.33] |
| f869 | 0.034 | 2 | 3 → 4 | **4** | [-17, -17, 0, 0] |
| f870 | 0.050 | 2 | 5 → 6 | **6** | [-33.67,-33.67,-16.67,-16.67,-0.67,-0.67] |
| f871 | — | — | — | **弹已消失**（`done()` 触发；事件流报 `projectile timeout`） | |

⟹ **5 次规则确实存在、确实会触发**：条件正是"**35 ms 窗口内累计 ≥5 次撞墙/撞盾接触**"
（2 次/帧 × 3 帧 = 6 次，全部年龄 ≤33.67 ms → 第 3 帧判定 6≥5 → 销毁）。
**它是一道"弹被挤在墙体几何里"的去抖保护，不是"整局反弹次数上限"。**
（该现象在 `probe_bl_v3.log` 与 `probe_bl_v2.log` 两次独立开图中都复现；
v4 那次抽到的角落格恰好没有墙体 fixture 重叠，所以 B 组没触发 —— **触发与否完全取决于种子点是否真的压住墙**。）

### 5. 消失路径的旁证（为什么"销毁原因"字段会和寿命混在一起）

**【代码原文】**`RoundModel.update`（`46989e…js`）顺序：
`_removeDestroyed() → b2dworld.Step(dt,10,10) → _filterAndDispatchCollisionEvents()（撞墙事件在这里 push）→ _removeDestroyed() → tanks.update → projectiles.update(dt)（剪枝在这里）`；
**【代码原文】**`RoundController.update`（`82e43e…js`）随后：
`for (var projectile in projectiles) { if (projectiles[projectile].done()) { this.model.timeoutProjectile(projectiles[projectile].getId()); } }`

⟹ **push → 同帧剪枝 → 同帧 `done()` 判定**，而且**"反弹满 5 次"和"寿命到"走的是同一个销毁出口
（`PROJECTILE_TIMEOUT`）** —— 实测两个用例的事件名都是 `projectile timeout`。

## 三、实验 ②：激光撞墙到底反不反弹

### 1. 场地与设置（`probe_bl_v4.log:83-89`）

```
跑道 = {"rot":-π/2, "dir":"-x", "tank":(25,5), "wallInner":(0.4,5), "dist":22.1}
给武器 {"setType":0(LASER), "activeType":0, "activeFields":"{\"_fired\":false,\"_timeSinceFire\":0}", "defaultType":-1}
tank_a @(25,5) rot=-1.5708（朝 -x）；枪口到墙内表面 22.1 m ≈ 7.4 帧
开火后场上弹数=1；tank_a 立刻挪到 (65,35)（不在弹道上）
```

* **【代码原文】**建弹走的是**基类**，没有任何 LASER 专属类：
  ```js
  case Constants.WEAPON_TYPES.LASER: {
    projectile = Projectile.create(projectileState, Constants.LASER_MAX_LIFETIME,
      Constants.PROJECTILE_BOUNCE_TIMEOUT_WINDOW, Constants.PROJECTILE_BOUNCE_TIMEOUT_COUNT, this, this.relayEvent, this);
    b2dBody = B2DUtils.createProjectileBody(this.b2dworld, projectile, Constants.LASER.RADIUS.m);  // RADIUS.m = 0
  }
  ```
* **【代码原文】**`B2DUtils.createProjectileBody`：`restitution = 1.0`、`friction = 0`、`bullet = true`（CCD）、`RADIUS=0`。
* **【代码原文】**`Constants`：`LASER:{RADIUS:{px:0.0,m:0.0/20.0}, SPEED:{px:3600,m:180.0}, OFFSET:{px:50,m:2.5}}, LASER_MAX_LIFETIME:0.8`。
* **【代码原文】**撞墙的唯一处理是 `case PROJECTILE_MAZE_COLLISION: { data.projectile.hitMaze(); break; }` —— **只 push 时间戳，不改速度、不销毁**。

## 四、对沙箱的施工含义（JS track / JS 融合 / Rust —— 三处都要改）

> 前置：**改任何一项都必须 JS track + JS 融合 + Rust 三处同改**（权威版 §19.1）。

### 4.1 反弹上限（结论①）

1. **【必须删掉任何"总共反弹 N 次就消失"的写法。】** 实测 21 次反弹照飞；
   若照"5 次"实现，长走廊/多次折返的弹会被沙箱**提前判死**，
   而游戏里它还在飞 ⟹ 沙箱与游戏"子弹集合"不一致（树少一颗弹 = 漏威胁）。
2. **正确语义（三处逐字同改）：**
   * 每颗弹维护 `bounces: Timestamp[]`；
   * 撞墙（`PROJECTILE_MAZE_COLLISION`）**和撞盾**（`PROJECTILE_SHIELD_COLLISION`）都要 `push(now)`（原版两个 `hit*` 都 push）；
   * 每次 update 先剪枝、再判死，顺序不能反：
     ```
     currentTimeout = now - 35ms
     for i in 0..len-1:  if bounces[i] >= currentTimeout: { splice(0,i); break; }   // 找不到就一条不删
     done = (timeAlive >= lifetime) || stopped || (bounces.length >= 5)
     ```
     ⚠️ **"找不到就一条不删"是原版行为，不是笔误** —— 实测证据：单条记录能撑到 467 ms（弹）/ 383 ms（激光）才被删。
     如果实现成"按 35 ms 窗口过滤整个数组"，会让数组**提早变短** ⟹ 5 次更难触发 ⟹ 与游戏不一致。
   * **帧粒度等价式**（若沙箱坚持按帧存）：`35 ms ≈ 2.1 帧` ⟹ "**最近 3 帧（含当前帧）内接触数 ≥5**"。
     但**推荐按时间戳（秒/毫秒浮点）存**，不要硬编码"3 帧"——`MAX_DELTA_TIME=0.1`、掉帧校正后帧长会变。
3. **触发后的归类**：原版走 `RoundController.update → model.timeoutProjectile(id)`，事件名是
   **`PROJECTILE_TIMEOUT`**（与寿命到**同一个出口**）。沙箱若要区分死因，必须另开一个内部标记，
   **不要指望从游戏事件里区分**。
4. **优先级：低（建议先写 TODO，不要顶替语义）。** 自然对局里要凑齐"35 ms 内 5 次接触"，
   需要**一帧多次墙体接触**（≥2 次/帧 × 3 帧，或 ≥5 次/帧 × 1 帧）——实测正常飞行的接触密度是
   **0.034 次/帧（弹）/ 0.042 次/帧（激光）**，差两个数量级。真正会触发的是退化情形：
   弹生成在墙体/fixture 重叠里、被两面墙夹住。
   **【我的解释】** 它是一道"防卡死"保护，不是平衡性规则；`MIN/MAX_FIRING_PATH_BOUNCES`（AI 瞄准用的 1~6 次）
   是**另一回事**，别混。
5. **别忘了几类弹的差别（同一份源码）**：
   * `Shotgun.hitMaze` 调 `this._super()` → **push**（所以霰弹也吃这条规则）；
   * `Shrapnel.hitMaze` **完全覆盖、不调 super** → 破片**永不 push**，它撞墙是把速度乘 0 → `done()`（`|v|²<=0.01`）当场销毁；
   * `HomingMissile.update` 里**同样有那段剪枝循环**（它自己重写了一份，没有调用基类 update）⟹ 导弹也要一起改。
6. **一条给"三处同改"的验收线**：拿本次的 `probe_bl_bullet_frames.csv` 当回归基线 ——
   沙箱跑同一个场景（走廊垂直反弹）必须复现：**600 帧活着、21 次接触、`bounces.length` 撞墙后恒为 1、ta=10.0 才死**。

### 4.2 激光（结论②）

1. **【改沙箱档案】** 把 `LASER:{bounces:0, wall:'vanish'}` **改成"不消失、镜面反弹"**：
   撞墙时 `v := v − 2(n·v)n`（restitution=1），**并保持 `|v| = initialSpeed = 180 m/s`**
   （基类那条"偏差>0.01 就归一化"要一起实现，否则反弹几次速度会漂）。
   `bounces` 字段的语义就是 §4.1 那条"卡住保护"，**不是"不反弹"**。
2. **寿命**：`0.8 s`（`LASER_MAX_LIFETIME`），不是"撞墙消失"。1/60 步长下 = 48 帧。
3. **"缺激光扫掠"要补的是判死几何，不是反弹**：半径 0 + 3.0 m/帧 ⟹
   **判死必须用线段扫掠**（`p(t-1) → p(t)` 的线段 ∩ 坦克/墙），不能只在帧末做点判。
   **实测证明游戏本体自己是对的**：撞墙接触点精确落在墙面（0.4004 / 69.5956），
   撞墙帧的坐标 (2.2475 / 67.825) 是 TOI 语义 ⟹
   **Rust/JS 判死对齐的应该是"TOI/扫掠"，而不是"逐帧位置渐近"**。
4. **激光速度 3.0 m/帧（不是 3.6）**：1-1 那条"帧↔秒只走一条函数"若按 0.02 s/帧 算，
   激光会变成 3.6 m/帧 —— 本次实测给出反例，**按 1/60 s**（`18 m/s → 0.3 m/帧` 同样吻合）。
5. **加分项：激光撞墙后 `deadlyToOwner=false→true`**（与普通弹同一条 `PreSolve` 代码）。
   沙箱里"自己的弹刚出膛 0.2 m 就撞墙反弹回来打死自己"是**真实存在**的（见 §附录A 实测的 0 帧自杀）。

  f769  round  tank killed            victim=tank_b  killer=tank_b      ← 自杀

## 附录 B（附带实测）：为什么"回合里坦克会突然消失"

`probe_bl_v2.log` / `probe_bl_v3.log` 里出现过 `gc.getState()=="in round"` 但 `getTanks()=={}` 的现象，
根因**不是** bug，而是：击杀发生后 `roundFinishingDuration` 归零 → 回合结束 → `RoundModel.endRound()` 里
`this.tanks={}`（tank 全清空），而 GameController 的状态机**还没切到 BETWEEN_ROUNDS**。
【实测】`RoundModel.endRound` 确实有一行 `this.tanks={}; this.projectiles={}; …`（代码原文）。
**给后续探针的纪律**：每个实验前先 `requireRound()`（本探针已内建：读 `gc.getState()` + `getTanks()`，
不满足就 `waitForRound()` 重等并把真实状态打进日志）；**别在坦克死后继续 teleport/setControl**
（`setControl` 会响亮抛错，这点 `match.js` 已经做对了）。
