### 2.4 变化来自哪里（两条，分开说）

**① `df=0` 类归零 ← v172 的【消费层】修正，不是 Rust 物理修好了**

- 【代码原文·新】`game_core/js/vantage_sandbox.js:2722`：`dead: r.deathFrame >= 0,   // v172：fd=0 也是死（首帧命中）`
  （rescore 路径同款在 `:2895`：`dead: rn.deathFrame >= 0`）。
- 【代码原文·旧】`_backup/v163_20261002_164627/vantage_sandbox.js:2241` / `:2389`：`dead: r.deathFrame > 0,`
  ⟹ 旧版**只要 `death_frame==0` 就把这条 op 当活**。
- 【代码原文】Rust 的 `death_frame` 合法值含 0：`rollout.rs:1299-1303`（"v153：death_frame 数的是能走几步…第 k 帧撞上 = 能走 k 步"，`death_frame[op] = k as i32`），
  扫掠回溯合并 `rollout.rs:1309-1311`。
- 【代码原文】bridge 是**透传**：`vantage_rust_bridge.js:449` `deathFrame.push(outDeathFrame[i])`（没有 `>0` 过滤）。
- 【实测】定点探针：同一"起点接触"局面，**新的 `rdf` 已经是 `[0×9]`**（旧探针记录里是 `[-1×9]`）——`rdf` 来自 `rust[i].dead ? rust[i].deathFrame : -1`，
  所以旧记录里的 `-1` **只可能**是 `dead=false` 造成的，即**旧消费层的 `>0` 把 `fd=0` 吃掉了**。
- **⟹ 修正旧报告 §五.1 的推断**：旧报告写"Rust 起点接触漏判，根因推测 Box2D `World::step()` 只在 `new_fixtures` 时 `find_new_contacts()`"，
  并建议"给 Rust 补 k=0 起点检查"。【推断】该结论**方向错了**：Rust 一直在判 `fd=0`，缺的是 JS 消费端的 `>=0`；真正落地的也正是消费层修正。
  （**我没做的**：没有回退到 10-11 的 wasm 去逐字节证明"旧 Rust 也返回 0"——**这一条属于【推断】**，证据是"消费层代码对照 + 新旧 `rdf` 现象"。）

**② "两边都判死时帧号 0 个不同 → 27.8% 差 1 帧" ← v171/v172 的激光扫掠**

- 【实测·B】新旧唯一变量就是 v171/v172 的扫掠（`rollout.rs:1113-1117 sweep_hit` ↔ `vantage_sandbox.js` 的 `sweepHit`）。

   我把 `falseRed` 的帧数（239/521/542）标成"**上界**"，**不能**当"假红"证据。

## 六、无法判断的

1. **`v167` 门下"是否真的产生过误判"** —— 本轮 **0 个越界帧**（6 个 v167 门样本、9,900 帧）⟹ **没有可判定的帧**。
