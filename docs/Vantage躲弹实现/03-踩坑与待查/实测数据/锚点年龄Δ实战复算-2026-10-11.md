## 二、Δ 的分布（按弹种）

口径：`Δ = 记录帧 t − anchors[].abs0`，`abs0 = rootAbsT + anchorOffset`（`tree.diag.anchorProbe`，逐帧）。
与上一次代理 §五 表的口径**完全相同**（他用 `tree.diag.anchorProbe.abs0` 与 `records[i].t`）。

### 2.2 按弹种 —— **给不出**（如实说）

- 能算 Δ 的只有上面 **2 份**录像，里面 `anchorProbe` 只出现过 **一种前缀：`b-`（BULLET 族）**。
  ⇒ **激光 `l-` / 追踪导弹 `hm-` / 破片 `mb-` / 双管 `db-` / 霰弹 `sg-` / 加特林 `gg-` 都没有 Δ 样本**。
- 为什么：`anchorProbe` 只收录"树威胁表里有、且实时 projectile 取得到"的弹；
  另外 **7 份 `vantage_record_*.json`（v106/v118）根本没有 `anchors`/`abs0` 字段**（只有 `proj` 明细），
  **13 份 `vantage_tree_diag_*.json`（8 月）也没有 `abs0`**（grep 命中 0）⇒ 都无法复算 Δ。
- 能拿到的"近似量"：这 9 份录像里 `threatIds`/`proj` 出现过的前缀只有 **`b`（7 份）与 `db`（3 份）**——
  **激光/导弹/破片一次都没进过威胁表**（至少在这 9 份录像里）。
  ⚠️ 这不代表它们永远不进树（`isBallisticProjectile` 只做"轨迹白名单"，激光/导弹走折线分支也能成威胁）；
  只是**这 9 份实战录像里没有**。

### 2.3 Δ 与什么相关（【实测】+【我的解释】）

| 候选相关量 | 实测 | 判断 |
|---|---|---|
| **弹的存活时长/年龄** | v136 五颗弹年龄 4.00~5.62s，Δmax **都是 0.367**；v137 年龄 1.15~1.67s，Δmax 0.317~0.417 | **不相关**（Δ 被别的量截断） |
| **`track.length`** | 每颗弹 `Δmax / (len·frameDt)` = **0.04 ~ 0.10**（v136 0.07~0.10，v137 0.04~0.05） | **不相关**：Δ 远没走到轨迹末端 |
| **commit 节奏（= 距上次重锚的时间）** | Δ(t) 逐帧锯齿：段末回落、段内线性涨，**上升斜率 dΔ/dt 恒 = 1.000**（v136 n=1128，v137 n=306，min=max=1.000） | **强相关，唯一决定量** |
| `anchorOffset` 自身 | 记录里没直接给 `anchorOffset`，但 `abs0` 逐帧不变（= 复用）或跳到 `rootAbsT`（= 重模拟） | 判别量，见 §三 |

【我的解释】实战录像里 Δ 的**唯一决定量 = 距上一次重锚（段末 commit）的时间**，所以：
- Δ 的 **median ≈ 半段长**（0.067~0.083s ≈ 4~5 帧）；
- Δ 的 **max ≈ 最长的一段**（0.367 / 0.417s ≈ 18~21 帧 @0.02）；
- 与弹的年龄、寿命、轨迹长度**都不相关**（因为每段末都被重置）。

## 三、★ 锚点长期复用还影响什么（含"重锚条件是否失效"的核实）

### 3.1 【代码原文】复用门长什么样

`vantage_tree.js:1774-1806`（`reanchorThreatsAtCommit`，:6396 在每次段末 commit 调用）：

```js
var shift = Math.max(0, _timeAcc - oldRootAbsT);          // oldRootAbsT = 上一棵树的 rootAbsT（= 上次 commit 时刻）
var needFrames = trackFramesForTree(tree);                 // :1823 = max(horizon 8s + EVAL 1.5s, 最深节点) 换算成帧
if (old && old.track && old.track.length >= needFrames && shift <= 1.0) {
    th.track = old.track;                                  // ← 复用：轨迹一个字都不动
    th.anchorOffset = (old.anchorOffset || 0) - shift;     // ← 只把锚点整体往过去平移 shift
} else {
    th.track = null; th.anchorOffset = 0;                  // ← 重模拟：锚点归到现在
    missing = true; ...
}
```

**两处要指出来的事（【代码原文】+【我的解释】）**：
1. **门槛检查的是"本次 shift"（commit 到 commit 的间隔），不是"累计偏移"。**
   注释（:1785-1788）写的是要防"**shift 累积过大 → 最深未来查询越界**"，
   但 `anchorOffset` 是**逐次累减**的：只要每次 `shift ≤ 1.0`，累计量可以无限大。
   **实现与注释的意图对不上**——这是本轮最硬的一条发现。
2. `shift <= 1.0` 与"1 秒"的语义：**它管的是单段时长**，不是"锚点年龄超过 1 秒就重锚"。

### 3.2 【实测】当前 build：`shift <= 1.0` **一次都没挡过**

运行期探针 `_tools/headless/_probe_reanchor_gate.js`（只读 `dumpDiagnostics()` / `getTree()`，用 `rootAbsT` 变化判定 commit）：

| 跑 | 帧 | commit 次数 | shift median / p90 / **max** | `shift > 1.0` 的次数 |
|---|---|---|---|---|
| 第 1 次（v1 脚本） | 700 | 83 | 0.323 / 0.408 / **0.493** | **0 / 83** |
| 第 2 次（v2 脚本，已修 commit 帧采集滞后） | 700 | 139 | 0.170 / 0.170 / **0.204** | **0 / 139** |

⇒ **在本场景里 `shift ≤ 1.0` 永远成立**（最长的一段只有 0.49s）。
⇒ **真正决定"复用还是重锚"的是另一条：`track.length >= needFrames`。**

第 2 次跑的**逐威胁-commit 决策核对**（v2 脚本把 commit 帧的 anchor 采集滞后一帧修掉后）：

```
决策: reuse=288  resim=1  new=2           （共 291 行）
门限自检:  reuse 且 (len>=need && shift<=1.0) 成立 = 288/288
           resim 且 门不成立                 = 1/1
  reuse 例: len 562→562 @need 561, shift 0.136/0.170/0.204 ...（全部相同：轨迹被原样复用）
  resim 例: len 481→562 @need 561, shift 0.170（唯一一次：len < needFrames）
  shift>1.0 的 commit 数 = 0
```

**289/289 行与代码原文的门完全一致** ⇒ 门没坏；**问题在于这一条对"跑满窗口"的轨迹会永久成立**：

- 轨迹一旦以「窗口截断型」建立（`len ≈ needFrames+1`），它的长度**冻结不变**，而 `needFrames` 长期稳定在 561
  ⇒ `len(562) >= need(561)` **永远成立** ⇒ **锚点被永久复用、Δ 无上界增长**。
- 同一次跑里 Δ 从 0 一路涨到 **20.38s**（700 帧跑满），而那条轨迹只覆盖 `562 × 0.0167 ≈ 9.4s`
  ⇒ **后半程 Δ 早就超出轨迹覆盖范围**（位置查询会 `null` / 钳到末帧，见 3.3）。

### 3.3 【实测】为什么实战录像（v136/v137）反而**不**复用

把两份录像的 `len`（= `th.track.length`）与按当前代码估的 `needFrames` 对起来：

| 录像 | frameDt | 观测 `track.length` | `needFrames` 估计 | 复用了没有 |
|---|---|---|---|---|
| v136 | 0.01685 | **220 → 501**（随时间单调下降，= 弹的剩余寿命） | ≈ 555（`max(ceil((8+75·dt)/dt)+5, …)`） | **每次都重锚** |
| v137 | 0.02000 | **400 → 451** | ≈ 480 | **每次都重锚** |

- 逐帧 `len` 序列与 Δ 锯齿**同步**：每回落一次（重模拟），`len` 就减掉"这一段走过去的时间"（≈13 帧）
  ⇒ 印证 `ensureThreatTracks → simulateBulletTracks(needFrames)` 生成的轨迹**被这颗弹的剩余寿命截断**，
  于是 `len < needFrames` **每一次 commit 都不成立**（v136 的 501 < 555；v137 的 451 < 480）。
- ⚠️【限制】上表的 `needFrames` 是**按当前 build 的公式估的**（v136/v137 的代码早于 v167，`trackFramesForTree` 的常数可能不同）；
  但**结论不依赖准确值**：实测现象（每段末 Δ 回落 + `len` 同步变短）已经证明这两个 build 在**每次段末都走了重模拟分支**。

### 3.4 「重锚是不是从不发生 / `shift ≤ 1.0` 什么情况下不满足」——核实结果

| 问题 | 答案 |
|---|---|
| `shift <= 1.0` 会永远满足吗？ | **不是"永远"**，但它管的是**单段时长 > 1 秒**：长段（>50 帧 @0.02 / >60 帧 @0.0167）、暂停/冻结后恢复、掉帧卡顿。**本场景 222 次 commit 里 0 次**（max 0.49s）。 |
| 那"重锚"会不会从不发生？ | **对"轨迹长度 ≥ 窗口"的弹，是的**——一旦建成就是永久复用（本次实测 Δ→20.4s）。对"轨迹被寿命截断"的弹（短命弹 / 老弹），**每次 commit 都重锚**（实战录像 100%）。 |
| 作战风险 | 头部场景（人操+Laika）里普通子弹满寿命远长于窗口 ⇒ 走"永久复用"那一支。 |

| 段末结构事件 | `collapse-root-siblings` 39 次 / `rebase-time` 39 次 / **`rebase-subtree` 39 次** |
| ⇒ `rebaseSubtreeRigid` 是否提前 return 0 | **39 次全部返回 >0**（都记了 `rebase-subtree` 事件）；即那一批坍缩里 `\|S−prevTg\| > 1e-6` **成立** |
| **断言①** `\|子.rolloutSamples[0] − realTankState\|` | median **0.020m** / p90 **0.271m** / **max 1.255m**；>0.15m 的有 **15/44** 帧 |
| 对照：`\|子.simState.tank − realTankState\|` | median 2.13m / p90 4.25m / max 5.85m（**这条本来就该不一样**，见下） |
| 断言② `\|S−prevTg\|>1e-6 且 rebase 返回 0` 的次数 | **只读测不到**（那要进 product code 打点）——间接结论见上一行 |

**口径与限制（重要）**：
- "归属车"我用 **root 位姿**判（坍缩时 `root.simState.tank = realTankState`），**不是**用子节点距离挑车（后者是循环论证）；
  两台 vantage 车都在场时按 root 位姿就近归属（本次 40 : 4）。
- 我的探针**每帧把 vantage 车瞬移 ~0.036m**（人为扰动）。1.255m 的偏差里，有多少是"commit 到采样之间坦克又走了一帧/一次瞬移"，
  **无法判断** —— 所以**不能据此判定 S2 有缺陷**。
- 结论：**中位数上不变量成立（0.02m），但在 1/3 的坍缩帧上有 0.15~1.26m 偏差** ⇒ 支持"加只读断言盯住它"，不支持"现在就改 rebase 逻辑"。

## 五、无法判断的 + 需要什么实验

1. **按弹种的 Δ 分布：拿不到**（实战录像里激光/导弹/破片/霰弹/加特林**一个 Δ 样本都没有**；其余录像没有 `abs0` 字段）。
   要它只能**专门录一局用这些武器的实战**。
2. **"当前 build 在实战里的 Δ" 无法回答**：`game_core/测试反馈/` 里能算 Δ 的录像最新是 **v137（9/27，40+ 天前的 build）**，
   而今天已到 v167。**必须用当前 build 重录一局实战**（录制器现成：`startReason=auto-death` 自动抓取即为一份 `vantage_record_*.json`）。
3. **`shift > 1.0` 到底什么时候发生**：本场景 222 次 commit 里 0 次。需要专门构造：单段 >1s、长冻结后恢复、卡顿。
4. **`rebaseSubtreeRigid` 提前 return 0 的次数**：只读测不到（需要 product 侧计数，见 §六 的补丁）。
5. **头场景的 Δ 数字本身抖动极大**：同一 build、同一探针族、两次独立跑 median 差了 47 倍（0.17 vs 7.97）
   ⇒ 单一 median/p90 **不要写进定案**；要用"复用分支的占比"和"Δ 是否无上界"这种**定性/结构量**来判。
6. **本次结论只基于 2 份实战录像 + 3 个探针**；没有跑训练、没有重录实战（磁盘与时间限制）。

## 六、建议（按优先级）

1. **P0 修复用门的语义（本次最硬的一条）**：
   `shift <= 1.0` 改成对**累计偏移**的检查，例如
   ```js
   var newOffset = (old.anchorOffset || 0) - shift;      // 复用后锚点相对新根的偏移
   if (old && old.track && old.track.length >= needFrames && Math.abs(newOffset) <= 1.0) { 复用 }
   ```
   （等价于"锚点年龄 Δ ≤ 1.0s"）。理由：① 代码注释**本来就是这个意图**；② 这样 Δ 回到实战录像量级（≤0.42s）；
   ③ 现在这条门对长命弹**永远成立**，等于没有。
   ⚠️ 代价：重模拟频率上升（每 ~1s 一次全弹轨迹），**要主人先拍板再动**；动的话按定案纪律升版 + 全量回归。
2. **马上用当前 build 录一局实战**（人操 + Laika 即可，auto-death 自动成档），然后跑
   `python _tools/headless/_probe_anchor_delta_records.py` 复算 Δ + 复用占比。这是把 ①② 写进定案前的**必要证据**。
3. **§四 的两个观测项按裁决落地**（补丁位置已给），并在下一份实战录像里读这两个计数器：
   - (a) `vantage_sandbox.js` 的 rescore 路径里"威胁表有弹、实时 projectile 取不到"处 `++_e8DefaultLifeCount`，
     `vantage_tree.js` 的 `dumpDiagnostics()` 里透出（再加进 `recFrame` 的 `meta`）；
   - (b) `vantage_tree.js` commit 里 `rebaseSubtreeRigid` 之后加 try/catch 只读断言 + 计数（`tree.diag.s2*`），
     **不改 `prevTg`/平移/缓存逻辑**。
4. **头场景数字的表述**：请用"**复用门第二条件永远成立时 Δ 无上界（实测到 20.4s）**"这种结构描述，
   不要用"head 场景 median 0.2s"——后者是场景抖动的产物。
