## 一、一句话结论

> ### **【实测】游戏判死；沙箱（融合世界死亡权威）在一般情形不判死；两边不一致 ⟹ 沙箱必须补「线段扫掠」。**
>
> - **游戏侧**：只要「本帧真实位移线段」与坦克**真实夹具多边形（车体 3.0×4.0 + 炮塔 0.7×1.4）**相交，
>   游戏就判死。本次 5 类几何构造（整车宽、近满车宽斜切、斜切、切角、切炮塔）**全部实测判死**：
>   `tank deadly collision`（`tankA=tank_b`、`pid`=激光 id、`nb=0`、`ta≈0.067s`）+ `tank killed`
>   （`victim=tank_b`、`killer=tank_a`）；对照控制帧（先把 tank_b 摆到弹道外再泵帧）**一次都没死**。
> - **沙箱侧**：融合世界只用「**逐帧点采样 + 退化半径 0.05 的圆**」判死（`acquireFusedBullet` 见 §四）。
>   一帧跨过坦克时，若两个帧采样点都离坦克几何 **> 0.05m**，`simulateTankBatchJsFused` 就报 `dead=false`。
>   **【实测】miss_oblique / miss_corner / miss_turret 三类：沙箱三条路全 false，游戏全判死。**
>   **【实测】miss_almostfull（弦长 2.22m ≈ 74% 车宽）：融合权威仍 false，旧 `checkDeath`（半径 0.25）反而 true，游戏判死。**
> - **只有「正好垂直、且穿过整车宽车体」这一类两边一致判死**（每帧位移≈车宽，两个采样点落在车体两侧边上、或一侧点落在车里）；
>   而且沙箱这次判死的余量只有 **gap=-0.02m** —— 是 0.05 退化半径护栏的**偶然**结果，不是扫掠。
>   **【实测】解析扫描：在「线段真命中」的摆位里，点采样漏判占 22.3%~25.1%；只统计「两端采样点都在坦克外」的纯扫掠型真命中，漏判占 81.6%~88.8%。**
> - **重点项**：`geoHit` **兜不住**。它就是逐帧的点-多边形距离测试（半径仍是 0.05），`needsSweep:true` 只是**没人读的元数据**。
> - **一条必须先说清的前提偏差**：任务里「1/60 秒步长下激光每帧走 3.0 米」是**平均**；
>   **【实测】无头虚拟时钟下 `RoundModel.update(deltaTime)` 拿到的是 16ms/17ms 交替（Phaser 固定步长累加器），
>   激光逐帧位移 = 2.88m / 3.06m**（周期 3：[17,16,17]ms），平均才是 3.0m。
>   这使「两个采样点正好落在车体两条侧边上」的严格构造**不可实现**；但结论不变。

## 二、实验构造方法（可复现）

### 2.1 环境

```js
m = new Match();
await m.open({ humanIds:['tank_a','tank_b'], aiCount:0, vantCount:0,
               rebaseAtMenu:true, bootFrames:300 });   // open() 内部已 await waitForRound()
```

- 无头虚拟时钟；每个 `__vtStep(1)` = 一帧；`match.waitForRound()` 确认 `gc.getState()==='in round'` 且两辆坦克都在。
- 每个实验前跑 `requireRound()` 守卫；坦克死后 `endRound` 会清空 `tanks`（上一份实测踩过），本探针每类几何**重开一局**。
- 探针只在页面内**运行时**包裹 `RoundModel.update` 以记录每帧 dt（内存里，不落盘改代码），其余全是只读调用。

### 2.2 谁持激光

- 【代码原文】`Constants.WEAPON_TYPES = {BULLET:-1, LASER:0, ...}`；`LASER:{RADIUS:{px:0,m:0}, SPEED:{px:3600,m:180}, OFFSET:{px:50,m:2.5}}`；`LASER_MAX_LIFETIME:0.8`。
- 给 `tank_a`：`LaserWeapon.createInitialWeaponState(IdGenerator.instance.gen('lw'),'tank_a')` → `gc.roundController.setWeaponState(ws)`，
  读 `gc.getActiveWeapon('tank_a').getType()` 确认 **= 0**；再读实际弹丸 `getType()` = 0、`fixture.m_radius` = **0**。**【实测】**
- 在长直道里开火；开火帧后把 `tank_a` 也挪出弹道（激光撞墙后 `deadlyToOwner=true`，会打回自己）。

### 2.3 量「下一帧线段」而不是假设 3.0m

- **【实测】`RoundModel.update(deltaTime)` 的 dt 是 16ms/17ms 交替**（周期 3：[17,16,17]，平均 16.667ms）：
  `probe_dt_quick.log`；激光逐帧位移实测 **2.88m / 3.06m**（`180 m/s × dt`）。
- 探针维护 `window.__vtDtLog`（每帧 dt），**按周期预测下一帧 dt**，再把这一步位移作为 `[p0,p1]`；
  同时把沙箱 `setFrameDtSec()` 设成同一个值（并额外跑 0.016s / 0.017s 两个口径做稳健性对拍）。
- 每类实验先做**对照**：把 `tank_b` 摆到弹道外 → 泵 1~2 帧 → **确认不死**；
  再把它摆到搜索出来的位姿 → 泵 1 帧 → 观察生死。

### 2.4 摆位搜索（怎么判「真实几何上应该命中」）

用**游戏自己的夹具顶点**（`tank_b.getB2DBody().GetFixtureList()` 读 `sh.GetVertices()`，探针不硬编码形状）：

- tank_b 实际夹具：**车体 3.0m×4.0m**（局部 `[-1.5..1.5]×[-2..2]`）+ **默认弹的炮塔 0.7m×1.4m**（局部 `x∈[-0.35,0.35]`，`y∈[-2.7,-1.3]`）。**【实测】**
- 「**应该命中**」的判据 = **线段 `[p0,p1]` 与上述任一夹具多边形相交**（点在内也算）。
  这是按原版 CCD/TOI 的语义定义的；本探针用 5 类构造在真游戏里逐一验证了它确实会判死（见 §三）。
- 摆位参数：`C = segMid + sA·u + d·n`（`u`=激光单位方向，`n`=左法线），
  `rot = atan2(u.y,u.x) − θ`（θ=激光方向与坦克局部 +x 车宽轴的夹角）。
- 筛选条件：① 线段真命中；② 坦克剪影所有采样点离墙 ≥0.35m（保证 `teleport` 不被推、融合世界里不压墙）；
  ③ 弹道前方 3 帧净空（≥9m）。
- 分类指标（全部用真实夹具算）：
  - `chord` = 线段穿过多边形的弦长（取两夹具最大）；
  - `r0/r0.05/r0.25` = 两个采样点到多边形的最近距离 − 半径（负=该半径的圆能看见）。
- 搜索出来的位姿先**只调沙箱**（真实世界不推进）：
  `adapter.simulateTankBatchJsFused(pose, [静止], 3, {startPose:pose, tGlobal:0})`（死亡权威）、
  `adapter.checkDeath(pose,[p0,p1])`（旧路径，弹半径 0.25）、
  `adapter.simulateBulletTracks(3)`+`checkDeath`（track 路径）；
  然后才 `teleport` + `pump(1)` 走游戏。

### 2.5 「退一步」的解析扫描

用同一份**真实夹具多边形**做 360 个方向 × 冲击参数 `d∈[-5,5]`（步长 0.01m，每个方向 1001 个摆位）的**纯几何扫描**：
线段长度取实测的 2.88 / 3.0 / 3.06m 三档；统计「线段真命中但两端采样点都 >0.05m（或 >0.25m）⇒ 点采样看不见」的比例。
**扫描不是游戏实测**，但它用的是游戏真实夹具顶点；上面的 5 类真游戏构造是它的抽样验证。

- 但只要相位再偏一点（两端净空 >0.05m），融合就立刻漏 —— 表#2 就是弦长 2.22m、净空 +0.072m，
  **权威立刻 false**，而更粗的旧 checkDeath（半径 0.25）还看得见。**【实测】**

## 四、重点：`geoHit`（几何回溯补判）能不能兜住激光？

### 4.1 【代码原文】`geoHit` 是什么

`vantage_sandbox.js` 的 `simulateFusedBatch` 在每帧 `Step` 之后跑一个几何扫描；它在 rollout 结束时**回溯补判**：

```js
// v153：几何判死**扫描**（只记不改速）……逐帧记录“第一次几何重叠”发生在第几帧
var gbp = gbs.body.GetPosition(), gbf = gbs.body.GetFixtureList(), gbr = 0;
try { gbr = gbf && gbf.GetShape && (gbf.GetShape().m_radius || 0); } catch (eGbr) {}
var gBoxes = fusedSensorAabbs(fc.candidates[i]);
var gGate = fusedCircleSensorGap(gbp.x, gbp.y, gbr, gBoxes);
if (gGate.gap === null || gGate.gap >= 0.35) continue;
var gExact = fusedCircleSensorPolyGap(gbp.x, gbp.y, gbr, fc.candidates[i]);
if (gExact && typeof gExact.gap === 'number' && gExact.gap < 0) { geoHit[i] = k; ... }
```

```js
// 回溯补判
if (!dead[i] && geoHit[i] >= 0) { dead[i] = true; deathFrame[i] = geoHit[i]; audit.geometryFallback = true; }
```

**关键三点（逐字可核）：**

1. `gbp = gbs.body.GetPosition()` —— **帧采样点**，不是线段。整个循环没有任何 sweep/segment 代码。
2. `gbr` 就是融合子弹体的半径；激光的真实半径是 0，`acquireFusedBullet` 把它回退成 **0.05**，
   所以 `gExact` 是「**半径 0.05 的圆 vs 多边形**」的精确距离，判据是 `gap < 0`。
   【代码原文】`if (!(radius > 0) || !isFinite(radius)) { var _fb = (prof && prof.radiusFallback > 0) ? prof.radiusFallback : 0.05; ... radius = _fb; }`
3. 还有一个纯性能门 `gGate.gap >= 0.35 → continue`（AABB 粗筛）。AABB 是多边形的超集，
   所以这个门只会「还没算就跳过」，不会制造额外漏判；但在 audit 里它会让 `polyGap` 字段偶尔记成 AABB gap（命名有点误导）。

### 4.2 【实测】它兜住了吗

| 类别 | 融合 audit 的 `polyGap` 最小值（全帧） | `contacts` | `geometryFallback` | 真实线段弦长 | 游戏 |
|---|---|---|---|---|---|
| 整车宽 | **−0.02**（负，扫描命中 k=0） | 有 geometry 项 + 有 sensor 接触 | false（接触先判死） | 3.0m | 死 |
| 近满车宽斜切 | **+0.07** | 空 | false | 2.22m | 死 |
| 斜切车体 | **+0.52** | 空 | false | 1.45m | 死 |
| 切车体角 | **+0.71** | 空 | false | 0.88m | 死 |
| 切炮塔区 | **+0.32** | 空 | false | 1.34m | 死 |

> **结论：`geoHit` 只能兜住「某一帧的采样点正好落在坦克几何 0.05m 以内」的激光；兜不住「线段中间穿过、两端采样点都在 0.05m 外」的激光。**
> 表#2~#5 的 `polyGap` 全为正 ⟹ 扫描从未命中；与此同时真实扫掠线段穿过了 0.88~2.22m 的坦克几何。
> **所以 `geoHit` 不是「扫掠补判」，它只是「换了个半径的点采样补判」。**
> 严格说：它不是「完全兜不住」——如果两帧采样点恰好贴在车体边（车宽=位移的那个特例），它会用 −0.02 的 gap 命中；
> 但那是**点采样的运气**，不是扫掠。

### 4.3 ★ 更深一层：为什么融合世界的 CCD（`bullet=true`）也救不了

【代码原文】融合子弹体确实是 `bullet=true`（`B2DUtils.createProjectileBody`），但**候选坦克与弹碰撞用的夹具全是 sensor**：

```js
// createFusedCandidateBody
sfd.isSensor = true;                                  // ← 与 PROJECTILE 接触的传感器夹具
sfd.userData = { type:'fusedSensor', opIndex: opIndex };
sfd.filter.categoryBits = TANK; sfd.filter.maskBits = PROJ;
```

【代码原文】Box2D 的 CCD/TOI 主循环（`f1a5ef…js`，char ~122914）：

```js
for(c=this.m_contactList;c;c=c.m_next)
  if(1!=c.IsSensor() && 0!=c.IsEnabled() && 0!=c.IsContinuous()){ ... ComputeTOI ... }
```

**`1 != c.IsSensor()` ⟹ 传感器接触被 TOI 排除。**
所以即使融合子弹是 `bullet=true`，激光 vs 候选坦克也**不会走 CCD**；它只剩下「Step 后的点接触 + geoHit 点扫描」。
【我的解释】这是「为什么 fusion 的 CCD 看起来没生效」的代码级根因。

**对照真游戏**：
- 【代码原文】`B2DUtils.createProjectileBody`：`projectileBodyDef.bullet = true`（CCD）。
- 【代码原文】真坦克的碰撞夹具是**非 sensor**（`createTankBody` → 车体 fixture `categoryBits=TANK`，`maskBits` 含 `PROJECTILE`；炮塔同理）。
- 【代码原文】`b2Contact` 构造：`(s.GetType()!=dynamic || s.IsBullet() || h.GetType()!=dynamic || h.IsBullet()) && (flags|=e_continuousFlag)`
  ⟹ 子弹 `bullet=true` ⟹ 接触被标 continuous ⟹ 真游戏的 `SolveTOI` 会处理它。
  **这解释了「为什么真游戏能一帧扫中、沙箱不能」**：不是「沙箱没写扫掠」这一句，而是
  **沙箱在死亡通道上把碰撞夹具改成了 sensor，恰好被 Box2D 的 TOI 排除**。

### 4.4 【代码原文】沙箱里其它「处理了激光」的地方（以及 `needsSweep` 的真相）

| 位置 | 内容 | 实际作用 |
|---|---|---|
| 弹种档案 `_projProfile[LASER]` | `{radiusFallback:0.05, bounces:0, wall:'vanish', needsSweep:true}` | **`needsSweep` 全仓只有这一处（定义）+ 一行注释，从未被读取**；`wall` 也从未被读取；只有 `radiusFallback`（融合）和 `bounces`（折线路径）被真正使用 |
| `acquireFusedBullet` | 半径 0 → 回退 0.05，并 `fusedDropLog('...半径退化...→回退半径 0.05')` 打警告 | **这是沙箱对激光唯一的“特殊处理”**，也就是本次漏判的直接来源 |
| `getProjectilePaths` | `effBounces` 取档案的 `bounces:0` → `calculateProjectilePath(..., maxBounces=0, ..., collideWithTanks=false)` | 激光折线 = **一条到第一面墙为止的直线**（且不查坦克）。但上一份实测②已证：真激光撞墙会镜面反弹、`\|v\|` 不变、活到 0.8s ⟹ 第一次反弹后的折线是错的 |
| `isBallisticProjectile` | 【代码原文】`return t===BULLET \|\| t===DOUBLE_BARREL \|\| t===SHOTGUN \|\| t===GATLING_GUN;`（注释：`LASER(0) 半径 0、不反弹，不进 Box2D 轨迹`） | **LASER 被整条 track 路径排除** ⟹ `simulateBulletTracks` 根本不返回激光；表#1~#5 的 `track dead` 全 false 是**“没有这颗弹”**，不是“点采样漏” |
| `checkDeath` | 死亡世界里的子弹体半径硬编码为 `consts.BULLET_RADIUS`（=0.25），与 `bulletPositions` 的真实弹种无关 | 旧路径对激光用的是 **0.25 的“粗点采样”**，比融合的 0.05 更灵敏（表#2 里它反而 true），但同样不扫掠 |
| `vantage_tree.js` | `grep 'needsSweep\|radiusFallback\|LASER'` **没有任何命中** | 树层没有第二套激光处理；激光的死亡结论只能来自沙箱 |

### 4.5 `checkDeath` 的预筛半径：是什么、会不会筛掉这些情况

【代码原文】`buildConstants()`：

```
DEATH_PREFILTER_RADIUS = sqrt( (TANK.WIDTH.m/2)^2 + max( TANK.HEIGHT.m/2,
    |BULLET_TURRET.OFFSET_Y.m − BULLET_TURRET.HEIGHT.m/2|,
    |BULLET_TURRET.OFFSET_Y.m + BULLET_TURRET.HEIGHT.m/2| )^2 )
  + BULLET.RADIUS.m + 0.15
```

代入真值（`WIDTH=3.0, HEIGHT=4.0, TURRET.OFFSET_Y=−2.0, TURRET.HEIGHT=1.4, BULLET.RADIUS=0.25`）：

```
sqrt(1.5² + 2.7²) + 0.25 + 0.15 = 3.0887 + 0.40 = 3.4887 m
```

【实测】探针读到 `prefilterRadius = 3.4887`。
【代码原文】预筛逻辑：**只要有一颗子弹中心落在半径内就继续；一颗都不在才 `return false`**。

**它会不会把「一帧跨车」筛掉？不会。** 两条理由：

1. **【实测】本次 5 类的最近端点离车心 = 1.53~2.33m，全部 < 3.4887m**，预筛都放行；
   沙箱报 false 是后面的点重叠判定，不是预筛。
2. **【我的解释 + 数值验算】不可能筛掉**：坦克所有夹具顶点都在半径 `R=3.0887m` 的圆内；
   一条长度 `L` 的线段若与该圆相交，则至少一个端点距圆心
   `≤ sqrt(R² + (L/2)²)`；把 `L=3.06m` 代入 = `sqrt(9.540+2.341)=3.447m < 3.4887m`。
   ⟹ **任何真命中的一帧，至少一个端点必然落在预筛圆内**，预筛恒放行。
   【实测】解析扫描 164444/164572/164628 个真命中摆位里，**预筛会筛掉的数量 = 0**，与上面一致。

**结论**：漏判不是预筛造成的；预筛是无辜的。真正的分界线是「0.05m 点采样 vs 扫掠」。

## 五、对施工的含义：JS 融合 / JS track / Rust 三处怎么改

> 前置不变：**权威版 §19.1「改任何一项都必须 JS track + JS 融合 + Rust 三处同改」**。
> 但本次实测给出一条更准确的分工：**死亡判定的第一现场是 JS 融合世界**（树的 `deathAuthority` 以它为准），
> Rust 只做候选；track/折线当前**根本不包含激光**或只包含一条到墙为止的直线。
> 所以三处的工作量不是平均的：**JS 融合补扫掠是主工程；track 要么补弹要么明确“不负责激光”；Rust 与 JS 同轮镜像。**

### 5.1 JS 融合（`vantage_sandbox.js`，主工程）

1. **给候选体的 sensor 多边形加一个「线段 × 凸多边形」测试**（不是现在的「点圆 × 多边形」）：
   - 数据源现成：`fusedSensorAabbs` / `fusedCircleSensorPolyGap` 已经在遍历候选体的全部 sensor 夹具（车体+炮塔）；
     只需再加一个 `fusedSegmentSensorPolyHit(segA, segB, body)`（对每个 sensor 多边形做线段相交/包含判定）。
2. **在 `simulateFusedBatch` 的逐帧循环里，对 `needsSweep` 弹记录 Step 前/后的 body 位置**：
   - `k=0` 的线段 = 摆放位置 → 第 1 次 Step 后位置；
   - `k≥1` = 上一次 Step 后位置 → 本次 Step 后位置；
   - 这样**自动使用真实的逐帧位移**（2.88/3.06m，不需要硬编码 3.0m），也自动跟上校准后的 `_frameDtSec`。
3. **命中后按 `geoHit` 同款回溯补判**：记 `sweepHit[i]=k`，rollout 结束后 `if (!dead[i] && sweepHit[i]>=0) { dead=true; deathFrame=k; }`。
   - 【代码原文/纪律】v153 明确「不立刻置 dead，因为立刻停车会让 JS/Rust 轨迹分叉」；补扫掠**不能破坏这条**：
     扫掠只记录命中的 k，不改速度/位置；补判放在 rollout 之后。
   - 【我的解释，需施工时复核】同帧内「先撞墙反射、再撞坦克」的折线不能简单用「Step 前→Step 后」一条直线代替
     （那条直线会穿墙）。两种落法：
       - **(A) 显式折线**：把一帧按墙的 TOI 切成若干子段，只把**实际飞过**的子段拿去测坦克（推荐；与 Box2D 的 TOI 语义一致）；
       - **(B) 让 CCD 自己跑**：把候选坦克的 projectile-mask 夹具从 sensor 改成**非 sensor**，让 Box2D 的 `SolveTOI` 处理。
         ⚠️ 但这会让子弹对候选坦克产生**真实接触响应**（顶停/反弹），可能改变候选轨迹、破坏 v153 的「不提前停车」，
         且要和 Rust 的 box2d 端口逐位对齐；**建议先不要走 (B)**，除非做过轨迹对拍。
4. **`radiusFallback: 0.05` 保留为“护栏 + 响亮日志”，但不能再当 `needsSweep` 弹的判死依据**；
   建议把 `needsSweep` 从「死元数据」变成真正读的开关（或给 slot 加 `sweep=true` 标志）。
5. **顺手修 LASER 档案的另两处（上一份实测已证）**：
   - `bounces:0` 现在被 `getProjectilePaths` 用成「只射到第一面墙」；真激光撞墙**镜面反弹、`|v|` 不变、活到 0.8s** ⟹ 档案要改成与真值一致（反弹、寿命 0.8s）。
   - `wall:'vanish'` 全仓没人读，可留注释但别当成语义。
6. **回归判据**：把本文 §三表的 5 个位姿做成硬对拍——同一个 pose、同一个 `p0/p1`，
   融合世界必须和游戏一样 `dead=true`（尤其表#2~#5）。解析扫描的漏判率应从 22~25% 降到 ~0
   （只允许“正好相切/顶点掠过”的测度零残差）。

### 5.2 JS track（`simulateBulletTracks` / `isBallisticProjectile` / `getProjectilePaths`）

1. **当前事实（比“缺扫掠”更严重）**：`isBallisticProjectile` **直接把 LASER 排除**，
   `simulateBulletTracks` 根本不返回激光 ⟹ track 路径上「这颗弹不存在」。
   表#1~#5 的 `track dead=false / fd=-1` 就是这个原因，而不是“点采样漏”。
   ⟹ 二选一（**必须明确选一个，不许含糊**）：
   - (a) **把 LASER 纳入 track**（真半径 0、`bullet=true` 的 body），并让 track 的逐帧死亡检测也走扫掠；
   - (b) **明确 track 不负责激光**，并保证树**不会**因为 track 里没有激光而得出“安全”的结论
     （即激光的威胁/死亡只能来自带扫掠的融合路径）。
   **【我的解释】**按现有架构 (b) 更省：融合是死亡权威；但**威胁表/评分是否也需要激光**要另一项实测（本文没测）。
2. **`getProjectilePaths` 的激光折线**：`effBounces` 取档案 `bounces:0` + `collideWithTanks=false`
   ⟹ 一条到第一面墙的直线。第一次反弹之后全错；要按上一份实测改成「镜面反弹 + 0.8s 寿命」，
   或明确标注它只保证「首次撞墙前」。
3. **`simulateNode` 的 `checkDeath`**：现在是「折线逐帧取点 + 半径 0.25 的圆」，
   即使把 LASER 纳入 track，**同一帧跨过仍会漏**（只是比融合的 0.05 少漏）。若 track 继续参与激光判死，
   必须改成「相邻两帧位置连成的线段 × 坦克多边形」；否则别让 track 对激光下结论。

### 5.3 Rust（`game_core/rust/vantage_core/`）

1. 【代码原文】`rollout.rs` 的 TODO(v9) 已自己写明：
   ```
   · LASER（真 `LASER.RADIUS.m=0`、180 m/s）：真实判定是逐帧的线段扫掠
     （`Projectile` 基类 + Box2D CCD），不是半径 0.05 的圆。本轮 JS 侧仍用
     档案 `radiusFallback: 0.05` 的退化护栏，Rust 从 bridge 收到同一个 0.05；
     两边口径一致但都不对。要改必须 JS 融合世界与 Rust **同一轮**落线段×多边形。
   ```
   实测证实了这段 TODO：Rust 收到的确实是 0.05 的圆，且 `box2d.rs::solve_toi`
   同样有 `if c.is_sensor() ... continue`（char/行 2939 附近）⟹ Rust 的融合世界也不会用 CCD 扫到激光。
2. **改法**：在 `rollout.rs` 的逐帧 loop 里对 sweep 弹落「上帧位置→本帧位置」的线段×候选多边形的相交；
   与 JS 用**同一判据、同一帧号定义（`death_frame = k` = 能走 k 步）**。
3. `rescore.rs` 的节点增量重评分用的是 threats 的 track/path（JS 传来的），也要同轮镜像；
   否则「点/线段」两套口径会在增量刷新后再分叉。
4. **bridge 必须带显式 `needs_sweep` / `is_laser` 标志**，不能只靠半径：
   游戏里激光半径是 0，JS 融合把它变成了 0.05，Rust 侧无法从数值反推。
5. **验收**：JS 与 Rust 对同一组 §三表位姿给出相同的 `dead/deathFrame`；
   再跑一次 `diff_rollout*` 类的轨迹对拍（当前环境缺 MSVC 跑不了，属于既有待办）。

### 5.4 一句话施工口径

> **JS 融合：把激光从「0.05 点采样」改成「线段扫掠」；
> JS track：要么把激光加进去并同样扫掠，要么明确树不拿 track 对激光下结论；
> Rust：同轮镜像 + bridge 传显式 sweep 标志。三处不许只改一处。**

## 六、无法判断的 / 需要主人或后续实测补的

1. **游戏 CCD 是否覆盖所有「线段相交」**：本文实测了 5 类（整车宽、近满车宽、斜切、切角、切炮塔）全部判死，
   但**没有穷举**「正好相切/只掠过顶点」的测度零情形。§三的解析扫描把「线段 ∩ 多边形」定义为「应该命中」，
   这里可能对**恰好相切**的一小撮摆位过于严格（Box2D 的 TOI 用 slop/容差）。
   【我的解释】这不影响结论方向（漏判率 22~25%，相切集合是测度零）。
2. **斜向开火时曾观测到「激光速度方向与预期相反」的个别局面**（`probe_lsx_v1/v2.log`，方向 dir=(0.707,0.707) 实际 v=(-127,-127)）。

   **根因未查明**（不是本文任务范围）；【我的解释】可能与炮口偏移/炮塔夹具的生成帧有关，但不能坐实。
3. **树实战里的 `_frameDtSec` 到底校准成多少**：本文为了「同一帧对拍」是按每帧实测 dt 手动设的（0.016/0.017/预测值）。
   【代码原文】树有 `calibrateFrameDt`；**它实际写进沙箱的是什么值、是不是一个平均常量**，本文没有测。
   【我的解释】若生产上是一个平均常量，激光的逐帧位移会和真实 16/17ms 交替有 ±0.09m 的相位差；
   **补扫掠后这个问题会自动消失**（扫掠用 Step 前/后的真实位置），但在补之前会让“贴阈值”的漏判更多。
4. **「让传感器夹具变成非 sensor、交给 Box2D CCD」这条路可不可行**：本文只读代码推断「TOI 会处理」，
   **没有做实验**（需要改产品代码）。它对候选轨迹的停车/反弹副作用也没有量化。
   【我的解释】不建议先走；若要走，必须先做 JS/Rust 轨迹对拍。
