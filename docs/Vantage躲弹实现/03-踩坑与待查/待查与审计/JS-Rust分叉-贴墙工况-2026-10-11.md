## 一、现象

坦克**完全贴墙**（零间隙）时，JS 融合世界与 wasm Rust 融合世界对同一段候选轨迹
给出不同位姿：第 1~2 帧的 Box2D 位置求解器把坦克从墙里推开的量不同。
上一轮报告记到的量级是 **~1.5e-3 m**：

- 场景：`tank.x = 墙内表面 0.4 + 半宽 1.5 = 1.9`（车宽 3.0 m，`TANK_WIDTH_M` 见
  `game_core/rust/vantage_core/src/rollout.rs:117`）
- 上一轮记录：`k=1` 时 JS x=1.9029… vs Rust x=1.9038…（差 ~0.9e-3 m）

**这不是本轮引入的**：本轮 ①/② 只改子弹（`rollout.rs` 弹体步进 / JS track / JS 融合），
一行未碰坦克↔墙的物理与求解器。但按项目纪律（"JS↔Rust 不一致"必须留档），单列本档。

## 二、复现方法

```bash
# 仓库根目录
node game_core/rust/_probe_wall_flush_divergence.js
```

探针做的事（与 `diff_rollout_bridge.js` 同一套加载配方，走真 JS 生产链路）：

1. `_diff_proj_semantics_harness.js` 加载真 `Box2D` + 真 `Constants` + `VantageSandbox`；
2. 4x4 迷宫（`H.makeMaze(4,4)`，左墙内表面在世界坐标 x=0.4）；
3. 假坦克摆在 `(1.9, 5)`，`rot=0`（车宽方向与墙零间隙），空场无子弹；
4. 9 个 ops 跑 75 帧：先 `setRustPhysicsEnabled(false)` 跑 JS 融合，再 `initRust` +
   `setRustPhysicsEnabled(true)` 跑 wasm Rust；逐帧比 9 个候选的位姿；
5. 打印 `max|Δpos|` 与它出现的帧、以及第 1~2 帧两边的 x（这一格是给"第 1~2 帧被推开的量"看的）。

## 三、实测数据（2026-10-11，本代理实跑）

`dt=1/60`，75 帧，同一场景两边各跑一次（无子弹、9 个全 0 操作）。

| 场景 | 初始位姿 | max\|Δpos\| | 出现帧 | k=1（JS x / Rust x） | k=2（JS x / Rust x） |
|---|---|---|---|---|---|
| A 左墙贴平（静止） | (1.9, 5) rot=0 | **1.301e-5 m** | k=2 | 1.902934 / 1.902921 | 1.903217 / 1.903204 |
| B 角点贴平（静止，同时贴左墙+下墙 y=2.4） | (1.9, 2.4) rot=0 | **1.597e-4 m** | k=1 | 1.903854 / 1.903739（y 也差 1.1e-4） | 1.904263 / 1.904189 |
| C 左墙贴平，第 2 次调用（warm cache） | (1.9, 5) rot=0 | 1.301e-5 m | k=2 | 同上 | 同上（与第 1 次同值） |
| D 迷宫 4x3 / 3x4 | (1.9, 5) rot=0 | 1.301e-5 m | k=2 | 同上 | 同上 |
| E 对照（**不是**贴墙：rot=-90° 后车嵌进墙 0.5 m） | (1.9, 5) rot=-π/2 | 1.929e-1 m | k=9 | 1.408063 / 1.216249 | 1.404073 / 1.211218 |
| F1 贴左墙前进（沿墙滑行） | (1.9, 5) rot=0 | 2.452e-4 m | k=1 | 1.902934 / 1.903179 | 1.903217 / 1.903384 |
| F2 贴左墙前进+右转 | (1.9, 5) rot=0 | 1.606e-2 m | k=57 | 1.955001 / 1.957029 | 2.014041 / 2.014529 |
| F3 贴左墙前进+左转 | (1.9, 5) rot=0 | 3.063e-2 m | k=19 | 1.961287 / 1.960307 | 2.017479 / 2.016909 |
| F4 原地右转 | (1.9, 5) rot=0 | 1.016e-3 m | k=9 | 1.955001 / 1.955236 | 2.009401 / 2.009542 |

【实测】结论：
- 任务里记的 **~1.5e-3 m 属于 F4「贴墙原地转向」这一档**（实测 1.016e-3 m，同量级）；
  我用的 A 工况（不转向、纯静止贴墙）只有 **1.3e-5 m**。
- 贴墙+转向/长距离蹭墙时，分叉会随接触几何变化**放大**：F2/F3 实测到
  **1.6e-2 ~ 3.1e-2 m**（1.6~3.1 cm）。**这一档不再是"1.5 毫米"**，不要用本档
  的 1.5e-3 数字去覆盖 F2/F3。E（车体嵌墙 0.5 m）是另一个更严重但**不同**的工况
  （不是"完全贴墙"），单独列出仅供对照，本档不为它背书。

## 四、量级评估

- 判定阈值参照：子弹半径 **0.25 m**、车宽 **3.0 m**、危险粗筛余量
  `DANGER_MARGIN = 0.15 m`（`rescore.rs:28`）、CCD/sensor 传感器的尺寸。
- **A/B/C/D/F1/F4**（完全贴墙 ± 原地转向）：**≤ 1.6e-4 ~ 1.0e-3 m**，远小于
  子弹半径与车宽；【推断】不足以翻转“这一帧是否会撞上”的判定，也不影响
  `diff_rollout_bridge` 那类带 0.1 m 间隙的场景。
- **F2/F3**（贴墙持续推进+持续转向 57/19 帧）：1.6~3.1 cm。仍小于 0.15 m 的粗筛
  余量，但已**不再是非阈值量级**；【推断】如果树在这种贴墙蹭行的段末上做亚厘米级
  的候选比较，可能被它污染。**建议按 F2/F3 单列后续项**（见第六节），本代理不擅自修。
- ⚠️ 上表 max 是 **候选坦克第 0 号**的 75 帧最大偏差；它**不会**回灌真实世界
  （融合/克隆世界是只读预测），所以不会造成"越跑越偏"的实机漂移。

## 五、为什么本轮不修

1. **不是本轮改动引入的**：①/② 只碰子弹（`rollout.rs` 的弹体接触枚举/寿命/bounces、
   JS track/融合的同一套），坦克↔墙的求解器一行未动。改它属于另一项施工。
2. **改动面大且危险**：分叉的根在 JS Box2D（`game_core/js/f1a5ef972c273fb89a098cb50b0f22e7.js`）
   与 Rust 移植（`vantage_core/src/box2d.rs`，`solve` `:3170` / `solve_position_constraints`
   `:3574`）的接触 manifold / 迭代顺序 / baumgarte 位置修正差异，不在弹体逻辑。
   贸然"对齐"会把所有坦克预测（不只贴墙）一起改，必须按「同一轮 JS+Rust 同改 + 全量回归」
   的口径做，不适合塞进本次收尾。
3. **任务书明确要求本项"不修，只记档"**（阶段 1-2ab 收尾 ④）。
4. **执行路线有 JS 融合确认兜底**：`rescore` 的候选最终还要过执行路线的 JS 融合确认
   （见 `diff_commit_slice_rust.js` ④⑤ 的机制），单帧候选位姿的毫米级差异不会直接
   变成"树说活着、实机打死"。

## 六、建议什么时候修

满足任一条件时，单列一项处理（推荐先做第 1 条，代价最小）：

1. **先做判别**（不改产品代码）：在真实录制里找"贴墙蹭行/原地转向"的段，量
   `JS 融合 vs wasm Rust` 的段末偏差分布，确认 F2/F3 的 1.6~3.1 cm 是否真的
   翻转过树的 `pickBest`/死亡候选；把结论回写本档。
2. 任何要动 **坦克↔墙接触**的改动（换求解器/改迭代次数/改 OBB/sensor 几何）之前，
   必须把本档当回归基线：JS 与 Rust 同一轮改，并新增一个
   `diff_*`（容差按工况定，F2/F3 现状不是 1e-9）钉住上表。
3. 若未来引入对"段末位姿"更敏感的判死/评分（例如激光扫掠、贴墙绕角），且
   亚厘米级位姿会进阈值 —— 那时必须先把 F2/F3 压下去。
