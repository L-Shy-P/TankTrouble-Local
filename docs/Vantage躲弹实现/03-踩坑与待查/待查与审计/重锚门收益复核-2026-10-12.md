## 二、新旧口径对照表

**口径定义**（必须先立住，否则数字没法比）：

- **【旧口径】**= `tree.diag.anchorProbe` 的**快照行**，Δ = 采样帧的 `t − a.abs0`。
  上一轮的 `344 / 72.5% / 20.994` 就是这个口径；它加了一个 `diagFresh` 过滤
  （`diag.lastCheckAt === tNow`）——**该过滤无法识别空弹窗口的陈旧快照**（见旁路报告 §2.4）。
- **【新口径】**= `dumpDiagnostics().liveAnchors[].delta`（v169 新增导出，`vantage_tree.js:7976-7994`），
  Δ = `_timeAcc − (rootAbsT + anchorOffset)`，**每次调用现算**，读的就是 `tree.threats` 本身。
- 取位 null 判据（与产品 `trackPosAt` `:2024-2035` 同式）：`round(Δ / trackFrameDt) >= trackLen`
  （即 Δ 超出 `trackLen × trackDt` 的覆盖）。
- 深节点盲区判据（沿用上一轮探针）：存在节点 n 使 `(n.tEndSec − t) + Δ > len × trackDt`。

### 3.2 探针（`_tools/headless/_probe_reanchor_recount.js`，只读）

同一跑里同时采两种口径，并按**帧**分类：

- `ticking` = `diag.lastCheckAt === tNow`（本帧 `runDiagnostics` 被调用过）；否则 = **冻结/未 tick 帧**
  （`tick` 在 `:7416/:7418/:7420` 有早退，冻结时 `runDiagnostics`（`:7598`）根本不跑）。
- `probeFresh` = `ticking && diag.anchorProbeAt === tNow`（`anchorProbeAt` 写在 `:7070`）——
  **只有这一种帧的 `anchorProbe` 行才是"本帧现算"的**；`ticking && !probeFresh` 就是
  `runDiagnostics` 在 `:6946` 刷了 `lastCheckAt`、却在 `:6947-6958` 因 `tree.threats` 为空提前返回的
  **空弹窗口**。
- **旧口径** = 全部 `ticking` 帧的 `anchorProbe` 行（= 上一轮 `diagFresh` 的过滤结果）；
  **新口径** = `dumpDiagnostics().liveAnchors`，按帧同分类。
- **交叉校验**：`probeFresh` 帧上，快照行与同 id 活锚点的 `abs0` 逐行比对（B2 只有 2 行不一致、
  maxDiff 0.323——那是同一 tick 里 `runDiagnostics` 在 commit **之前**（`:7598`）跑造成的先后差）；
  并且**新口径算出的 null 次数与产品自己在快照帧上报的 `px===null` 次数完全相等**
  （B2：1249 = 1249；B6：873 = 873），说明"取位 null"不是我另写的判据，就是产品 `trackPosAt` 的行为。
- 场景固定与上一轮一致：无头 Chrome + 虚拟时钟，`humanIds:['tank_a']`（每 40 帧转向 + 持续开火）、
  `aiCount:1`、`vantCount:2`；每跑 `--frames=900`。

### 3.3 局限（**不许当定案用的那些**）

1. **不能逐帧复现上一轮那一跑**：没有 v167 二进制、那跑也没记 `rngSeq`（地图是 RANDOM）。

   **能确定的是机制与量级**：同一门重跑可以更大（B2 1249、B6 873）、也可以更小（B1/B3/B4 = 0）。

## 四、结论：这次修复的真实收益评估

### 4.1 修复本身的定性：**是错的就修，修得对**

- v167 的 `shift <= 1.0` 查的是"**相邻两次 commit 的间隔**"，而注释（`:1785-1787`）写的是
  "**旧轨迹最多只复用到 1.0s 偏移内**（防累积过大→最深未来查询越界得到 null）"——
  **实现与注释不符**，是确定的实现 bug（不是风格问题）。
- 本次实测把"危害"从推断变成证据：改回 v167 门后，**满窗口型活弹的 live Δ 涨到 20.16s（B2）、
  是覆盖 9.37s 的 2.15 倍**；`trackPosAt` 对**活着的**弹返回 null 占到 47.3%（B2）/ 51.9%（B5）/
  32.7%（B6）的样本。这不是读数问题，是产品函数在树上"看不见一颗活弹"。
- 【推断】下游后果（旁路报告 §3.3 的"时空窗整体落到过去⇒跳过死亡重扫⇒假绿"等）我没有在本次复核里
  直接测死判结论；但"树里看不见这颗弹"这一条已由产品自己的 `trackPosAt` 返回值坐实。

### 4.2 收益**没有被高估**的部分

- **满窗口型的取位 null 归零**：修前 1249/2642（B2）→ 修后 0/240（A1）、0/508（C1）、0/370（E1）。
- **满窗口型的深节点越界盲区归零**：修前 89.8%/91.0%/87.6% → 修后 0%。
- **满窗口型 Δ 被压回门限**：max 20.161s → ≤1.241s；中位 8.857s → ~0.05~0.19s。
- 这三条是本轮用 **live 口径**独立复算出来的，与上一轮的"满窗口型 null 0 / Δ≤1.22"**对得上**。

### 4.3 收益**被说大了**的部分（口径纠正）

- 报告 §一/§四 的「取位 null 0」「深节点盲区 72.5% → 0」**只在"满窗口型"子集上成立**；
  **全样本盲区比例修后依然很高**：A1=63.4%、A2=60.8%、A3=66.6%、C1=4.0%、E1=15.7%（随树深/回合变）。
- 主导全样本盲区的是 **`len<needFrames` 的寿命截断型轨迹**：它们的 `cover` 只有 0.03~0.2s，
  永远满足 `Δ + horizon > cover`；**那道门对它们不适用**（它们每次 commit 都重模拟）。
  上一轮报告 §七.2 已把这类单列为"不在本次范围"，但**§四 的总结句把两者混成一个数**，
  读报告的人会以为"树的盲区没了"。
- 影响面也要按场景打折：6 次 v167 门复现里只有 3 次（B2/B5/B6）吃到"活弹看得见→看不见"这个故障；
  另外 3 次（B1/B3/B4）因为回合早死或弹没活过覆盖，null=0。【推断】所以"影响面 = 只要有一颗
  满窗口型弹在树秒下活过 ~9.4s"，是否常见要看真实对局；无头脚本局里约一半。

## 五、`liveAnchors` 的读法（给下一个人）

### 5.1 字段在哪、长什么样

- 入口：`VantageTree.dumpDiagnostics()`（**没有活动树时返回 `null`，先判空**）。
- 位置：`game_core/js/vantage_tree.js:7976-7994`（v169 新增；`hasPath` 也在）。**本跑实测可用**
  （证据 §A/§B/§E，每条 `===` 开头都有一行 `liveAnchors 原样示例`）。
- 原生结构（每条，最多 **16** 条，`:7978` `i < 16`；`MAX_EVAL_BULLETS=64`，`:1537`）：

```js
{ id, anchorOffset, abs0, delta, trackLen, trackDt, hasTrack, hasPath }
// abs0       = rootAbsT + anchorOffset      （:7985）锚点 0 时刻（树全局秒）
// delta      = _timeAcc − (rootAbsT + anchorOffset)  （:7986）**锚点年龄 Δ**，就是本轮要的口径
// trackLen   = th.track ? th.track.length : 0        （:7987）
// trackDt    = th.trackFrameDt（≤0 时回退 FRAME_DT）  （:7988）
// hasTrack   = 1/0                                    （:7989）
```

- 现场示例（B2 第一帧有活弹；字段名为探针转写后）：

```
{"t":0.034,"rootAbsT":0.017,"liveAnchors":[
  {"id":"b-496e-15","abs0":0.017,"delta":0.017,"len":481,"tdt":0.02,"anchorOffset":0,"hasTrack":1}]}
```

### 5.2 三条现成判据（直接用，别再自己发明）

```js
var d = VantageTree.dumpDiagnostics();
if (!d) return;                       // 没有活动树
var tNow = d.tNow;
d.liveAnchors.forEach(function (a) {
  var cover = a.trackLen * a.trackDt;                     // 轨迹覆盖多少秒
  // ① 取位 null（与产品 trackPosAt :2024-2035 同式；Δ 相对轨迹末端越界）
  var null_now = !a.hasTrack || a.trackLen === 0 ||
                 Math.round(a.delta / a.trackDt) >= a.trackLen;
  // ② 深节点越界：对每个节点 n（n.tEndSec 可在 getTree().walk() 里拿）
  //    (n.tEndSec - tNow) + a.delta > cover   ⇒ 该节点的查询越过轨迹末端
  // ③ 这些值是否"本帧现算"：liveAnchors 永远现算；不要再读 d.diag.anchorProbe！
});
```

- 想拿真实弹数配平：`d.liveProjectileCount`（`:7995`，来自沙箱 tick 的 `_liveProjectileCount`）。
- 想查"哪条出口没重锚"：`d.reanchorDiag`（`:7952-7971`，`ensureEarlyReturn` / `ensureByCaller` /
  `paths` / `over1Examples` / `probe`）——这是定位工具，不是 Δ 口径。

### 5.3 **旧 `anchorProbe` 什么时候可以读**（唯一合法条件）

- `d.anchorProbeAge`（`:7972-7973`，= `_timeAcc − diag.anchorProbeAt`）**等于 0** 时，
  `d.diag.anchorProbe` 才是本 tick 现算的；**`> 0` 一律丢弃**。
- ⚠️ **`diagFresh`（`diag.lastCheckAt === tNow`）不能当判据**：`runDiagnostics` 在 `:6946` 先把
  `lastCheckAt` 刷成"现在"，再在 `:6947-6958` 因 `tree.threats` 为空提前返回——
  这就是"空弹窗口里 anchorProbe 每一列（包括 `px`）都是上一份冻结快照"的成因。
- ⚠️ 即便 `anchorProbeAge === 0`，也要注明它是在 **commit 之前**采的（`runDiagnostics` 在 `:7598`，
  commit 的 `reanchorThreatsAtCommit` 在 `:6497`）——同一 tick 里 `abs0` 会有一次 commit 前后差。
- **建议写进以后的报告模板**：任何 Δ 一律写 `liveAnchors[].delta`；旧口径只能作为对照，
  且必须带 `anchorProbeAge` 过滤。**本复核就是按这条做的，两套口径的数字都在 §二/§四。**

### 5.4 读法的注意点

1. **最多 16 条**（`:7978`）。`MAX_EVAL_BULLETS` 是 64（`:1537`），超过 16 颗威胁时这个导出会截断
   ——要全量得另开导出（本轮没做，因为场景只有 ≤7 颗）。
2. 它读的是**模块单例 `_tree` 的最后一次 tick**；`vantCount=2` 时两个 vantage AI 各 tick 一次，
   `_timeAcc` 也各加一次 `dt`（`:7425`）⟹ 无头脚本局的"树秒"≈ 2× 泵帧，绝对秒数不要跨环境比。
3. `delta`/`abs0`/`anchorOffset` 都 `Math.round(...*1000)/1000`（毫秒级）；判 null 时用
   `Math.round(delta/trackDt) >= trackLen`（别用 `delta > cover` 这种近似，会差半帧）。
4. 树冻结（真死定格，`:7420-7428`）时 `liveAnchors` 仍在、但 `_timeAcc` 不再前进：
   Δ 是常量——那是"定格"，不是"不老化"；判断帧是否在走要用 `ticking = lastCheckAt === tNow`。

## 六、无法判断的

1. **上一轮那一跑（344 / 72.5% / 20.994）里究竟混进了多少陈旧行**：没有 v167 二进制、没有 rngSeq，
   无法逐帧重放。我能给的边界是：同门 6 跑里，陈旧行对 null 的贡献可以是 **0**（B2/B6）、
   也可以是 **16.6%**（B5=63/380）；对 Δmax/盲区可以整份都是陈旧（B1：30.583s / 75.9% vs live 0.356s / 0%）。
   **【推断】**上一轮那跑的 4 个威胁的样本数（652/600/172/80）与各自"存活 ×~30 帧/树秒"高度吻合，
   更像 B2/B6 形态（陈旧占比小）；但这只是推断，不是定论。
2. **旧口径下 `px===null` 的真实语义**：空弹窗口里 `px` 是**冻结值**——既不是"现在的取位失败"，
   也不是"现在的取位成功"。B1 就是例子：旧口径 `Δ>覆盖` 617 行、`null` 却 0 行。
   所以"344 次取位 null"这句话在旧口径下严格说应读作"**344 行上报的 px 是 null**"，
   而其中哪些是"现在"的——**只有 live 口径能回答**。
3. **修后全样本盲区（15.7%~66.6%）会不会有害**：主导项是 `len<needFrames` 的寿命截断型轨迹。
   【推断】多半良性（弹在节点时刻早已过期），但**没有测"这些节点最终有没有误判绿/橙"**。
4. **下游后果没有测**：`threatCoarseBox` 时空窗跳过死亡重扫 ⇒ 假绿、`threatCurrentPoint` 钳到末帧
   ⇒ 假红——这些是旁路报告的【推断】+ 上一轮 §3.3 的清单，我只坐实了"产品 `trackPosAt` 返回 null"
   这一层，**没有用死判/评分数据验证假绿假红真的发生**。
5. **其它弹种 / 真人局 / 更多威胁**：全是 BULLET 族、无头脚本局、威胁 ≤7；激光/导弹/破片/霰弹/加特林
   与 >16 颗弹的截断行为一个样本都没有。
6. **门限余量**：满窗口覆盖 9.37s ≈ horizon 8.1s + 1.0s 门 + EVAL（`:802` `EVAL_FRAMES=75`）；
