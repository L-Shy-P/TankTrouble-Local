## §1 Box2D 漏报接触（绿死的物理层根因，未定案）

### ⚠ v160 之后需重测
v160 修好 Rust 可用率后，**卡顿大幅减少**，本文档里「卡顿导致弹位滞后」类的现象
可能自己消失或变形。重测后若仍复现，再按下面流程查。

### 现象（确定，有录像）
v151 录像 `vantage_record_1790864832299.json` 等：

```text
t=7.933  polyGap=-0.26   contacts=[]  deathFrames=[-1]
t=7.967  polyGap=-0.30   contacts=[]  deathFrames=[-1]
t=8.000  polyGap=-0.22   contacts=[]  deathFrames=[-1]
t=8.033  polyGap=-0.18   contacts=[]  deathFrames=[-1]
t=8.067  polyGap=-0.13   contacts=[]  deathFrames=[-1]
t=8.167  polyGap=-0.39   contacts=[{k:2,op:0,pid:...}]  deathFrames=[3]
t=8.183  真实死亡
```

**连续 5 帧子弹圆已经压进坦克多边形 0.13~0.30m，融合世界完全没报接触。**
`polyGap` 是圆→凸多边形的精确距离（v150），负值=真重叠。

三层审计（v151）显示：**pair 在接触链表里、bodyActive=true、但 `IsTouching()=false`**。

### 已排除
- ❌ 威胁表漏弹：凶器全程在 `threatIds`
- ❌ 轨迹大偏移：`bulletErr ≈ 0.13m`
- ❌ 融合世界没摆弹：`placements` 里有，`src=real/track`
- ❌ 我的 AABB 假阳：v150 已改精确多边形距离
- ❌ 我的审计量错夹具：v149 已修（旧版只量最后一个 sensor）
- ❌ **「fat-AABB 门」假说**：原游戏 `RoundModel.PreSolve` 判死用的也是同一个
  `IsTouching()`，若门会漏，原游戏也该漏判。**这个假说已自我推翻。**

### 假说（按可信度排）
1. **传感器夹具 vs 实体夹具**：我们的融合坦克用 `isSensor` 夹具碰子弹；原游戏用
   实体夹具 + 判死后 `SetEnabled(false)`。Box2D 对两者走**不同判定分支**
   （`b2Contact.Update` 的 sensor 分支 vs `Evaluate()` 分支）。
2. 接触在 Step 后未同步（`Collide()` 在 Step 开头跑，`IsTouching()` 反映 Step 前一帧）。
3. 某条粗筛让某个 body/fixtures 未参与（见 §3）。

### 判别方法（决定性，一次性对照实验）
**同一份地图、同一坦克姿态、同一颗弹、同一位置**，跑两遍：

```text
A：融合坦克用 isSensor 夹具 → 记 IsTouching()
B：融合坦克用实体夹具       → 记 IsTouching()
```

- **只有 A 漏** → 假说 1 成立，改夹具口径（并连 §3 粗筛一起复核）
- **A、B 都漏** → 差异在别处，转 §3

配套四层同帧对账（每帧同时记）：
```text
① pair 在不在接触链表
② IsTouching()
③ 换实体夹具口径后是否 touching
④ 精确形状距离（polyGap）
```

### 影响面
**最高等级。** 这是「绿死」的直接来源，也是 v152 违规补网存在的原因。

### 代码位置
- JS 融合：`game_core/js/vantage_sandbox.js` → `simulateFusedBatch` 的接触扫描
- 夹具创建：`createFusedCandidateBody`（实体夹具 mask=Maze；sensor 夹具 mask=Projectile）
- Rust 复刻：`game_core/rust/vantage_core/src/rollout.rs` → `world.contacts()` / `is_touching()`
- 原游戏判死：`game_core/js/46989e393ad0e356ac8a0c6c53b362f9.js` → `RoundModel.PreSolve`

## §2 橙死 / fd 口径（v153 已修，但需复核）

### 现象（确定）
`fullDeathFrame` 原本 = 碰撞帧 + 1，整体偏大 1：

| 实际能走几步 | 旧 fd | 旧画色 | 你的定义 |
|---|---|---|---|
| 0（起手就撞上） | 1 | 红 | 红 ✓ |
| **1（走 1 步就死）** | **2** | **橙 ✗** | **红** |
| 2 | 3 | 橙 | 橙 ✓ |

后果：`isTerminalDead = fd<=1` 永远凑不齐 → 节点真死判不出来 → AI 一直以为有余地。

### 已修（v153）
JS 融合 + Rust `rollout.rs` / `rescore.rs` 统一改成 `deathFrame = 碰撞帧`。

### 待复核
- **回溯补判（v152/v153）的 fd 是否与真接触同一口径**，没验证过。
- `safeFramesForDeath(fd=0)` 的处理：`fd<=1 → 执行 1 帧`，是新加的边界，没实测。

### 判别方法
看死亡瞬间 `deathTree`：**9 个孩子应全红（fd<=1）**。若还有橙，查：
1. 那个橙的 fd 是接触路径给的还是回溯补判给的（`fusedAudit.contacts[].source`）
2. 两条路径对同一碰撞报的 fd 是否一致

## §3 粗筛是否改变了死亡判定语义（主人点出的关键，未验证）

### 背景
主人：「我们为了提升自己的死亡检测性能，做了大量粗筛死亡的优化项，
**语义和原游戏不一样的吧**。」

### 粗筛清单
| 粗筛 | 位置 | 干什么 | 铁律要求 |
|---|---|---|---|
| `MAX_EVAL_BULLETS = 64` | `vantage_tree.js` | 只留最紧迫 64 颗参与 rollout/死亡检测 | 只能决定「先算谁」 |
| `limitThreats` | 同上 | 按入圈时间+最近距离截断威胁表 | 同上 |
| `bulletCannotReach` | `invalidateStaleNodes` | 判「打不到」就跳过死亡重扫 | 同上 |
| `threatCoarseBox` | 同上 | 时空盒粗判 | 同上 |
| `CONTACT_MARGIN = 4.0` | 同上 | 坦克按圆粗滤 | 同上 |
| 近似摆弹 | `simulateFusedBatch` | 轨迹取不到时按真实位姿+速度前推 | 不许静默丢弹（v119） |

### 铁律（`AI架构与可调参数总表.md §7.3` 第 3 条）
> 粗筛（性能优化）不得改变语义：粗筛只能决定「先算谁」，不能决定「算不算」。
> 任何「跳过一个节点复核」的路径，都必须在**执行节点**上留一条兜底。

### 待验证
**没逐条验证过。** 需要回答：每条粗筛被跳过时，执行节点上是否仍有兜底？
特别是 `bulletCannotReach` 和 `threatCoarseBox` 这两条会**跳过整次死亡重扫**。

### 判别方法
对每条粗筛，构造一个「粗筛说打不到、实际能打死」的最小场景，断言死亡仍被检出。
现有的 `diff_tree_coarse_reach.js` 只覆盖了 `bulletCannotReach` 一条。

### 影响面
高。任何粗筛假阴 = 直接漏判死亡 = 绿死。

## §5 树深度停在 1 层（机制确定，主因未定）

### 现象
`seg=1` 时树常驻 `root + 9 孩子 ≈ 19` 节点，深层长不出来。

### 机制（确定）
```js
if (!tree.commitNode || segmentEndDue(tree, worldDt)) { commit(...); return; }
growStep(...)   // ← seg=1 时永远走不到这里
```
`safeFramesForDeath` 把软死节点的 seg 压到 1 → 每 tick 都到段末 → 提交后 `return`
→ `growStep` 不跑。

### 已尝试（已按主人要求注释掉，留文档）
v154 `growAfterCommitIfNeeded`：提交后若新节点软死且无孩子，补一次分叉。
风险：`seg=1` 时每 tick 多一次 `rolloutNine`（9×EVAL_FRAMES），75 帧下 ~1.2ms/tick。
**面板上没有开关。**

### 待定
这是不是「AI 短视 / 主动撞子弹」的主因？没验证。
可能另有原因：`evalFrames=3` 本来就只看 60ms（调到 75 再评价）。

## §8 给以后的自己（三条硬约束）

1. **「对齐原游戏」不是安全牌。** 我们的系统为了预测性能改过大量语义，

### 9.2 地雷破片（MINE=4）—— **单点出发 + 直线 + 不反弹**

```js
// Mine.getProjectileStates
for (var i = 0; i < MINE_NUM_SHRAPNEL; ++i) {          // 30 片
    var speed = 25 + Math.random()*10;                  // 25~35 m/s
    var direction = Math.random() * Math.PI * 2.0;      // **全方向均匀随机**
    ProjectileState.withState(..., WEAPON_TYPES.MINE, this.x, this.y, speedX, speedY);
    //                                                ↑ 地雷中心点，**无半径偏移**
}

// Shrapnel.hitMaze / done
hitMaze: function() { this.b2dbody.GetLinearVelocity().Multiply(0.0); }   // 撞墙速度清零
done:    function() { return this.b2dbody.GetLinearVelocity().LengthSquared() <= 0.01; }

// Shrapnel.update
if (!this.isDeadlyToOwner()) this.makeDeadlyToOwner();   // 注意：**这游戏所有子弹都不认敌我**，
                                                          // 能杀对手的都能杀自己，不是地雷特性（主人 2026-09-10 纠正）
```

**结论（已确认）**
1. 30 片**全部从地雷中心一个点**出发。视觉上的半径只用于碰撞体/贴图，**不参与爆炸出生点**。
2. **方向全随机** —— 树无法预测具体方向，任何方向都可能 ⇒ 威胁 = 「从该点出发的所有直线」。
3. **不反弹**（`hitMaze` 清零速度），撞墙即停、随即消失。
4. 会杀死自己人（`makeDeadlyToOwner`）。

**⇒ 可用的 sound 粗筛**：充要条件是「从爆炸点能有一条不被墙挡住的直线打到 AI 的扫过区域」。
被墙挡住 ⇒ 任何方向都过不去 ⇒ **整个地雷（30 片）直接跳过**。
时空口径：要按 `nodeCoarseBox` 的**扫过区域**判，不能拿坦克静态位置判；时间窗用破片速度 25~35 m/s 反算。

**v161 已做（第一步，最保守的一刀）**：`getProjectilePaths` 里对 MINE 传 `maxBounces = 0`
→ 路径计算从 **6 次全图射线降到 1 次**，30 片共 180 → 30 次。依据是上面的 `hitMaze`；
路径末端正好落在墙上，与真实行为一致。回归 `diff_shrapnel_no_bounce.js`。

### 9.3 霰弹（SHOTGUN=2）—— **单点 + 小扇形 + 会反弹**

- 20 粒、散布 0.3 弧度、同一发射点
- 撞墙后还活 0.7 秒 → **会反弹**，所以 `maxBounces=5` 对它是合理的
- 每发 20 × 6 = **120 次全图射线**，这是「霰弹不论朝哪发射都卡一下」的量
- 待做（主人思路）：
  ① 用**发射点→AI 的最短路径**（现有弹簧绳）做下界粗筛——最短路径 > 可飞距离 ⇒ 20 粒全跳
  ② 反射后按**同一堵墙扫过的连续区间**取两个边缘点反射，保守包住整簇，不逐粒算

### 9.4 其它类型

- `LASER(0)`：半径 0、不反弹，被 `isBallisticProjectile` 排除 → 不进 Box2D 轨迹
- `HOMING_MISSILE(3)`：会制导，`calculatePath` 的直线/反弹模型对它**本来就不适用**（已知且未修的独立问题）
- `BULLET(-1)/DOUBLE_BARREL(1)/GATLING_GUN(5)`：正常反弹弹

### 9.5 性能链条（为什么粗筛救不到路径计算）

```text
computeThreats
  └─ adapter.getProjectilePaths(bounces, maxLen)      ← **每颗弹、无条件**
       └─ B2DUtils.calculateProjectilePath             ← 最多 6 次全图 RayCast
  （粗筛 bulletCannotReach / 时空盒 在这之后，只省融合世界精算，省不到这里）
```

### 9.6 各弹种物理语义总表（原游戏代码为准，2026-09-10 核对）

| 弹种 | type | 撞墙行为 | 反弹 | 结束条件 | 融合世界现状 |
|---|---|---|---|---|---|
| BULLET | -1 | `bounces.push(now)` | ✅ | 寿命 10s / 反弹 5 次 | ✅ 一致 |
| LASER | 0 | 同 base | ✅ | 寿命 0.8s | ⚠️ 被 `isBallisticProjectile` 排除，没 track（已知独立问题） |
| DOUBLE_BARREL | 1 | 同 base | ✅ | 寿命 | ✅ 一致 |
| SHOTGUN | 2 | base + `timeAlive=max(t, 1.3)` | ✅ | 寿命 2.0s，**撞墙后只剩 0.7s** | ⚠️ 我们给满寿命 → 偏保守、浪费性能 |
| HOMING_MISSILE | 3 | 同 base + **激活 2s 后制导转向最近坦克** | ✅ | 寿命 10s | ❌ 我们按直线+反弹算，**模型不对** |
| **MINE(破片)** | 4 | **速度清零** | ❌ | 速度≈0 即消失 | ❌ **我们让它反弹** → 地雷绿死 |

hitMaze: function() { this.bounces.push(new Date().getTime()); },

// Shrapnel 覆写（唯一"方向反了"的一个）

## §10 v163：地雷绿死的**真正根因** —— `lifetime === 0` 被当成 0 秒寿命

### 现象（长期存在，不是新引入）
地雷致死时树全绿：`placements` 里有破片、`contacts=[]`、`dfs=[-1]`，
而且 `polyGap` 最小值出现在 **k=0**（之后再没变近）。

### 根因（代码级，已实证）
```js
// 原游戏 Projectile 构造函数：第 2 参是 lifetime
Projectile.constructor(function(projectileState, lifetime, timeoutWindow, ...) {
    this.lifetime = lifetime;
})

// RoundModel 各弹种的 create 参数（逐个核对）
//   BULLET          → Constants.BULLET_MAX_LIFETIME (10s)
//   LASER           → Constants.LASER_MAX_LIFETIME (0.8s)
//   DOUBLE_BARREL   → 真实常量
//   SHOTGUN         → Constants.SHOTGUN_MAX_LIFETIME (2.0s)
//   HOMING_MISSILE  → Constants.HOMING_MISSILE_MAX_LIFETIME (10s)
//   GATLING_GUN     → Constants.GATLING_GUN_MAX_LIFETIME (2.0s)
//   MINE            → Shrapnel.create(projectileState, 0, ...)   ← **唯一一个 0**
```
破片靠 `Shrapnel.done()`（速度≈0）结束，**完全不靠寿命**。

而我们的融合世界把 0 当寿命用：
```js

...

```
⇒ 每一片破片都只活到 k=0 帧。**这解释了全部数据**：摆位里有、之后没接触、
`polyGap` 最小值在 k=0。

### 修法（v163）
新增哨兵语义：**`lifetime === 0` = 「这颗弹不靠寿命结束」**，取值走 `NO_LIFETIME_SEC`。
只有 `MINE` 是 0（其它弹种都是真实常量），所以这个判据是精确的、不会误伤。
回归 `diff_shrapnel_lifetime_zero.js`（含"逐个核对各弹种 create 参数"的守门断言）。

### 教训
- 我之前调 `polyGap`（1.22→0.59）只是**碰巧让摆位更准**，根因一直在寿命判据上。
- 「按原游戏语义逐弹种核对」这件事必须做全：**一个 `lifetime=0` 的特例就能让整类武器在预测里消失**。

## §13.4 【重要更正】§13.2 的机制被证伪（2026-09-07，主人质疑后复核）

## §15 「只有普通子弹稳定真死，其他弹种经常绿」——系统性错因（2026-09-07，主人提示后查）

### §15.1 共同错因（与 v163 破片 `lifetime=0` **同类**）

### §19.2 Rust 破片语义（依据真代码，逐字对齐 JS v162/v164）

真游戏 bundle `game_core/js/418577fd210ad079ea3d1e5e04050fe0.js` 的 `Shrapnel` 类：

```js
Shrapnel = Projectile.subclass();
Shrapnel.methods({
  update: function(dt){ if(!this.isDeadlyToOwner()) this.makeDeadlyToOwner(); ... }, // 不调 _super()
  hitShield: function(){ this.b2dbody.GetLinearVelocity().Multiply(0.0); },
  hitMaze:   function(){ this.b2dbody.GetLinearVelocity().Multiply(0.0); },
  done:      function(){ return this.b2dbody.GetLinearVelocity().LengthSquared() <= 0.01; }

```

Rust `run_rollout_batch` 弹体步进循环（判据顺序与 JS 完全一致）：

1. `life_left -= frame_dt()`；`<=0` → 停用退场（原逻辑，破片靠 JS 侧 v163 的

2. 速度恰为 `0` → 停用退场（原逻辑）。
3. 破片且已有上一帧方向：`dot = v_hat · prev_v_hat`；`dot < 0.999`（≈ 方向变化 >2.5°）

4. 破片：`len² <= 0.01` → 停用退场（等价 `done`）；且**不做**基类
   `Projectile.update` 的「速度乘回初速」归一化（因为 `Shrapnel.update` 不调 `_super()`）。
5. 非破片：仍按 v8 原逻辑（`|len²-init²|>0.01` 就乘回 `initial_speed`）。
6. 槽位每次摆位重置 `has_prev_dir=false`（对齐 JS 两个摆位分支的 `prevDirX=null`），

**旧实现保留**：Rust 分支里已按要求用注释保留「v8 及以前对所有弹种一视同仁做归一化」的旧代码；
JS 侧 v162 的旧判据（`pr.getType()===MINE`）在 v164 改成档案查询时也保留了历史注释。

**注意**：v162 的「方向变化」是启发式（不读真 `hitMaze`/接触事件）。Rust 只是**对齐**它，不是更好；

     （若墙的命中参数更小，则该帧不能算命中坦克），并处理同帧撞墙后的剩余反射段。
  b. 必须 **JS 融合世界与 Rust 同一轮落同一段判定**，否则「两边同一语义」的铁律被破坏；
     这是一次 ABI + 两个物理核 + 回归的联动改动，不是单侧补丁。
  c. 目前没有激光的真实行为录像用于验收（擦墙、穿坦克、同帧反射各是一类），
     贸然实现有把「假绿」变成「假红」的双向风险。
- 下一步建议：先录一份激光场景的真值录像（记录每帧激光位置/速度/死亡帧/接触），
  定死它与 Box2D CCD 的关系，再按 §19.4-①a/b 两侧同改。**禁止**只改 Rust 或
  只把半径调大凑合。

#### ② HOMING_MISSILE 制导 —— **未做（算法已读全，缺输入，拒绝瞎猜）**

真算法（bundle `418577fd210ad079ea3d1e5e04050fe0.js`，`HomingMissile.update`）：

1. `this.timeAlive += deltaTime`；清理 35s 窗口外的反弹时间戳。
2. `timeAlive > HOMING_MISSILE_ACTIVATION_TIME (2.0)` 后：`makeDeadlyToOwner()`；
   取 `roundModel.getTanks()` 与 `getMaze()`。
3. `startPosition = floor(missile.x / MAZE_TILE_SIZE.m), floor(missile.y / MAZE_TILE_SIZE.m)`；
   `maze.getDistancesFromPosition(startPosition)` 得 BFS 距离表。
4. 对每辆坦克算 `endPosition = floor(tank.x/tile), floor(tank.y/tile)` 的距离，
   取最小；平局时优先 `tank !== this.getPlayerId()`。
5. 若最小距离 `<=1`：目标 = 坦克真实坐标；否则
   `shortestPath = maze.getShortestPathWithGraph(startPosition, targetPosition)`，
   目标 = `(shortestPath[0].x+0.5)*tile, (shortestPath[0].y+0.5)*tile`（迷宫图下一格中心）。
6. `relativeToMissile = B2DUtils.toLocalSpace(this.b2dbody, targetPosition)`；
   以**当前线速度**为起点，按 `relativeToMissile.x` / `.y` 的正负各加/减
   `HOMING_MISSILE.ACCELERATION(40) * deltaTime`，再 `SetLinearVelocity`。
7. 最后与基类相同的归一化：若 `len² - initialSpeed² > 0.01`，把速度乘回 `initialSpeed`
   （即加速只改方向，速度上限是初速）。
8. 更新 `x/y/speedX/speedY` 与 `currentTargetPlayerId`，目标变化时发
   `HOMING_MISSILE_TARGET_CHANGED` 事件。

**卡点（为什么本轮不忠实复刻）**：

a. 目标选择需要**每帧全部坦克的位置**；融合 rollout 世界里只有 AI 自己的 9 个候选车体，
   没有其他坦克（对手在 AI 的 rollout 里没有未来轨迹），算不出「距离最近的坦克」。
b. ABI 没传 `timeAlive` / 激活状态 / 发射者 id / 目标位置 / 迷宫 BFS 图；
   Rust 侧也没有 `getDistancesFromPosition` / `getShortestPathWithGraph` 的移植。
c. JS 融合世界当前也没有制导（档案只标了 `steers:true`，步进循环不消费它），
   单改 Rust 会直接破坏「两边同一语义」。
d. 用「朝 AI 自己直飞」之类的猜测会系统性改变危险方向，属于主人明令禁止的「瞎猜」。

Rust `create_projectile_body` 与步进循环、JS `projectileProfileOf` 附近都留了
`TODO(v9)` 指向本节。

#### ③ `vt_rescore_nodes` 未加弹种数组 —— **已审计，本轮不需要改**

`vt_rescore_nodes` 收的是威胁 track/path，不是弹体数组；track 由 JS 按弹种预先算好

## §20 v10（ABI v10）已实施：未引爆地雷进威胁表 + 融合世界逐候选触发/包络起爆（2026-10-04）

### §20.1 动因（主人报告）

「地雷近距离爆炸有问题，远距离正常红。」——地雷在远处炸开时 AI 能正确预测到
会被破片打死（红）；近处（贴着 AI）炸时预测失效（绿），然后 AI 被打死。

### §20.2 核实到的事实（全部来自真代码，不是猜的）

**类与文件**

- 地雷 = `Mine extends Trap`，真 bundle `game_core/js/7b2ed8ad3598d7321f8f3d2b04b1eac8.js`
  （未压缩对照：`game_files/RELEASE-2026-05-11-01/js/tt/...mine.js...pagespeed...js`）。
- `Mine.fields = {_activated, _tripped, _detonated, _trippingTankIds, _detonationTime}`。
- 地雷只在 `gameController.getTraps()`（`RoundModel.traps`）里，**不在**
  `getProjectiles()`。旧威胁表 `computeThreats → getProjectilePaths → getProjectiles()`
  因此完全看不到未引爆的地雷 —— 这一条是「怀疑 A」。

**① 引爆条件（逐帧逻辑，来自 `Mine.update`）**

1. `timeAlive >= Constants.MINE_ACTIVATION_DELAY (0.5s)` → `_activated = true`。
2. 接触事件（`RoundModel.BeginContact/EndContact` 的 `TANK|TRAP`）→
   `Trip(entered)` → `RoundController.tripTrap` → `Mine.trip(playerId, entered)`：
   进入压入 `_trippingTankIds`，离开弹出。
3. `Mine.update`：`_trippingTankIds` 非空且 `_activated` 且未 tripped → `_tripped = true`。
4. 列表为空且 `_tripped` 且未 detonated → `_detonated = true`，
   `_detonationTime = Constants.MINE_DETONATION_DELAY (0.4s)`，**同一帧 update
   末尾先减一次 dt**（所以剩下 0.38s）。
5. 之后每帧减 dt；`released() = _detonated && _detonationTime <= 0`。

⇒ 地雷**不是碰到就炸**：被坦克碰过、且**那个坦克离开触发圈之后**才开始 0.4s
倒计时；坦克一直压在雷上则永不引爆。主人简报里「被触碰的那一帧生成碎片」与
代码不符，本文以代码为准。

**② 碎片生成（帧、位置、速度）**

- `RoundController.update` 在 `this.model.update(deltaTime)` **之前**遍历 traps，
  `released()` 命中 → `trap.getProjectileStates()` **同一帧立即** `setProjectileState`
  （先于本帧 `b2World.Step`）→ 再 `destroyTrap`。
  ⇒ 从「坦克离开的那一帧」到破片出现 = `ceil(0.4 / dt)` 帧（dt=0.02 → 20 帧）。
- `Mine.getProjectileStates()`：循环 `MINE_NUM_SHRAPNEL = 30` 次；
  - `speed = MINE.MIN_SPEED.m + Math.random()*(MAX_SPEED.m - MIN_SPEED.m)`
    = 25 ~ 35 m/s（`MIN_SPEED.m=500/20`、`MAX_SPEED.m=700/20`）；
  - `direction = Math.random()*Math.PI*2.0`；
  - `ProjectileState.withState(gen('mb'), playerId, WEAPON_TYPES.MINE,
    this.x, this.y, speedX, speedY)` —— **位置 = 地雷中心，无半径偏移**。
- 破片类 = `Shrapnel extends Projectile`，`Shrapnel.create(state, 0, …)` 第 2 参
  lifetime=0（靠速度判结束，不靠寿命）；刚体半径 `MINE_SHRAPNEL_RADIUS = 2/20 = 0.1m`；
  `hitMaze/hitShield` 把速度乘 0；`done() = 速度² <= 0.01`；`update` 不调 `_super()`
  （不归一化）。这些 v9 已在 JS/Rust 落地。

**③ 随机源**：`Math.random()` ×2（速度大小 + 方向），真随机、不可复现。
预测引擎不能用随机 ⇒ 必须用保守包络（见 §20.5）。

**④ 引爆前有没有碰撞体**：有。`B2DUtils.createTrapBody`（`b714588dc4621fe104113111ba90b1a7.js`）
造的是**动态圆刚体**：半径 `MINE.RADIUS.m = 16/20 = 0.8m`，density=0.1、friction=0、
restitution=1.0、fixedRotation=true、category=TRAP、mask=TRAP|TANK|MAZE|ZONE。
`RoundModel.PreSolve` 对 `TANK|TRAP` 调 `b2dcontact.SetEnabled(false)` —— 坦克与雷
**不产生物理阻挡**，但 Begin/EndContact 事件照常触发。地雷本身不会撞死坦克，
杀人只能靠引爆后的破片（**只走破片伤害**）。
另外 `Mine.update` 每帧按 `ACCELERATION=40` 给雷减速；刚放下时初速
`LAUNCH_SPEED=12.5m/s`（向后弹）、撞墙 restitution=1，约 0.3s 内停下。

### §20.3 三份录像的证据（A / B 结论）

三份录像（`vantage_record_1791045029962 / 1791045068913 / 1791045049486.json`）里：

- 所有相关死亡 `projectileType=4 (MINE)`、`projectileId=mb-*`（破片）。
- 死前若干帧 `projCount=0, threats=0, live=0`，chosen `fd=-1 / status=alive`
  （全绿）；随后**一帧之内** `projCount` 从 0 跳到 29~30（破片出现），下一帧或
  几帧后死亡。
- 全部录像 `fusedDrop.noThreat = 0`；detail 只有
  「无track且折线越界/缺失」（对已存在的破片）——说明威胁表没有漏掉任何
  **已经存在**的弹，问题在于弹之前根本不存在。
- 以录像 C 为例：地雷位置可由破片的 `anchors`/`placements` 反推约
  `(41.9, 13.0)`；地雷在 t≈9.267~9.283 释放破片，记录的 AI 当时在
  `(48.0, 24.7)`（约 13m 外），t=9.75 被 `mb-9c93-345` 打死
  （13m / 25~35m/s ≈ 0.37~0.52s，与 0.47s 吻合）。AI 全程没有靠近雷的触发圈
  （最小距离 ≈10.6m）⇒ 这颗雷是**别人（对手）触发**的：AI 能获得的唯一预警
  就是「雷已经 tripped/detonated、还剩多少 0.4s 倒计时」，旧引擎完全没读。

**结论：A 成立，B 也成立。**
- A：未引爆地雷不在 `getProjectiles()`，威胁表/融合世界/评分全看不到 ⇒ 绿。
- B：即使知道它未来会炸，30 片破片在「现在」不存在；`simulateFusedBatch` 只摆
  `getProjectiles()` 里现有的弹 ⇒ rollout 内跨不过起爆时刻 ⇒ 绿。
两者是同一个缺口的两个阶段，必须一起修。

### §20.4 修法（v10，JS 与 Rust 同一语义）

1. **威胁表**（`vantage_scoring.js computeThreats`）：新增 `adapter.getMines()`；
   每颗雷追加一条威胁：`isMine:true, path:null, speed:0`，
   `detonated` 用真实 `_detonationTime`、`tripped` 保守取 `0.4s`，
   折算 `tIn/tEnd`（最早 = 起爆时刻 + 圈边到雷心距离 / 35m/s，视界截断）；
   `armed/arming` 也进表（可见性/签名/渲染），但 `tIn/tEnd=null`（没有确定窗口）。
   `path:null/speed:0` 保证车道压分等折线消费者不会把雷当飞行弹。
2. **融合世界逐候选状态机**（JS `vantage_sandbox.js`；Rust `rollout.rs MineRuntime`）：
   对每颗雷、每个候选 op 维护 `tripped/countdown`，按真 `Mine.update` 的**判据顺序**
   （激活 → 圈内触发 → 离圈开始 0.4s 倒计时并同帧减一次 dt → 倒计时归零释放）

   外接圆 2.5 与炮塔前尖 2.7）。任意候选倒计时先归零就在该帧释放一套**共享**
   32 片包络（帧首判定、先于本帧 Step，与真游戏 `released()` 扫描先于
   `model.update` 同序）。
3. **破片包络**：真实 30 片随机方向/速度（25~35）；预测用
   **32 个等角方向 × 35 m/s（MAX_SPEED）**，半径 0.1m，`isShrapnel` 语义
   （撞墙清零当帧消失、速度²退场、不归一化）与 v9 完全一致。
4. **ABI v10**：`vt_version()` 9→10；`vt_rollout_batch` 与 `vt_score_paths`
   各新增尾参 `mine_flat: *const f64, mine_count: u32`，stride=6：
   `x,y,radius,flags,countdownSec,activationRemainingSec`（flags bit0=activated /
   bit1=tripped / bit2=detonated）。`vt_rescore_nodes` 本轮**未**接雷（见 §20.6）。
5. **Bridge/sandbox 接线**：`VantageRustBridge.rolloutBatch/scorePaths` 透传

6. **树层**（不算选路逻辑改动）：新增地雷 id 签名 + 离散状态签名

### §20.5 保守近似的取舍（**不许声称逐片等价真随机**）

- **方向包络**：真 30 片随机方向；我们用 32 个等角方向（角分辨率 11.25°）。
  这不是严格超集：真方向落在两个采样方向之间、且目标张角小于 11.25° 时，
  真破片可能命中而包络漏。用 32>30 + 全部取 MAX_SPEED(35m/s) 把这一残留
  压到最小；这是**保守近似**，不是精确复刻。
- **速度**：真 25~35 随机；包络全用 35 ⇒ 射程只多不少（保守）。
- **触发圈**：真=圆(0.8) vs 车体+炮塔多边形；我们用车中心圆 2.7 包络 ⇒
  触发只可能更早/更多，不会漏触发（保守）。
- **共享最早起爆**：同一帧里，只要**任意一个候选**的倒计时归零就释放共享包络，
  所有候选都吃这套破片 ⇒ 某候选永远不会碰到的雷，也可能被另一个候选“替它”
  引爆。这是有意的过保守（宁红不绿），代价是静止/绕路候选也可能被判危险。
- **`_tripped` 假设圈内坦克“现在离开”**：真实可能更晚、甚至永不引爆（坦克一直
  压着）。我们按 0.4s 起爆 ⇒ 只会更早红。
- **地雷静止假设**：真实雷放下后的前 ~0.3s 会移动/反弹；但雷要 0.5s 后才激活、
  激活后才可能被碰响，届时早已停住 ⇒ 只有「刚放下 0.5s 内」窗口有位置偏差，
  且那段窗口里雷本来也不致命。
- **节点起点晚于起爆时刻的雷不摆虚拟破片**：本 tick 对未来节点（`tGlobal` 已跨过
  起爆）不摆包络，避免“忽略墙把破片前推到节点起点”的假红；下一 tick 真破片进入
  `getProjectiles()` 后由现有 track 机制接管 ⇒ 最多晚一个决策 tick 才变红。
  根/执行节点（`tGlobal≈now`）不受影响，这正是录像里的致命窗口。
- **JS/Rust 1 帧接触时差**：实测「rollout 中途把停用刚体激活」时，JS 融合世界的
  首次 `IsTouching` 比 Rust 晚 1 帧（普通弹从第 0 帧起激活则逐帧一致）。
  新差分测试因此要求 dead 严格一致、死亡帧差 ≤1，并在测试注释里写明原因。

## §22 【已修】Rust 打分输入漏扣「节点时间偏移」⇒ 子弹永不消失（2026-10-04）

主人在另一处发现并报告：**「子弹寿命没有按节点的时间偏移扣减」** —— 即跨节点时寿命没被正确推进，
本来会自然消失的子弹在沙箱里不消失，进而造成假死等树的错误。**核实成立。**

### §22.1 证据（两套口径不一致）

喂给 **Rust 打分引擎**的那份数据（`vantage_sandbox.js` 建 `bridgeThreats` 处，约 2433 行）**只写**：

```js
bth.lifeLeftSeconds = Math.max(0, prj.lifetime - prj.getTimeAlive());
```

而 **JS 融合世界**（同文件 1524 / 1568 行）是：

```js
slot.lifeLeft = Math.max(0, slot.lifeTotal - slot.lifeAge - qLife);   // qLife = max(0, tGlobal - anchorOffset)
```

⇒ Rust 拿到的是「**以"现在"为基准**的剩余寿命」，但它的 9 操作 rollout 是从**节点自己的时刻**
（`opt.tGlobal`，可能在未来几十帧）往后跑的。
⇒ **凡是在「现在→节点起点」这段里就该到期的子弹，在 Rust 里永不到期** ⇒ 幽灵威胁 ⇒ 假死。
JS 融合世界因为扣了 `qLife`，所以**两边对同一颗弹的寿命判断不一致**。

### §22.2 修法（`vantage_sandbox.js`，1 处）

把 Rust 输入改成与 JS 完全同口径：

```js
var _qLife = Math.max(0, opt.tGlobal - (th.anchorOffset || 0));
bth.lifeLeftSeconds = Math.max(0, prj.lifetime - prj.getTimeAlive() - _qLife);
```

旧实现按要求**注释保留**。`index.html` 缓存戳 `vantage_sandbox.js?v=61→62`。
备份：`_backup/lifetime_fix/vantage_sandbox.js`。

### §22.3 已确认的旁证 / 待办

- `bth.lifeLeftSeconds` 的**默认值是 10 秒**（即「找不到该弹实体时」按几乎永不到期处理）——
  若 `getProjectiles()` 里取不到该弹（例如它刚好在"现在"这一刻消失），Rust 仍会把它当 10 秒的威胁。
  **待查**：这里是否也该按 `qLife` 扣、或者干脆跳过。
- 回归：`node --check` 通过；diff 套件 **45 PASS / 5 FAIL** —— 3 个是老环境问题
  （`diff_box2d/diff_rescore/diff_rollout` 缺 MSVC `link.exe`），另 2 个
  （`diff_rescore_bridge.js` / `diff_score_paths_bridge.js`）是**回滚 §20 时没跟着回滚的测试文件**，待清理。
