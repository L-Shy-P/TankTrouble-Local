## 一 一句话结论

**`geoHit` 不是 sweep 那种“合并规则写错”——它是 v153 有意设计的 JS-only 几何兜底（fallback，`if (!dead[i] && geoHit[i]>=0)`），专门补 Box2D sensor 接触的假阴性（fat-AABB 漏检、`polyGap<0` 却 `touching=false`）。v174 实测：两边都判死时帧号差 = 0（sweep 修复已生效，`diverged=0/posDiff=0/negDiff=0`）；但它确实造成 2/5400 个 op 的“JS-only 判死”（non-laser，geoHit 的 polyGap=-0.08/-0.13），即 JS 比 Rust 多一层几何敏感度——这是能力差，不是帧号 bug。**
**建议：本轮不动。** 把 JS 改成“取更早帧”会让 JS 在大量 `geoHit<contact` 的 op 上比 Rust 更早（与 sweep 修的方向相反，制造新的 JS-earlier 分歧）；给 Rust 补 `geoHit` 是“加能力”，会改变 Rust 快路的选树行为与性能。**这两条都是设计选择 ⟹ 按纪律停下，交主人拍板（§六）。**

## 二 `geoHit` 现状（代码原文 + 行号）

### 1. 扫描/记录（v153；当前 `vantage_sandbox.js:2169-2214`）

```js
// v153：几何判死**扫描**（只记不改速）。Box2D 对 sensor 的精确形状测试
// 被 fat-AABB 门挡住时 e_touchingFlag 保持 false，整场碰撞被漏掉（v151
// 录像实证 polyGap=-0.34 却 touching=false）。这里逐帧记录“第一次几何
// 重叠”发生在第几帧，但**不立刻置 dead**——立刻置 dead 会把候选停车，
// 使 JS/Rust 轨迹分叉（实测 diff_rollout_bridge 会因此报 0.32m 轨迹偏差）。
// 改成 rollout 跑完后回溯补判：接触路径没抓到时才用它，抓到时以接触为准。
for (i = 0; i < operations.length; i++) {
    if (geoHit[i] >= 0) continue;
    ...
    var gExact = fusedCircleSensorPolyGap(gbp.x, gbp.y, gbr, fc.candidates[i]);
    if (gExact && typeof gExact.gap === 'number' && gExact.gap < 0) {
        geoHit[i] = k;
        if (audit && audit.geometryEnabled) {
            audit.contacts.push({ k: k, op: i, pid: gbs.pid, category: 'geometry',
                polyGapAtContact: fusedR2(gExact.gap), source: 'polyGap-scan' });
        }
        gHitHere = true;
    }
}
```

- 只记录**第一次** `gap < 0` 的帧（`if (geoHit[i] >= 0) continue;`），**不改速度/位置**；门限先 `fusedCircleSensorGap >= 0.35` 跳过。
- v12（1-2④）在扫描里加了“制导弹按副本配对”（`gbs.isMissile` / `homing[].opIndex === i`），但**合并规则没变**。

### 2. 回溯合并（当前 `vantage_sandbox.js:2516-2522`）

```js
// v153：回溯补判。接触路径没抓到、但几何上确实重叠的，补上死亡帧。
for (i = 0; i < operations.length; i++) {

```

### 3. v174 里 sweep 修了、`geoHit` 特意不动（当前 `vantage_sandbox.js:2524-2533`）

```js
// v171（1-2③）：激光扫掠回溯补判。与 geoHit 同款：只在 rollout 结束后写 dead，...
// v12（1-2④）顺手修：**合并规则必须与 Rust 对齐（取更早帧）**。
//   ...（1049 条 JS/Rust 分歧）...
//   ⚠️ `geoHit` 那处不动：Rust 没有 geometry fallback，改它会让 JS 在非激光
//   场景比 Rust 更早（本 seed 非激光分歧为 0，另立项）。
for (i = 0; i < operations.length; i++) {
    if (sweepHit[i] >= 0 && (!dead[i] || sweepHit[i] < deathFrame[i])) { ... }
}
```

**所以现在的状态**：`sweepHit` = 取更早帧（与 Rust min 对齐）；`geoHit` = fallback（有意保持）。

## 三 它与 Rust 的关系（Rust 无 `geoHit` ⟹ 后果）

- `grep -n "geoHit" game_core/rust/vantage_core/src/*.rs` **无结果**：Rust rollout 只有“接触扫描 + 激光 sweep 合并”，**没有几何兜底能力**。
- 方向与 sweep **相反**：
  - sweep 的问题是“JS 把更早帧丢掉 ⟹ JS 偏晚”；修法是 JS 取 min。
  - `geoHit` 的问题是“JS 有 Rust 没有的能力”：JS 的几何扫描能发现 Box2D 接触漏掉的真实重叠（`polyGap<0`）⟹ **JS 可能判死而 Rust 判活**（`jsOnlyDead`），或 JS 的最终帧与 Rust 不同。
- 但因为它是 fallback（`!dead`），它**不会**覆盖任何更晚的接触：若 JS 也有接触/其它更晚事件先到，`geoHit` 帧被丢弃（与旧 sweep bug 同构）。所以它当前可能造成两种不对称：
  1. **JS-only 判死**（Rust 永远补不到）——实测本 seed 2 条（§四）；
  2. **JS 更晚的潜在帧差**（geoHit 早 + JS 有更晚接触时，JS 最终帧被更晚接触拖后；Rust 没有 geoHit，若它的接触更早就可能 Rust 早）——本 seed **未出现**（`negDiff=0`、`posDiff=0`）。
- 【推断】第 2 种是结构性风险：只要某个 seed 里出现“geoHit 帧 < 接触帧”的 op，fallback 就会把它丢掉；这是与 sweep 相同形状的 suppression，只是 Rust 侧没有对应候选来暴露它。

## 五 修法方案（只建议，未动手）

### 方案 A（**推荐本轮**）：不动

理由：

1. `geoHit` 是 v153 **有意设计**的 JS-only 几何兜底，目的就是补 Box2D sensor 接触的假阴性（fat-AABB 门挡掉、`polyGap<0` 却 `touching=false`，v151 录像实证 polyGap=-0.34）。关掉/改口径会把这批“假绿”放回去。
2. 当前**两边都判死时帧号差 = 0**；唯一的差异是 2/5400 op 的 JS-only 判死（0.037%），且它们都是真实的几何重叠（polyGap<0），方向是“JS 更敏感/更红”，与“假绿”风险相反。
3. Rust 没有 geoHit，是**能力差**不是**合并 bug**；sweep 那种“两边都有候选、一边丢帧”的问题在 geoHit 上不存在（Rust 根本没有候选）。

### 方案 B：JS-only 改成“取更早帧”

```js
// 现在：if (!dead[i] && geoHit[i] >= 0)
// 改成：if (geoHit[i] >= 0 && (!dead[i] || geoHit[i] < deathFrame[i]))
```

- 后果：JS 的最终帧会从“更晚的接触帧”提前到 `geoHit` 帧；在 `geoHit < contact` 的 op 上，JS **比 Rust 更早**（Rust 没有 geoHit，最快也只能到它的接触帧）⟹ **制造新的 JS-earlier 负帧差**，方向与 sweep 修相反。
- 因为 `geoEventOps=3638`（几何重叠很常见），这个改动会影响大量 op 的死亡帧（不止 2 条），可能显著改变树的选路/确认结果。
- 结论：这不是“与 Rust 对齐”，而是“把 JS 变得更早”；**不建议**在没有主人拍板的情况下做。

### 方案 C：给 Rust 补 `geoHit`（能力补齐）

- 后果：Rust 也能发现这 2 条（以及未来更多）几何重叠 ⟹ `jsOnly` 归 0，两边能力对称；但 Rust 快路是**树选路**用的，判死更多/更早会改变树行为；还要在 Rust 里实现逐帧 circle-polygon gap 扫描（现有 `sweep_hits_tank_pose` 是线段×多边形，circle-polygon 是另一套），有性能与回归成本。
- 这是**加能力**（设计/范围决策），不是修 bug；需要主人定“要不要让 Rust 快路也具备几何兜底”。

### 方案 D：删/关 JS `geoHit`

- 会让 `jsOnly` 归 0，但把 v153 要补的 Box2D 假阴性放回去（可能重新引入“假绿”），与项目“宁可红一点”的取向冲突；不建议。

### 建议

**A（本轮不动）✅；B/C/D 都需要主人拍板。** 特别是 B 与 C 是相反方向：B 是把 JS 改得更早（口径），C 是把 Rust 补到同能力（加能力）——**按纪律不自己拍**。

## 六 待主人拍板的点

1. **要不要保持 JS 的几何兜底能力？**（A）
   - 保持：接受 2/5400 op 的 JS-only 判死（JS 比 Rust 更红），换来 v153 的假阴性保护。
   - 不保持：需要选 B（JS 改成取更早，会更红/更早）还是 C（Rust 补 geoHit，能力对称）还是 D（关掉，回假绿风险）。
2. **树/确认路径允不允许“JS 判死、Rust 判活”？** 这 2 条都发生在 rollout 最后一帧（k=75）；若树的确认逻辑把 JS 融合当权威，它会红；若树只信 Rust 快路，这 2 条不会影响选路——需要主人明确哪条路是权威。
3. **要不要预防 `geoHit` 的 `!dead` suppression（潜在 JS-later 帧差）？** 本 seed 没有出现（diffPos=0），但结构风险在：只要 `geoHit` 帧 < 某个更晚接触帧，JS 就会丢掉更早帧。是否只改“帧合并”而不给 Rust 加能力（会制造 JS-earlier），需要设计判断。
4. **v12（1-2④）制导弹的 geoHit 按副本配对**是否也要纳入统一口径（本报告未分析导弹）。

## 七 无法判断的

1. **这 2 条 JS-only 在真游戏里到底谁对**：几何扫描说 `polyGap<0`（真实重叠），Box2D 接触没抓到；按 v153 的设计 JS 大概率更对，但没有这 2 个具体场景的真游戏 golden 可裁判（现有 golden 只有 5 个激光局）。
2. **无偏真实对局里的 geoHit 频率**：VM600 是“威胁富集采样”（每局 1~3 颗弹、瞄向坦克），2/5400 op（0.037%）、2/600 局（0.33%）只代表这个采样；真实对局频率需 `_probe_jr_death_real.js` 那类无偏采样。
3. **其它 seed 是否会出现 geoHit 的 suppression 型帧差**：本 seed `diffPos=0/diffNeg=0`；要下“永不产生帧差”的结论需要更多 seed 的 `_lfd_` 扫描。
4. **方案 C 的性能/回归代价**：未实现、未测；Rust 逐帧 circle-polygon 扫描可能不便宜，且会改变树选路。
5. **当前 v174 的导弹改动**对 `geoHit`（导弹副本配对）与 kill-frequency 的长期影响：本报告只测了当前快照，v174 之后还在变。
