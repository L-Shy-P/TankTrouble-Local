## 一、观测：token 序列

```
输入 = [
    N × 16   节点 token      （N 可变，树里有几个合法节点就几个）
    1 × 48   全局 token      （整局上下文，不随节点变）
]
```

### 1.1 为什么是 token 序列而不是扁平长向量

| | 扁平 4144 长向量（旧） | token 序列（本规范） |
|---|---|---|
| 第一层参数 | 512 × 4144 = 2.12M | 16 × 256 = 4.1K |
| 节点 0 和节点 5 的同一特征 | **两根完全不同的线** | **同一个编码器** |
| 树 30 个节点 → 300 个 | 💥 形状对不上 | ✅ 照常 |
| 节点之间互相看 | ❌ | ✅ 自注意力 |

### 1.2 节点 token（16 维）

> 数据源：Vantage 树的节点对象（`node.opName` / `node.segmentFrames` / `node.status` /
> `node.subtreeBest` / `node.inputs` / `node.simState` 等）。
> **具体字段在实现时对齐真实节点结构，这里锁定的是「维度数 = 16」和「每个维度的语义类别」。**

| # | 字段 | 说明 | 归一化 |
|---|---|---|---|
| 0 | `opType` | 操作类型 0~8（静止/前/后/左/右/前左/前右/后左/后右） | /8 |
| 1 | `depth` | 到根的层数（第几段） | /20 |
| 2 | `tFrames` | 到根的累计时间（帧） | /75 |
| 3 | `segFrames` | 本段长度（帧） | /30 |
| 4 | `trueDead` | 是否真死（fd≤1） | 0/1 |
| 5 | `fd` | 还能走几步 | /30 |
| 6 | `invalid` | 结构失效 | 0/1 |
| 7 | `exhausted` | 本分支耗尽 | 0/1 |
| 8 | `subtreeBest` | 子树最优分 | 归一 |
| 9 | `rolloutTotal` | 子树 rollout 总分 | 归一 |
| 10 | `tankX` | 该节点处坦克 x | /100 |
| 11 | `tankY` | 该节点处坦克 y | /100 |
| 12 | `tankRot` | 该节点处坦克朝向 | /(2π) |
| 13 | `nearestBulletDist` | 该节点处到最近子弹的距离 | /50 |
| 14 | `threatFrames` | 该节点处威胁窗口剩余帧 | /75 |
| 15 | `spare` | 预留（新增特征时不改维度） | — |

**用户定案**：操作类型、弹种这类**类别量直接用简单数字**，不做 embedding
（「弹种和操作类型就应该用简单的数字，我不认为网络无法区分」）。

### 1.3 全局 token（48 维）

| # | 字段 | 说明 |
|---|---|---|
| 0~1 | 我方坦克 x, y | /100 |
| 2 | 我方朝向 | /(2π) |
| 3 | 我方存活 | 0/1 |
| 4~5 | 敌方坦克 x, y | /100（无对手时置 0） |
| 6 | 敌方朝向 | /(2π) |
| 7 | 敌方存活 | 0/1 |
| 8 | 场上子弹数 | /8 |
| 9~16 | 最近 8 发子弹的距离 | /50，不足补 1 |
| 17~24 | 最近 8 发子弹的方位角 | /(2π)，不足补 0 |
| 25 | 树节点总数 | /512 |
| 26 | 树当前深度 | /20 |
| 27 | 剩余评估窗口 | /75 |
| 28 | 帧号（段内） | /30 |
| 29 | 地图宽 | /10 |
| 30 | 地图高 | /10 |
| 31 | 地图主题 | 0~4 |
| 32 | 总坦克数 | /8 |
| 33 | 我方分数 | 归一 |
| 34 | 敌方分数 | 归一 |
| 35 | 回合已进行时间（秒） | /120 |
| 36 | 当前武器弹夹剩余 | /8 |
| 37 | 武器冷却剩余 | 归一 |
| 38 | 有无道具可捡 | 0/1 |
| 39~46 | **A/B 双份记忆**（各 4 维，网络自己写） | — |
| 47 | 预留 | — |

> 第 32 维「总坦克数」正是用户要求的**预留多样输入类型**（不同环境的坦克数）之一。
> 地图配置、物理常量同理预留，**但用户明确说了「那是以后做的事，先验证普通环境能跑」**。

### 1.4 一个必须守住的点

> 用户定案：「选每层节点的时候，**肯定得看到整棵树**，不然纯盲人摸象。」

**因此节点 token 不能只装自己的信息。** 自注意力保证每个节点能看到其他所有节点的原始特征，
这是本架构相对旧方案的**唯一**根本优势，实现时不能退化成"每节点 + 一份全局摘要"。

## 二、动作：**每帧重新生成整条路线**

### 2.1 生成过程

```
每帧：
    起点 = 当前 root
    路线 = []
    while 当前节点有子节点:
        在当前节点的子节点里选一个      ← 网络输出（softmax over 子节点）
        路线.push(选中的子节点)
        当前节点 = 选中的子节点
    走到叶子 → 自然终止               ← 【不需要结束符】
    输出：整条路线
```

**用户定案**：
> 「我们的架构甚至不需要它输出结束符，因为**选到叶子就是结束符**。」

### 2.2 两层时间尺度

```
【帧内】token by token —— 沿父子边一个一个吐，直到叶子
【帧间】整句重新生成 —— 下一帧从新 root 重吐一遍，即使一模一样也重吐
```

### 2.3 为什么这不会产生深度偏差

**每一步的候选永远只是「上一个节点的子节点」→ 永远同层兄弟比较。** 结构上触发不了深度偏差。

用户此前否掉的（**本架构不做**）：
> 「不能让智能体给节点评分，然后我们用算法直接找分最高的**路径**，因为那会**导致更深的路线分数更高**。」

### 2.4 接口契约

```
智能体 → 树：一条路线（就这一个东西，没有分数的明面输出）
```

程序侧只做两件事：
1. **两条硬检查**（执行层强制，智能体无权覆盖）
   - 真死节点（fd≤1）不能作为生长父节点
   - 有非真死候选时，绝不选真死路线
2. **记录实际发生了什么**，直接作为事实传给下一帧（不是智能体的输出）

## 六、推理成本实测（2026-10-06 补）★ 这个数决定架构可不可行

### 6.1 为什么必须测

树的性能熔断阈值是 **60 ms**（`growMs > 60 → _growSkip`），
真实游戏 60fps 一帧预算 **16.7 ms**。
智能体跑在 `tick` 里，超了就是掉帧 / 熔断。

子代理曾报「N=496 时纯 JS 前向 **2746 ms**」——**这个数被我实测推翻了，差 20 倍。**

### 6.2 实测（Node 24，`_tools/nn_bench.js`）

```
                    子代理报的     实测（朴素 i-k-j）
N=496 d=256 L=3     2746 ms   →   123.6 ms
```

### 6.3 矩阵乘优化（关键）

| 实现 | 时间 | GFLOPS |
|---|---|---|
| A 原版 k-j 累加 | 2.97 ms | 1.37 |
| B 转置权重 + 8 路展开 | 1.70 ms | 2.39 |
| C 转置 + 4 行共享 | 1.61 ms | 2.53 |
| **D Float64 + 4 行共享** | **1.31 ms** | **3.11** |

**优化要点**：
1. **权重转置**（`wT[j*D+k]`）→ 内层循环变连续
2. **一次算 4 行**（`i += 4`）→ 4 行共享同一行权重，内存流量减 4 倍
3. **Float64 累加反而比 Float32 快**——省掉 fround 转换开销
4. **总提速 2.27 倍**

### 6.4 配置扫描（含参数量）

| d | L | 时间 | 参数量 | /Hybrid | 判定 |
|---|---|---|---|---|---|
| 64 | 3 | 9.0 ms | 187,105 | 0.82× | ✅ |
| 64 | 5 | 15.4 ms | 287,073 | 1.26× | ✅ |
| **128** | **3** | **15.7 ms** | **673,441** | **2.95×** | ✅ |
| 256 | 3 | 123.6 ms（优化后 ~54 ms） | 2,562,849 | 11.2× | ⚠️ 需降频 |

### 6.5 ★ 关键洞察：**不需要每帧跑**

**段长是 13 帧**（实测分布 3~23 帧，p50=13）。段内操作不变，
所以网络**不需要每帧前向**，每 2~4 帧跑一次即可：

```
d=256 L=3 (2.56M, 11.2×Hybrid)：
  优化后 54 ms/次  ×  每 4 帧一次  =  13.5 ms/帧均值  ✅ 进预算
```

**结论：最初定的 `d=256, L=3 → 2,562,849 参数` 不改。** 靠两条撑着：
1. 矩阵乘优化 2.27×
2. 按段降频（每 2~4 帧一次）

**不需要 WASM**，用户定的「第一版不引入 WASM/Rust」守住了。
