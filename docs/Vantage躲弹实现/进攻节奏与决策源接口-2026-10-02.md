## 一、进攻节奏：Δ = T_到达 − T_最小规避

### 1.1 主人口径

> 「这游戏不仅仅是算覆盖，而是**进攻节奏**的问题。对手可自由支配的时间越少，
> 他的节奏越差。当对手没有任何可自由支配的时间时，就意味着每一帧他都必须
> 按照唯一的路径来躲弹，此时想要拿下对手就是囊中取物了。
> 所以算攻击必须跟时间挂钩，算对手的操作与子弹速度的时间关系。
> ……完全一样的轨迹，射击点里对手坦克越近，对手肯定可支配时间越少，
> 他得立即躲。射击点再离得更近，根本就躲不掉了。
> 所以子弹位置、坦克姿态等有密不可分的关系。」
>
> 「树是**精确**的，而节奏是一种**感知**，或者在更高维度确实精确。」

### 1.2 形式化

**不要数"对手有几个存活操作"——那是对 Δ 的离散采样，是感知层，而且贵 9 倍。**
精确的量是连续的时间余量：

```
Δ(b, t) = T_到达(b, t) − T_最小规避(位姿)

  T_到达(b,t)  = 子弹 b 从第 t 帧的位置飞到"能够命中对手"那一点所需帧数
                 ← 纯弹道，树已经逐帧精确模拟
  T_最小规避   = 坦克从当前姿态脱离子弹危险圈所需的最少帧数
                 ← 由朝向/速度/转向率决定（不是位置！）

Δ ≫ 0  →  自由，他可以干别的
Δ ≈ 0  →  **强制帧**：必须立刻躲
Δ < 0  →  躲不掉了
```

**为什么它是精确的而不是感知的**：Δ 的两个分量都是几何-运动学上的确定量，
不是启发式。**"节奏差"= Δ 被压到 0 的帧占比高**，这是可以逐帧算出来的。

**主人那句"射击点离对手坦克越近，可支配时间越少"就是 Δ 的物理含义**：
同一条轨迹，子弹靠近他的那一段决定 `T_到达`；他的姿态决定 `T_最小规避`。
**两个量相减，所以谁也单独决定不了 —— 这就是"密不可分"。**

### 1.3 为什么不能塞进树

| | 树（防守） | 对手预判 |
|---|---|---|
| 对象 | 子弹 | 对手 |
| 性质 | **确定的**（出膛后时间线固定） | 不确定 |
| 可分离性 | 每颗弹独立，节点可单独查 | 影响 rollout 的**每一帧** |
| 失效范围 | **局部**（时空盒相交） | **全局** |

树的全部便宜，来自"子弹确定 + 局部失效"（`threatCoarseBox` / `nodeCoarseBox` /
`nodePossiblyAffectedByPending`）。**对手稍微不符预判就全量作废——所以对手不该进 rollout。**

### 1.4 正确的接法：独立评分项，每帧重算

```
❌ 错的（上一版方案）：把对手模型塞进 rollout → 预判 → 偏离即全量失效
✅ 对的（主人方向）：进攻是独立评分项，不依赖对对手的预测，
                    像杀戮场一样**每帧重算**，无需新增任何失效机制
```

**"唯一路径"不是预测的产物，是我们制造的结果**：
先用弹雨把 Δ 压到 0，等他只剩一条路，此时预判是**自洽且精确**的，再补刀。

**性能**：Δ 是 O(子弹数 × 帧数) 的标量计算，输入树里全有。
比"跑对手的 9 操作 rollout"便宜一个数量级。

## 二、杀戮场的时间表示（主人要求参考）

查证结论：**杀戮场的"时间"是折叠的，不能直接拿来做节奏。**

| 表示 | 在哪 | 时间形态 | 用途 |
|---|---|---|---|
| ① 杀戮场 | `vantage_tree.js` 的引导势能场 | **空间静态场**，时间折叠进**射线的路径长度**（最多 2 反弹 / 75 帧飞行是搜索范围，不是时间维度） | 射位引导 ✓ / 节奏 ✗ |
| ② threats | `vantage_scoring.js` 的 `computeThreats` | **每颗弹带显式时间**：`tIn`（进入时间）/ `tEnd` / `closestDist` / **`closestTime`** | 单弹威胁判定 ✓ |
| ③ 树 rollout | `perFrameScores[75]` | **逐帧时间序列** | ★ 节奏要用的就是这个底座 |

**结论：Δ 应该是 ③ 的逐帧序列上算，配 ② 的弹道时间，不要另造时间表示。**

## 三、决策源接口（切缝方案）

### 3.1 目标

把 `js/vantage_tree.js` 内部**焊死在函数体里的判断**抽成可替换的插槽，
树的节点结构 / rollout / 死亡确认 / invalidate **一行不改**。

### 3.2 插槽清单

```js
var DecisionSource = {
    // —— 防守（先切这 5 条）——
    scoreOps:   function(tree, candidates) { ... },  // D1 9 个操作的评分
    segFrames:  function(tree, op)         { ... },  // D3 本段执行帧数
    scoreGrow:  function(tree, leaves)     { ... },  // D4 扩哪个叶
    scoreBoost: function(tree, ctx)        { ... },  // D5 补偿几层
    scoreStale: function(tree, node, proj) { ... },  // D6 新弹是否毁路线

    // —— 进攻（位置先留好，实现待定）——
    tempoField: function(tree, state) { ... },       // Δ 场（注意：是"评估"，不是"预测"）
    fireIntent: function(tree, state, route) { ... },
};
```

三个实现换着插：`RuleDecision`（现状）/ `FlyDecision`（果蝇）/ `NNDecision`。

### 3.3 关键约束（接口分离的红线）

| 层 | 职责 | 禁止 |
|---|---|---|
| [1] 游戏世界 | `getTanks/getProjectiles/getMaze` | — |
| [2] 观测构造 | 游戏状态 → 数字 | 禁止决策 |
| [3] **决策源** | 数字 → 数字 | **禁止碰游戏状态、禁止碰树的内部结构** |
| [4] 决策应用 | 数字 → tree 操作 / `inputState` | 禁止决策 |
| [5] 执行 | `setInputState` | — |

**留在 [4] 的硬约束（决策源无权覆盖）**：
- `isTerminalDead`（fd≤1 的红绝对不选）—— 主人反复确认的不变量
- `段长 <= evaluatedFrames`
- 粗筛"只许假阳不许假阴"：`最终作废集合 = 几何粗盒 ∪ 决策源判定`（只能追加，不能免除）

## 四、Laika 决策栈恢复（已改，2026-10-02）

### 4.1 改了什么

`js/ai_vantage.js` 的 `update()` 原第三分支是**"全静止"**：

```js
} else {
    this.actions = [];
    this.inputState = InputState.withState(this.aiId, false,false,false,false,false);
}
```

**后果有两个**（都是实测代码确认的，不是推测）：

1. **VantageAI 离开面板就完全不动。** 原版 Laika 的
   `_updateState → _makeDecisionsAndUpdateGoal → _updateActionsToAchieveGoal`
   链条**一次都不会被调用**——整套进攻逻辑是**死代码**。
2. **树模式永不开火。** `js/vantage_sandbox.js:556` 的 9 个 OPERATIONS 里
   一个开火都没有（静止/前后左右/四个斜向），
   而 `ai_vantage.js` 写输入时 fire 位硬编码为 `false`。

**改成**（优先级：debugTarget > 面板操控 > Laika 决策栈 > 静止）：

```js
} else if (this.laikaFallback === false) {
    // 逃生开关：保留旧行为
} else {
    this._updateState(deltaTime);
    if (this._makeDecisionsAndUpdateGoal(deltaTime)) {
        this._updateActionsToAchieveGoal();   // 内部自己清空并重建 actions
    }
    this._updateInputToDoAction();
    this._updateAndRemovePerformedActions(deltaTime);
}
```

⚠️ **注意不要在这里清空 `actions`**：原版语义是"goal 变了才重建"，
无条件清空会打断正在执行的多帧动作（`TURN_TO` / `FIRE` 的 `duration`）。

### 4.2 顺带收益

原版 Laika 本来就有的进攻机制**现在可达了**：
`_updateStandardShootAfterGoal`（找射位开火）/ `_tryToRetaliate`（还击）/
`_updateStandardLayTrapGoal`（布雷）/ `_GOALS.HUNT`（追击）/
`checkFiringPath(bounces, spread)`（含反弹与扇面的命中检测）。

> ⚠️ 但它**不带对手预判**（瞄准当前位置 + 反弹位），是"手写进攻"的水平。
> 而且主人已明确：**Killfield 的进攻系统不要（差劲）**，纯几何法有待研究。

### 4.3 待清理的硬编码削弱

`js/ai_strength_config.js` 的 trait 系统已经覆盖了大部分"故意削弱"
（灵巧度→瞄准误差/反应延迟，聪明度→威胁范围/反弹预测）。
**`maximum` 预设**：`aggressiveness 1.0 / cleverness 0.95 / dexterity 0.95 /
determination 0.95 / vengefulness 1.0`。

但下面三处**不受 trait 控制**，需要改代码：

| 位置 | 削弱 |
|---|---|
| `_updateActionsToAchieveGoal` 开火扇面扫描 | `MathUtils.randomAroundZero(Constants.AI.FIRING_PATH_RANDOM_OFFSET)` —— 开火角度永远带随机抖动 |
| 同上，找不到射击方向时 | `MathUtils.randomSign(MathUtils.randomRange(MIN_TURN_AROUND_ANGLE, MAX_TURN_AROUND_ANGLE))` —— 随机转身 |
| `_GOALS.IDLE` | `Math.floor(Math.random()*3)` —— 随机闲置行为 |

**建议顺序**：先只恢复决策栈（已做），跑一局确认行为正常；再清这三处，对比强度变化。
