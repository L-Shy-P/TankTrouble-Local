## 一、目标形态（一句话）

```
一个 (节点ID, 相对时间) 说三件事：
    A 出 1 个     → 生长位置
    B 出 1 个     → 选的路线
    B 出若干个    → 射击帧
```

**没有"操作时长"这个量。** 输入不变就一直按着；下一个决策说变才变。

### 关键的 tick 现状（决定改动难度的地方）

`tick`（L7127）里现在的顺序是：

```
tick
  ├─ …规则系统维护…
  ├─ agentSeam(...)            ← L≈7355，每 tick 恰好一次
  ├─ var evalThreats = …
  ├─ if (tree._commitSlice) { stepCommitSlice(); return; }     ← 提前 return
  ├─ if (emergency) { …重建/重选…; return; }                    ← 提前 return
  ├─ …
  ├─ commit(tree, adapter, evalThreats, tankState, …)           ← L6251，段末提交
  └─ growStep(tree, adapter, …)                                  ← L5877，生长
```

**⚠️ 这是本次改动最硬的一块**：现状是「**先决策，后提交，最后生长**」，
而新语义要求「**A 决策 → 生长 → B 决策 → 提交**」。
顺序必须换，但**只许在智能体模式下换**（规则版必须逐帧不变）。详见 §4.5。

## 四、改动清单（按文件 / 按函数）

### 4.1 节点建在死前 / 真死不建 —— `buildCandidate`（L4022）

**现状**：`actualEnd = r.dead ? safeFramesForDeath(tree, r.deathFrame, segF) : segF`
→ 死亡时把**执行帧数**夹到 `min(fd−1, floor(fd×0.5), planned)`。

**新语义（权威版 §7.3）：节点落在哪一帧，不是"时长"多少。**

| 情况 | 节点建在哪 | 标记 |
|---|---|---|
| **没死**（活满 75 帧） | **75 帧末** | — |
| **非真死**（`d > 1`） | **死前 `d−1`** | — |
| **真死**（`d ≤ 1`） | **不建立节点**（或认为与父节点重合） | **必须标记**："这里死过" |
| **全真死绝境** | **给该节点标记"真死" + 把真死节点显示给智能体** —— 见下方检测条件（权威版 §7.3b / §7.3c） |

**全真死绝境的检测条件（主人 2026-10-07 定案，两条同时满足）：**
1. **所有的叶子都真死**；**并且**
2. **没有任何生长的余地** —— 生长要么**不合法**、要么**与已有节点重叠**。

> **⚠️ 平时（非全真死）不需要任何真死标记**：
> **"缺席"本身就是信号** —— 正常该延伸 9 支，只见 8 支 ⟹ 缺的那支真死（权威版 §7.3b）。

```
智能体模式： 没死 → 75 帧末
             非真死 → d−1
             真死   → 不建节点 + 打标记（不是"夹到 1 帧"）
规则模式  ： 保持 safeFramesForDeath 原样（一行不动）
```

**边界**（别漏）：`fd = 0`（起手就撞）和 `fd = 1`（走一步就死）都算**真死**，
现有代码走 `fd <= 1 → return 1`。新语义下 **`d−1` 会算出 `0` 或 `−1`（非法帧）**，
所以真死这一支**不能沿用"夹帧数"的写法**，必须走"不建节点 + 标记"。

> **收益（权威版 §3.4③）**：节点天然是合法停点 → **下游任何地方都不用再处理"死前"特例。**

### 4.2 "段长 / 操作时长" —— **这个语义不存在**（★ 我上一版写错了）

> **AI 认错**：上一版我写成"`segmentFrames` 从输入**降为派生量**"。**依然错。**
> 权威版 §7.1 定案：**根本不存在段长（操作时间）这个语义，智能体架构里已经没有它了。**
> 而且我引用的"段长 ≈13 帧"是**规则版的产物**，**跟智能体版无关**，**以后不许再拿它说事**。

**照此执行：**

- **禁止**在任何新增的智能体版代码里引入 `segmentFrames` / `duration` / `操作时长` 概念。
- 节点只带一个信息：**它在哪一帧**（`tGlobal`，从树根算起的相对时间）。
- 两个节点之间的间隔**没有名字，也不需要名字**。
- 代码里已有的 `segmentFrames` 字段是**规则版遗产**，**智能体版不许依赖**。
  为了不大改规则版，字段先**留着**，但在智能体版路径上**一律不读、不写、不判断**。
- `probeSegment`（L3679）**保留给规则版**，它只决定**规则版往哪铺、铺多远**。
- `plannedFrames` 同理：规则版遗产，智能体版不碰。

### 4.3 输入（观测）—— 见权威版「★ 输入规范」

**输入分两类**（权威版 §9）：

| 类别 | 定义 | 内容 |
|---|---|---|
| **静态输入** | **同一局内不变** | 地图及其配置（对称/人数上限/可刷新道具/毒雾）、玩家列表及战绩（击杀/胜利；**暂不逐帧更新**）、队友列表（游戏没有队友机制，**先加上备未来团战**） |

### 4.4 接口层契约 —— `vantage_tree_interface.js`

**现状**（L113 `validateDecision`）：只认 `growAt / growTimes / select / memory`；
`validateBundle`（L133）做格式校验；`Invariants.canGrowAt`（L38）/ `checkSelect`（L59）做语义。

**新契约**（统一原子单位，用权威版 §3.1b 的**「办法 2」**）：

```js
// ★ 定位单位：子节点ID + 反向相对帧（从该子节点往回数几帧）
Pick = { nodeId: <子节点ID>, back: <int, ≥0> }

A.decide(ctx) → { picks: [Pick, ...] }   // 生长位置（多个 = 在多处生长）
B.decide(ctx) → { picks: [Pick, ...] }   // picks[0] = 选的路线；picks[1..] = 射击帧
```

**为什么是「子节点ID」而不是「父节点ID + 操作类型」**（权威版 §3.1b）：
- 光有节点 ID **指不出是哪一支操作**（节点分叉 9 种）；
- **子节点 ID 唯一对应一条路**（每个节点只有一个父节点）+ **反向相对帧** → 完全确定一个位置；
- **办法 2 更简单**，所以 A/B 的三个输出都用它。
- 「更简单」**不等于**智能体不用学操作标识 —— **标记里就包含操作**（见下）。

**✅ 真死不需要标记操作**（权威版 §7.3b，2026-10-07 第六轮砍掉）：
**"缺席"本身就是标记** —— 一个节点正常该延伸 **9** 支，**只见 8 支 ⟹ 缺的那一支真死**。
→ 所以观测里**只有一种格式**：`nodeId`。
→ 也不需要给智能体喂「操作类型」（最多是**战况**里要输入**对手**的操作）。

**★ `Pick.back` 的取值约定（差 1 问题，权威版 §7.7 有完整推导）**：

| 量 | 值 |
|---|---|
| `L` = 节点相对父节点前进的帧数 | **没死：`L = 75`**；**非真死：`L = fd − 1`** |
| **合法范围** | **`back ∈ [0, L)`** |
| `back = 0` | 操作到本节点（执行 `L` 帧） |
| `back = L−1` | 只执行 1 帧（最少） |
| `back = L` | **不操作 → 禁止** |
| 实际执行帧数 | `L − back ∈ [1, L]` |

**⚠️ 两个陷阱**：`samples[0]` 是**父节点自己的状态**（不是新帧）；`samples` 长度是 `durationFrames + 1`。

**格式统一：可以**（权威版 §7.5）。主人原话：

> 「貌似可以**统一输出格式**，**A 也可以输出多个，就代表在多处生长**，
> 但那样**无法在新长出的节点上生长**，解决办法是**多次调用 A**。
> 不过这些**不是重点**，**只要 A 具备扩展能力即可**。」

→ 两边都出 `picks: [Pick, ...]`，**语义由调用方解释**：
- A 的 `picks` = **生长位置**（多个 = 多处生长）；
- B 的 `picks[0]` = **选的路线**，`picks[1..]` = **射击帧**。

**⚠️ A 输出多个的已知代价**：一次调用内**无法在本次刚长出的节点上继续长**；
要那样必须**多次调用 A**。（这不是重点，**重点是 A 具备扩展能力**。）

**必须同时改的校验**（否则静默失败 —— 本项目的血泪教训）：
- `validateDecision`：`growTimes` **删掉**（`决策源 §19.1` 已作废它）；
  selftest 里那条 `growTimes 99→8` 用例也要删。
- `validateBundle`：新格式非法时必须**报出具体是哪一项非法**（喂回 `{attempt, rejected, reason}` 做帧内重试）。
- `checkBundleSemantics`：`select` 的候选集**不再是 `commitNode.children`** ——
  新语义下 B 选的是一帧，而一帧可能落在**任意节点**的 rollout 上。

### 4.5 ★ 拆成两次调用（**风险已被主人解除**）

**要求**（权威版 §6 + 主人原话「**两个智能体肯定两步啊，怎么能合起来**」）：

```
帧开始
 ① 规则系统维护（推进物理 / 增量失效 / 段末重锚 / 节点预算 / 性能闸门）
 ② 摊开【当前树】→ A 决策 → 记录生长位置
 ③ 执行生长（growStep）
 ④ 摊开【更新后的树】→ B 决策 → 记录 route + fire
 ⑤ 段末 commit（消费 B 的 route）
 ⑥ 执行本段
```

**★ 权威版 §7.4 定案：两次调用【强绑定在同一帧】。**

> 主人原话：「**两次调用强绑定在同一帧**，开始调用的那一刻，**就不会出现任何新事件**，
> 因为**只有智能体在思考和操作**；而智能体射击出的新子弹，那本来就是**放到下一帧更新的**。」

→ **`A → 生长 → B` 整段在同一 tick 内完成，中间世界不推进、不产生任何新事件。**
→ 所以**不需要**担心"A 和 B 落在不同 tick"——它们**必须**在同一 tick。
→ 上一次我标为"最硬的一块/需先画时序表"的风险，**由这条定案直接解除**。

**仍要注意的**：`tick` 里 `_commitSlice` 和 `emergency` 两条路径有**提前 return**（见 §二末）。
两次调用必须放在**这两条 return 之前**，且**同进同出**（要么都调，要么都不调），
**不许出现"A 调了、B 没调"的中间态**。

### 4.7 射击接口（独立里程碑，当前一行都没有）

**优先级说明（权威版 §5.1，2026-10-07 第五轮）**：0 帧自杀过滤器**已从"硬不变量"降级为"能做就做"**。

> 主人原话：「那个主要是为了**过滤自杀的失误情况**，**如果不好搞，其实不搞也行**，
> **训练够了它就不失误了**……**只知道检测个 0 帧死**，也就是**坦克还没开始动就死了**，**很容易检测**。」

| 事项 | 优先级 |
|---|---|
| 检测「0 帧死」 | ✅ **要做，容易**。定义：**子弹射出瞬间就命中自己 / 坦克还没开始动就死了** |
| 把它从候选里**过滤掉** | ⚠️ **能做就做，做不了可以先不做**（主人想不出有效过滤办法） |

**要改的：**

| 目标 | 内容 |
|---|---|
| `vantage_sandbox.js` | `OPERATIONS`（L583-593）只有 9 个移动操作 → 要给融合世界加**射击通道**（rollout 里能在指定帧生成我方子弹） |
| `ai_vantage.js` | L104-111 **树模式把 fire 写死 false**；L65 注释「树模式永不开火」→ 要放开 |
| `vantage_tree.js` | 射击表要能沿选中路线传到执行层 |
| 执行层 | **0 帧自杀检测**（不是必须过滤）；真要做过滤，是**构造候选时直接划掉**，不是奖励、不是惩罚 |

**射击语义（权威版 §4.1，容易记错，重抄一遍）：**
- **「射击」= 按下射击键，不是"真的发射了子弹"。** B 输出的是**按键状态**。
- **帧级**；**只要帧号合法就没有条数上限**（像玩家极速点击）。
- **连续两帧指定 = 中间未松开 = 按住 2 帧**；有 **1 帧"自动松开"的后摇**。
- **为什么**：让 AI 也能用**加特林**（必须按住）。
- **只在选中的那条路线上插**。
- **树不管没出膛的子弹**（「不考虑薛定谔的子弹」）；子弹真出膛后走既有的刷新流程。

### 4.8 ★ 树的保真度补课（**本轮新发现的缺口**，权威版 §10）

**这块是本方案之外新冒出来的，必须单列里程碑。** 权威版 §10 主人新定：

| 缺口 | 现状 | 要补什么 |
|---|---|---|
| **捡道具** | `COLLECTIBLE` 在 `vantage_sandbox.js` 里**一次都没出现**，`pickup` 也搜不到 | 道具位置 / 与坦克碰撞 / **炮管形状改变**（影响碰撞）/ **护盾反弹子弹** / **武器队列** |
| **护盾** | L164 自述「**未克隆项：护盾 SHIELD 夹具（弹开行为暂缺）**」 | 把 SHIELD 夹具加进克隆世界 |
| **陷阱** | L164 自述「未克隆项：……陷阱」 | ⚠️ 主人已澄清「**陷阱就是地雷**」→ 先确认地雷现在是怎么模拟的 |

**刷新逻辑（权威版 §10.3，★ 因为不再打分所以大幅简化）：**

```
触发（5 条）:
  ① 子弹产生   ② 子弹非正常消失   ③ 坦克形状改变
  ④ 追踪导弹切换目标   ⑤ 对手（带护盾）改变操作方式

刷新 = 重做死亡检测 + 更新树          ← 不需要重算分数
```
- **"移除类"刷新（子弹消失）是单调的**：只会让帧【从死变活】→ **不重检**
- **"新增类"刷新（新子弹 / 形状改变 / 导弹换目标）** → **必须重检**

**⚠️ 注意 #3 的措辞陷阱**：触发条件是「**坦克形状改变**」，**不是"捡到道具"** ——
**只有捡第一个道具才改形状**；之后进**队列**，**用完一个自动装下一个**，**那一刻**才改形状。

**对手模型现状**（`vantage_sandbox.js` L166）：「对手坦克：**保持真实速度向量（一阶近似，输入未知）**」
→ 即**牛顿惯性假设**。但**主人已定新规则**（权威版 §10.4）：

| 规则 | 值 |
|---|---|
| 检测"对手改变操作" | 对手**真实操作 ≠ 本帧模拟里用的操作** |
| 什么时候才模拟对手 | **只在护盾 / 近距离**；平时不模拟 |
| **含对手的总模拟深度** | **≤ 1 秒 = 50 帧**（`1.0 / FRAME_DT`，`FRAME_DT=0.02`）【我的换算】 |

> **阶段 5 的子顺序**：先做「道具位置 + 拾取检测」→ 再补「形状改变」→ 最后补「护盾反弹」。
> ⚠️ 但**"用完一个道具"的判定还没挖到底**（权威版 §10.8），**它是形状改变的触发点**，
> **必须先补完再动手**。
