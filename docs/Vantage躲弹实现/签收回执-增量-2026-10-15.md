## 二、★ **第 4 条测量纪律：「一次 `eval` 内给同步计算计时 ⟹ 恒为 `0`」**

**你这批最该收的一条。** 施工侧实测：

| 观测 | 值 |
|---|---|
| 页内同一次 eval 里 `performance.now()` delta | **`0`** |
| 页内同一次 eval 里 `Date.now()` delta | **`0`** |
| **同一个循环，Node 侧 `process.hrtime`** | **`8.68 ms`**（**对照 ⟹ 不是循环被优化掉**） |
| `Date.now()` 的读数 | `1791803149326.3333` —— **带小数**（真 `Date.now` 是整数 ⟹ **已被虚拟钟接管**） |
| `window.__vt.t` vs `performance.now()` | **完全相等** ⟹ 同源虚拟钟 |

**⟹ 精确口径（三点，不能简化成"页内计时全废"）**：
- 🔴 **一次 `eval` 内部给同步计算计时 = 恒 `0`（作废）**
- ✅ **跨 eval / 跨帧的时间戳有效**
- ✅ **Node 侧包 `m.eval` + 在【同一 eval 内循环 N 次取均值】有效**（含 CDP 往返 `~1-3ms`，**必须摊掉**）

**它对历史数字的影响**（按探针源码口径扫，**未全量溯源 `prof/` 日志**，这点它已如实标注）：
- `_probe_missile_perf.js` **不受影响**（`0` 处 `performance.now`、`2` 处 `process.hrtime`）
- `_probe_p11b_pnow.js` **早就在研究这件事**（文件头原话）
- `_probe_multiai_clock.js` **跨帧取样 ⟹ 有效**
- **`_probe_timers` / `_probe_yield` / `_probe_multiai_check` 需逐个复核（未展开）**
- 🔴 **它自己的 `_probe_navtab_cost*.js` 里页内那几列作废**（已标出）

**⟹ 建议与前面三条一起进方针的"测量纪律"**：
| # | 纪律 |
|---|---|
| 1 | **测"随时间线性增长的量"，先问：读的是【实时值】还是【上一段快照】？**（`liveAnchors` vs `anchorProbe`） |
| 2 | **对拍/探针脚本【自己的输入】先验单位**（有人把"每帧位移"当"速度"，**追了一整轮不存在的 bug**） |
| 3 | **"回归全绿" ≠ "改动生效"** —— 必须做**反向验证**（改前必 FAIL / 改后必 PASS） |
| 4 | **🆕 一次 `eval` 内给同步计算计时恒为 `0`** —— 页内测开销必须【跨 eval/跨帧】或【同 eval 内循环 N 次取均值】 |

## 三、导航表建表开销 —— **一个要勘误的数字 + 一条对"当前产品可用"的结论**

### ⚠️ 先勘误：**`117ms` 不是"页内测的"**（我们上一份回执里没提这条，这里补）

- **源头**：`prof/r6_missile_perf.log` 的 `122.596 ms/batch`（第 6 轮报告引用为 `117ms`）
- **产出者** `_probe_missile_perf.js:238`，**计时方式 = `process.hrtime`（Node 侧）+ `WARM=3/ITERS=30`【热均值】** ⟹ **不是页内**
- **真差因（三个，都不是计时器）**：
  1. **它跑的是【假迷宫】**（`:60-97 makeMazeFake` = **BFS + 手工回溯**，**不是游戏 jKstra 双向 Dijkstra**）
  2. **`30` 次热均值 vs 冷首发**
  3. **需算格对数不同（可达性）**
- ⟹ **`117ms` 对"产品有意义的场景"（真迷宫 + 冷首发）低估约 5 倍**

### 真迷宫 + 冷首发（Node 侧墙钟，本轮实测）

| 迷宫 | 格对 | **冷首发** | 热 |
|---|---|---|---|
| **`6×4`（当前游戏实际尺寸）** | 504 | **`5.0 ms`** | 2.9~3.6 ms |
| `6×5` | 648 | 9.4 ms | — |
| `10×6` | 3 406 | 53.6 ms | — |
| **`16×10`** | 13 110 | **`292 ms`** | 310/415/784 |
| **`20×12`** | 48 606 | **`2 812 ms`** | 1356/1517/2387 |

- **增长律：总 ∝ `(w·h)³·log`**（格对 ∝ `(w·h)²` × 单次 Dijkstra ∝ `(w·h)log`）
- **【推断】** `24×14 ≈ 8~15 s` · `30×20 ≈ 40~70 s`
- 🔴 **红线**：`20×12` 已是 `1.4~2.8 s` 一次性阻塞
- ✅ **但当前产品是 `5~8 × 4~5` ⟹ `3~10 ms`，【现状可接受】**
- **内存不是瓶颈**（`16×10` 表 = `25.6KB`、`30×20` = `360KB`）

### 建议（**只建议**）—— 施工侧意见

| | 做法 | 施工侧意见 |
|---|---|---|
| **A** | **换图/开局时就建**（把卡顿从"正被打那一刻"挪走） | ✅ **无风险，建议至少做** |
| **E** | **超预算就本局停用制导 + 响亮告警**（安全阀） | ✅ **建议做** |
| **B** | 懒建（只建用到的 `from` 行），单行 `~3ms`（`3000` 倍省） | ⚠️ **只在 JS 融合路可用；Rust rollout 里弹的格由 Rust 决定 ⟹ 救不了 Rust 路** |
| **C** | 分摊多帧 + 未建好前按直飞 | 🔴 **语义变化 ⟹ 要主人拍** |
| **D** | 反向 Dijkstra（`n` 次代替 `n²`），省 ~`100` 倍 | 🔴 **要么在 Rust 复刻平局行为（当初 D3 正是为避开它才传表）、要么自写 ⟹ 忠实性要重新论证 ⟹ 要主人拍** |
| **F** | 跨局缓存 | ❌ **不建议**（迷宫每局重生成，命中率低） |

**⟹ 施工侧建议：`A` + `E` 现在就做（无风险）；`B/C/D` 记档，等"要不要上大迷宫"定了再说。**

## 四、`hidden` 哨兵拆分 —— **已完成**（这条会影响录制格式，请回填）

### 做了什么
- **`hiddenState()` 里含实时量的字段**（`q.fps` / `pg`(Phaser 累加器) / `tf`(`timerFires`) / `lu`(墙钟)）
  **与【决定性】字段混在一个哨兵里** ⟹ **每次回归都可能出现"仅 hidden 不一致"，要人工分辨**
- **拆成两个**：**`hs`（决定性，硬 FAIL）+ `hx`（观测性，仅信息，独立计数 `hiddenObsMismatch`）**
- **决定性** = `rc/th/wpn/col/err/rnd/ai/b2d/raw` ｜ **观测性** = `q/pg/tf/lu`

### ⭐ 它用一个 40 次实验，把"flaky"和"真不确定"分清了
> **`31 PASS / 9 次仅-hidden FAIL`** ⟹ **`9/9` 只有 `tf` 一个字段不同**（`__vtStats().timerFires`），**恒为 `±1`**
> 其余（`rc/th/wpn/col/rnd/ai/b2d/raw` + `7` 个可见计数）**逐帧全同**
> **两种签名**：**帧 `0` 起差 `1200` 帧**（`5` 次）或 **帧 `817` 起差 `50` 帧后收敛**（`4` 次）
> ⭐ **后者与第 6 轮的 `hiddenMismatch=50` 完全吻合** ⟹ **很强的交叉验证**
>
> **⟹ 没有发现"本该决定性却偶发变化"的字段**（这是施工侧原本最担心的）

### 验收（**含一条"不能省"的守卫**）
- ⭐ **人为破坏决定性字段 ⟹ 新 `hs` 报 FAIL**：`hs.col+7` / `hs.rnd[0]+0.123` / 坦克位置 `+0.5` /

  ；而 **`hx.tf+99` ⟹ PASS `hiddenObs=1`** ⟹ **`hs` 没被拆废** ✓
- **`20×1200` 改前 `19+1hidden` → 改后 `20/20`**（两轮 `run A`/`run B` 都 `20/20`）
- **`verify_record --runs 3`（v4）**：回放#1 vs #2 PASS · 回放#1 vs 原始录制 PASS · **全计数 `0`**
- ⚠️ **它自己补了一句关键的**：**新代码噪声探针 `30×` = `30/30`（`obsOnly=0`，`tf` 非必现）** ⟹
