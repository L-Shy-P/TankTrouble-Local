## 0. 结论速览（先看这里）

当前代码里“时间基准错位”确实不止已被修的那一条。按代码可证程度和影响面排序：

1. **S1（高）**：融合世界摆弹时，子弹寿命用 `lifeTotal - lifeAge - qLife`，其中 `lifeAge = getTimeAlive()` 是“现在”的年龄，而 `qLife = tGlobal - anchorOffset` 是“节点起点相对轨迹锚点”的时间。二者不是同一个基准，**永远多扣 `nowTGlobal - anchorOffset`**（=轨迹锚点年龄，录像实测 0.016~0.417s）。结果：子弹在预测里提前消失 → 漏判死亡 → fd 偏大或 -1 → **假绿/假安全**。这条通过 `slot.lifeLeft` 同时传给 `simulateRustBatch` 和 `simulateTankBatchScored`，所以 **Rust rollout 也一起错**。
2. **S2（高）**：`commit()` 里节点时间用 `shiftSubtreeTime(tree, prevTg)`（prev 的**预测段末**）平移，而同一段代码用 `reanchorThreatsAtCommit(..., _timeAcc - oldRootAbsT)`（**真实已过**时间）平移威胁。两个平移量在“提前提交”（新弹改道/静止段提前结束/卡墙/真死回退）时可以差很大一截，节点时间窗整体偏 δ ⇒ 评分/死亡/粗筛框/窗口签名全部错位。`rootAbsT` 本身是同步更新的（见 §B5 回答），错的是**节点平移量**。
3. **S3（高）**：新修的 `bth.lifeLeftSeconds = lifetime - age - _qLife`（`vantage_sandbox.js:2446`）里 **`opt` 不是 `rescoreTankSamples` 的参数或局部变量**，`typeof opt === 'undefined'`，所以 `_qLife = max(0, -anchorOffset)`，对新轨迹（A≥0）等于没扣。而且 Rust `rescore.rs:1175-1176` 把 `life_left_seconds` 当作“轨迹锚点时刻的剩余寿命”再扣一次 `q_life = t_k - anchor_offset`；JS 传的却是“现在/节点起点”口径 ⇒ 两边语义相反，复用轨迹（A<0）会**双重多扣**。这条让 Rust 增量重评分给出的 fd 偏大/假绿。
4. **S4（高，地雷场景）**：同一个 `rescoreTankSamples` 里破片用 `prj.lifetime`（MINE_SHRAPNEL=0）而不是 `lifetimeSecOf()` 的 `NO_LIFETIME_SEC` 哨兵。Rust 重评分世界第一帧就把破片停用（停用发生在接触扫描之前）⇒ 地雷致死被漏判 ⇒ **假绿**。v163 在融合世界修过的那个根因，在这条路径上原样存在。
5. **S5~S10**：见 §2 逐条。其中 S5（commit 内 `_rootAbsTNow` 未同步）、S7（`tGlobal≈0` 分支用“现在真实弹体”而非节点起点弹位）值得一起查；S9 回答 B7：树里实际生效的“缓存签名”是 `freshSig`，它**不含绝对时间**，在等量平移下不变是设计使然，但 S2 破坏等量前提；`scoreCache`/`dataVersion` 目前已无消费者，所以“时间推进后缓存不失效”不是独立 bug，而是 S2 的放大器。

**最可能成因**：如果只能指一条，指 **S1**（子弹寿命的 `qLife` 基准），理由见 §4；若一处性打印证实“提前提交很频繁且 |δ|>0.1s”，则 **S2** 会成为第一嫌疑。

## 1. 本文使用的时间基准定义（全部以代码为准）

| 量 | 含义 | 定义处 |
|---|---|---|
| `_timeAcc` | 跨局累计的绝对时间（真实世界步长累加） | `vantage_tree.js:1413`；`7124 _timeAcc += worldDt` |
| `tree.rootAbsT` | 当前树根对应的绝对时刻 | `createTree` 设 `_timeAcc`；`commit` 里 `6231/6367/6507` 设为 `_timeAcc` |
| `nowTGlobal` | “现在”相对当前根的秒数 `max(0, _timeAcc - rootAbsT)` | `nowTGlobalOf()` `2220-2222` |
| `node.simState.tGlobal` | 该节点**末态**相对当前根的时间 | `buildCandidate` `4017`、`applyRolloutScore` `2558` |
| `node.rolloutStartT` | 该节点 rollout 第 0 帧相对当前根的时间 = 父节点末态时间 | `buildCandidate` `4020` |
| `th.anchorOffset`（本文记 A） | 该威胁轨迹/折线第 0 帧相对当前根的时间 | 新轨迹生成时置 0（`ensureThreatTracks` `1848-1849`）；后补新弹 `cloneThreatWithOffset` `1939` 置 `nowT-rootAbsT`；复用旧轨迹时 `1770` 做 `A -= shift` |
| `tGlobal - A`（代码里的 `q`） | 从**轨迹锚点**到该时刻的时长；用于查轨迹下标 | `vantage_tree.js:1903/1917`、`vantage_sandbox.js:1416`、`vantage_scoring.js:1762` |
| `tGlobal - nowTGlobal` | 从**现在**到该时刻的时长；用于“从现在前推真实弹体” | 仅 `vantage_sandbox.js:1509` 的 `advFrames` |
| `lifeTotal - lifeAge` | 子弹在**现在**这一时刻的剩余寿命 | `vantage_sandbox.js:390/1524/1568`，`lifeAge = pr.getTimeAlive()` |

> 关键：**A == nowTGlobal 只在轨迹刚生成的那一个 tick 成立**。轨迹一旦被复用，A 会停留在过去（甚至为负），而 `nowTGlobal` 随 `_timeAcc` 增长。

## 2. 逐条嫌疑

### S1（高）融合世界/给 Rust 的 `lifeLeft`：寿命样本是“现在”，推进量却用“轨迹锚点”

1. 文件 + 行号 + 片段（`game_core/js/vantage_sandbox.js`）：

```
1416:  var q = (opt.tGlobal > 1e-6 ? opt.tGlobal : 0) - (th.anchorOffset || 0);
1417:  qLife = Math.max(0, q);
...
1509:  advFrames = Math.max(0, Math.round((opt.tGlobal - nowTg) / FRAME));   // 位置用 nowTGlobal
...
1524:  slot.lifeLeft = Math.max(0, slot.lifeTotal - slot.lifeAge - qLife);   // 寿命用 anchorOffset
1568:  slot.lifeLeft = Math.max(0, slot.lifeTotal - slot.lifeAge - qLife);
```

2. 这个量按哪个基准算、被用在哪个基准上
   - `slot.lifeTotal - slot.lifeAge = pr.lifetime - pr.getTimeAlive()`：按**现在**（tree tick 的真实时刻）算。
   - 减去的 `qLife = max(0, tGlobal - A)`：按**轨迹锚点**算。
   - 要得到“节点起点还剩几帧”，正确减法是 `tGlobal - nowTGlobal`（从“现在”到“节点起点”）。二者相差
     `Δ = qLife - (tGlobal - nowTGlobal) = nowTGlobal - A`，即**轨迹锚点年龄**，在 A==nowTGlobal 之外恒 > 0。
   - 结果 `slot.lifeLeft` 偏小 Δ：子弹在 rollout 里提前 Δ 秒被 `bs.lifeLeft -= FRAME; <=0 停用` 杀掉；`simulateRustBatch`（`1269`）和 `simulateTankBatchScored`（`2235`）把这个值原样交给 Rust，所以 Rust 的 9 操作 rollout 也一样提前。

3. 会不会导致节点颜色错误：**会**（条件是死亡发生在该弹自然到期前 `Δ` 秒内）
   - 方向单边：只会让子弹“早死”，不会晚死 ⇒ 死亡被漏判 ⇒ `fd` 偏大或 -1 ⇒ **绿/浅绿“安全”但实际上会被这颗弹打死**，正好是用户主诉的一半。
   - 不直接产生“假红”。但若同一分支里 `th` 不存在（`!placed` 兜底、`threat:false`），`qLife` 保持 0，寿命没被前推、位置却被 `advFrames` 前推了 —— 那是 S8 的方向相反的错，见 S8。
   - 覆盖面：`simulateFusedBatch` 是所有路径的公共摆弹函数（JS 融合权威 + Rust rollout 输入），每个 tick 的 growStep、`scanNodeDeath`、`confirmExecutionNodeDeath` 都吃它。

4. 如何只读验证
   - 录像字段（已有、只读）：`records[i].t` 是 `_timeAcc`，`records[i].anchors[].abs0` 是 `rootAbsT + A`。因此
     `t - abs0` **就精确等于 Δ**。本次对 `vantage_record_1790426192501.json`、`vantage_record_1790509445005.json` 统计：
     `n=1309/365`，min 0.016s，median 0.067~0.083s，p90 0.20~0.267s，p99 0.334~0.384s，max 0.367~0.417s。
     即：在这两个录像里，每条有轨迹的弹的剩余寿命至少被多扣 1 帧、中位 3~4 帧、p90 10~13 帧、尾部 20 帧。
   - 交叉对拍（只读）：同一条 threat 的 `th.track` 里 `alive===false` 的下标 i 表示“轨迹自己认为在 `abs0+i*trackDt` 死”；融合世界实际按 `lifeLeft/FRAME` 帧后停用。两者换算到绝对时刻，差值应等于 `nowTGlobal - A`；不等即坐实。
   - 若要看当前版本：建议临时打印（本轮不改）在 `1417` 后打印
     `slot.lifeAge`、`slot.lifeTotal`、`qLife`、`(opt.nowTGlobal||0)-(th.anchorOffset||0)`、`slot.lifeLeft`；只读对比前两者的差。
   - 注意：录像时间是 2026-09-26/27（v162 之前的小版本），只用于量级证据；当前版本的行号/行为以本报告为准。

5. 严重度：**高**。理由：无条件存在（只要 A≠nowTGlobal）、方向单边指向“假安全”、在公共摆弹路径上同时污染 JS 融合与 Rust rollout；唯一缓和是只在子弹寿命末端改变结论。

### S2（高）`commit()`：节点按 `prevTg` 平移、威胁按 `_timeAcc - oldRootAbsT` 平移

1. 文件 + 行号 + 片段（`game_core/js/vantage_tree.js`）：

```
6226:  var prevTg = hasKids ? (prev.simState ? prev.simState.tGlobal : 0) : 0;
6231:  tree.rootAbsT = _timeAcc;
6263:  reanchorThreatsAtCommit(tree, adapter, threats,
6264:                        oldRootAbsT !== undefined ? oldRootAbsT : _timeAcc);
```

```
1752:  var shift = Math.max(0, _timeAcc - oldRootAbsT);
1770:  th.anchorOffset = (old.anchorOffset || 0) - shift;
```

2. 时间基准
   - 子节点的 `tGlobal/rolloutStartT` 原本相对 `oldRootAbsT`。新根是 `tree.rootAbsT = _timeAcc`，要保住绝对时刻，必须统一减 `S = _timeAcc - oldRootAbsT`（真实已过时间）。威胁那边正是这么做的（`1752/1770`）。
   - 节点那边减的是 `prevTg = prev.simState.tGlobal`，即**被执行节点的预测段末**，不是真实已过时间。二者之差
     `δ = S - prevTg`：
     - 正常段末提交：`segmentEndDue` 要求 `_timeAcc >= cmt.tEndSec = oldRootAbsT + prevTg`，所以 `δ ∈ [0, 一个真实步长)`，量级 0~1 帧；
     - **提前提交**：`cmt.tEndSec = _timeAcc; _forcedReselect = true`（`5336-5337` 卡墙、`5696-5697` 真死回退、`7319-7321` 新弹改道/静止段提前结束、`7238-7239` 点击目标刷新）只改了 `tEndSec`，**没有改 `prev.simState.tGlobal`**。此时 `prevTg` 仍是计划段末、`S` 才刚过完一小段 ⇒ `δ` 是**负的整段剩余时间**（几十到几百毫秒）。
   - 结果：被保留的子树（新根的 9 个候选及其后代，正是用户看得到、下一段要执行的那些节点）的 `tGlobal/rolloutStartT/tEndSec` 整体偏 `δ`；而 `tree.threats` 的 A 已经按 S 正确重锚。于是：
     `nodeCoarseBox.t0 = rootAbsT + rolloutStartT` 与 `threatCoarseBox.t0 = rootAbsT + A` 相差 `δ`；
     `nodeWindowSig` 相对时间窗与威胁窗相差 `δ`；
     重评分/rollout 时 `q = tGlobal - A` 相差 `δ` ⇒ 弹位沿轨迹错 `δ*speed`。

3. 会不会导致节点颜色错误：**会**
   - 提前提交时 `δ<0`：节点起点被低估，弹位被“向后读” ⇒ 本该命中的碰撞被判晚/漏判 ⇒ `fd` 偏大/假绿。
   - 正常提交时 `δ≥0`（≤1 帧）：小量、方向略偏红，通常 1 帧内不改变颜色档位。
   - 放大路径：`rebaseSubtreeRigid` 会清空被重摆节点的 `freshSig/scoreCache`（`6147-6148`），所以 commit 里随后那句 `refreshCandidateScores(tree,adapter)`（`6301` 附近）**一定会**用错位的 `tGlobal` 重算这些节点颜色；粗筛框也会在后续 `invalidateStaleNodes` 中错位。
   - 同时 `tEndSec` 被低估 ⇒ `segmentEndDue` 提前为真 ⇒ 段提前结束 ⇒ 可能连环提前提交、δ 反复出现。

4. 如何只读验证
   - 现有录像不能直接给出 `δ`（没有 `prevTg`/`S` 字段），但可以先看“提前提交是否频繁”：`records[].seg < records[].planned`、`dumpDiagnostics().diag.events` 里的 `force` / `stuck` / `true-dead-retreat`、以及 `structureHistory` 里的 `stuck-in-segment` / `rebase-time`。
   - 只读断言办法（建议临时打印，不改逻辑）：在 `commit()` 的 `6226` 后打印 `prevTg`、`_timeAcc - oldRootAbsT`、`δ`，并在 `shiftSubtreeTime` 后对每个保留节点核对
     `oldRootAbsT + old_rolloutStartT == tree.rootAbsT + new_rolloutStartT`；差额就是错位量。
   - 另一条只读对拍：取同一节点在 commit 前后的 `tEndSec`，减去 `rootAbsT` 得 `tGlobal`；绝对结束时刻 `rootAbsT + tGlobal` 应当不变，若不变则平移正确，变化量即 δ。

5. 严重度：**高**。理由：一旦提前提交，误差是整段剩余时长（可到 0.2s 以上），弹位错几米；而且直接重算的正是用户最常看的根层 9 候选。唯一不确定的是当前版本里提前提交的实际频率与平均 δ，需要上面那行打印来定量。

### S3（高）`rescoreTankSamples`：`opt` 不在作用域（新修的那一行实际不生效）；且该 ABI 要的寿命语义与本行相反

2372:  rescoreTankSamples: function(nodes, threats, cfg, pendingThreats) {

2446:          - (th.anchorOffset || 0));

2. 时间基准
   - `rescoreTankSamples(nodes, threats, cfg, pendingThreats)` **没有 `opt` 形参**，`createVantageAdapter` 里也没有闭包 `var opt`；`vantage_sandbox.js` 全文没有 `var opt`。三个调用点（`vantage_tree.js:2716`、`2966`）最多传 4 个实参。因此 `typeof opt === 'undefined'`，`_qLife = max(0, 0 - A) = max(0, -A)`。
     - 新轨迹 A=0（`ensureThreatTracks` 生成时置 0）：`_qLife=0`，`bth.lifeLeftSeconds = lifetime - getTimeAlive()`，**与旧写法一模一样**。

   - Rust `rescore.rs` 的语义：`t_k` 是节点第 k 帧（`start_t + k*dt`），`q_life = max(0, t_k - A)` 是从**轨迹锚点**到该帧的时长；它从 `life_left_seconds` 里减这一项。这说明 `life_left_seconds` 必须是**轨迹锚点时刻的剩余寿命**
     `L* = (lifetime - age_now) + (nowTGlobal - A)`（A<nowTGlobal 时），而不是节点起点/现在口径。
   - JS 实际给 `L_js = (lifetime - age_now) - max(0,-A)`，误差
     `Δ = L_js - L* = -(nowTGlobal - A) - max(0,-A)`：
     A≥0 时少给 `nowTGlobal - A`；A<0 时少给 `nowTGlobal - 2A`（A 为负，等于 `nowTGlobal + 2*trackAge`）。Rust 再减一次 `q_life`，子弹在验证世界里比真实早 `|Δ|` 秒消失。

3. 会不会导致节点颜色错误：**会**
   - `refreshCandidateScores` → `refreshFusedLayer` → `tryRustRescoreLayer` 是默认快路（`RUST_PHYSICS_ENABLED` 默认 `true`，`needsJsScoring()` 默认 false：`actionCostPerFrame=0`、`safeFilterK=1`）。
   - 被 `applyLayerResults` 写回的正是候选层的 `fullDeathFrame`（节点颜色来源）。寿命被提前扣掉 ⇒ `deathFrame` 偏晚或 -1（`rust-candidate`）⇒ **候选层假绿**；只有最终被选中的那条路线会被 `confirmExecutionRoutePick` 用 JS 融合复核，其余 8 个候选的颜色停在 Rust 结果上。
   - `rerouteTreeForCurrentThreats`（新弹/点目标）也走这条批量重评分。

4. 如何只读验证
   - 已可确定：`node -e` 里对同样写法的闭包验证 `typeof opt` 为 `undefined`；源码里用 `grep -n "var opt" game_core/js/vantage_sandbox.js` 为 0 条。
   - 只读对拍：录像/诊断里的 `structureHistory` 有 `death-update-audit`（fd 变化）与 `js-death-confirm`（Rust 候选 fd → JS 融合 fd）。对触碰同一颗将到期子弹的节点，比较 `rust-candidate` 的 fd 与 JS 确认后的 fd；若一致地“Rust 说活得更久/不早死”，S3 成立。
   - 若要直接看值：临时打印 `_qLife`、`anchorOffset`、`prj.lifetime - prj.getTimeAlive()`、`opt`（必然是 undefined）。本轮不改。

5. 严重度：**高**。理由：默认快路；候选层颜色直接来自它；而且“已修”的那一行被证明不生效，说明该路径实际上从未被修正。唯一缓和：只在子弹寿命末端改变结论（但地雷破片是 0 寿命，见 S4）。

### S4（高，地雷场景）Rust 重评分路径把 `lifetime===0` 当 0 秒寿命

1. 文件 + 行号 + 片段：

  function lifetimeSecOf(pr) {

## 3. C9：两个 Rust ABI 的 `life_left` 语义确实不一致（只读核对）

| ABI | 语义 | 证据 | JS 应传什么 |
|---|---|---|---|
| `vt_rollout_batch` / `vt_score_paths` 内嵌 rollout（`rollout.rs:745-752`） | `life_left` 是 **rollout 第 0 帧（节点起点）** 的剩余寿命，逐帧 `-= frame_dt` | `rollout.rs:745 life_left = bullet.life_left.max(0)`；`839-840` 递减 | `(lifetime - age_now) - (tGlobal - nowTGlobal)` |
| `vt_rescore_nodes`（`rescore.rs:1175-1176`） | `life_left_seconds` 是 **轨迹锚点 A 时刻** 的剩余寿命；每帧用 `q_life = t_k - A` 把它推进到节点帧 | `rescore.rs:1175-1176` | `(lifetime - age_now) + (nowTGlobal - A)`（= 锚点剩余寿命，与节点 `start_t` 无关） |

- JS 侧：`simulateRustBatch`/`simulateTankBatchScored` 把融合 slot 的 `lifeLeft`（按上表第一行口径）交给 Rust rollout —— **口径会一致，只要 slot.lifeLeft 按第一行算**；但当前 slot 按 `tGlobal - A` 扣（S1），错。
- `rescoreTankSamples` 把 `bth.lifeLeftSeconds` 交给 Rust rescore —— 应按第二行算；当前新修的行按第一行思路（且 `opt` 不存在）算，错（S3）。
- 结论：同一个字段名 `life_left` 在两个 ABI 里是两种时间基准，JS 侧用同一套表达式喂两边，必然至少错一边。

## 5. 最可能是用户看到的“节点颜色错误”的成因

**首选：S1（`lifeLeft` 的时间基准错位，`vantage_sandbox.js:1416/1524/1568`）。**

理由：
1. 它是唯一**每一批 rollout 都参与**、且**方向单边**（只会让子弹早死）的时间基准错误；节点颜色来自 `fullDeathFrame`，而 `fullDeathFrame` 来自这批 rollout 的 deathFrame。它同时通过 `slot.lifeLeft`（`1269/2235`）污染 Rust 的 rollout，所以不是“只有 JS 融合错”。
2. 它和刚修的 `bridgeThreats` 是**同一个错误基准的两次出现**：`lifeAge` 是“现在”，`qLife` 是“锚点”。修 Rust 输入时引用的“JS 融合世界口径”正是这个错的式子，因此修的方向本身没有把这条基准掰正。
3. 方向正好对应主诉的“显示安全实则被杀”：预测里子弹提前消失 ⇒ 该死的分支被判 `fd=-1` 或 fd 大 ⇒ 绿/浅绿节点被实际打死。
4. 量级已由录像量化：`t - abs0`（= Δ）中位 0.07~0.08s、p90 0.20~0.27s、最大 0.42s；75 帧窗口下对应 3~4 帧、10~13 帧、20 帧。对 2s 的霰弹/加特林弹和 0.8s 的激光，这不是边角量。
5. 已知的边界：如果一次死亡发生在子弹离自然到期还远的时候，S1 不改变结论；所以它能解释“经常性的绿死”，但不能解释所有颜色错。

**并列第二：S2（提前提交时 `prevTg` vs `S`）。**
- 它造成的误差可能比 S1 更大（整段剩余时间）、且一次影响根层全部候选；如果临时打印证明“提前提交很频繁、|δ| 常见 >0.1s”，则 S2 会升为第一嫌疑。
- 它同时解释了 B5 的粗筛错位与 B7 的“缓存不失效”：不是 `rootAbsT` 没更新（代码里更新了），而是**节点和威胁用了两个不同的平移量**。

**S3/S4** 是 Rust 增量重评分路径的独立成因：S3 让“已修”的那一行实际无效并叠加二次扣减（候选层假绿），S4 在地雷场景把破片在第一帧杀掉（地雷假绿）。如果用户的颜色错误集中出现在“9 候选里只有执行的那条后来被确认、其余全绿”的情况，优先看 S3；如果集中在地雷/破片，优先看 S4。
